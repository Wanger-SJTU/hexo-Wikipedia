过去五个月，我们的团队做了一个实验：用 <strong>0 行人工手写的代码</strong>构建和发布一个内部beta产品。

这个产品有内部日常用户和外部alpha测试者。它能发货、部署、挂掉、再修好。不同的是——每一行代码（应用逻辑、测试、CI配置、文档、可观测性、内部工具）都是 Codex 写的。我们估计这样构建比手写代码快了约 <strong>1/10</strong> 的时间。

<strong>人导航，Agent执行。</strong>

我们刻意选择了这个约束，以便把工程速度提升几个数量级。我们有几周时间要交付最终约百万行代码。为此，我们需要理解：当软件工程团队的主要工作不再是写代码，而是设计环境、指定意图、建立反馈循环让 Codex agent 可靠工作——会发生什么？

这篇文章是关于用一群 agent 构建一个全新产品的经验——什么坏了，什么复合了，以及如何最大化我们唯一真正稀缺的资源：<strong>人的时间和注意力</strong>。

## 从一个空 git 仓库开始

第一个 commit 进入空仓库是在 2025 年 8 月底。

初始脚手架——仓库结构、CI 配置、格式化规则、包管理器设置、应用框架——由 Codex CLI 使用 GPT-5 生成，辅以一小部分现有模板。甚至指导 agent 如何在仓库中工作的初始 AGENTS.md 文件也是由 Codex 自己写的。

没有预先存在的、人工编写的代码作为锚点。从一开始，仓库就是由 agent 塑造的。

五个月后，仓库包含约 <strong>百万行代码</strong>，跨越应用逻辑、基础设施、工具、文档和内部开发者工具。在那段时间里，大约 <strong>1500 个 PR</strong> 被打开和合并，团队只有三个工程师驱动 Codex。这意味着每个工程师每天平均 3.5 个 PR，而且随着团队扩展到七个人，吞吐量还在增加。重要的是，这不是为输出而输出：产品被数百个用户内部使用，包括每天的内部 power users。

在整个开发过程中，人类从未直接贡献任何代码。这成为团队的核心哲学：<strong>no manually-written code</strong>。

## 重新定义工程师的角色

没有人工编码引入了不同类型的工程工作，集中在系统、脚手架和杠杆效应上。

早期进展比我们预期的慢，不是因为 Codex 无能，而是因为环境规格不足。Agent 缺乏实现高级目标所需的工具、抽象和内部结构。我们的工程团队的主要工作变成了<strong>让 agent 能够做有用的工作</strong>。

实践中，这意味着 depth-first 工作：把大目标分解成更小的构建块（设计、代码、审查、测试等），提示 agent 构建这些块，然后用它们解锁更复杂的任务。当某件事失败时，修复几乎从来不是"再努力试试"。因为取得进展的唯一方法是让 Codex 做工作，人类工程师总是介入任务并问："<strong>缺什么能力，我们如何让它对 agent 既清晰又可执行？</strong>"

人类几乎完全通过 prompts 与系统交互：工程师描述一个任务，运行 agent，允许它打开 PR。为推动一个 PR 完成，我们指示 Codex 在本地审查自己的更改，在本地和云端请求额外的特定 agent 审查，响应任何人或 agent 给出的反馈，并循环迭代直到所有 agent 审查者满意（Effectively 这是一个 Ralph Wiggum Loop）。Codex 直接使用我们的标准开发工具（gh、本地脚本、仓库嵌入的 skills）来收集上下文，无需人类复制粘贴到 CLI。

人类可以审查 PR，但不是必需的。随着时间推移，我们几乎把所有的审查工作都推给 agent-to-agent 处理。

## 提高应用可读性

随着代码吞吐量增加，我们的瓶颈变成了人类 QA 能力。由于固定约束一直是人的时间和注意力，我们通过让应用程序 UI、日志和应用指标本身对 Codex 直接可读来为 agent 增加更多能力。

例如，我们让应用可以按 git worktree 启动，这样 Codex 可以为每个变更启动一个实例并驱动它。我们还将 Chrome DevTools Protocol 接入 agent runtime，为 DOM 快照、截图和导航创建 skills。这使得 Codex 能够复现 bug、验证修复，并直接对 UI 行为进行推理。

可观测性工具也是一样的。日志、指标和 traces 通过本地可观测性栈暴露给 Codex——对于任何给定的工作树都是临时的。Codex 在完全隔离的应用版本上工作——包括它的日志和指标，一旦任务完成就被拆除。Agent 可以用 LogQL 查询日志，用 PromQL 查询指标。有了这些上下文，像"确保服务启动在 800ms 内完成"或"这四个关键用户旅程中没有 span 超过两秒"这样的 prompt 就变得可处理了。

我们经常看到单个 Codex 运行在单个任务上工作超过六个小时（通常在人类睡觉的时候）。

## 让仓库知识成为记录系统

上下文管理是让 agent 在大型复杂任务上有效工作的最大挑战之一。我们最早学到的教训之一很简单：<strong>给 Codex 一张地图，而不是一本 1000 页的说明书。</strong>

我们试过"一个大 AGENTS.md"方法。它以可预测的方式失败了：

- <strong>上下文是稀缺资源</strong>。巨大的指令文件挤占了任务、代码和相关文档——所以 agent 要么错过关键约束，要么开始为错误的约束优化。
- <strong>太多指导变成无指导</strong>。当一切都"重要"时，就没有重要的了。Agent 最终在本地模式匹配而不是有目的地导航。
- <strong>它立刻腐烂</strong>。一个整体手册变成了一堆过时的规则。Agent 无法判断什么是仍然真实的，人类停止维护它，文件悄悄地成为一个诱人的麻烦。
- <strong>难以验证</strong>。单个 blob 不适合机械检查（覆盖率、新鲜度、所有权、交联），所以漂移是不可避免的。

所以，我们不把 AGENTS.md 当作百科全书，而是当作<strong>目录</strong>。

仓库的知识库存在于结构化的 `docs/` 目录中，作为记录系统。一份简短的 AGENTS.md（约 100 行）被注入上下文，主要作为地图，指向其他地方更深层的事实来源。

<strong>仓库内知识库布局：</strong>

设计文档被编目和索引，包括验证状态和定义 agent-first 操作原则的核心信念集。架构文档提供了域和包层级的顶层地图。质量文档对每个产品域和架构层进行评分，随着时间跟踪差距。

计划被当作第一类 artifact。临时的轻量计划用于小变更，复杂工作被捕获在 execution plans 中，包含进度和决策日志，这些都 check in 到仓库。活跃计划、已完成计划和已知技术债务都是版本化的并放在一起，允许 agent 在不依赖外部上下文的情况下工作。

这实现了<strong>渐进式披露</strong>：agent 从一个小而稳定的入口开始，被教导接下来去哪里看，而不是一开始就压垮它们。

我们通过机械方式强制执行此操作。专用 linter 和 CI 任务验证知识库是最新的、交联正确的、结构正确的。一个定期的"doc-gardening" agent 扫描过时或不再反映真实代码行为的文档，并打开修复 PR。

## Agent 可读性是目标

随着代码库演变，Codex 设计决策框架也需要演变。

因为仓库完全是 agent 生成的，它首先为 Codex 的可读性而优化。正如团队的目标是改善新工程师入职时的代码可导航性一样，我们的人类工程师的目标是让 agent 能够直接从仓库本身推理完整的业务域。

从 agent 的角度来看，它在运行期间无法访问上下文中的任何东西——实际上就不存在。存在于 Google Docs、聊天线程或人们脑海中的知识对系统是不可访问的。仓库本地的、版本化的 artifacts（如代码、markdown、schema、可执行计划）都是它能看到的。

我们了解到，随着时间的推移，我们需要把越来越多的上下文推入仓库。那次 Slack 讨论使团队在架构模式上达成一致？如果 agent 无法发现它，它就像三个月后加入的新员工不知道一样不可读。

给 Codex 更多上下文意味着组织和暴露正确的信息让 agent 可以推理，而不是用临时指令让它应接不暇。就像你会为一个新团队成员介绍产品原则、工程规范和团队文化（包括 emoji 偏好）一样，给 agent 这些信息会带来更好对齐的输出。

这个框架澄清了许多权衡。我们倾向于 agent 可以完全内部化并在仓库内推理的依赖和抽象。通常被描述为"无聊"的技术往往更容易被 agent 建模，因为它们具有可组合性、API 稳定性和训练集中的表示。在某些情况下，让 agent 重新实现功能子集比绕过公共库的不透明上游行为更便宜。例如，我们没有使用通用的 p-limit 风格的包，而是实现了自己的 map-with-concurrency helper：它与我们的 OpenTelemetry 检测紧密集成，具有 100% 的测试覆盖率，并且行为完全符合我们 runtime 的期望。

将更多的系统拉入 agent 可以检查、验证和直接修改的形式会增加杠杆——不仅对 Codex，对其他也在代码库上工作的 agent（如 Aardvark）也是如此。

## 强制执行架构和品味

文档本身无法保持完全 agent 生成的代码库内聚。通过<strong>强制执行不变量</strong>，而不是微观管理实现，我们可以让 agent 快速发货而不破坏基础。例如，我们要求 Codex 在边界解析数据形状，但不规定这如何发生（模型似乎喜欢 Zod，但我们没有指定那个特定的库）。

Agent 在<strong>严格边界和可预测结构</strong>的环境中最为有效，所以我们在严格的架构模型周围构建应用程序。每个业务域被分成固定的层级集，具有严格验证的依赖方向和有限的可允许边集。这些约束通过自定义 linter（当然是 Codex 生成的）和结构测试强制执行。

下图显示规则：在每个业务域（例如 App Settings）中，代码只能"向前"通过固定的层级集（Types → Config → Repo → Service → Runtime → UI）。跨领域关注点（auth、connector、telemetry、feature flags）通过一个明确的接口进入：Providers。其他都是不允许的，并被机械地强制执行。

这是在你有数百名工程师后才实施的架构。有了 coding agent，它就成了早期的前提条件：约束是让速度而不衰减或不漂移的基础。

实践中，我们用自定义 linter 和结构测试以及一小套"品味不变量"强制执行这些规则。例如，我们静态强制结构化日志、schema 和类型命名约定、文件大小限制，以及具有自定义 lint 的平台特定可靠性要求。因为 lint 是自定义的，我们编写错误消息将修复指令注入 agent 上下文。

在人类优先的工作流中，这些规则可能显得迂腐或约束。有了 agent，它们成为乘数：一旦编码，它们同时在各处应用。

同时，我们在哪些地方约束重要、哪些地方不重要上保持明确。这类似于领导一个大型工程平台组织：在中心强制执行边界，在本地允许自治。你深刻关心边界、正确性和可重复性。在这个边界内，你允许团队——或 agent——在表达解决方案的方式上有相当大的自由度。

最终代码并不总是符合人类风格偏好，这没关系。只要输出是正确的、可维护的、对未来 agent 运行可读的，它就达到了标准。人类品味不断反馈到系统中。审查评论、重构 PR 和面向用户的 bug 被捕获为文档更新或直接编码到工具中。当文档不足时，我们将规则提升为代码。

## 吞吐量改变了合并哲学

随着 Codex 的吞吐量增加，许多传统工程规范变得适得其反。

仓库以最小的阻塞合并门运作。PR 是短命的。测试 flake 通常通过后续运行解决，而不是无限期地阻塞进度。在一个 agent 吞吐量远远超过人类注意力的系统中，纠正是便宜的，等待是昂贵的。

在低吞吐量环境中这是不负责任的。在这里，这是通常正确的权衡。

## "Agent 生成"实际意味着什么

当我们说代码库是由 Codex agent 生成时，意味着代码库中的<strong>一切</strong>。

Agent 生产：
- 产品代码和测试
- CI 配置和发布工具
- 内部开发者工具
- 文档和设计历史
- 评估 harnesses
- 审查评论和回复
- 管理仓库本身的脚本
- 生产 dashboard 定义文件

人类始终保持在循环中，但工作在与以往不同的抽象层级上。我们优先排序工作，将用户反馈翻译成验收标准，并验证结果。当 agent 遇到困难时，我们将其视为信号：识别缺少什么——工具、护栏、文档——并通过让 Codex 自己写修复来反馈到仓库中。

Agent 直接使用我们的标准开发工具。他们拉取审查反馈，响应内联，推动更新，通常压缩并合并自己的 PR。

## 增加自主级别

随着更多开发循环被直接编码到系统中——测试、验证、审查、反馈处理和恢复——仓库最近跨越了一个有意义的门槛：Codex 可以端到端驱动一个新功能。

给定一个单一的 prompt，agent 现在可以：

## 1. 验证代码库的当前状态

## 2. 复现报告的 bug

## 3. 记录展示失败的视频

## 4. 实现修复

## 5. 通过驱动应用程序验证修复

## 6. 记录展示解决方案的第二个视频

## 7. 打开 pull request

## 8. 响应 agent 和人类反馈

## 9. 检测并修复构建失败

## 10. **仅在需要判断时才升级给人类**

## 11. 合并更改


这种行为严重依赖于这个仓库的特定结构和工具，不应该假设它在没有类似投入的情况下泛化——至少现在还不行。

## 熵和垃圾回收

完全自主的 agent 也引入了新问题。Codex 复制已经存在于仓库中的模式——甚至是那些不均匀或次优的。随着时间推移，这不可避免地导致漂移。

最初，人类手动处理这个问题。我们的团队过去常常每周五（20% 的工作时间）清理"AI 垃圾"。不出所料，这不能规模化。

相反，我们开始将我们称之为"golden principles"的东西直接编码到仓库中，并建立一个定期清理过程。这些原则是有主见的、机械的规则，使代码库对未来 agent 运行保持可读和一致。例如：(1) 我们更喜欢共享 utility 包而不是手写的 helper，以保持不变量集中，(2) 我们不探测数据"YOLO 风格"——我们验证边界或依赖类型化 SDK，以便 agent 不会意外地在猜测的形状上构建。定期，我们有一组后台 Codex 任务扫描偏差、更新质量等级，并打开有针对性的重构 PR。其中大多数可以在不到一分钟内审查并 auto-merged。

这就像垃圾回收。技术债务就像高息贷款：几乎总是更好的做法是<strong>持续小额度地偿还</strong>，而不是让它复合并在痛苦的爆发中处理。人类品味被捕获一次，然后持续地在每一行代码上强制执行。这也让我们能够在每天的基础上捕获和解决不良模式，而不是让它们在代码库中传播数天或数周。

## 我们仍在学习的

到目前为止，这个策略在内部启动和在 OpenAI 采用方面效果良好。为一个真正的用户构建真正的产品帮助将我们的投资锚定在现实上，并引导我们走向长期可维护性。

我们还不知道的是，在一个完全 agent 生成的系统中，架构一致性如何在多年演变中发展。我们仍在学习在哪里人类判断添加最多的杠杆，以及如何编码这种判断以便它复合。随着模型随着时间继续变得更有能力，我们也还不知道这个系统将如何演变。

越来越清楚的是：<strong>构建软件仍然需要纪律，但纪律更多出现在脚手架中而不是代码中</strong>。保持代码库内聚的工具、抽象和反馈循环越来越重要。

随着 Codex 这样的 agent 在软件生命周期中承担更大的部分，这些问题将变得更加重要。我们希望分享一些早期经验可以帮助你推理在哪里投资你的努力，这样<strong>你就可以 just build things</strong>。
