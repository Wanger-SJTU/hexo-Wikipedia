## 1\. 回顾大语言模型生成响应的过程

让我们首先回顾一下大语言模型生成响应的基本流程。设想我们有一个大型语言模型，表示为 LLM({\\bf s},\\theta) ，其中 \\theta 表示模型的参数， 而 {\\bf s} 是模型接受的token序列。token词汇表我们记作 \\mathcal {V} 。

**接收提示并生成响应**

1. **接收提示**：首先，语言模型接收一个提示 {\\bf p} （即一系列token）。基于这个提示，模型预测下一个token出现的概率分布 {\\bf P} 。
2. **预测与采样**：根据预测的概率分布，模型进行采样以确定下一个token，记为 s\_1 。
3. **迭代过程**：随后，语言模型将接收到的提示 {\\bf p} 和已生成的token序列 s\_1 作为输入，继续预测下一个token的概率分布，并采样得到新的token s\_2 。
4. **生成结束**：这个过程会持续进行，直到模型采样到一个表示结束的token（例如 `<|endoftext|>`），或者达到预设的生成token数量上限。

需要注意的是， {\\bf P} 的维度是 \\vert {\\mathcal V}\\vert 。这里我们使用的是最简单的采样策略，即贪心的根据 {\\bf P} 直接采样。

## 2\. 如何干预大语言模型的响应

在不进行微调的情况下，如何影响大型语言模型生成的响应格式？许多人的第一反应是利用提示，即在提示中明确指出希望模型返回的响应类型，例如指定输出为JSON格式。 

然而，值得注意的是，由于大语言模型存在幻觉问题，依赖提示来干预模型的响应可能不是最佳选择。特别是在模型的智能水平有限时，这种方法可能会失效。实际上，我们有一个更为直接的方法来干预模型的响应。

这个方法就是屏蔽词汇表 \\mathcal{V} 中的某些token，迫使模型按照你的要求生成响应。通过这种方式，可以更有效地控制模型的输出，而不必依赖于提示的准确性。

举一个简单的例子，假设 \\mathcal{V} 中只有如下几个token：

* a
* b
* c
* 1
* 2
* 3

现在，我们要求大语言模型只能生成数字，而不能生成除了数字之外的东西，我们可以将 \\mathcal{V} 中的前三个给屏蔽掉，让大语言模型只从后面3个采样。

因此，上一小节的伪代码的第4行和第5行可以进一步的优化成下面的样子：

\\begin{aligned} {\\bf P} &\\leftarrow LLM({\\bf s},\\theta) \\\\ {\\widetilde{\\bf P}} &\\leftarrow m({\\bf s})\\odot{\\bf P} \\\\ s &\\sim {\\widetilde{\\bf P}} \\end{aligned} \\tag{1} \\odot 表示Hadamard积，指逐元素相乘， m({\\bf s}) 是一个**掩盖函数**，被掩盖的token会被置为0，不被掩盖的会被置为1。

发现了吗？这里的掩盖函数 m({\\bf s}) 和 {\\bf s} 有关，换句话说，掩盖的token是可以随着 {\\bf s} 不断变化的！正是这个性质使得我们可以让大语言模型按照我们的指导和要求去生成响应。

## 3\. 如何生成满足要求的响应

我们先来讨论比较简单的情况，假设我们要求大语言模型返回的响应满足某个正则表达式，例如下面的正则表达式。

正则表达式`[0-9]+\.[0-9]+`用于匹配一个或多个数字后跟一个小数点，再后跟一个或多个数字的字符串。

* `[0-9]+`：这部分表示匹配一个或多个数字（0到9之间的任意数字）。\[0-9\]是一个字符集，表示任何单个数字字符，而+是一个量词，表示前面的元素（在这个例子中是数字字符）可以出现一次或多次。
* `\.`：这部分匹配一个点`.`字符。在正则表达式中，点是一个特殊字符，它通常表示任何单个字符（换行符除外）。为了匹配实际的点字符，我们需要使用反斜杠\\来转义它，使其成为一个普通的点字符。
* `[0-9]+`：这部分与第一个\[0-9\]+相同，表示匹配一个或多个数字。

例如，这个正则表达式可以匹配以下字符串：

* 123.456
* 0.12345
* 999.999

但是，它不会匹配以下字符串：

* .123（没有数字在点字符之前）
* 123..456（有多个点字符）
* \-123.456（有负号）
* 123.（点字符后没有数字）
* 123.456e10（包含指数部分）

接下来，我们以这个正则表达式为例，研究如何去设计掩盖函数 m({\\bf s}) 。

实际上，我们有一个非常简单和直观的思路。遍历整个token词汇表 {\\mathcal{V}} 中的每个token，查看这个token和已生成的响应 {\\bf c} 是否**部分匹配**正则表达式。如果不匹配，就掩盖这个token，反之则不掩盖这个token。

下面是用Python实现的核心逻辑。

```makefile
import regex as re

V = ...  # 词汇表，故意省略，写的...

regex = "[0-9]+\.[0-9]+" # 需要大语言模型的响应遵循的正则表达式

completion = ... # 已生成的响应，故意省略，写的...

# 构造当下的掩盖函数
mask = []
for token in V:
    match = re.fullmatch(regex, completion + token, partial=True) # 检测是否部分匹配正则表达式
    if match is None:
        mask.append(0) # 掩盖
    else:
        mask.append(1) # 不掩盖
```

这个方法可以让大语言模型按照我们的要求生成响应。但需要注意的是，这个方法非常的消耗时间，因为我们每生成一个token就需要遍历整个词汇表以计算掩盖函数。有什么加速的方法吗？

##  4\. 如何进行加速

在论文《Efficient Guided Generation for Large Language Models》中，作者们提出了一种创新的加速策略。要深入理解这一策略的核心思想，我们必须首先认识到正则表达式在本质上与**有限状态机**（Finite State Machine, FSM）是等价的。

**有限状态机**是一种简洁而强大的计算模型，它由**状态集**和**字符集**构成。该模型从某个**初始状态**出发，每次接收一个字符输入，根据**预设的转换规则**，转移到下一个状态。在新的状态中，它再次接收字符输入，并继续按照规则进行状态转移，这个过程不断重复。通过这种方式，有限状态机能够高效地处理和识别字符串模式。

我们仍然以前面的正则表达式为例，利用下面的Python代码，我们可以得到和`[0-9]+\.[0-9]+`等价的有限状态机。

```makefile
import interegular

regex = "[0-9]+\.[0-9]+"
fsm = interegular.parse_pattern(regex).to_fsm()

print(fsm)
```

![](https://proxy-prod.omnivore-image-cache.app/1152x396,sB4Rcy3DVpRC3sGAq0O1v95f2ohAlLbV4-a0gsMOqzBs/https://pic1.zhimg.com/v2-1a8e6974637b40185e9d2c6a9a52e00c_b.jpg)

第一列表示该有限状态机的状态名称，在这个图中，有6个状态，分别是0-5。

第二列表示这个状态是否是终止状态，终止状态表示这个匹配已经成功了，可以终止并被接受。

后续的列表示字符的名称，如果某一行的字符名称对应有状态，表示这个字符在这一行的状态下允许被接受。例如第2行的，`.123456789`都有状态，表示在状态1下，可以接受`.123456789` 这些字符。

下面我们以字符串`3.14`为例，演示一下上面的有限状态机是如何运转的。

首先，有限状态机一定是从初始状态开始运转，在上面的图中，初始状态是0。然后读取第一个字符`3`，3在第一行中对应的是1，表示状态要转换到1，那么我们就转到状态1，也就是第二行。

读取下一个字符`.`，在第二行中对应的是3，表示状态要转换到3，也就是第四行。

读取下一个字符`1`，状态转换到4，也就是第5行。

读取下一个字符`4`，状态转换到5，也就是第6行。

读取结束，第6行是终止状态，最终`3.14`被接受，表示这个字符串符合我们设定的正则表达式。

当我们设计好一个正则表示式后，一定可以把它对应的有限状态机（也就是上图）计算出来，计算出来后，我们只需要跟踪字符串的状态，然后根据状态找到它允许接受的字符和不接受的字符，以此我们就能快速的得到掩盖函数 m({\\bf s}) 。

需要注意的是，在上面的演示过程中，我们假设token和字符是一一对应的，实际上大语言模型的token并不等价于字符，但这并没有关系，我们只需要在起始阶段做一次转换即可。

---

对于任何正则表达式，我们可以通过上一节介绍的方法，利用大语言模型生成符合特定要求的响应。那么，这种方法是否同样适用于生成JSON格式的数据呢？

遗憾的是，JSON格式比正则表达式更为复杂。尽管正则表达式能够描述一些简单的JSON结构，但面对复杂的JSON数据，正则表达式就显得力不从心了。

然而，这并不是一个不可克服的问题。JSON数据实际上属于上下文无关文法（Context-Free Grammar，CFG）的范畴。CFG是形式语言理论中的一个重要概念，它定义了一类可以通过上下文无关文法生成的语言，而正则表达式正是CFG的一种特例。

首先，我们可以借鉴第3节中提出的思路，采用部分匹配的方法，逐步构建掩盖函数，但这个思路比较的消耗时间。

其次，正如正则表达式与有限自动机（Finite Automaton）等价，CFG与下推自动机（Pushdown Automaton，PDA）等价。因此，我们可以利用下推自动机（PDA）来模仿第4节中的方法，以实现加速构建掩盖函数。

因此，从技术上来看，让大语言模型生成完美的符合格式要求的JSON并不是问题。

实际上，这种方法不仅限于JSON，所有属于CFG的语言，如SQL、Python、Java等程序设计语言，同样适用。

有理由相信，GPT-4的JSON模式，正是采用了这个策略。但在实际应用过程中，有几点需要特别注意：

1. 大语言模型能够生成满足符合格式要求的响应，但格式中的具体内容仍然有可能受到幻觉影响。例如，你可能期望得到`{"age": 22}`，但模型可能生成了`{"age": 20}`。
2. 大语言模型可能会持续生成内容，直至超出token限制，导致输出不完整，这也是OpenAI在其文档中建议检查响应是否完整的原因。例如，模型可能生成后面的数字特别长，超出了token上限。生成的响应因此并不是合法的JSON格式，因为它缺少了`}`。
3. 对于程序语言，使用这种方法，我们只能确保大语言模型生成的响应符合语法规范，但无法验证程序的逻辑正确性。例如，如果程序中引用了一个未定义的变量，CFG是无法检测到这种错误的。因此大语言模型在CFG的约束下，还是会生成逻辑错误的代码的。

## 6\. 进一步的启示

第5节，我们讨论了如何根据CFG约束大语言模型生成响应。后面也提到了它的一些局限性。我们能更近一步吗？特别是对于程序语言，我们能尽量的避免写程序中的一些低级错误吗，例如引用了未定义的变量，使用了实际上不存在的方法。

实际上是可以的，大家回想一下利用IDE写程序的场景，在利用IDE写程序时，IDE会根据上下文的关联信息，甚至相关的文档信息告诉你哪些方法是合法的，是目前可以调用的。

因此，在生成掩盖函数 m({\\bf s}) 时，我们完全可以利用这些工具来辅助我们，进而近一步的对大语言模型进行约束，减少它的幻觉，增加它响应的准确度。

这个思路的详细内容可以参考论文《Guiding Language Models of Code with Global Context using Monitors》

有理由相信，未来IDE一定会以这种形式嵌入大语言模型，而不仅仅是以简单的直接续写或生成代码。

前面我提到，这个方法是非常有潜力的。因为它和RAG的本质很类似，它们都是在不微调模型的情况下，尽量的缓解大语言模型的幻觉，使得大语言模型的响应更加的符合用户的要求。

甚至我们还可以以此来设计一个简单的RAG方法，当用户的问题检索到相关内容后，利用相关内容去生成掩盖函数 m({\\bf s}) ，从而影响最终模型的响应，这不是在输入端对大语言模型做增强，而是在输出端对大语言模型做增强。
