## 1\. 背景

之前一篇文章（见下面的链接信息）讨论了使用Linux perf基于SPE查找高通ARM平台代码伪共享的分析案例，下面继续讨论如何查找L1缓存中热点代码和错误预测的热点代码检测方法。

## 2\. 分析L1D 数据缓存的热点问题

### 2.1 使用 perf PMU 事件的示例方法

首先，我们先使用PMU分析采样 L1D事件，并使用 perf record 命令对原代码进行分析，看下能得到什么样的结果。

![](https://proxy-prod.omnivore-image-cache.app/1376x530,swDzdxaC8FZ9woLx3mqjXpw67ueWIUDUK6N7GPlkAc3I/https://picx.zhimg.com/50/v2-a882b29baf2d26428f7b39d2da079c2d_720w.jpg?source=2c26e567)

分析结果显示，memcpy 产生的 L1D 未命中次数最多。让我们对源代码中 memcpy 部分进行分析，并找到导致缓存未命中的内存访问。

![](https://proxy-prod.omnivore-image-cache.app/1007x1137,sSABz5XC2uLZDcednqLvaNO3Gfpc5j37UQtbbSyQdxm8/https://pica.zhimg.com/50/v2-5d5b381b5bb4889e9487fa5a29ebfddc_720w.jpg?source=2c26e567)

性能记录结果存在大量性能下降问题。热点配置文件显示有许多热点导致 L1D 缓存未命中。但是，这些性能下降的分析结果可能会把我们引向错误的调查方向，因为许多代码行不是内存操作。我们可以使用 Arm SPE 提供的精确采样机制来解决此问题，如使用 SPE 对配置文件对L1D缓存事件进行如下所示分析。

### 2.2 使用SPE配置文件分析L1D 缓存事件的示例 

以下是使用 SPE分析的示例。

![](https://proxy-prod.omnivore-image-cache.app/1090x410,sDWp58aTQPMOFY4yGc38TOsrdJx6bCmLpViQYU-Ks-GM/https://pic1.zhimg.com/50/v2-c9a2811c5577815e7c03c92a68525a7a_720w.jpg?source=2c26e567)

分析结果显示，memcpy 产生的 L1D 未命中次数最多。让我们对 memcpy的源代码进行分析，并找到导致未命中的内存访问。

![](https://proxy-prod.omnivore-image-cache.app/1283x657,s_Btn1cIjJOdIy-cFCJbUVcKAR3fa0ejFOVWV4FeyVbY/https://picx.zhimg.com/50/v2-dddc642ac9922bc96993f3f0c632273a_720w.jpg?source=2c26e567)

上面是使用 perf 记录的注释显示了可能导致未命中的一系列内存操作。

不出所料，memcpy 是一个频繁重复的循环复制内存块。指令 ldp q0， q1， \[x1， #80\] 将 64 个字节（L1D 缓存大小）从输入缓冲器加载到两个 Neon 寄存器中。这会导致 L1D 缓存未命中，因为输入缓冲区比 L1D 缓存大小大得多。

现在，我们尝试将其映射到 C++ 源代码，以寻找优化机会。

![](https://proxy-prod.omnivore-image-cache.app/1273x342,sMM3vSNH9PTO3Q_dwDy4nn2SKQGMx2Z_XsZjrNHjWihQ/https://pic1.zhimg.com/50/v2-2a31db70184eb9d06a8980519c5493ee_720w.jpg?source=2c26e567)

第一个 memcpy 操作从输入缓冲区复制字符串 s。在测试数据集中，字符串大多足够长，可以触发上述汇编代码中的循环热点。第二个 memcpy 操作复制一个最大大小为 2 个字节的字符。这不会触发导致热点的循环。我们无法控制测试数据集的大小和模式，因此我们几乎无法避免这种缓存未命中。

## 3\. 错误分支预测的热点检测

### 3.1 使用 perf PMU 事件的示例方法

仍然，我们先使用PMU分析采样，并使用 perf record 命令对原代码进行分析，看下能得到什么样的结果。

![](https://proxy-prod.omnivore-image-cache.app/1272x486,sMd_pLekWlNwdJK2QhpJWWY3WLjzVbpOwFhuTKZ4UNcw/https://picx.zhimg.com/50/v2-9b84644755937904cfe0a661a60cd01b_720w.jpg?source=2c26e567)

分析结果显示，memcpy产生的分支错误预测次数最多。让我们对 memcpy 二进制文件的源代码进行分析，并找到导致错误预测的分支。

![](https://proxy-prod.omnivore-image-cache.app/1281x960,syYrx8qR0Dy-aEuEampEi4oQQbUAy_FCadd4wUIzt7M4/https://picx.zhimg.com/50/v2-147a122ba2232e9388120f14b31ac68e_720w.jpg?source=2c26e567)

同样，之前使用 perf 记录的分析存在严重的性能下降问题，因为分析得到的热点出现在许多位置，并且不准确，因为它们中的大多数都不是分支指令。这是基于 PMU 的采样的一个众所周知的问题，因为在采样过程中中断会导致延迟。基于 SPE 的分析可以帮助解决此问题。

### 3.2 使用SPE配置文件分析分支预测 

![](https://proxy-prod.omnivore-image-cache.app/1290x433,smfYo99h2ld-8BNBSxBzYJCC-8Q0lk1kdE7FhH7VovQ4/https://pica.zhimg.com/50/v2-1afe25682473ec71fc39940939a508b6_720w.jpg?source=2c26e567)

SPE 分析样本显示，libc memcpy 库导致了大量的分支错误预测，占 79.53%。可以看到，这个版本的 memcpy 函数已经根据要复制的缓冲区大小进行了很好的优化，使用SIMD 寄存器用于复制大型数据块，并检查数据大小针按照128、32、16、8 和 4 字节的顺序进行了对应优化处理。

为了在 memcpy 库中找到错误预测的分支，我们可以在 SPE 采样记录上使用 perf annotate 命令来调查 memcpy 汇编代码。

![](https://proxy-prod.omnivore-image-cache.app/1058x825,sQLrijMkpEB5IIwykPUNeFKof78eXmudPe4v4VcgZ4zA/https://picx.zhimg.com/50/v2-6cbcaa23b3dc5b2bce4714f8c5491444_720w.jpg?source=2c26e567)

从上面分析的汇编代码中，我们可以看到几乎所有的错误预测（97.28%）都来自SPE跟踪的样本地址0x85044处的分支操作码。需要注意的是，虽然 SPE 是一种统计采样方法，但我们仍然可以预期这种方法会捕获热点循环。

为了进一步理解分支执行行为，函数中的分支逻辑总结如下：

```angelscript
97.28 : 85044: tbz w2, #3, 8505c 
```

如果未设置寄存器 w2 的第三位（要复制的 memcpy 缓冲区大小），则此指令将跳转到分支目标地址。仅当缓冲区大小小于16时，代码才会到达此指令。因此，此指令逻辑如用 C语言编写，就好像 （大小 < 8） goto .L8505c;。分支错误预测是由此逻辑引起的，其中需要从比较操作中解析缓冲区大小以确定代码路径。

为了评估提高此分支性能的潜在机会，我们检查了分析的源代码中的主循环。其主要逻辑是将基于数据转换为基于 CSV数据。为此会连续将数据字段从一个缓冲区复制到另外一个缓冲区。复制每个数据字段后，它必须将逗号分隔符或行尾追加到复制的数据中。以下示例代码显示了热点循环：

```arduino
Loop {  
    memcpy(csv_line, arrow_field, size_of_field);        // copy a field of normal size  
    memcpy(csv_line, delimiter_or_end-of-line, 1_or_2);  // copy a very short separator  
}
```

本例分析的整个代码中使用数据字段（正常大小）和非常短的分隔符（1 或 2 个字节）反复调用 memcpy。这种模式使训练 CPU 分支预测器变得更加困难，因为两个 memcpy 操作组合在一个循环中。第一个 memcpy 操作按列顺序填充字段，这很容易预测，因为同一列的字段通常大小相似。但是，带有分隔符的第二个 memcpy 操作会破坏此预测路径。使用 memcpy 附加分隔符似乎效率低下，因为这可能就像使用 \*buf++ = ' , '; 附加字符一样。

由此可见，我们编写的源代码必须足够通用以处理这种情况，尤其是作为公共库的使用情况下。

手机数码与生活领域创作者

数码圈最不能相信的一句话就是“性能不够，优化来凑”。为什么会这么说呢？今天咱们就一起来简单聊一聊！

虽然手机这个东西软硬件协调都很重要，但是大部分情况下，底子越好，效果也就越好。

优化这个东西很玄学不好说，也就当硬件还可以的时候，怎么调基本上都很难“翻车”。

![](https://proxy-prod.omnivore-image-cache.app/888x614,sVdwMPo31h6TATfwoluBBIgDl0Pd1CrnHo94Ajf4Ni4o/https://pic1.zhimg.com/50/v2-dc14ad7795071e45ed60e9eb0e5c06e3_720w.jpg?source=1def8aca)

但是把五六年前的处理器优化得跟现在的中高端处理器一样流畅，还是很有挑战性的！

很遗憾的是，目前还没有手机厂商能够做到，当然也包括身为科技巨头的苹果和华为。

举个例子，搭载了高通骁龙 680 处理器的华为 nova 11 SE，配合无比丝滑的鸿蒙 4.0 系统，有传言说流畅度可以媲美骁龙 8 Gen2。

然而在实际体验当中，却难以达到骁龙 8+ 手机的流畅度，更别说骁龙 8 Gen2 了。

![](https://proxy-prod.omnivore-image-cache.app/1308x0,sTw11nw41r_AjAAWIg5W2WllJcvaBTUxglZFySJtDBcw/https://pica.zhimg.com/50/v2-aac353650bcc115f4842211a6694eeea_720w.jpg?source=1def8aca)

当然苹果的 iOS 搭配三四年前的 A 系列芯片、华为的鸿蒙 OS 搭配麒麟芯片，即使放到现在，流畅度依然是挺不错的～

不过，这属于是自家的软硬件相结合，与优化和调教别家厂商的硬件还是有很大区别的。

另外，搞优化其实也有成功案例，就比如华为自研的 XMAGE 能把索尼 IMX766 调教得很好，直出效果并不比一些更大底的手机差。

通过算法优化在一定程度上确实能弥补硬件的不足，但是俗话说得好，“打铁还需自身硬”。

![](https://proxy-prod.omnivore-image-cache.app/600x0,sg4FJJiD-5DH63K0soX6vwxHTqM7tz-hXJPPdGFiy7t8/https://picx.zhimg.com/50/v2-a1ec9feb8871a404ff6fb6e9630bf245_720w.jpg?source=1def8aca)

所以，想要一款综合体验很不错的手机，那必须要有过硬的配置，不要太过于看重软件系统的优化了。你们说是吧？
