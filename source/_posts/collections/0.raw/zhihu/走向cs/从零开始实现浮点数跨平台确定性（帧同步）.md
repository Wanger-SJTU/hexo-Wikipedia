跨平台确定性是指：一段程序，在多个平台（如x64和arm64），输入相同数据，执行任意多次，都能获得完全一致的输出数据。主要运用场景包括游戏帧同步等。

最近做了一点确定性相关工作。研究了Jolt物理引擎的确定性部分。为C++寻路库recastnavigation修改了确定性支持，[recastnavigation-deterministic](https://link.zhihu.com/?target=https%3A//github.com/SlimeYummy/recastnavigation-deterministic)，[recastnavigation-rs](https://link.zhihu.com/?target=https%3A//github.com/SlimeYummy/recastnavigation-rs)。用Rust实现了确定性版本的ozz-animation骨骼动画库runtime，[ozz-animation-rs](https://link.zhihu.com/?target=https%3A//github.com/SlimeYummy/ozz-animation-rs)。（以上，感兴趣求个star。）

在过程中，发现关于浮点数跨平台确定性的资料分散，一些十几、二十年前的内容早已过时。至今仍存在确定性必须用定点数，浮点数无法实现确定性，无法用于帧同步的论断。事实上，在主流平台上（x64、arm64）实现浮点数确定性是完全可能的。

言归正传。阅读本文需要对IEEE浮点数的符号、指数、尾数、`Inf`、`NaN`等有了解。不过别担心，只要你是一名有经验的开发者，跟随文章的思路一定能很快读懂。

#### 为什么不用**定点数**？

定点数是跨平台确定性的终极方案，哪怕是浮点数确定性无法实现的平台，定点数仍然可以。不用定点数，是因为：

- 性能差，不便于SIMD化。
- 互操作性差。缺乏标准实现，需要频繁地做浮点、定点转化才能调其它库。
- 改造已有库工程量大，光是把`float`、`f32`改名`fixed`就要把所认文件撸一遍，再测一遍。考虑到`float`指针宽度4byte，定点数为了精度至少要用8byte的`int64`，稍不注意就会改出隐藏bug。

#### 浮点数的不精确性

现在回到浮点数，为了用浮点数实现确定性，让我们从浮点数最基础的性质开始。

浮点数与整数不同，无法精确地表示其定义范围内的所有数。如32位浮点数500.0表示为0x43FA0000，500.00003表示为0x43FA0001，两者只差最低位的一个bit。因此，位于两者间的500.00001是没有32位浮点数精确表示的。

事实上，浮点数能精确表示的数字，其底数部分必须为的幂之和。如：

`0.875 =  +  + `

此外，浮点数计算有精度丢失问题，如32为浮点数运算中：

`1000.0 + 0.00003 = 1000.0`

乍一看会以为上面的计算出错了，但CPU实际就是如此运行的。基于浮点数无法精确表达所有数的理由，32位浮点数中，紧邻1000.0的下一个数是1000.00006，1000.00003无法被精确表示，所以相加后被舍去了。

那么浮点数的不精确性会影响确定性吗？答案是不会。

回忆确定性的定义：相同输入永远得到相同结果。嗯，相同结果。「相同的错误结果」也是相同结果。只要保证**错误相同，确定性仍然成立**。

最后，浮点数只具有部分相等性与部分有序性，对应Rust中的`PartialEq`和`PartialOrd`。原因是`+0.0`、`-0.0`、`NaN`等特殊值存在特殊运算法则。实现确定性时记得小心地处理它们。

#### 确定性丢失了会怎样？

确定性要求完全一致的输入得到完全一致的结果，或许有人认为上述要求太过严格。所以在着手实现确定性前，我们先演示一遍确定性丢失的后果。

让我们假设某种硬件/软件的问题存在，导致`foo()`函数计算结果在不同平台存在微小差异，比如最低位差了一个bit，考量下面代码：

`let num = foo();
if num > 3.0 {
    return true;
} else {
    return false;
}
`

假设`num`在两个平台上分别被计算为`3.0`(`0x40400000`)和`3.0000002`(`0x40400001`)这两个二进制上只差一个bit的浮点数，最终依然会返回`false`与`true`的不同结果。

怎么办？有反应快的朋友可能会说：尾数截断。

没错。尾数截断可以缓解问题。比如我们对`num`取整数位，这时`3.0`和`3.0000002`都可以同样返回`false`了，甚至歪到`3.9`都没问题。可是`2.9999998`(`0x403FFFFF`)呢？或者换一种截断方法，抹掉浮点数底数后4位，结果也类似。代替等于操作的绝对值小于`(num - 3.0) IEEE 754-2008规范。这份规范为我们提供了基本的浮点数运算规范，涵盖：加、减、乘、除、开平方等。使硬件带来的不确定性问题大为缓解。

主流硬件对IEEE 754-2008基本做到了支持。X64和arm64对做的均不错，并且x64浮点数默认64位内部精度，也没有恼人的系统API改变浮点数行为。所以，只要有可能，把程序编译为64位总是更优之选。

SSE、AVX、NEON同样支持IEEE 754-2008，乃至CUDA也支持。[ozz-animation-rs](https://link.zhihu.com/?target=https%3A//github.com/SlimeYummy/ozz-animation-rs)库通过Rust的Portable SIMD做到了SSE2与NEON的跨平台确定性，Jolt物理引擎使用C++自行封装SSE/AVX/NEON，支持跨平台确定性。我查到的资料中，有一位《无人深空》的开发者，自称实现了PC、PS4，乃至PS4 GPU间的确定性地图生成！

有些平台会额外提供特定优化指令，牺牲精确性换取少许性能提升。比如著名的FMA（fused multiply–add）指令，即C99`fmaf()`，就不在IEEE规范内。还有SSE经典的`_mm_rsqrt_ps()`倒数平方根指令， 与NEON的对应版本有效数字位数不同。Rust Portable SIMD封装的指令均支持跨平台确定性，可以放心使用。C/C++则可能需要自己查阅文档封装了。

最后，虽然IEEE 754-2008保证了大部分浮点数确定性，但意外总是存在的，尤其在处理特殊值`+0.0`、`-0.0`、`NaN`的时候。参考以下代码：

`let a: f32 = 0.0;
let b: f32 = 0.0;
let x = a / b; // x == NaN (0x7FC00000)
let y = x * -1.0; // y == NaN (0xFFC00000 on X64, 0x7FC00000 on ARM64)
`

代码中的y，在x64平台为NaN（`0xFFC00000`），在arm64平台为NaN（`0x7FC00000`）！这破坏了确定性……吗？

「确定性需要保证每个bit都一致」，我承认我在前文过度简化了描述。如果上述计算只进行到y为止，它**仍满足确定性**。因为在浮点数定义中，所有NaN都是一致的（正负0也类似），即使它们底层的二进制表示不同。

然而，浮点数有一种快速取符号操作`sign = (y as i32) & 0x80000000`，确定性此时被破坏了。不同NaN返回0或非0。此操作在标量运算中不常见，但在SIMD中作为优化很常见。解法是改用`y let a: f32 = foo(); // foo returns 1000.0
let b: f32 = 0.00003;
let c: f32 = 0.00003;

let x = (a + b) + c; // x == 1000.0
let y = a + (b + c); // y == 1000.00006
`

X和y由于运算顺序，产生了不同结果。

现代编译器的指令重排、常量合并等优化，恰恰可以视为结合律、分配律的应用。仍然以上面的代码为例，b与c都是事实上的常量，假设两个平台上的编译器，编译器1不做任何优化（即x式），编译器2在编译期加和b与c得到0.00006（即y式），确定性被破坏了。

更多时候，编译器为了优化内存/缓存访问，会做大面积的指令重排，这点不方便举例，有兴趣请自行了解。

此外，编译器有可能将标量（FPU）版本的浮点数计算转化为矢量（SIMD）版本。对非常接近0的小数字执行FTZ（flush-to-zero）优化。还有我们在硬件一节提及的FMA（fused multiply–add）优化。以上优化都可能引入额外的不确定性。

好消息也是有的，IEEE同样规范了编译器的行为，保证编译结果支持浮点数确定性。

当前Rust编译器默认输出浮点数确定性结果，我们注意不要开启额外优化即可。

C/C++默认优化级别较高。需要手动关闭fast-math，`-ffp-model=precise`（clang/gcc）、`/fp:precise`（MSVC），关于fast-math涉及的优化可以参考这里。还需手动关闭浮点数融合指令，即我们前文所述的FMA乘加指令、平方根倒数指令等，`-ffp-contract=off`（clang/gcc）、`/fp:contract`（MSVC VS2022以上）。另外，在Rust中混编C/C++时也要开启这些标签。

如果再保守一些，在多平台上统一编译器吧。Clang是不错的选择。

#### 第三方库问题

终于搞定硬件与编译器，可以正式开始写代码了。如果你在此时得知，编写确定性代码时不要轻易使用第三方库，除非你能保证第三方库的确定性，你会作何感想？如果再加上一条，此处的第三方库包含libc呢？

IEEE规范了浮点数的基础运算，但没有规范sin、cos、exp等复杂函数。这导致了不同版本的libc中，它们的实现不保证相同（比如MSVC和GCC里就不同）。用Rust的兄弟们先别笑，C/C++中了枪，同样使用libc的Rust能独善其身吗？Rust的数学库偷懒用了libc版本。

解法嘛。可以像Jolt引擎一样，自己实现数学库。或者Rust使用libm数学库，C/C++换用musl版本的libc。

随机数。各个平台上的随机数算法需保持一致，必须使用伪随机，Xorshift、线性同余等都可以。别忘了随机数种子，切勿引入时间戳等非确定性输入。准确讲，整个确定性系统都不能依赖外部时间，乃至一切外部输入。

随机数会出现在某些算法与容器中，如Rust哈希表`HashMap`第三个泛型参数，引入了随机数强化安全性，需要被替换掉，否则遍历哈希表时的元素顺序是随机的。

排序。如果排序算法是稳定的，对于固定的输入序列，输出序列唯一，满足确定性。然而libc内置的`qsort`是不稳定的， 不同实现的版本，可能导致两个值相等，内部字段不同的对象顺序颠倒。

序列化。大部分序列化/反序列化库没有考虑确定性，尤其是JSON类文本格式。且不说`atof()`等函数在libc内实现是否相同，即使相同也未必具备确定性。因此更推荐二进制序列化方案，拷字节引入的麻烦总是较少。Rust推荐rkyv、bincode。C/C++的protobuf、messagepack理论上可用，我没自己测试过。

多线程。如果使用多线程（如Jolt引擎），多线程代码执行顺序问题同样需要纳入考量。多线程涉及的细节，本文不展开说。

总之，对待第三方库的原则应当是怀疑一切，一切不保证确定性的库和API都不能被使用。

#### 最终银弹

读到这里的诸位，大概被浮点数确定性的奇葩行为折腾的够惨了。常言「没有银弹」，跨平台浮点数确定性不存在简单的处理方法吗？当然不存在。不存在一劳永逸的方法。可银弹我认为是有的，虽然这颗银弹又丑又挫，又不优雅，以至于我都不好意在开篇提起它。

但它有效。

我们需要一套日志系统，尽量详尽地记录确定性系统中每一步中间结果。把那些浮点数们，使用上文推荐的序列化库，统统写到磁盘上。

然后，找到所有你能找到的目标平台设备，PC、MAC、手机、树莓派、Github action、Circle CI、云服务器……运行你的代码，比较日志输出结果是否满足确定性。前文我在硬件章节所述的NaN符号问题，库章节所述的qsort问题，都是通过这种方法发现的。

如果有可能，把这套日志系统作为工具提供给库的使用者，或者干脆部署的最终用户机器上。当确定性出现问题时，收集日志，分析问题。

只有当我们在足够多的平台上运行过程序后，我们才可以稍微自信地说，这段代码大概率做到跨平台确定性了。

为什么只是大概率？这不每年都会出新硬件嘛。
