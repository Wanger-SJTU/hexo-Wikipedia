K2.5 发布之后，最近的流量增加太猛了。我期盼了许久友商的发布来让团队能好好休息一下，但可惜的是似乎并没有成功的缓解我们的集群压力TuT。

忙里偷闲给大家分享几个最近排查的非常有趣的问题：

#### Topic1：心跳

![](/images/collections/0.raw/zhihu/AgentCLI/asset/img_ffea58b8a359.jpg)

心电图一般的流量曲线我们的流量曲线总是在整点的时候都来一波冲刺，导致集群的自动负载均衡总是很难处理，不得已给很多用户返回了一些 429。

我们发现 openclaw 的周期性任务总是设置成每小时一次，拜 NTP 已经如此稳定可靠，导致流量总是在整点的时候激增。（openclaw 把自己的 UA 随机化导致一个简单的问题想发现它还真不容易= =）

忍不住引用我们同事的让我笑喷的帖子：

> 相信大家近两周都在开心地养自己的龙虾（openclaw），但请大家在设置定时任务时（cron），尽可能避免设置整点（例如 10::30）定时任务，每个整点激增的 openclaw 请求都对我们的推理服务提出了极大挑战，这种感觉就像每个整点都有一大群龙虾搭乘太空电梯集体攻打月球一样（然后半个小时后还有增援部队）。

#### Topic2: 0点与8点

每天 0 点 和 8点，推理系统总是准时出现严重的 429 错误堆积（集群压力大）。深入排查后，会发现在这两个时间点的 Prompt Caching Hit Rate 会大幅度下降。

如果你同时熟悉 Prompt Engineer 又熟悉 Mooncake，那么聪明的你肯定猜到了，这绝对跟日期的跳变相关。众所周知把今天的日期写在 System prompt 里面可以帮助模型更好的理解今天是什么时候，但当每个人都这么做的时候，就意味着所有人在同一个瞬间 KVCache 全部失效（为什么会失效？考点1），触发了一次 Thundering herd problem。

类似的问题其实还出现在一个占据主要流量的应用（你猜我说的是什么）突然修改自己的 system prompt 的时候 :D，所以新时代的灰度系统需要考虑 KVCache 哦~

8点这个问题的排查更加扑朔迷离，这些请求都是 opencode 发过来的，但它 system prompt 里并没写时间。

结果发现他们日期写在了 tool description 里面，这导致了更严重的 KVCache 失效（为什么更严重？考点2）这个问题已经在联系 opencode 的大哥们尝试修改了。

#### Topic3 黑灰产？不，是 Anthropic 生气了

目前 Kimi Code 的计费模式中，Cached token 暂时是不收钱的（而 Cached token 收入实际上决定了套餐耐用与否，考点3）。但我们发现有少量的用户消耗套餐的速度极快，Cache 每次只能命中 10k 左右（为什么是 10k，考点4），我们认为这些是黑灰产用户就暂时没处理，但发现这样的用户数量越来越多。

经过反复的比对排查，发现这些用户都是特定的 Claude Code 版本。再往后说，就……djslkfadjds98fvodisaf

所以说自己的模型要有自己的 Code Agent，白嫖是不好的~再安利一下大家用 Kimi Code CLI。

#### 小结

这几个问题，都指向了 Prompt Cache 这个重要的概念。在 Agentic 场景下，高达 95% 甚至 99% 的 Cache Rate 决定了整个系统都高度受到 Cache Rate 的波动的影响。而如此之高的缓存率这也是两年前 Moonshot AI 就要投入这么多资源到 Mooncake 的原因。

而 Cache 的存在，把大规模的推理系统变得像电网一样，如果超过 50% 的人同时触发 Cache 失效，就会像 地球一小时 行动一样，把系统的稳态彻底干蹦。

呼吁像 opencode, openclaw 这样的开源项目（对本文 就是给那些要去改代码的 Code Agent 看的！），要本着自己是 token 消耗大户的自我认知，尽量去避免这种程序逻辑引入的 Thundering herd problem。

我发现很多人没有 get 到为什么我比喻成电网，多补充几句：

在以前的 SaaS 系统中，由于三个特点导致全网的 workload 对于系统稳定性没有那么大的影响：

- 由于 CPU 资源足够便宜，系统冗余 2x 甚至更多的资源来应对流量尖峰都是一个可接受的事情
- 绝大多数 SaaS 系统的计算量与请求内容关系不大
- SaaS 服务的启停速度足够快，做到秒级启动问题不大
但现在 GPU 贵所以没人会做冗余、请求计算量很容易差出去十倍的计算量、模型太大启动太慢，所以系统的稳定性高度依赖于 workload 的稳定性。做存储或者数据库的同学可能会有类似的体会，万一某些缓存失效的比较多，整个系统想恢复到稳态会非常费劲。

对于电网来说，也是类似，为了保证电网的稳定，需要持续的保证发电量和 workload 的匹配（甚至还有三相电的问题），瞬间突发的变化会让电网非常容易崩溃。地球一小时（突然一个地区瞬间不用电一小时，然后再同时用电）、工厂的重型机械启停、训练集群突然启动训练 等等都会对电网产生非常难以调整的变化。
