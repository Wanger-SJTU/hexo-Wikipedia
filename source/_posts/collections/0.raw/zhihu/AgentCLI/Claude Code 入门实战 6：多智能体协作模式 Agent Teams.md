### Claude Code 入门实战 6：多智能体协作模式 Agent Teams

如果你已经熟悉 Claude Code 的子代理（Subagent）功能，应该了解这种模式：一个主对话将任务委派给子代理，子代理独立执行后将结果返回。这种「主 → 从」模式虽然高效，但存在明显的局限——子代理之间无法直接沟通，所有协调必须经过主对话中转，更谈不上智能体之间的相互校验或讨论。

<strong>Agent Teams</strong> 正是为了突破这一瓶颈而设计的。它不只是把任务并行化，而是引入了一种全新的协作范式：多个 AI 实例在同一个项目中协同工作，它们可以<strong>互相通信、共享任务进度，甚至通过对抗式讨论来验证彼此的判断</strong>。

本文从核心概念、工作原理、配置方法、实战场景到注意事项，全面讲解 Agent Teams 的使用方法。

<strong>前置说明</strong>：Agent Teams 目前仍是<strong>实验性功能</strong>，需要手动启用。功能细节可能随版本更新发生变化。
### 核心概念

#### 什么是 Agent Teams

Agent Teams 是 Claude Code 中用于协调多个 Claude 实例在同一个项目中协同工作的机制。它的核心思路是：每个队友智能体都运行在各自独立的上下文中，并且可以<strong>点对点直接通信</strong>——通信不再仅限于「主智能体 → 子智能体」的单向模式。

在一个 Agent Teams 会话中，有一个智能体担任<strong>团队负责人（Team Lead）</strong>，负责拆解任务、创建队友、协调进度和汇总结果。其余的<strong>队友智能体（Teammates）</strong>各自独立运行，彼此之间可以直接交换信息、质疑对方的结论，并在他人的工作基础上继续推进。

#### 核心组件

Agent Teams 由四个核心组件构成：

┌─────────────────────────────────────────────────────┐
│                  Team Lead（团队负责人）             │
│        拆解任务 / 创建队友 / 协调进度 / 汇总结果      │
│                                                     │
│  ┌──────────┐     ┌───────────┐     ┌────────────┐  │
│  │  队友 A   │←──→│  队友 B    │←──→ │   队友 C   │  │
│  │ 独立上下文 │    │ 独立上下文 │     │ 独立上下文 │  │
│  └─────┬────┘     └──────┬─────┘     └─────┬─────┘  │
│        │                 │                 │        │
│        └─────────────────┼─────────────────┘        │
│                          ↓                          │
│              共享任务列表（Task List）               │
│         pending → in_progress → completed           │
└─────────────────────────────────────────────────────┘
                         ↑↓
                    Mailbox（消息系统）
              定向消息 / 广播消息 / 空闲通知

<strong>Team Lead（团队负责人）</strong>

团队的主会话，承担以下职责：

- 将复杂任务拆解为可并行执行的子任务
- 创建队友智能体并分配初始任务
- 监控各队友的执行进度
- 汇总结果并向用户呈现最终产出
Team Lead 也可以直接执行任务，但在复杂协作场景中，通常建议让它专注于协调（可通过委托模式强制）。

<strong>Teammates（队友智能体）</strong>

独立运行的 Claude 实例，每个队友具备以下特征：

- 拥有<strong>独立的上下文窗口</strong>，加载与普通会话相同的项目上下文（CLAUDE.md、MCP 服务、技能等）
- 收到 Team Lead 提供的启动提示和任务描述
- 可以与其他队友<strong>直接通信</strong>，无需经过 Team Lead 中转
- 完成当前任务后，可自行从共享任务列表中认领下一个任务
<strong>Task List（共享任务列表）</strong>

所有智能体共享的任务看板，每个任务有三种状态：

- `pending` — 待处理，等待认领
- `in_progress` — 进行中，已被某个队友认领
- `completed` — 已完成
任务之间可以设置依赖关系。当某个队友完成了其他任务所依赖的前置任务后，被阻塞的任务会<strong>自动解锁</strong>，无需人工干预。为了避免多个队友同时抢占同一个任务，任务认领使用了<strong>文件锁机制</strong>来防止竞争条件。

<strong>Mailbox（消息系统）</strong>

智能体之间的通信通道，支持两种发送方式：

- <strong>定向消息（message）</strong>：发送给指定的某一个队友
- <strong>广播消息（broadcast）</strong>：同时发送给所有队友（成本随团队规模增长，建议谨慎使用）
消息即时送达，无需轮询。队友完成任务进入空闲状态时，会自动通知 Team Lead。

### 工作原理

#### 协作流程

一个典型的 Agent Teams 工作流程如下：

用户提出需求
    ↓
Team Lead 分析需求，拆解为多个子任务
    ↓
Team Lead 创建队友，分配初始任务
    ↓
┌──────────────────────────────────────────┐
│  队友 A 执行任务 1                        │
│  队友 B 执行任务 2     ← 并行推进         │
│  队友 C 执行任务 3                        │
│                                          │
│  队友之间可以互相通信、质疑、对齐          │
│  完成任务后自动从任务列表认领下一个        │
└──────────────────────────────────────────┘
    ↓
所有任务完成
    ↓
Team Lead 汇总结果，呈现给用户

#### 上下文与信息流

每个队友在创建时会加载以下上下文：

- 项目级上下文：`CLAUDE.md`、MCP 服务配置、已启用的技能
- Team Lead 提供的启动提示和任务描述
- 共享任务列表的当前状态
<strong>需要注意的两个关键点</strong>：

- <strong>CLAUDE.md 正常生效</strong>：队友会从各自的工作目录读取 `CLAUDE.md` 文件。你可以利用这一点为所有队友提供项目级的编码规范、架构约定等统一指导。
- <strong>对话历史不会继承</strong>：Team Lead 的对话历史<strong>不会</strong>传递给队友。队友只能看到 Team Lead 明确传递的信息。因此，如果你在主对话中有重要的背景信息，需要在创建团队时显式包含在任务描述中。

#### 队友之间如何共享信息

- <strong>消息系统</strong>：队友发送的消息会即时送达目标对象，Team Lead 不需要主动轮询
- <strong>空闲通知</strong>：队友完成任务进入空闲状态时，自动通知 Team Lead
- <strong>共享任务列表</strong>：所有智能体都能查看任务状态，并认领当前可执行的任务
- <strong>文件系统</strong>：所有队友共享同一个项目文件系统，一个队友的文件修改对其他队友即时可见

#### 数据存储

团队和任务的相关数据存储在本地：

- <strong>团队配置</strong>：`~/.claude/teams/{team-name}/config.json`
- <strong>任务列表</strong>：`~/.claude/tasks/{team-name}/`
团队配置文件中包含 `members` 数组，记录每个队友的名称、Agent ID 和 Agent 类型。队友通过读取该文件来发现团队中的其他成员，从而建立通信。

### 多智能体方案对比

Claude Code 提供了三种并行工作方案，适用场景各不相同。

维度Subagents（子代理）Agent Teams（团队模式）Worktree（工作树）拓扑结构星型：主对话居中，子代理汇报网状：队友之间直接通信无拓扑：完全独立的会话上下文各自独立窗口，结果摘要返回主对话各自独立窗口，完全自主运行各自独立窗口，独立 Git 分支通信方式子代理只能向主对话汇报队友之间可以直接互发消息无自动通信，需手动协调协调方式主对话统一调度共享任务列表 + 自主认领完全手动并发安全单会话内安全文件锁防冲突Git 分支隔离Token 成本较低较高（约 3–4 倍）低（无协调通信开销）学习曲线低中等低适用场景专注型任务，只需要结果复杂任务，需要讨论、协作和对抗验证长期并行的独立功能开发<strong>选型建议</strong>：

- 子任务独立、只需执行和返回结果 → <strong>Subagents</strong>
- 任务复杂、需要多角度讨论和跨角色协作 → <strong>Agent Teams</strong>
- 需要队友之间相互校验和挑战 → <strong>Agent Teams</strong>
- 独立功能分支、长期并行开发 → <strong>Worktree</strong>
- 控制成本优先 → <strong>Subagents</strong>

### 快速配置指南

#### 前置条件

- 已安装 Claude Code 且版本不低于 `2.1.33`
- 可以访问配置文件 `~/.claude/settings.json`
- （可选）如需分屏查看多个智能体，建议安装 tmux 或使用 iTerm2
如有需要，先更新 Claude Code：

claude update
claude --version

#### 第1步：启用实验性功能

Agent Teams 默认关闭，需要手动启用。有两种方式：

<strong>方式一：编辑 settings.json（推荐，永久生效）</strong>

编辑 `~/.claude/settings.json`：

```text
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```


如果已有其他配置，将该字段合并到现有 `env` 节点中即可：

```text
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1",
    "OTHER_EXISTING_SETTING": "value"
  },
  "hooks": {
    ...
  }
}
```


保存后重启 Claude Code 使配置生效。

<strong>方式二：环境变量（临时生效，适合快速测试）</strong>

export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
claude

该设置仅在当前终端会话内生效，关闭终端后失效。

#### 第2步：选择显示模式

Agent Teams 提供两种显示模式：

<strong>进程内模式（In-Process）</strong>

所有队友运行在同一个终端中，一次只显示一个队友的输出，可通过快捷键切换。

- 适用于任何终端环境（VS Code、Windows Terminal、普通 shell）
- 不需要额外工具
- 使用 `Shift+Up/Down` 在队友之间切换
- 适合快速验证、简单协作或无法使用 tmux 的环境
<strong>分屏模式（Split-Pane）</strong>

每个队友都有独立的终端窗格，可以同时看到所有队友的输出。

- 需要 tmux 或 iTerm2
- 更容易掌握整体进度
- 可以直接进入某个窗格与对应智能体交互
- 适合复杂任务、多智能体协作和调试场景
默认模式为 `auto`：检测到 tmux 环境时自动使用分屏模式，否则使用进程内模式。

手动指定模式：

```text
{
  "teammateMode": "in-process"
}
{
  "teammateMode": "tmux"
}
```


也可以在启动时为单次会话覆盖：

claude --teammate-mode in-process
claude --teammate-mode tmux

#### 第3步：安装 tmux（分屏模式需要）

如需使用分屏模式，先安装 tmux：

# macOS
brew install tmux

# Ubuntu / Debian / WSL
sudo apt update && sudo apt install tmux

验证安装：

`which tmux && tmux -V`

<strong>iTerm2 替代方案（macOS）</strong>：

- 安装 it2 命令行工具：`brew install mkusaka/it2/it2`
- 打开 iTerm2 → Settings → General → Magic
- 启用 `Enable Python API`
Claude Code 会自动检测终端环境，无需额外配置。

<strong>提示</strong>：在 iTerm2 中推荐使用 `tmux -CC` 作为进入 tmux 的入口点，这样可以利用 iTerm2 的原生窗口管理来显示 tmux 窗格，获得更好的分屏体验。
#### 第4步：验证配置

重启 Claude Code 后，运行 `/config` 命令。在配置列表中确认 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` 已启用。如果没有出现，检查以下两点：

- `env` 字段是否位于 `settings.json` 的正确层级
- 值是否为字符串 `"1"`（注意引号）

#### 第5步：创建你的第一个团队

进入 Claude Code 后，直接用自然语言描述目标即可：

> 创建一个智能体团队来重构认证模块。
> 将工作分解为可以独立完成的并行任务。

Claude 会自动拆解任务、创建队友并开始协同推进。

<strong>团队的两种启动方式</strong>：除了你主动要求创建团队外，Claude 在分析任务后如果判断并行工作有价值，也可能<strong>主动提议</strong>创建 Agent Teams。但无论哪种方式，Claude 都不会在未经你确认的情况下创建团队——你始终拥有最终决定权。如果希望更精确地控制，可以手动指定队友和职责：

> 创建一个包含 3 个队友的团队：
> - 队友 1：重构登录流程
> - 队友 2：重构注册流程
> - 队友 3：为两者编写和更新测试
>
> 每个队友使用 Sonnet 模型。
> 队友 3 在队友 1 和队友 2 完成后再开始。

### 高级控制

#### 委托模式（Delegate Mode）

默认情况下，Team Lead 可能会自己动手写代码，而不是把任务交给队友。如果你希望它只负责协调和调度，可以开启<strong>委托模式</strong>。

启用方式：团队启动后，按 **`Shift+Tab`** 切换到委托模式。

在委托模式下，Team Lead 只做以下事情：

- 创建或关闭队友
- 给队友发消息、对齐方向
- 管理任务列表、跟进进度
它不会修改代码、执行命令或直接实现功能。当你的目标是让 Team Lead 纯粹充当「项目经理」角色时，委托模式非常有用。

#### 计划审批（Plan Approval）

对于复杂或高风险的任务，可以要求队友在动手之前先提交执行计划，由 Team Lead 审批通过后再开始实施。

> 创建一个架构师队友来重构数据库模式。
> 要求在进行任何修改之前先提交计划供审批。

在计划审批模式下，队友只能读取文件和调查信息，无法修改代码。完成调研后，队友将计划提交给 Team Lead。

Team Lead 可以做出两种决策：

- <strong>批准</strong> — 队友退出规划模式，开始实施
- <strong>拒绝并反馈</strong> — 队友保持规划模式，根据反馈修改计划后重新提交
你还可以在创建团队时指定审批标准：

> 创建一个需要所有队友计划审批的团队。
> 审批标准：
> - 计划中必须包含测试覆盖方案
> - 涉及数据库变更时必须包含迁移脚本
> - 不允许修改公共 API 的签名

#### 指定队友模型

默认情况下，队友使用与 Team Lead 相同的模型。你可以针对不同任务指定不同模型，实现成本和质量的最优分配：

> 创建一个包含 4 个队友的团队：
> - 1 个使用 Haiku 的研究员，负责快速检索和信息收集
> - 1 个使用 Opus 的架构师，负责复杂的设计决策
> - 2 个使用 Sonnet 的实现者，负责代码编写和测试

#### 预批准权限

队友执行文件操作或命令时会向 Team Lead 请求权限确认。在大型团队中，频繁的权限请求会成为瓶颈。

在创建团队前，使用 `/permissions` 命令预先批准常用操作：

`> /permissions`

为项目目录下的文件操作、常用命令等添加预批准规则，队友即可直接执行，无需每次请求。

如果你完全信任团队的操作范围，也可以跳过所有权限检查：

`claude --dangerously-skip-permissions`

<strong>安全提示</strong>：跳过权限检查意味着队友可以不经确认地执行任何操作（包括删除文件、运行危险命令等），请仅在充分评估风险后使用。
#### 关闭队友与清理团队

<strong>关闭单个队友</strong>：

`> 请关闭队友 researcher`

Team Lead 发出关闭请求后，队友可以选择同意并安全退出，也可以拒绝并说明原因（如正在执行关键操作）。

<strong>清理整个团队</strong>：

`> 清理团队`

Team Lead 会移除共享的团队资源。执行清理前会检查是否仍有活跃队友——如果有正在运行的队友，清理会失败。因此请先关闭所有队友，再执行团队清理。

<strong>注意</strong>：务必通过 Team Lead 执行清理操作。由队友执行清理可能无法正确处理团队上下文，导致资源状态不一致。
#### 通过 Hooks 把控质量

Hooks 可以作为质量关卡，在队友完成工作的关键节点进行自动化检查：

- <strong>TeammateIdle</strong>：队友完成任务进入空闲状态时触发。如果检查脚本发现问题（如 lint 不通过、测试失败），返回 `exit 2` 并附上反馈信息，队友会收到反馈并继续工作
- <strong>TaskCompleted</strong>：任务即将标记为完成时触发。返回 `exit 2` 可以阻止任务完成，将修改意见返回给队友
示例：在 `settings.json` 中配置自动化测试检查：

```text
{
  "hooks": {
    "TaskCompleted": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "./scripts/verify-task-quality.sh"
          }
        ]
      }
    ]
  }
}
```


配套的验证脚本 `./scripts/verify-task-quality.sh`：

#!/bin/bash
# 读取任务信息

```text
INPUT=$(cat)
TASK_SUBJECT=$(echo "$INPUT" | jq -r '.task.subject // empty')
```


echo "正在验证任务：$TASK_SUBJECT" >&2

# 运行项目测试
if ! npm test --silent 2>/dev/null; then
  echo "任务验证失败：测试未通过。请修复失败的测试后重新提交。" >&2
  exit 2  # 阻止任务完成，反馈给队友
fi

# 运行 lint 检查
if ! npm run lint --silent 2>/dev/null; then
  echo "任务验证失败：代码风格检查未通过。请执行 lint:fix 后重新提交。" >&2
  exit 2
fi

exit 0  # 通过检查，允许任务完成

### 实战应用场景

#### 场景1：多视角并行代码审查

单个审查员往往只能关注一种类型的问题。通过拆分审查维度，让多个队友从不同角度同时分析同一套代码，更全面地发现遗漏。

> 创建一个智能体团队来审查 PR #142，包含三个审查员：
> - 安全专家：检查注入风险、认证缺陷、敏感信息暴露
> - 性能分析师：查找 N+1 查询、内存泄漏、不必要的循环
> - 测试验证者：检查边界情况覆盖和测试充分性
>
> 各自独立完成审查后，由 Team Lead 汇总为按优先级排序的问题清单。
> 如果不同审查员对同一段代码有不同看法，记录分歧并标注。

<strong>为什么适合 Agent Teams</strong>：三个审查维度互相独立，可以完全并行。审查员之间的分歧本身就是有价值的信息——如果安全专家和性能分析师对同一段代码有不同的优化建议，Team Lead 可以记录这个权衡点。

#### 场景2：对抗式调试

当问题的根本原因不明确时，让多个智能体同时验证不同假设，比逐一排查更高效。

> 用户报告结账接口出现间歇性 500 错误，约 5% 的请求会失败，无明显规律。
>
> 创建 5 个调查员分别验证以下假设：
> 1. 数据库连接池在高并发下耗尽
> 2. 库存扣减存在竞态条件
> 3. 第三方支付 API 超时处理不当
> 4. 内存压力导致 GC 暂停
> 5. 微服务间的网络抖动
>
> 要求：
> - 每个调查员必须给出支持或否定其假设的具体证据
> - 调查员之间互相挑战、质疑对方的结论
> - 最终存活的假设最可能指向根本原因

<strong>为什么适合 Agent Teams</strong>：对抗式调试的核心在于队友之间的<strong>直接通信和互相挑战</strong>——这是 Subagents 无法做到的。当调查员 A 找到证据支持”连接池耗尽”时，调查员 C 可以立刻质疑：”如果是连接池问题，为什么只有结账接口受影响而查询接口正常？”这种对抗式讨论能迅速淘汰不成立的假设。

#### 场景3：跨层功能开发

将一个完整的功能拆分为互不干扰的层级，让队友各自负责一个模块。

> 创建一个智能体团队来开发通知系统，包含以下队友：
> - 队友 1（后端）：设计并实现通知 API（创建、列表、标记已读、删除）
> - 队友 2（数据库）：设计表结构、编写迁移脚本、添加索引
> - 队友 3（前端）：实现通知铃铛组件、下拉菜单、通知列表页
> - 队友 4（实时）：WebSocket 集成，实现新通知的实时推送
> - 队友 5（测试）：编写端到端集成测试
>
> 任务依赖：
> - 队友 1 依赖队友 2（需要数据库表先就绪）
> - 队友 3 依赖队友 1（需要 API 接口先定义好）
> - 队友 4 依赖队友 1 和队友 3
> - 队友 5 依赖所有其他队友
>
> 每个队友只修改自己负责范围内的文件，不要跨模块操作。

<strong>为什么适合 Agent Teams</strong>：跨层开发的关键在于<strong>任务依赖管理</strong>。Agent Teams 的共享任务列表能自动处理依赖解锁——当数据库队友完成迁移后，后端队友的任务自动变为可执行状态，无需人工协调。同时，每个队友只操作自己的文件范围，最大程度减少合并冲突。

#### 场景4：技术方案竞标评审

当面临重要技术决策时，让不同队友分别论证不同方案，最终选出最优解。

> 我们需要为项目选择状态管理方案。创建一个评审团队：
>
> - 队友 A（Redux 方案）：论证使用 Redux Toolkit 的优势、编写示例代码
> - 队友 B（Zustand 方案）：论证使用 Zustand 的优势、编写示例代码
> - 队友 C（Pinia 方案）：论证使用 Pinia 的优势（如果是 Vue 项目）
>
> 每个队友必须：
> 1. 基于当前项目的实际代码给出论证（不要泛泛而谈）
> 2. 编写一个真实的示例，展示该方案在当前项目中的使用方式
> 3. 列出该方案的缺点和潜在风险
>
> 队友之间互相质疑对方方案的薄弱点。
> Team Lead 最终基于讨论结果，输出一份对比分析报告。

#### 场景5：大规模代码迁移

当需要在大量文件中执行统一的变更时，多个队友并行处理可以显著缩短耗时。

> 项目需要将所有 API 请求从 axios 迁移到原生 fetch。
> 涉及约 60 个文件，分布在 src/api/、src/services/、src/hooks/ 三个目录。
>
> 创建一个迁移团队：
> - 队友 1：负责 src/api/ 下的所有文件
> - 队友 2：负责 src/services/ 下的所有文件
> - 队友 3：负责 src/hooks/ 下的所有文件
> - 队友 4：负责更新所有受影响的测试文件
>
> 迁移规则：
> - 将 axios.get/post/put/delete 替换为 fetch，保持接口行为不变
> - 错误处理统一使用项目中已有的 handleFetchError 工具函数
> - 不要修改业务逻辑，只替换请求方式
>
> 队友 4 在其他三个队友完成后开始工作。

### 最佳实践

#### 何时适合使用 Agent Teams

<strong>适合的场景</strong>：

- 任务可以拆分为多个<strong>互相独立</strong>的工作单元并行推进
- 需要多个角度的分析或审查（代码审查、方案评审、对抗式调试）
- 跨层或跨模块的功能开发，各队友负责不同的文件范围
- 大规模批量变更（迁移、重命名、格式统一等）
<strong>不适合的场景</strong>：

- 任务本身是严格顺序的，无法并行
- 多个队友需要频繁修改同一个文件（极易产生冲突）
- 工作之间存在强耦合，队友之间需要频繁等待
- 体量很小的日常任务——协调成本可能超过收益

#### 给队友足够的上下文

队友会自动加载项目级上下文（CLAUDE.md、MCP 服务、技能），但<strong>不会继承</strong> Team Lead 的对话历史。因此，在创建队友时提供的启动提示（spawn prompt）至关重要——它是队友理解任务背景的最关键来源。

一个好的启动提示应包含：任务目标、涉及的文件范围、技术约束和期望的产出物。例如：

> 创建一个安全审查队友，启动提示如下：
> "审查 src/auth/ 目录下的认证模块，重点检查 Token 处理、会话管理和
> 输入验证方面的安全漏洞。项目使用 JWT Token 存储在 httpOnly Cookie 中。
> 对发现的每个问题标注严重等级（高/中/低），最终输出审查报告。"

相比”审查认证模块”这样的笼统描述，具体的上下文能让队友更快进入工作状态，减少方向偏离。

#### 等待队友完成

Team Lead 有时会在队友尚未完成时自己动手实现任务，或者过早地认为团队已经完成工作。如果你观察到这种行为，可以明确指示：

`> 等待所有队友完成各自的任务后再继续`

结合<strong>委托模式</strong>（`Shift+Tab`）可以更彻底地解决这个问题——在委托模式下，Team Lead 被限制为只能协调调度，不会自行编写代码。

#### 新手入门建议

如果你是 Agent Teams 的新手，建议从<strong>不涉及代码编写</strong>的任务开始：审查 PR、调研技术选型、调查错误原因。这类任务有明确的边界，能让你体验并行探索的价值，同时避免了并行实现带来的文件冲突和协调挑战。在积累经验后，再逐步过渡到跨层功能开发等需要编写代码的协作场景。

#### 任务拆分原则

好的任务拆分是 Agent Teams 成功的关键。遵循以下原则：

- <strong>文件范围不重叠</strong>：每个队友操作不同的文件或目录，最大程度避免合并冲突
- <strong>粒度适中</strong>：任务过小则协调开销大于收益，任务过大则反馈周期长、返工风险高。理想的任务应是<strong>自包含的工作单元</strong>——一个函数、一个测试文件、一份审查结论
- <strong>依赖关系明确</strong>：如果任务 B 依赖任务 A 的结果，必须在创建团队时显式声明
- <strong>产出可验证</strong>：每个任务应有明确的完成标准，便于 Team Lead 验证和 Hooks 自动检查
- <strong>合理分配任务量</strong>：建议每个队友分配 5–6 个任务。过少会导致队友频繁空闲，过多则容易产生上下文过载

#### Token 成本管理

每个队友都是独立的 Claude 实例，拥有各自的上下文窗口。活跃队友越多，Token 消耗越高。

<strong>成本控制策略</strong>：

- <strong>先用单会话评估复杂度</strong>：在启动团队之前，先用单个会话快速评估任务是否真的需要多智能体协作。如果单个会话能在 10 分钟内完成该任务，使用 Agent Teams 的额外协调成本大概率不值得
- <strong>控制团队规模</strong>：通常 3–5 个队友就能覆盖大多数场景，首次使用建议从 2–3 个开始。超过一定规模后收益递减，三个专注的队友往往胜过五个分散的队友
- <strong>模型分层</strong>：研究和信息收集任务用 Haiku，编码实现用 Sonnet，架构决策用 Opus
- <strong>及时关闭空闲队友</strong>：任务完成的队友如果不再需要，主动关闭以释放资源
- <strong>避免不必要的广播</strong>：广播消息会发送给所有队友，每条消息的成本随团队规模线性增长
<strong>成本效益判断</strong>：Agent Teams 的 Token 消耗约为单会话的 <strong>3–4 倍</strong>。它的价值体现在耗时较长的复杂任务中——例如跨层功能开发从串行的 30–40 分钟压缩到并行的 10–15 分钟，多假设调试从 1–2 小时的逐一排查压缩到 15–20 分钟。当时间节省显著超过额外的 Token 成本时，Agent Teams 才是值得的选择。

#### 监控与干预

不要在启动团队后完全放手。建议定期：

- 使用 `/tasks` 查看任务进度，确认队友没有卡住
- 检查队友之间的通信内容，确认方向没有偏离
- 如果某个队友长时间没有进展，主动介入或重新分配任务
- 团队完成后及时清理资源

### 常见问题排查

<strong>团队创建后队友没有开始工作</strong>

- 检查 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` 是否正确设置为 `"1"`
- 确认 Claude Code 版本不低于 `2.1.33`
- 在进程内模式下，按 `Shift+Down` 切换查看队友是否已创建但未显示
- 确认任务描述足够复杂——如果任务过于简单，Claude 可能直接在主会话中完成该任务而非创建队友
- 重启 Claude Code 后重试
<strong>队友之间通信没有生效</strong>

- 确认队友处于活跃状态（未被关闭或挂起）
- 检查是否使用了正确的队友名称
- 广播消息的成本较高，确认是否真的需要广播
<strong>分屏模式没有生效</strong>

- 确认 tmux 已正确安装：`which tmux && tmux -V`
- 确认是在 tmux 会话中启动的 Claude Code（而非普通终端中启动后再尝试分屏）
- 如果使用 iTerm2，确认已安装 `it2` 命令行工具
- VS Code 内置终端、Windows Terminal、Ghostty 等终端<strong>不支持</strong>分屏模式，请使用进程内模式作为替代
- 或者显式设置：`claude --teammate-mode tmux`
<strong>tmux 残留会话未清理</strong>

团队异常退出后，tmux 会话可能残留。使用以下命令排查和清理：

# 列出所有 tmux 会话
tmux ls

# 杀掉指定的残留会话
tmux kill-session -t 

<strong>队友遇到错误后停止工作</strong>

队友在遇到错误时可能会停止，而不是自行恢复。排查方式：

- 在进程内模式下按 `Shift+Down` 切换到该队友，或在分屏模式下点击对应窗格，查看其输出和错误信息
- 直接给该队友发送补充指示，引导其绕过错误继续工作
- 如果队友已无法恢复，创建一个新的队友来接替未完成的任务
<strong>Team Lead 提前认为工作已完成</strong>

Team Lead 有时会在所有任务实际完成之前就判断团队已完成工作。如果出现这种情况：

- 告诉 Team Lead 继续等待：”还有队友的任务未完成，请等待所有任务完成后再汇总”
- 使用 `/tasks` 检查是否有仍在进行中或未认领的任务
- 开启委托模式（`Shift+Tab`）可以减少 Team Lead 自行抢占任务的倾向
<strong>权限请求过于频繁</strong>

队友的权限请求会上报给 Team Lead，在大型团队中可能造成阻塞。应对方式：

- 在创建团队<strong>之前</strong>，通过 `/permissions` 预批准常用的文件操作和命令
- 如果项目环境允许，可使用 `--dangerously-skip-permissions` 跳过权限检查
<strong>Token 消耗异常高</strong>

- 检查是否有队友在空转（无实际进展但持续消耗 Token）
- 减少广播消息的使用频率
- 及时关闭已完成任务的队友
- 考虑将简单任务的队友切换为 Haiku 模型

### 总结

Agent Teams 代表了一种从「单智能体执行」到「多智能体协作」的范式升级。它与 Claude Code 生态深度结合，在保留子代理能力的基础上，引入了结构化的团队协作机制——共享任务列表、点对点通信、计划审批、委托模式。

它最适合的场景是：任务可拆分、角度可互补、讨论有价值。当你面对需要多视角分析的审查任务、原因不明的复杂 bug、跨层级的功能开发时，Agent Teams 能提供单智能体模式无法达到的效率和质量。

同时也要清醒认识到它的代价：更高的 Token 成本、实验性功能的不稳定性、以及多智能体协调本身的复杂度。对于简单直接的日常任务，单个会话或 Subagents 仍然是更经济的选择。
