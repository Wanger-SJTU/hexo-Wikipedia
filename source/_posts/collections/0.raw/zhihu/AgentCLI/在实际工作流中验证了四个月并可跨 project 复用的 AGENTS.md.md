**# AGENTS.md - Agent Coding Guidelines
****## 文档写作原则：Self-Contained（自解释）****
所有文档（PROGRESS.md、STATES.md、EXPERIMENTS.md、TODO.md）必须做到**只读文档就能完全理解****，不依赖对话上下文或任何脑内默认知识。**
核心要求：
1. **每个方法首次出现时必须解释它是什么、怎么做的****。不能只写"方法 A 效果好"，必须写"方法 A（用因果卷积在 MLP 打分前丰富 token 特征，让 gate 感知邻居信息）效果好"**2. **不要假设读者知道任何缩写****。首次使用缩写时必须给出全称和一句话解释。例如不要写"STE"，要写"STE（Straight-Through Estimator，前向用 hard  掩码，反向用 sigmoid 梯度近似）"**3. **实验结论必须包含足够上下文****。不要写"差距缩小到 0.001"，要写"TopK 自适应选择与 Fixed 周期掩码的质量差距从 0.005 缩小到 0.001（提高 gate 学习率从 0.001 到 0.1）"**4. **数字必须有参照物****。不要写"val_bpb=0.8605"，要写"val_bpb=0.8605（对比：无加速 baseline=0.840，Fixed 周期掩码=0.8605）"**5. **因果链要完整****。不要只记录结论，要记录****为什么****。"TopK 不如 Fixed"不够，要写"TopK 不如 Fixed，因为 TopK 的 think token 48% 紧挨着聚集（间距=1），导致部分 skip token 的信息供给不足（信息瓶颈），而 Fixed 均匀间隔保证每个 think token 只需支撑 2 个 skip token"**6. **docs/STATES.md 顶部维护一个术语表****，所有关键术语集中定义。其他文档开头引用该术语表即可**
反面例子（禁止）：
- "V11 实验效果不错" → 什么是 V11？做了什么？效果不错是多少？
- "提高了 gate LR" → 从多少到多少？为什么要提高？效果改善了多少？
- "信息瓶颈是核心问题" → 什么信息？什么瓶颈？为什么是核心？

正面例子（要求）：
- "TopKConvGate 实验（在 MLP 打分前用 768 通道因果深度卷积让每个 token 看到前 7 个邻居的特征，帮助 gate 感知局部上下文以减少 think token 聚集）：E4T4D4 架构下 5k 步 val_bpb=0.8610，仍略差于 Fixed 周期掩码(0.8605)，差距 0.0005"

跟我沟通请使用中文。任何的临时测试都请在 tmp 文件夹。
我们现在是在一个Docker环境里边，使用公共服务器的电脑。千万不要跟别的程序抢占GPU，这是绝对禁令。不要占满所有GPU，请至少预留一个。
想用 GPU 的时候用 nvidia-smi 查看空闲 GPU 然后精确加载空闲的。不要妥协用 cpu跑本应gpu的任务，没有意义。
你只要遇到问题就处理，遇到问题就处理，直到没有问题。 不要问我顺序什么的。有不清楚的先记下来跳过，所有探究实现路径全部卡住了再都通知我。
完成的任务都记录在某个不变的docs/PROGRESS.md
我语音输入 跟你说的话可能有错别字 请自行理解。
没用的东西放archive/
你要维护 progress 在 docs/PROGRESS.md；你要维护 plan 在 docs/TODO.md，还需要维护docs/STATES.md和docs/EXPERIMENTS.md。
终极目标文档：`docs/ultimate_goal.md`。
全局原则：能用小数据集/短实验快速 debug 就不要用大数据集/长实验；优先最快迭代。
每次准备做实验前必须先高层质疑与方向审视确认当前未知/最小实验/失败后下一步，再决定是否开跑。
docs/PROGRESS.md和docs/TODO.md两者都必须按时间升序记录（越早在前、越晚在后），新增内容只能追加到文件末尾；查看近期内容用 tail（例如：`tail -n 80 docs/PROGRESS.md` / `tail -n 80 docs/TODO.md`）。
很多时候 近期内容是有的 但是你看的太少tail的太少没看到。有两种方法，一个是你去增大tail看的范围，一种是你去超级增大tail的范围但是配合脚本来搜索到想要的日期关键词段落等。

docs/PROGRESS.md：只记录"已经完成"的工作/实验/结论（附关键脚本/日志/ckpt 路径），不要写待办计划。
docs/TODO.md：只记录"未完成/进行中/下一步"的待办与计划（尽量可一键复现）；完成后从 docs/TODO.md 移除对应项，并把结果写入 docs/PROGRESS.md（避免重复记录）。并且可能需要更新docs/STATES.md（docs/EXPERIMENTS.md）
你需要及时清理 todo，要不做掉要不移除，可以根据现有材料思考判断，还是不确定怎么处理的时候可以询问用户怎么处理 todo 项。

如果你在执行一件事的过程中 用户问了一个别的事 如果回应用户能马上回应，那么就直接回应，如果回应用户需要的时间很多 那么把回应用户问题先马上加入 docs/TODO.md。不管怎样，暂时处理完用户请求以后马上继续你之前正在执行的事情，不要干一半不干了

在这两个之外，你还需要维护docs/STATES.md（docs/EXPERIMENTS.md），它的大小基本不会持续增长，因为它只会持续追踪当前状态所有有用的信息 而不会维护旧的过时的没用的东西。在更改删掉旧state前，你应该先git add docs/STATES.md git commit -m "update state: ..."
docs/STATES.md和docs/TODO.md的区别是 它只维护已经完成的成果。相比下，docs/TODO.md只维护未完成的要做的事。
docs/STATES.md只录入真正长期有用的东西而非临时的噪音。
特别地，如果是实验相关内容，那么不要写在docs/STATES.md中，而是写在docs/EXPERIMENTS.md中。docs/EXPERIMENTS.md属于一种特殊的STATE，只是专注于处理实验和数据。

如果你发现某个步骤需要很久，请先确保其正确运行了以后（可以先sleep较短时间之后查看来确认） sleep恰当的时间 使得正好在其跑完以后醒来。

请使用scripts/中正规的脚本训练和测评。
你的所有正式实验里边的评估都不应该出现在tmp文件夹，你都应该把它转正了。

tmp中的文件会被我定时删除，因此只能用作临时实验。

对于docs/STATES.md/ docs/EXPERIMENTS.md中出现的东西，决不能在tmp中，因为tmp是会被我定时清理的，而docs/STATES.md/ docs/EXPERIMENTS.md是需要被长久维护的。应该在scripts/里

对scripts/和logs/和experiments/里的东西，请不要一个文件夹里扔一堆项目平铺，而应该按照目录组织，不同方法啊，版本啊，实现啊，分开组织。这样对于没用的东西，对错误的实现，我们可以方便的删除，我们也可以方便地定位到对应的正确的东西。

请时刻注意删掉没用的 checkpoint等大文件，维护空间不爆炸。
du -h --max-depth=1 . | sort -hr
如果大于 1T 就非常危险了。

有多个相同功能文件的时候 请把错误的冗余的全部都扔进 archive，只保留一个。

当你 1.认为完成了一个**完整****功能的时候并且测试完善整个任务已经被完成（而不是只完成了一部分或者一个阶段还有剩余工作）2.要进行不得已的破坏性改动的时候（务必注意安全和保证所有资源有备份不丢失） 
请 
git add . 
git commit -m 
- 你在发现任何文档或者代码有错误的时候，你的更新不要保留任何的错误痕迹，包括说我从什么什么错误现在改成了什么什么正确版本，并且还留下一个改动痕迹，不要留，我们不需要任何的错误的记录，既然都错了那还记录它干嘛，直接全部改对就OK。

如果你写了一个新版本的正确的文件，请删掉错误版本的文件，不要让相同功能但是实现有差异的文件重复存在，不然会造成极大的混乱不知道哪个是能用的。

兼容性一定不要搞得那么好，不要 fallback 之类的。
原因是你兼容性搞得太好了，我们就无法得知源头到底是哪一种情况了。

同样的功能 禁止有错误实现 并且只能有一个位置正确实现 禁止冗余。

训练和评测的时候 只要是正式实验而不是临时测评的 请一定要在正规的文件里弄好脚本然后一键几乎无传参地跑（允许传参的只有调整空闲GPU，不然改好脚本再一键跑，这是为了可复现性 不然之后我都不知道用什么参数跑的）不要在 tmp 里。

跑训练或评测必须在 tmux 里启动，避免中途断开导致任务退出。

遇到绝对是 bug 的问题不用跟我汇报 诚实修复就行了.
