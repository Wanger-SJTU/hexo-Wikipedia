“你应该编写高内聚、低耦合的代码”

每一个软件工程师都会听到这句话、这句话也被多数人奉之为圭臬。Talk is cheap, 我们不妨看看以下这个简单的设计题；若是你，会怎么设计？

设计一个User类和一个Pages类. User类有自己的持久化数据，例如name, id. pages有自己的持久化数据 id, content.  由于系统的磁盘有限，需要统一管理所有数据库操作。如果我们屏蔽掉最后一句话，常见的写法是：

##user.py

```text
class UserModel:
     name: str
     id: str 
```

....

```python
class User:
     data: UserModel
     def send(self msg): ...
```


##pages.py

```python
class PagesModel:
      content: list[str]
      id: str
class Pages:
      data: PagesModel
      def read(self, index): ...
```

当我们考虑到需要全局配额的时候，最简单的想法是：创建一个Database对象， 让它来管理所有数据分配。

那么代码就会变成：

## database.py

```python
class DB:
     def insert_user(user_data):...
     def insert_pages(pages_data):...
```


## user.py

```text
class UserModel:...
class User:
     db: DB
```


## pages同理
在这个人为创造的DB类中，DB可以执行一些配额限制，例如优先保存User data，删掉本地缓存等等。

当你试图运行的时候，Python将会报一个循环导入的错误：User依赖了DB， 但是DB又需要知道User的具体数据类型来执行插入。标准的循环引用。

常见的循环导入原因有很多，例如为了图方便创造一个万能Context类，到处引用当逃生舱，这里就不一一列举了。就结论来说，<strong>一个概念通常包含多个方面， 而这些方面本身是不应当内聚在一起的</strong>。 如果为了直觉而将它们放在一起，就容易造成意外的耦合和循环（尽管可以避免，但需要十分小心，这反而违背了开发降低心智负担的原则）。

一个概念所包含的五大基本方面
一个概念几乎总是包含以下几个方面：

- <strong>配置Config</strong>。配置是那些在运行过程中不发生变化的数据。
- <strong>持久化（数据）Persistency</strong>。持久化是那些在运行中会发生变化，<strong>其真相来源不是内存而是磁盘</strong>的数据。
- <strong>运行时 Runtime/Resource</strong>。运行时资源指的是运行时的特定资源，例如计算资源，内存，网络端口，磁盘大小，etc
- <strong>核心 Core</strong>. 核心才是一般所说的概念本身，例如一个User类，可以增删改查，进行运算。<strong>由于副作用被推给了上述三者，Core的写法接近于函数式编程。</strong>
- <strong>可观测性 Observability.</strong> 可观测性指的是系统内部运行的事件集合。它通常被人所忽视，或者被poorly implemented，例如试图使用类型系统实现可观测性。对于一个概念，合理的依赖图如下：

![](https://pic3.zhimg.com/v2-351c5f98351f047df94843466cfe150c_r.jpg)你会发现，由于<strong>全局资源有限</strong>，最终还是不得不引入一个全局管理器倒过来管理所有子模块的资源 -> 这导致了所有的循环依赖和God Object ！

更好的设计
这时我们意识到，有一个全局资源模块是<strong>无法避免</strong>的。在这一假设下，如果我们想要避免循环依赖，唯一合理的想法只有“将子模块的资源迁移至<strong>资源模块</strong>，而不是和原始概念放在一起”。

概念图如下：

![](https://pic3.zhimg.com/v2-4836ac8b48a549037db33824db512a5e_r.jpg)不难注意到箭头方向已经悄然改变——刚刚发生了依赖倒置。

闲聊：有另外一种方案是将System彻底视作底层组件。这样的问题是System将无法知道任何业务细节。例如，使用原生Database连接管理数据。这种情况下自然不会引入循环依赖，但是也失去了“优先级”、“异质保存”（例如缓存，缩略图，etc）、“批量写入”等业务相关的细节。System必须提供通用的例如priority 配置来“表达”这种需求。如果我们将System承认为最高级别，让它“管理”整个资源模块，那么理论上，由于写的是代码，任何复杂的管理需求都可以被表达。在这种切分下，<strong>静态资源和运行逻辑分开。静态资源可以像树一样被组织，而运行逻辑随意引用资源</strong>。这样是不可能出现循环引用的。

在上面列出的五大方面中，<strong>配置、持久化、运行资源</strong>都可以看作这里的静态资源，因此应当被类似地组织。也就是说，文件夹应该以这样的形式组织：

src/
   configs/
          user.py
   persistency/
          user.py
   runtime/
          user.py
   core/
       user.py
其中，引用方向为 `core->runtime->persistency->configs` 而不是一个文件将所有逻辑打包。

资源为什么要被区分为三种
因为这三种资源的来源和可信度是异构的。

- 配置是“一旦启动即固定”的。因此可以全部加载进内存。
- 持久化层是“内存中不可信，需要访问磁盘”才知道的。<strong>可能有第三方修改磁盘数据导致改变。这是经典的并发编程场景。</strong>
- 运行时则代表了 <strong>进程被分配到的可用资源集合</strong>。 它不是提前可知的，但却是全局受限的。因此，<strong>子组件通过“申请”的形式向全局资源池申请资源来使用资源，而非依赖于自身配置使用资源。</strong>注意持久化层可以使用配置，运行时也可以使用配置+持久化。在现在大火的LLM Infra中其实可以窥见类似的模式切分：

- 所有模型都是从config初始化而来
- KV Cache（有的时候）是持久化层，取决于是否实现Disk缓存。
- 运行时占比极重，例如GPU Memory, 调度，通信，etcvllm的V0引擎至V1引擎的一大推动力即V0将所有代码全部耦合进入Engine，创造了一个God Object. 根据我们的分析，不难知道，更加合理的模式应当是有一个专门的ResourceManager, 其中将Scheduler, KV Cache Manager, Communication分离，然后通过依赖注入初始化Engine（执行逻辑）。

在GPU内存中储存的数据是否算持久化层？这个问题非常有趣，我的思考结果是不算，因为GPU Memory没有持久化索引。如果GPU Memory有一个配套的文件系统——那么它就是了。
故意选择这个例子，一个原因便是我感觉LLM Infra社区有一种误解，只要快其他都不是事。如果您的主要兴趣在于设计模式，请忽略这段碎碎念 :->
<strong>可观测性的重要性</strong>
实际上，一个程序无需可观测性也可以运行——但同样，你也无法知道它的任何内部运行情况，无法诊断错误，无法研究它，无法进行改进。智谱日前发布了一篇blog: 

[https://z.ai/blog/scaling-pain](https://link.zhihu.com/?target=https%3A//z.ai/blog/scaling-pain)智谱遇到了“线下完全无法复现的bug”。没有完善的可观测性数据，系统中的任何错误就仿佛没有发生过一样。

如何编写可观测性的代码
在我对 我的个人项目 Yuubot（一个agent 群聊bot项目）的重构过程中，我不得不承认，编写完善可观测性的方法只有一种设计模式：EventBus

在抛出结论之前，我大致介绍一下我之前的努力：我试图让每个工具返回自身的 result 和一个可观测字段 Usage. 即返回值为 `result | Usage` Usage中包含时间，计费，等等。但是很快，我遇到了问题：

<strong>强制压缩所有原始数据变成几个固定的统计字段会妨碍后续的扩展</strong>

且不说这种返回值写起来有多别扭，假设我们希望统计特定工具A的特定开销（例如网络延迟），我们就不得不扩展Usage类型，使其包含网络延迟项目；而对于其他工具来说，它们不一定有这一项。最终，Usage会膨胀成一个God Object, 等于所有项目的集合。 

尽管，类型上来说这是完美的，但是系统变得过于僵硬。经过一轮又一轮的重构之后，我最终选择了EventBus模式：工具自己向一个EventBus发布特定事件（可以是任意数据），<strong>只有感兴趣的观察者才记录相关事件：</strong>

![](https://pic2.zhimg.com/v2-c4cff0875d9c17293f8ed5b7cac12f6d_r.jpg)EventBus通过依赖注入插入各个发布者（事件发生处）内部，发布者<strong>自己负责调用</strong>（所以可能发生忘记发布的情况！）。Observser提前订阅事件流，以便于第一时间捕捉。

这一设计模式使得 <strong>特定Observer可以和特定Publisher达成协作而不干扰其他对象</strong>。缺点是，写子类的人可能会忘记调用，导致一些静默错误。

Trade Off
没有完美的设计模式。除非我们可以写高维代码，而不是一维代码。（比如说，按照职责划分的话，合理的文件夹结构应该是一个二维矩阵，但是现在的文件夹都是树）。

观察我们的推导路线不难看出，这种“水平切分”的原动力是“资源有限，需要一个资源模块管理所有分配”。这也是为什么水平切分通常常见于大型项目，因为它们总是尽量吃满一切资源，而不得不使用全局模块管理。除了大型项目以外一个常见的情况是Admin面板——你希望观察和配置所有资源，此时自动引入了一个全局模块，所以最好是水平切分。 <strong>如果你的应用并没有复杂到这种地步，那么按照领域/概念内聚所有资源自然是可行并且更为简单的。</strong>

这种切片方法要求开发者为一个概念编写多个文件，按照依赖顺序维护多个文件。看上去这违背了设计原则（仅一处修改），但是纵观多数大型项目，其架构最终都会演变成这种被称为“水平切分”的架构模式。任何需要动态扩展的框架都只能 1. 要么选择 `TYPE_CHECKING`, 2. 要么选择这种设计模式。尽早避免技术债务，在当今的ai coding世代看上去更为重要一些。
