编译器为什么不再只是工具：MLIR、图编译和 GPU runtime 的边界正在重写（05）

LLM believer .All in AI.

在传统软件里，编译器更像构建阶段工具：源码进来，二进制出去，任务完成。但在 AI 系统里，这个边界越来越站不住。图编译、MLIR、多层 IR、GPU lowering、layout、buffer planning 这些东西，已经不只是在“翻译程序”，而是在提前定义运行时将面对什么样的资源现实。

先说结论

- AI compiler 首先处理的不是指令，而是结构：图边界、shape、layout、buffer 生命周期和并行形态。
- 编译器和 runtime 的关系正在从“前后阶段”变成“相互约束”。
- 一旦 compiler 开始决定工作单元、数据流边界和资源现实，它就已经是系统组件了。如果顺着前几篇的脉络往上走，逻辑其实已经很清楚了。

第一，AI 时代的系统中心正在从经典宿主抽象，迁移到 GPU 主导的执行栈。
第二，GPU 已经不只是“普通设备”，而是一个有自己执行秩序的计算域。
第三，runtime 暴露出来的也不再只是 API，而是一组新的执行原语：stream、event、kernel launch、memory op、graph execution、allocator。

那接下来的问题就是：编译器在这里到底处于什么位置？

在很多工程师的默认认知里，编译器还是老位置。它属于工具链，主要在构建阶段工作，把源代码转换成可执行表示，再交给运行时去执行。这个理解在传统应用开发和不少通用系统软件里都没有问题，但放到 AI 系统里，就明显不够了。

原因很简单：AI 系统中的 compiler，尤其是图编译器、MLIR 一类多层 IR 框架、以及面向 GPU 的 lowering/codegen 体系，已经不只是在“翻译程序”，而是在定义运行时将面对什么样的资源形态和执行形态。

也就是说，编译器在这里越来越像系统组件，而不再只是工具。

这一篇最核心的判断其实很简单：如果只停留在传统工具链视角，很容易把 compiler 理解成一个离运行时比较远的“优化器”或者“构建工具”。但在 AI 系统里，compiler 往往是在提前决定 runtime 将要面对什么样的世界。

一、传统编译器视角为什么不够解释 AI 系统
先说传统视角为什么会失效。

在经典的应用编译链里，编译器要解决的主要问题通常是：

- 语义正确性
- 指令选择
- 寄存器分配
- 优化级别权衡
- 目标平台代码生成当然里面也有链接、ABI、调试信息、LTO、profile-guided optimization 等复杂环节，但总体上，编译器和运行时之间的边界是比较稳定的：编译器负责产出某种可执行形式，运行时负责实际加载和执行。

而在 AI 系统里，这个边界开始被不断推平。因为 AI 程序不是一段普通控制流加局部数据结构，它更像是一个围绕 tensor、shape、layout、memory hierarchy 和并行结构组织起来的程序图。编译器如果只停留在“把图翻译成代码”的层面，就抓不住真正决定系统行为的部分。

一个简单例子：某个算子的 lowering 如果决定把中间结果 materialize 到 HBM，而不是在片上直接消费，那么这不只是一个代码生成细节，而是会直接改变 runtime 要面对的内存压力、带宽压力和后续 kernel 边界。换句话说，编译器的一个决策，已经在定义系统资源使用模式。

再比如 layout。
在传统代码里，layout 当然也重要，但往往被看作数据表示选择。而在 GPU AI 系统里，layout 不只是表示问题，它会影响：

- memory coalescing
- shared memory tile 组织
- vectorized load/store 形态
- tensor core friendly mapping
- communication shard 方式
- runtime 是否能高效 batch 和复用 cache这种影响范围已经远远超过“优化选项”的范畴。

所以 AI 编译器最关键的变化，并不是它更复杂了，而是它开始决定运行时的资源现实。

这类系统里，一个反复出现的现象是：很多问题表面上看像 runtime 问题，继续追会发现其实是 compiler 提前把边界划死了；反过来，很多表面上像“某个 lowering 细节”的东西，一旦落到真实 serving 或训练系统里，又会迅速变成资源管理问题。也就是说，compiler 在这里不是旁观者，而是现实塑造者。

二、为什么 AI 编译器首先是“结构编译器”，而不只是“指令编译器”
很多传统编译器优化，最终落点在指令级别。而 AI 编译器首先处理的，往往不是指令，而是结构。

这里的结构包括：

- 计算图结构
- shape 结构
- tensor layout 结构
- buffer 生命周期结构
- 并行切分结构
- kernel 边界结构
- 通信与计算交错结构换句话说，AI 编译器的第一工作不是把某个操作翻译成若干机器指令，而是决定“什么东西应该作为一个执行单元出现”，“哪些边界应该被消掉”，“哪些状态应该被保留”，“数据该以什么结构在系统中流动”。

这也是为什么 MLIR 这类多层 IR 在 AI 系统里格外自然。因为单层 IR 很难同时承载：

- 图级变换
- 算子级重写
- 张量级布局信息
- 并行层次映射
- 目标设备的低层约束AI 程序不是简单地“先高层表达，再一步跳到汇编”，它中间天然需要经过多层结构降解。你必须先在图级看 fusion 与边界，在 tensor 级看 shape 与 layout，在 block/thread 级看 tiling，在更底层看寄存器与指令选择。

这种多层次结构性，决定了 AI compiler 不是一个薄薄的翻译器，而更像一个把“程序结构”不断转化为“资源结构”的系统。

三、MLIR 这种体系真正重要的，不只是多层 IR，而是多层契约
很多人谈 MLIR，容易聚焦在“有很多 dialect”“可扩展”“便于转换”这些表层优点上。它们当然都对，但如果从系统角度看，MLIR 更深一层的重要性在于：它让不同层次之间可以建立明确契约。

这个契约什么意思？

比如在高层图 IR 中，你可能关心的是：

- 算子之间能否融合
- 某些 shape 是否静态
- 某类广播或转置是否可以提前规约
- 某段图是否适合常量折叠到更低层的 tensor IR，你关心的变成：

- layout 是什么
- buffer 是否复用
- 某段 reshape 是否只改视图不搬数据
- 哪些 op 的边界还值得保留再往下到 GPU 相关 lower IR，你关心的又是：

- tile 如何切
- block/thread 如何映射
- shared memory 是否够用
- vector width 怎么选
- async copy 是否可插入这些层次并不是相互独立的。高层的某个判断，会影响下层能否做到某种优化；而下层硬件约束，也会反过来要求高层保留某些结构信息。

所以 MLIR 重要的地方，不在于“层多”，而在于它把这种跨层约束关系显式化了。每一层 IR 不是只负责局部翻译，而是在定义一个新的资源与执行契约。

一旦从这个角度看，compiler 就明显不只是工具链了。它其实是在维护一条跨层契约链，而这条链直接决定 runtime 能否成立。

四、图编译最关键的贡献，不是“把图跑起来”，而是重画执行边界
很多人第一次接触图编译，会把它理解成一种“自动生成高效执行代码”的技术。这当然是一个结果，但如果问图编译在系统层面最重要的贡献是什么，我的答案会更偏一点：

图编译最重要的贡献，是重画执行边界。

为什么边界重要？

因为系统的很多成本都埋在边界里：

- 一个 tensor 是否需要 materialize
- 一个中间结果是否写回 HBM
- 某个 op 是否可以被吸收到邻近 op
- 某段计算是否值得作为独立 kernel 存在
- 某些变换是否应该在图级解决，而不是 runtime 临时拼接这些都不是“翻译正确性”问题，而是资源组织问题。

举个常见例子。假设有一串 elementwise + normalization + reduction 之类的图。如果不经过图级边界重画，runtime 看到的可能是多个独立 kernel，意味着多次 launch、多次全局访存、多次中间结果落地。可一旦图编译器判断这些结构适合融合，它其实不是在做语法变换，而是在：

- 缩短中间数据生命周期
- 降低全局带宽消耗
- 改写 launch 粒度
- 改写后续 memory planning 的现实基础也就是说，图编译器在这里是在重定义系统将要处理的工作单元。

这就是为什么图编译不能只被理解为“性能优化器”。它在本质上决定了工作负载如何被切分成 runtime 可见对象。

如果换成更工程化的说法，我会觉得图编译器真正厉害的地方，不是它能做多少 pass，而是它决定了哪些复杂性留给运行时，哪些复杂性在编译期被消掉。这个划分一旦做错，后面整个系统都会跟着别扭。

五、shape、layout 和 buffer planning，为什么都是系统语义
如果说图编译决定大边界，那么 shape、layout 和 buffer planning 决定的就是 AI 程序最核心的中观结构。

先说 shape。

shape 在很多 AI 程序里不是一个简单元数据，而是执行现实的一部分。某个维度是静态还是动态，某个 batch 是固定还是变长，某段 context 是可预估还是高度波动，这些都会影响：

- kernel specialization 机会
- graph capture 稳定性
- allocator 策略
- batch policy
- distributed 切分方式所以 shape information 并不是“编译器内部方便做优化的附属信息”，而是运行时制度的输入。

再说 layout。

我一直认为 layout 是 AI 系统里最容易被低估但最重要的隐藏主轴之一。因为 layout 一旦定错，后面很多层都会跟着错：

- kernel 访存模式会差
- shared memory tile 会不顺
- tensor core 利用会差
- fusion 机会会减少
- 通信打包成本会变高
- cache 复用会恶化很多时候，一个系统的表现不是输在有没有某个神奇算子，而是输在 layout 选得不对，以至于每一层都在为这个决定埋单。

最后说 buffer planning。

buffer planning 往往被看作代码生成附属步骤，但从系统角度看，它其实是在定义程序的内存现实：

- 哪些 buffer 可复用
- 哪些必须保活
- 哪些中间值可以不 materialize
- 哪些值可以在更高层被消掉
- 哪些阶段需要预留 workspace这些决策将直接决定 runtime allocator 面对的压力和 serving system 或训练 runtime 能否稳定组织资源。

所以 shape、layout、buffer planning 全部都是系统语义。

六、编译器和 runtime 的关系，正在从“前后阶段”变成“相互约束”
在传统视角里，编译器和 runtime 经常是前后阶段关系：编译器产出，runtime 消费。

AI 系统里，这种关系越来越像相互约束。

为什么？

因为 runtime 并不是一个中立容器，而是有自己鲜明的执行语义：

- stream 组织
- event 依赖
- graph capture/replay
- allocator 约束
- launch overhead
- shape 多样性
- 多租户或多请求时的调度边界如果编译器不理解这些语义，它生成的执行结构就很可能和 runtime 天然不匹配。

举几个例子：

第一，如果编译器过度追求某种超大融合，把原本可重用的中间边界全部抹平，可能会让 runtime 在动态 shape、多请求混跑场景下失去调度弹性。
第二，如果编译器选择的 layout 对单 kernel 最优，但会让后续跨算子或跨通信边界的转换代价激增，整个系统未必更优。
第三，如果编译器对 shape specialization 做得过深，可能在 serving 场景里带来过多版本爆炸和 cache miss。

反过来，runtime 也不能假装自己只是执行器。它必须知道编译器会如何组织工作，才能决定：

- 哪些图适合 capture
- 哪些 kernel 应该优先 warmup
- 哪些 buffer 生命周期可以配合 allocator 重用
- 哪些 shape 分布值得单独缓存执行计划这就是为什么我说，编译器和 runtime 在 AI 系统里正在共同长成一个系统层。

七、AOT、JIT 与 specialization，不再是纯工具链问题
一旦编译器和 runtime 深度耦合，AOT、JIT、specialization 这些传统工具链话题，也会获得新的系统含义。

在一般程序里，AOT 和 JIT 经常被讨论成性能与灵活性的折中：AOT 快、稳定，JIT 灵活、可依据运行时信息优化。

但在 AI 系统里，这些选择会进一步影响整个执行系统：

- 动态 shape 是否值得在运行时特化
- 某些 request 分布是否适合缓存特化版本
- 某个模型在不同 batch size/context length 下是否应该使用不同 graph
- 什么时候值得用编译时间换掉运行时 launch 和调度成本也就是说，specialization 在这里不是局部编译优化，而是系统整体资源与延迟结构的一部分。

比如推理系统里，如果你发现大量请求落在少数几个 context length 区间，那么对这些区间做更深的特化，可能会显著改善 graph replay 稳定性和 kernel 形态；但如果请求分布非常散，你又可能需要保留更高的动态性，否则版本爆炸会让 runtime 缓存体系反而变差。

这类判断已经不再只是编译器工程师内部的技术选择，而是系统级 trade-off。

八、为什么说 compiler 正在承担“执行结构设计器”的角色
如果把前面的现象全部压缩成一句话，我会说：

AI 编译器正在从“翻译器”变成“执行结构设计器”。

所谓执行结构设计器，意思是它不再主要解决“如何把语义变成代码”这一单点问题，而是在设计：

- 执行边界
- 内存边界
- 数据流边界
- specialization 边界
- 图与 kernel 的边界
- 运行时与静态期的责任边界这就是为什么 AI 编译器和传统编译器在工程味上看起来如此不同。前者总在和 runtime、kernel、memory planning、serving workload 纠缠；后者则更多在目标代码质量、优化 passes 和语言语义支持之间平衡。

不是说传统编译器不复杂，而是 AI compiler 的复杂度来源明显更“系统化”。

九、MLIR、图编译、kernel DSL 之间，不是替代关系，而是分层关系
讨论 AI 编译栈时，容易出现一个误区：要么把所有东西都叫编译器，要么把它们割裂成互不相干的工具。

更合理的看法应该是，它们是分层关系。

图编译层关心的是：

- 图边界
- 算子融合
- 形状传播
- 高层等价变换MLIR 一类多层 IR 框架关心的是：

- 跨层语义承载
- 变换的组织与约束传递
- 从高层结构到低层执行结构的平滑降解kernel DSL 关心的是：

- tile、layout、pipeline
- block/thread/warp 映射
- memory movement
- 目标硬件层次的显式控制它们不是互相替代，而是在共同完成“把 AI 程序转化为可执行资源结构”这件事。

这也是为什么你很难用一句“某个编译器框架很强”来解释整个系统。真正强的不是单点工具，而是这些层之间契约是否打通。

十、这对系统软件视角意味着什么
把 compiler 放回系统视角之后，会得到几个很实在的结论。

第一，编译器边界就是系统边界的一部分。
某些问题在图级解决还是在 runtime 解决，不是实现偏好，而是系统架构判断。

第二，性能很多时候是“编译期和运行时共同造成的”。
你不能只怪 runtime，也不能只怪 kernel。layout、fusion、tiling、launch 组织、allocator、batch policy 经常是串在一起的。

第三，编译器会越来越吃工作负载统计信息。
因为它设计的是执行结构，而执行结构是否合理，很大程度上取决于真实请求分布、真实 shape 分布、真实硬件拓扑和真实内存压力。

第四，编译器团队和 runtime 团队之间的边界会越来越模糊。
最强的系统往往不是某边单独做到极致，而是二者相互理解，形成共同优化闭环。

十一、所以，AI 时代的 compiler 更像 OS 里的什么
如果一定要类比，我会说：AI 时代的 compiler，越来越像传统 OS 里的“内核政策层”和“资源组织层”的混合体，而不只是用户态工具。

这个类比当然不能机械对应，但它有助于理解：

- 它在定义哪些对象会出现
- 它在定义这些对象如何组合
- 它在定义静态阶段和动态阶段的责任划分
- 它在定义后续资源调度的可能空间所以我不喜欢把 AI compiler 叫做“只是 codegen 工具链”。那样会低估它对整个执行系统的塑形能力。

十二、调试、回归和可解释性，为什么也在把 compiler 推向系统层
很多人提到 compiler，会先想到性能；但在 AI 系统里，另外一个越来越强的现实是：没有足够好的 compiler 中间层，你很难建立稳定的调试和回归体系。

为什么？

因为 AI 程序的行为边界经常跨层：

- 图级变换改了一个边界
- layout 改了一个内存现实
- kernel lowering 改了某个数值路径
- runtime 因为 shape 变化走了另一条执行路如果没有相对清晰的 IR 和跨层契约，问题就会很快变成“系统黑箱里某处变了”。性能回归也好，数值偏差也好，运行时不稳定也好，最终都很难解释。

这就是为什么成熟 AI compiler 不只是为了产出快代码，还必须承担：

- 中间表示可观测
- 关键变换可定位
- 不同 lowering 路径可比较
- 与 runtime 行为的关联可追踪一旦一层组件同时承担了性能、正确性和可解释性的责任，它就已经明显是系统组件，而不是单纯工具了。

从团队协作角度看也是一样。只要一家公司真的开始同时做 compiler、runtime、kernel 和 serving system，它就会很快发现：compiler 已经不是“交付一个离线产物”的部门，而是在定义整条系统链路的接口。如果这层接口不稳定，后面所有团队都会跟着反复返工；如果这层接口清晰，很多跨层优化才有可能逐渐制度化。

十三、结语：编译器正在长成系统组件
这篇我想落在一个非常明确的判断上：

在 AI 系统里，编译器不再只是把程序翻译成可执行形式的工具，而是在定义运行时要面对什么样的资源现实、执行结构和边界条件。

MLIR、图编译、layout 选择、shape specialization、buffer planning、kernel lowering，这些东西合在一起，实际上是在决定：

- 哪些工作单元会存在
- 哪些内存边界会存在
- 哪些数据移动会发生
- 哪些动态性被保留
- 哪些执行路径被固化一旦它开始决定这些问题，compiler 就已经不只是工具，而是系统组件。

下一篇，我会把这个判断继续压到一个更具体也更“硬件味”的话题上：

为什么 fusion、tiling、layout 不是局部优化？
为什么我更愿意把它们看作 GPU 时代新的资源管理接口？

附：真正强的 AI compiler 团队，最终都会被工作负载拉回现实
最后补一句更工程化的话。一个真正强的 AI compiler 团队，最后一定会被真实工作负载重新塑形。因为只有进入真实 workload，你才会知道哪些变换是长期有效的，哪些 specialization 只是局部漂亮，哪些 IR 设计真的便于跨层协作。也正因为如此，AI compiler 很难长期作为“离产品很远的工具团队”存在，它最终一定会和 runtime、kernel、serving、distributed system 一起形成更紧的系统闭环。
