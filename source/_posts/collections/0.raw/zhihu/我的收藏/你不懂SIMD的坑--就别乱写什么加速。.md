我看到不少人说：哎呀我写的SIMD怎么这么慢啊，这不行那不行的。我说:只要你觉得自己没错，那一定是别人的错。要怪就去骂INTEL这个老邓.

因为AMD解决了很重要的几个问题.(我只管AMD  YES就完事儿).


#### 先说寄存器:

MMX寄存器：能装64位数据(8字节).
XMM寄存器：能装128位数据(16字节)。
YMM寄存器：能装256位数据(32字节) : 分高128(xmm),和低128(xmm)
ZMM寄存器：能装512位数据(64字节) : 分高256(ymm),低256(ymm)

问题就出在ymm寄存器开始搞出来的(因为它是用2个xmm寄存器组合的),这种其实就是一种兼容策略，涉及到状态。

这个问题叫状态转换

#### 状态转换是啥???

简单的说就是依赖,当你拿一个ymm寄存器(256位)来操作单个128位(xmm)时,intel处理器(6代前)这个老邓会有几十个时钟周期等待,因为它认为你在操作低128位(xmm)时 ，如果高128(xmm)有垃圾数据 它不知道怎么办，至于延迟等待做了啥 只有它们知道.比如暂存起来之类的(根据处理器手册解释是:影响推测结果,对前序指令的依赖有延迟,如果高位全是0,后续操作可直接合并不用等待). 所以，

所以VEX前缀扩展就出来解决问题了,特别是老向量库还在用MMX，XMM的会非常的慢.

#### 通通用带V前缀的指令

先说3个典型状态表示：

A  状态:  干净的 ，比如 全0， 刚开机会处于这个状态，或执行vzeroupper(高位清0).也是intel老邓搞出来救场的.

 B 状态: 修改状态,表示有数据时，对ymm等寄存器修改操作等.

C 状态: 保存状态，关键就在这,执行保存(操作/传输等)时当没有用V扩展时，它会拆分几个操作. 比如操作低128位(正常执行),但高128位是未知的,处于等待几十个周期.这就是假依赖.

错误例子(混用V版本和非V版本)：

vaddps ymm0, ymm1, ymm2 ; 执行256位指令，不是V扩展,但这里无所谓,还没到不同状态切换阶段.**addss xmm3, xmm4 ; 执行非V版本的128位指令，处于B状态. 这个状态要转换到C状态 就是一顿忙等待...期间可能会把垃圾数据暂存。

vmulps ymm0, ymm0, ymm5 ; 再次执行256位指令，需要先把展存数据取出来再存放到高128位，状态表示：C→B，耗时70+周期,要避免这些全用V扩展就是了.

正确例子(全部用V扩展)：

vaddps ymm0, ymm1, ymm2 ; 状态B**vaddss xmm3, xmm3, xmm4 ; 用VEX版128位指令，上层清零，保持状态B
vmulps ymm0, ymm0, ymm5 ; 状态B（无需状态转换）

同时V扩展还是非破坏的：

addsd xmm0, xmm2 ;老的2操作数 

vaddsd xmm0, xmm1, xmm2  ; 新的3操作数，非破坏操作

其实熟悉x86编码的应该很清楚，x86很多需要手动的显示切换状态的指令，这就是一种兼容策略，所以你就能明白为啥每次新架构指令有个清0指令的配套。

说白了其实也算是依赖链问题的其中一种。

<strong>还有中断问题：</strong>

传统中断处理程序只保存XMM寄存器（低128位），不保存YMM高128位，导致状态C转换（拆分保存数据）

<strong>使用 ： XSAVE/XRESTORE 来解决</strong>

xsaves [mem]  ; 保存所有向量寄存器（包括YMM/ZMM）
 ; 执行YMM指令。。。
 xrestore [mem] ; 然后 恢复寄存器

#### 编译器也有坑

使用memset等库函数时 老/拉跨的编译器会插入SIMD指令(怕出现混用V扩展)，这些函数可能隐含使用YMM寄存器（CPU分派器选最优指令集）。。。

PS： AMD没有这些问题，AMD( Ryzen,EPYC等 )从设计上就避免了寄存器状态拆分的机制,你使不使用VEX指令，都不会触发这些高代价转换。

INTEL应该是6代后就优化了部分问题.(AVX512后又跑出来一些问题..，比如避免上面状态转换的vzeroupper指令和vzeroall指令，但到了AVX512这个指令又非常慢...), 

另外vzeroall指令不要再windows上用。会破坏ABI.

寄存器相关部分还有2点基本常识:

- 用对齐版本的加载/传输指令.
-  数据对齐规则：MMX(8字节对齐),XMM(16字节对齐),YMM(32字节对齐),ZMM(64字节对齐)
数据对齐性能损失其实没那么不堪/重要，比如：非对齐访问可能比对齐慢1-2个时钟周期(cpu处理边界耗时)，但非对齐的比强制对齐更灵活,随便造. 主要是有些架构不对其会触发信号，触发信号影响指令那边的缓存，导致RAS 重置(RAS=返回地址栈，也是一块缓存(call/ret跟踪,很小，深度在32/个条目,所以递归最好控制在32下.))，

### SIMD预热问题

<strong>CPU的256位执行单元高128位</strong>在闲置时会被关闭，省电，再次启用时需要“热机”，会短暂的有性能下降.

关闭到启用延迟约14微秒，期间执行256位指令时，CPU会用低128位单元分两次处理 :因为高128位去要启用.

如果675微妙内没用到整个256位，高128位会再次关闭（处于省电模式）.

 要避免这个性能波动，最直接的办法就是主动预热:

在需要256位指令前，先执行一条垃圾指令,如清0：vpxor ymm0, ymm0, ymm0，无实际作用但激活高128位.

### 整数与浮点的旁路时延

以PS结尾的(PS表示单精度，D表示双精度)单精度浮点指令如 MOVAPS 比双精度 MOVAPD 或整数MOVDQA等指令编码更短。在有些处理器上，你要是使用MOVAPS来传输整数到寄存器就会有旁路时延，但内存访问没事。 

### 清0操作推荐

PXOR xmm0, xmm0将寄存器置零效率最高

PXOR xmm0, xmm0 ; 高效清0（优于XORPS/XORPD）

清0这个在X64是有说法的.也是兼容演变的重要亮点(bushi), 这个其实通俗的说是：叫消除依赖,前面也说了,

如前一条指令的结果是后一条的输入就会导致流水线停顿,所以现代X86处理器有一堆的清0操作，但执行飞快，几乎0周期内完成.通用寄存器就不说了，SIMD的清0大改就这些常用:

VXORPS ymm0, ymm0, ymm0

VPANDN ymm2, ymm2, ymm2

VPSUBQD ymm3, ymm3, ymm3

还有置1之类的:

VPCMPEQB系列...

C/CPP编译器也会把你的(循环单元素置1/0)编译为这些指令，但记住这些还是有必要的.

注意：只能是0(全0)/1(全1),其他任何值不都不算置1/置0操作.

### 现代CPU微操作(uOP)内部缓存限制()

不要一把梭的使劲造/堆AVX指令,现代流水线一个周期从解码后缓存里拿出来能在1周期内同时执行多个宏操作(可分解多个微操作),但是是有边界的(窗口限制)，这个叫Op Cache条目，存储解码后的微操作/宏操作的.但是是有限制的.

比如条目超限例子:

 VPADDQ YMM0, YMM1, YMM2 ** VPADDQ YMM3, YMM4, YMM5 
 VPADDQ YMM6, YMM7, YMM8 

...一堆这种操作

C/cpp语言也同理，比如循环体内塞满一堆这种AVX...

这个条目是: 每/单条目计算的,某些架构最多7条带EVEX前缀的AVX-512指令...(总容量几个KB,一个Op Cache条目只能存两个相邻64B缓存行的指令操作).

如果你在热点代码中使用AVX之类的时候就要注意这些，消耗很大.因为超限也会触发状态转换/模式切换.

由于当前这是在OC模式,<strong>OC模式(op cache)就是解码后的缓存,如果发生转态转换(模式切换)，延迟（10个内）不仅仅是</strong>流水线停顿,还会有：**重新解码，分支路径反复切换等惩罚。

<strong>正确用法:</strong>

 VPADDQ YMM0, YMM1, YMM2 
 ADD RAX, RBX                                   ;    非AVX指令，和前面分隔，绕开条目限制.  
 VPADDQ YMM3, YMM4, YMM5 
 VPADDQ YMM6, YMM7, YMM8 

如果不指导架构之间的差异或具体目标，建议不要密集使用AVX,比如4条，6条的那种。(数据加载这些无所谓，几乎没啥延迟，主要是操作比如运算之类的才是)，应该2-3条后插入其他指令来对齐.

当然还是其他微操作窗口限制 如执行单元，这个就不说了。编译器会重排，码er无需关心.

总之避免一堆垃圾杂堆.分解成小份量. 哪怕是加分支条件循环都可以(现代CPU分支预测器很强 无需关心预测惩罚).

### 布尔操作

布尔向量指令：PAND/PANDN/POR/PXOR 这几个的整数版本在部分AMD和Intel处理器中 可使用更多执行单元，效率高于浮点版本 如ANDPS.

#### 一次处理大块数据和边界问题

如：数组长度不是向量长度的整数倍时.

要考虑一次操作而不是2/N次拆分,

比如假设你要处理10个元素的一块内存（数组），但是你一个zmm能装不低于10个，多多出来的咋办？屏蔽掉就是了。用MASK屏蔽掉索引外的数据.只操作部分数据.

另外,有些水友关心影响优化问题。我建议是，写纯汇编，而不是inline asm. 比如哪怕是一系列类型擦除操作各种转换都有影响呢，inine asm 最大的用处是 写类似裸机/底层操作的时候能能临时用到ring0 的一些比如RDMSR之类的,也没有宿主OS依赖/运行时环境等依赖，不需要啥优化 因为是干净的二进制。而RING3上面你不需要关心性能，编译器有一套完善的优化策略,你用了ASM， 编译器很南对 inline asm 进行数据流分析(因为这些是全局性的，跨过程分析的，还有寄存器分配问题，inline asm就像内存屏障一样 自己想象。) 简称负优化，所以并不是你写的asm指令有问题，而是你干扰了编译器。

而纯汇编没有这些问题和冲突，完全掌控代码生成和寄存器分配，元编程有强大的宏和表达式一系列工具解决编译时计算和代码生成，运行时代码部分可以针对特定 CPU 微架构进行深度优化，

举个例子，比如密集循环操作(多个不同内存快操作): 你可以用单个负偏移来节省索引寄存器/变量和条件分支指令。

然后也没有额外脏数据/代码，也没有运行时,写的如何看自己了.
