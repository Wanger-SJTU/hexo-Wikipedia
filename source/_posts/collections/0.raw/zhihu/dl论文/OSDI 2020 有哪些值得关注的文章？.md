训练优化

Retiarii: A Deep Learning Exploratory-Training Framework
来自微软的工作。Retiarii是一个针对AutoML任务所设计的系统（开源在https://github.com/microsoft/nni/），主要是为了解决当前DL计算框架的两大问题：

- 对于AutoML的支持不够好。例如两个要explore的模型之间可能只有很小的差别，但在这些框架中却需要各自实现一份，过程比较重复冗长；又或者用户直接定义一个“巨无霸”模型，通过动态图或控制流的方式来决定具体explore的时候走哪个分支，但这就会导致模型巨大，且复杂的分支条件给优化带来麻烦，显然也不够优雅。
- 由于框架把AutoML中每个子模型的训练当作一个独立的过程，则无法利用exploratory-training过程中不同任务的相关性来加速模型搜索。一个直观的例子：当两个模型的区别仅仅只有一个子模块时，其他相同模块理论上不需重复训练，而只需单独比较这个不同模块的优劣即可。对此，Retiarii的解决方案有以下几点创新：

- Mutator抽象：AutoML的训练过程其实就是在一个大的搜索空间内找出比较好的子结构及其组合(即DFG, data-flow graph)。与其对于每个组合都用一种完整的DFG去描述，不如定义一个base model，然后每种DFG= base model + diff。这里的diff就是Mutator希望起到的作用。
- JIT引擎：为了实现Mutator希望达到的效果，Retiarii需要频繁地基于base model之上做各种mutate操作，这就需要一个Just-in-time (JIT)的执行引擎来执行每个DFG。
- 多模型相关性联合优化：有了Mutator和JIT之后，最有趣的部分来了，也就是如何做Cross-model优化。Retiarii基于算子批处理、子图权重共享等方法，能够有效地对搜索过程中的多个DFGs做子图去重、训练并行化等。值得一提的地方是并行训练部分，Retiarii针对AutoML采用了一种特殊的混合并行方式（如下图），将参数存在PS上，每个GPU根据自己要处理的DFG拉不同的参数下来，且每个GPU也是读取不同的数据，相当于结合了数据并行与模型并行，能够同时训练多个DFGs的同时，也能通过PS方式解决参数过大导致单节点存不下的问题。

KungFu: Making Training in Distributed Machine Learning Adaptive
Mai Luo老师在帝国理工学院期间的工作。当前分布式训练场景中，许多算法超参（学习率、batch size）以及系统超参（worker数量、通信拓扑等）都会对整体训练收敛时间产生影响，相关研究也表明在训练过程中对这些超参进行动态配置会有加速收敛的作用。而现在主流的计算、通信框架在分布式训练的弹性支持上做得还不够完美，通常是只解决了其中部分问题。Kungfu则是希望实现一个兼顾易用性、高效性、动态性的弹性训练框架。

KungFu有三个设计层面的创新点：

- [易用性] 用户可定义Adaptation Policies (APs)，声明不同训练状态下应如何改变超参数。这里说的“状态”，是指KungFu会提供监控系统训练指标的功能，包括梯度统计情况、workers的性能等，这些指标的集合构成所有训练状态。举个例子，当某个worker显著变慢时，把它从训练中踢掉，然后调整此时的全局学习率（因为全局batch size变小了）。
- [高效性] APs的触发和执行，依赖于对系统训练指标的收集（如梯度信息）。由于收集指标本身是有开销的、可能导致原本的训练性能受损，KungFu提出了一种非阻塞的集合通信层，能够在不同worker之间使用非阻塞的方式去同步这些指标信息，从而避免影响训练性能。
- [动态性] 由于需要动态调整超参数，现有系统（如Horovod Elastic或Auto-Scaling）要求用户使用动态图执行模式（例如PyTorch和TensorFlow eager mode），否则无法在运行过程中调整参数。动态图模式会在每一轮迭代重建计算图，优点是能够支持动态参数，缺点是会引入较大开销（相比于静态图）。KungFu引入了一个巧妙设计，将这些动态参数设计成静态图中的节点。在运行过程中，这些节点能够根据APs的要求，实时计算出当前状态下所需要的参数并将结果输出给计算图，在兼顾了性能的同时也实现了参数的动态性。KungFu代码开源在https://github.com/lsds/KungFu

A Unified Architecture for Accelerating Distributed DNN Training in Heterogeneous GPU/CPU Clusters
系统名叫BytePS，来自字节跳动AI-Lab机器学习系统团队。也是我本人参与的工作。BytePS在去年其实就已经开源：https://github.com/bytedance/byteps，这次OSDI以论文形式发表出来。我们针对目前GPU/CPU异构集群的特点，提出了一种更适合这种异构集群的分布式训练通信架构。

目前数据并行的主流方案是All-reduce和PS两种架构（在工业界All-reduce是真正的主流，Horovod就是其中典型代表），而它们依然因设计上的问题存在性能瓶颈。BytePS的提出就是针对这些问题，重新设计了机器间网络通信和机器内的PCIe通信，使得端到端的性能有大幅提升。BytePS也已经部署于字节跳动内部的真实训练业务中。

【研究动机】我们发现目前基于All-reduce与PS的架构在设计上存在几个主要问题：

- 机器间网络通信问题现在的GPU训练集群通常都是异构的，即同时拥有GPU/CPU两种资源。而且不同于GPU资源，CPU通常是比较富余的。在这种异构场景下，All-reduce和PS对资源的使用情况如下图所示。

从图中看出，All-reduce的同构化设计导致其无法充分利用这种异构资源，即只有GPU workers之间使用集合通信，将CPU的计算和带宽能力都浪费了；而PS虽然能够利用CPU机器作为PS，却可能在CPU server数量较少的时候（集群中资源是动态的）产生流量热点，从而导致拥塞。所以对于机器间的网络通信，All-reduce和PS都存在一些缺陷。

## 2. 机器内PCIe通信问题


如今一台训练机器通常都含有多张GPU卡（例如8卡）。在做机器间的通信前，机器内部的多GPU需要首先做一次本地通信，通过PCIe或者NVLink连接。

我们观察到，目前的网卡如Mellanox CX5带宽已达100Gbps，已经很接近PCIe 3.0 x16的128Gbps链路带宽。而不幸的是，现在流行的机器内聚合方式（例如8卡直接做一次all-reduce）会使PCIe成为瓶颈，导致网卡的100Gbps带宽打不满。即使对含有NVLink的拓扑，我们也能发现类似的PCIe竞争导致的瓶颈问题。

## 3. CPU瓶颈问题


在问题1中我们看到，相比于All-reduce而言，PS架构实际上是存在更大的潜力的，因为后者能充分利用异构资源。那为什么现实中工业界都在用All-reduce做训练？除了流量热点问题以外，PS实际上还存在一种CPU瓶颈，限制了其性能。

顾名思义，PS (Parameter Server)需要将参数存储在Server上，这就意味着需要将优化器(如Adam/RMSProp等)放在Server上去执行。然而，优化器所涉及到的操作对于CPU来说还是太heavy了。尤其对于100Gbps的梯度输入，CPU根本处理不过来。

【设计】针对以上三个问题，BytePS提出了各自的解决方案：

- 机器间通信优化方案我用一个比较直观的方式介绍解决方案的intuition：

（1）对于PS架构，它只enable了GPU机器与CPU机器之间的通信。那么当CPU机器数量较少的时候，GPU机器的带宽就会打不满。例如下图中，每个GPU机器实际上只达到2/3的理论带宽。依然有提升空间。

（2）对于All-reduce架构，它只enable了GPU机器之间的通信。如下图所示，CPU与GPU之间的带宽资源就被浪费了。

（3）最优方案，其实就是将All-reduce和PS结合起来，使得GPU与CPU机器之间，以及GPU与GPU机器之间都能通信，每台机器的带宽全都能充分利用起来，如下图所示。

思路已经有了。接下来的问题是，既然将两个策略结合起来了，该如何决定分配给每个策略的workload才能使得通信时间最小？经过推导，我们能够得到一个optimal的分配策略。有趣的是，它能够在数学上统一All-reduce和PS两种通信策略，并且泛化到了更一般的情况。详细推导可以看paper。

## 2. 机器内通信优化方案


High-level的思想是去减少瓶颈链路所要传输的数据量。我们同样通过例子来说明。下图是一个8卡机器拓扑，标记0-7的灰框表示GPU，P0和P1表示PCIe switch。现实当中，我们发现P0-CPU0以及P1-CPU1是带宽最小的链路（约80Gbps），我们的目标就是最小化这条链路上传输的数据量。目前主流的做法是对这8卡直接做一次All-reduce，这样P0-CPU0需要传输的数据量是7M/4（根据All-reduce的通信量计算得出），其中M是每张卡上的梯度大小。注意到该做法并没有利用CPU的计算能力。

接下来是我们的方案，主要是利用了CPU的计算能力：

（1）首先，每个PCIe switch下的4张卡先做一次local reduce-scatter，这样每张卡会有M/4已经聚合好的梯度；

（2）每张卡将自己的M/4拷贝到host memory上。注意这个过程使得P0-CPU0只传输了M/4*4=M的流量；

（3）最后，由于此时两个NUMA node的host memory各自有一份大小为M的梯度，我们再利用CPU将这两份梯度加起来。但是这个过程的传输只发生在带宽较大的QPI上（ 300Gbps），并不会产生瓶颈。

于是我们看到，以上方案使瓶颈链路的传输量从7M/4降低为M，显著降低了通信时间。我们总结出的设计原则是：尽量避免cross-NUMA GPU的直接通信，可以利用CPU进行reduce来间接完成。在paper中，我们还介绍了NVLink拓扑下的解决方案。这里不多介绍。

## 3. CPU瓶颈优化方案


前面提到优化器对于CPU而言过于heavy，这也是PS架构的性能缺陷之一。但是我们又希望能够利用上CPU的计算能力，这时候就需要考虑如何将CPU高效地用起来。经过分析，我们发现优化器实际上做了两件事：（1）Sum：将来自其他GPU worker的梯度加起来得到一份聚合后的新梯度，（2）Update：利用新梯度，对参数进行更新。Update对于CPU来说确实heavy了；但Sum其实是CPU-friendly的，毕竟求和操作在CPU上已经有很多成熟的优化手段（例如AVX指令集）。

基于此，我们提出了Summation Service来替代PS架构当中的Server。如下图所示，我们将Update移到计算能力更强大的GPU上，并使CPU只做Sum，如此就能解决CPU瓶颈问题。

前面介绍的三个设计点融合起来，就得到了下图所示的BytePS完整系统架构图：

- 在每台GPU机器上，我们有一个Communication Service模块，负责聚合本地多卡的梯度（即机器内多卡通信）；
- 在每台GPU/CPU机器上，运行一个Summation Service模块，处理来自其他GPU机器的梯度；
- 这些模块之间通过网络互连，通信策略使用的是设计点1中提到的方案。
【实现】在网络通信上，我们做了较多RDMA相关的优化，Implementation章节有详细介绍我们在部署时遇到的RDMA Slow Receiver问题以及对应的解决方案。BytePS系统支持TensorFlow/PyTorch/MXNet，并且也提供了各种各样的Python接口方便用户使用。

【实验】最后简单说一下性能。我们在ResNet50, VGG16, UGATIT-GAN, Transformer, BERT-Large, GPT2模型上都做了性能测试（针对系统吞吐率）。从端到端结果来看，在256张V100的实验规模中，BytePS的吞吐率能够超越Horovod达84%。在字节跳动内部真实的落地场景中，我们也能观察到类似的加速效果。

调度优化

AntMan: Dynamic Scaling on GPU Clusters for Deep Learning
来自阿里巴巴PAI团队，也是Wencong继Gandiva之后又一调度力作。Antman面向深度学习集群任务调度场景，主要针对DL集群中GPU利用率低、任务排队时间长等问题，提出应该利用DL任务对资源使用所具备的一些动态性和规律性，进行dynamic scaling。Antman已经在阿里内部集群部署。

Antman是“调度”和“计算框架”协同设计后的统一架构，更高层地说，计算框架的改动也是为了更好地服务于调度。这篇工作有一些思想在之前的Gandiva [OSDI’18]工作里也见到过，例如以mini-batch作为调度单元、每个DL任务本身资源需求 (intra-job resource demand) 的测量观察等。但是个人理解，Antman相比Gandiva的一个重要改进在于对计算框架本身做了深度改动，使得computation和memory management能够更好地适应调度的需要。

Antman的主要设计点如下：

- 对计算框架的改造（简单说就是如何使TF/PyTorch支持dynamic scaling）
- GPU显存管理: 针对现有计算框架分配显存后无法及时回收的问题（下图a-c所示），做了一些GPU显存管理方面的改进（下图d-f）。例如（1）计算框架能够及时地回收已经空闲的内存区域；（2）允许部分空间swap到CPU memory上，后续在显存充裕时再swap回GPU memory（通过后面提到的调度器控制）。

- GPU计算优化：提出GPU Op Manager，主要思想是使框架的Op在GPU kernel层面的执行顺序变得可控，并结合多个任务的所有Op做更合理的launch顺序。这样，多个任务各自的计算效率可能都得到提高，因为减少了任务间的切换成本。
- Implementation部分介绍了对计算框架改动的一些细节，主要修改了TF/PyTorch的内存分配、Graph Executor与CUDA算子的交互等。不过似乎因为跟公司内的集群调度有较大耦合，暂时没有开源。2. 调度层面（如何调度大量计算任务）

- Global scheduler：负责全局GPU资源分配，主要针对resource-guarantee任务（对SLA要求高）和opportunistic任务（对SLA要求较低）做综合调度。
- Local coordinator：负责每张卡上的任务调度，可以理解为GPU Op Manager的上层。优先将资源留给resource-guarantee型任务，剩余的再给opportunistic任务。Antman在一个超5000 GPU的集群做了部署，平均任务排队时间缩短了一半，显存利用率提升了42%，GPU利用率提升了34%。对于如此规模的GPU机群而言，这些都是相当可观的数字。

Heterogeneity-Aware Cluster Scheduling Policies for Deep Learning Workloads
来自微软和斯坦福的工作，一作Deepak去年也在SOSP发表了PipeDream。这次他们这篇工作讨论的问题是如何针对异构场景设计一种DL任务调度系统，其中异构的含义包括多种加速器（GPU / FPGA / ASIC）以及各种不同的调度算法（例如FIFO和min makespan等）。不同加速器的性能和成本差异很大，而现有调度算法并没有考虑这种异构性，导致调度上依然存在更多优化空间。

这篇工作提出了Gavel系统，能够考虑异构加速器的差异性，并能支持多种不同指标的调度算法，使它们都能很好地考虑这种异构性。Gavel将每个任务所需要的计算拆解成多个阶段，每个阶段可能分配到不同加速器上（例如60%的时间单独跑在一张V100上，剩下40%的时间跟另一个任务跑在同一张A100上）。Gavel的核心就是在这些可能的拆解组合（文中称为heterogeneous allocation）当中搜索出一个最佳的策略，方法是将每种组合都转化为effective throughput，这样不同组合之间就存在可比性。

在具体实现中，Gavel使用抢占式轮询的调度策略，保证每个任务都能够按照比例分到在GPU上的计算时间。Gavel也针对多种不同指标（如平均任务完成时间、最小化最大工作完成时间）做了实现，并在小规模物理集群和大规模仿真当中都验证了效果。

HiveD: Sharing a GPU Cluster for Deep Learning with Guarantees
HiveD是微软OpenPAI下的一个子项目：https://github.com/microsoft/hivedscheduler，也是一个多租户集群DL任务调度的相关工作。

这篇工作提了一个概念叫做sharing anomaly，意思是共享集群中的多个任务，由于调度上的不合理，每个任务拿到的GPU可能是比较分散的（例如分布在多个机器上），导致local affinity比较差。HiveD希望从设计上避免sharing anomaly的出现，并提出了一种新的抽象叫Virtual Private Clusters (VC)，将集群划分为多个逻辑上的小集群，如下图所示。只要VC的规划本身考虑了affinity的因素，任何以VC为粒度的调度算法都将不会导致sharing anomaly的出现。

具体设计中，这些VC的划分实际上是动态的，根据集群资源情况可以实时调整。HiveD提出了一个Buddy Cell Allocation算法来做动态划分。

HiveD的实验部分相当详尽（近5页的eval）。从结果来看，HiveD能够完全去除sharing anomaly现象，也能显著降低集群的任务排队时间。

PipeSwitch: Fast Pipelined Context Switching for Deep Learning Applications
PipeSwitch是一篇很有趣的工作，主要解决了这样一个问题：如何在GPU上进行高效的多任务切换。现有的多任务系统支持例如Nvidia MPS远谈不上高效（切换时间甚至达几秒，而很多推理任务的SLO可能是毫秒量级）。但这样的系统对于调度是有重要作用的。考虑这样一个场景：将训练和推理任务混合部署在同一个集群里。训练任务一般是时间较长，SLO不敏感；推理任务则是对SLO相当敏感，且可能具备明显的潮汐特性（例如一些在线推理到了晚上workload会比白天轻一些）。这两类任务的差异还是很显著的，因此很多公司倾向于将它们各自部署在单独的集群中，但就会导致资源利用率问题，比如训练任务无法在晚上利用推理集群空闲出来的GPU资源。如果我们既想要将训练和推理混合部署，同时又希望它们之间的切换能够高效呢？这就是PipeSwitch希望解决的问题。

PipeSwitch为DL定制了一套专门的多任务GPU context switch方案，能够使得多任务在同一GPU上高效地进行分时复用，并且这些任务的切换时间只在毫秒级别，在满足推理任务的SLO前提下完成切换。

之所以说是专为DL定制的，是因为PipeSwitch利用了DL任务一个非常重要的特性 – DNN模型通常都包含多个layer，且计算都是按layer的顺序进行的，最前面的layer会在前向传播时首先被用到。于是基本思路就有了：在做context switch的时候，优先将靠前的layer所需要的状态信息加载进GPU中，同时GPU就先计算这些已经ready的layer，整个过程被流水线化了（如下图b所示）。而现有做法（图a）则是将整个DNN作为一个大黑盒，将它无脑地完整加载到GPU之后，再按layer进行计算。相比之下，显然PipeSwitch这种思路高效得多。这种流水线的思路其实在去年SOSP上出现的PipeDream和ByteScheduler中也都有体现。

以上设计思路在实现过程中还有一些小问题，例如Pipeline的启动开销较大、GPU显存如何管理等，PipeSwitch都对应提出了Grouping 、统一内存管理等方案去解决。这里不再展开了。最终效果是PipeSwitch能够实现不超34.6ms的额外切换开销，远低于Nvidia MPS。

Serving DNNs like Clockwork: Performance Predictability from the Bottom Up
这篇工作提出了一种降低inference长尾效应的解决方案Clockwork。SOSP’19上也有一篇Parity Models工作解决类似的问题。

因为inference过程中各种资源竞争等问题导致软件执行时间未必是高度可控的，总会有一些inference请求无法被及时处理，于是latency就会出现统计意义上的长尾。Clockwork的思路比较直接 -- 如果预估某worker当时的状态无法满足一个请求的SLO，那就不让该worker执行该请求。整个架构图如下所示，会在host上布置一个controller接收所有的用户请求，同时controller当中的调度器会负责并根据worker的状态分发请求作业。

Ansor: Generating High-Performance Tensor Programs for Deep Learning
Ansor是来自伯克利和阿里的工作，一作Lianmin也是TVM的作者之一。Ansor聚焦在如何自动生成高性能的tensor program。思路如下：

- 首先需要一个充分大且全面的tensor program搜索空间。目前的一些解决方案要么需要依靠一些预先人为定义好的模版来做搜索（如TVM），要么用一些过于暴力的局部剪枝（如Halide），两者都很容易错过较优解。Ansor用一种分层的方式获得了更充分的搜索空间，包括用sketch方式提取high-level的程序结构信息，以及用annotation方式提取low-level的局部程序优化选项（并行、tiling等方式）。Ansor的这种采样方式能够获取到比TVM等方式更大的搜索空间。
- 有了足够大的搜索空间后，接下来需要从这个空间中找出满意的方案。由于可行解太多，Ansor使用了启发式的进化算法加速搜索过程。另外，由于在一种硬件上搜出来的方案不一定适合其他硬件，Ansor将搜索中用到的Cost Model设计成是可以被learnt的，即该方案具备不同硬件上的可移植性。
- 前两步主要针对如何生成高性能 tensor program。然而一个DNN graph里有较多sub-graph，如果对所有sub-graph去搜索的话开销太大。而另一方面，并不是所有sub-graph都对end-to-end性能有显著影响。针对该问题，Ansor设计了一个基于梯度下降的优化算法去找出其中对end-to-end影响较大的sub-graph，然后只对这些sub-graph做搜索优化。这样就能进一步降低复杂度。Ansor的整体工作流程如下，首先经过task scheduler选出值得优化的sub-graph（设计点3），然后经过program sampler进行搜索空间的准备（设计点1），接着进入performance tuner进行搜索和优化（设计点2），最后在真实硬件上运行并收集反馈信息。

以上设计也都是通用的，在Intel CPU / ARM CPU / Nvidia GPU上的评测显示Ansor相比于TRT / TVM等系统都有显著的性能提升。

A Tensor Compiler for Unified Machine Learning Prediction Serving
一篇来自微软的工作。之前介绍的工作基本围绕DL进行，这篇则是个例外 – 它关注的是传统机器学习算法与DL框架的结合。

我们知道基于Tensor抽象的DL框架已经有了相当多的编译优化工作，比如之前介绍的Ansor就是很好的例子。而对传统机器学习算法（例如决策树、随机森林等）的编译优化却比较少，尽管它们其实依然有大量的应用和经济价值。那么能否使传统ML算法也能复用目前DL框架的这些优化成果呢？只要将传统ML算法编译成基于Tensor的程序就行了。于是这篇工作就提出的HummingBird (HB)系统就应运而生。

文章主要介绍了多种编译设计及其对应的优化，例如如何将一个决策树模型变成一个GEMM (矩阵乘)运算等。目前HB已经能够对接PyTorch和TVM，支持上千种常见ML算法，其经转换后的Tensor程序性能也比转换成有相当明显的提升。

Rammer: Enabling Holistic Deep Learning Compiler Optimizations with rTasks
RAMMER是我很喜欢的一篇工作，可以说是将目前主流的两种编译手段（op间优化、op内优化）结合了起来，提出了一种更全面的方案，能够进一步发挥编译优化的潜力。

总所周知，目前的DL框架都会将DNN建模成一个Data-flow graph，其中每个节点称为一个op。现有的编译优化方式，一种是op间优化，例如两个互不依赖的op其实可以并行计算；另一种是op内优化，对每个op内部的矩阵乘等计算做优化，例如cuDNN。这两种方式共同的局限性，就是没有打破op之间的边界，因此失去了联合优化的机会。

（说到这里，感觉又是一个系统领域经典的“要分层还是要效率”的tradeoff问题）

RAMMER三点核心设计：

- 针对以上问题，RAMMER提出一种叫做rTask的计算抽象。DNN graph当中的op都能够用rTask描述，然后形成一个大的由rTask组成的graph再做计算调度。
- 对于计算调度，为了能跑在多种不同加速器上，RAMMER又提出了vEU概念（virtual Execution Unit），将加速器的计算能力分解为多个子vEU。每个vEU执行具体的rTask，那么宏观来看，包含多个vEU的每个加速器实际上就能同时执行来自不同op的rTask，成功地打破了op的边界。且这些设计思路对于不同硬件都是通用的。
- 由于rTask粒度比较细，在实际调度时，众多rTask可能会引入较大的调度开销，且调度算法越复杂则开销越大。RAMMER的解决方案是将调度决策直接在编译阶段就完成，避免runtime调度。这是因为其实DNN的计算图以及每个op的执行基本上都是很固定的，我们只需通过一些简单的profile就能够获取到性能数据，找到满意的调度决策后，直接将规则定下来再编译即可。总体来说，RAMMER提出的inter-op和intra-op协同优化的思路很赞；文章的writing也很好，让我这种没做过编译优化的人也能很快搞清楚RAMMER的核心贡献。最后在Nvidia GPU / AMD GPU / Graphcore芯片上的实验验证了RAMMER相对于XLA / TRT / TVM等主流系统的性能优势。
