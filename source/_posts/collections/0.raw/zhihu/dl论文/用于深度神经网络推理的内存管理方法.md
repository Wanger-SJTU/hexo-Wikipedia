近日在设计一个内存分配器，调研学习了一篇论文《Efficient Memory Management for Deep Neural Net Inference》（[https://arxiv.org/pdf/2001.03288.pdf](https://link.zhihu.com/?target=https%3A//arxiv.org/pdf/2001.03288.pdf)），整理个人学习笔记和感悟如下。

### Introduction

深度神经网络可以表示为一个有向无环图，图中包含若干个表示计算操作的节点（node）和中间计算结果的边（edge）。节点也叫做算子（operator），节点之间的中间计算结果也叫tensor，一个维度为[N,C,H,W]的tensor所占据的内存大小为```N x C x H x W x bytes_per_element``` 。一个有向无环图中的各个节点，可以根据网络结构和数据依赖关系，排布为一个算子执行序列，每个算子以上一个算子的中间计算结果作为输入，经过计算后将结果传递给下一个算子。因此，<strong>某一个中间计算结果不必永地久占据着内存，当需要它的算子完成计算后，这部分内存就可以被之后的tensor重复使用了</strong>。如果一个tensor还会被后续的算子使用（作为输入），那么称这个tensor是活跃的；反之，如果一个tensor后续不会再被使用了，则这个tensor是不活跃的（dead）。不活跃的tensor所占据的内存可以被后续tensor复用。

不论是移动端还是嵌入式设备，抑或是SoC，存储空间总是有限的，并且访问存储器的速度与其容量是呈负相关的关系。另一个问题是，<strong>某些网络中含有跳连接结构（残差块、inception block等），不同于别的tensor，在这些结构中，某些tensor会长时间保持活跃状态</strong>，将一直占据着内存空间。因此，设计一个高效的内存分配复用策略，将会优化深度神经网络在推理过程中的性能（内存占用、内存峰值等）。

![](/images/collections/0.raw/zhihu/dl%E8%AE%BA%E6%96%87/asset/img_eef560408093.jpg)

为此，论文《Efficient Memory Management for Deep Neural Net Inference》提出了几种策略。

#### 术语

![](/images/collections/0.raw/zhihu/dl%E8%AE%BA%E6%96%87/asset/img_24b1e1eb44ee.jpg)

#### Tensor Usage Interval

对于tensor t，其Tensor Usage Interval定义为```{`{first\_op_{t}, last\_op_{t}} }`` ，其中， first\_op_{t} 表示第一个使用tensor t的op索引， last\_op_{t} 表示最后一个使用tensor t的op索引。对整个神经网络的算子进行拓扑排序，表示算子执行的顺序，每个op都有一个单独的索引。如上图，op2输出的tensor的Tensor Usage Interval为{2,5}.

#### Tensor Usage Record

对于tensor t，Tensor Usage Record定义为```{` first\_op_{t}, last\_op_{t}, size_{t} `}```，其中，``` size_{t} `` 是tensor t在内存中占据的字节数。

#### Operator Profile

某个op的Operator Profile是一个Tensor Usage Record的集合，op的索引落在集合中的每个tensor的生命周期之中。

#### Operator Breadth

某个op的Operator Breadth定义为其Operator Profile包含的所有tensor的size之和。如上图，op3的Operator Breadth为```36+28+16=80```。 

#### i-th Positional Maximum

将每个op的Operator Profile按tensor size降序排列，排序序列中的第i个数即为i-th Positional Maximum。

### 策略1：共享对象（Shared Objects）

文章称第一种策略为*Shared Objects。*该方法会为每个tensor分配一个shared object，Tensor Usage Interval无交叉的两个或多个tensor可以共享同一个shared object。因此，单个shared object的size等于将其分配到的所有tensor的size中的最大值。这种策略的目标是尽可能使得所有shared object的总size最小。

#### 理论下限

![](/images/collections/0.raw/zhihu/dl%E8%AE%BA%E6%96%87/asset/img_c8772e3668e2.jpg)

将每个Operaetor Profile中的tensor根据tensor size降序排列，将得到一个排好序的Operator Profile序列。可以理解，最大的shared object的size将大于等于序列中的第一个元素；同理，第二大的shared object的大小，将不小于序列中的第二个size。

以上图为例，每个op的Operator Profile中的tensor降序排列，得到```{32},{32,28},{36,28}……```一堆序列。再在每个位置（Positional）上取最大值，最终得到```{64,40,16,8}``` 。所以，对该计算图，最少会分配4个shared object，这4个shared object的size分别不小于64、40、16、8。这也就是这种策略的最好情况。

文章采用贪心算法，提出了<strong>Greedy by Breadth</strong>和<strong>Greedy by Size</strong>两种算法：

#### Greedy by Breadth

![](/images/collections/0.raw/zhihu/dl%E8%AE%BA%E6%96%87/asset/img_61ae8e758a9d.jpg)

- 初始化：tensor usage records中的tensor都未分配到shared object（置为null）
- 排序：按照每个op的Operator Breadth以降序排列，得到一个op序列
- 遍历op序列
- 遍历当前op的Operator Profile中的tensor：

- 如果当前tensor已经分配了shared object，则遍历下一个tensor
- 否则，遍历已分配的shared object序列，如果存在某个shared object，其size不小于当前tensor的size，则将已存在的最小的shared object分配给当前tensor。如果没有合适的shared object，则创建一个新的shared object，分配给当前tensor，新的shared object的size即为当前tensor的size。

#### Greedy by Size

![](/images/collections/0.raw/zhihu/dl%E8%AE%BA%E6%96%87/asset/img_4ee9e30a8532.jpg)

另一种算法Greedy by Size思想与Greedy by Breadth类似，不同之处在于Greedy by Size将所有tensor降序排列，并遍历考察每个tensor。即，从大到小排序计算图中的所有tensor，先为size大的tensor分配空间。

两种算法的时间复杂度均为 O(kn^{2}) ，其中，k为tensor数量，n为计算中的算子的数量。

### 策略2：Offset Calculation Approach

文章提出的第二种策略称为Offset Calculation，主要思想是预分配一大块内存，生命周期有交叠的不同tensor共享这一块内存，并通过合理规划存放位置（offset），达到恰好最大程度利用这块内存的目的。试验表明，从分配的总的内存大小的角度而言，这种方法效果最优。

#### 理论下限

某个op的Operator Breadth定义为其Operator Profile包含的所有tensor的size之和，因此，当执行到某个op时，这个op对应的Operator Breadth里的所有tensor同时存在于内存中（且互不交叠）。这些tensor的size之和等于Operator Breadth。所有算子的Operator Breadth的最大值，就是Offset Calculation策略的下界。

同样，文章采用贪心思想，提出Greedy by Size和Greedy by Breadth两种算法

#### Greedy by Size for Offset Calculation

![](/images/collections/0.raw/zhihu/dl%E8%AE%BA%E6%96%87/asset/img_900fb6da25e2.jpg)

Greedy by Size for Offset Calculation的算法清晰明了：

- L1：首先，根据tensor size非增顺序排列所有tensor
- L6：遍历tensor序列，对当前tensor *t*，遍历已分配offset的tensor* x*：

- L11~L18：如果tensor *t*和tensor *x*的生命周期有交叠，则采用<strong>最佳适配法</strong>，找到<strong>使得分配后内存碎片最小</strong>的tensor *t*的offset
- L19~L20：否则，将*prev_offset*，即0，分配给当前tensor *t。*（很自然的，因为当前tensor和已分配的tensor生命周期均无交叠，意味着和其他tensor的内存位置不会踩，那么当前整个存储空间都可以使用，所以直接分配offset = prev_offset）

下图是使用该策略的示意图：

![](/images/collections/0.raw/zhihu/dl%E8%AE%BA%E6%96%87/asset/img_cb05df7a2c73.jpg)

右图横轴为memory buffer size，纵轴为tensor的活跃周期，即tensor usage interval。总的内存占用，即为0~8个算子中，其Operator Breadth的最大值，即为第5个算子，```64+36+16+8=124```。 

#### Greedy by Breadth for Offset Calculation

另一种算法与Greedy by Size for Offset Calculation的算法类似，不同之处在于，Greedy by Breadth初始化时，是按照op的Operator Breadth降序排列。

#### Experiment

文章对上述两种策略的几种算法在MobilenetV1，MobilenetV2，DeepLabV2，InceptionV3等网络上进行测试，结果如下：

![](/images/collections/0.raw/zhihu/dl%E8%AE%BA%E6%96%87/asset/img_6cd9fc9e0041.jpg)

可以看到，<strong>Greedy by Size for Offset Calculation性能最优</strong>，可以达到理论下届（除DeepLabV3）。在某些网络上，Shared Object策略性能更优；在某些网络上，Offset Calculation策略更优。

### 个人感悟

上述算法在tensorflow中都有具体的实现代码。文章中提到了上述几种策略和算法的适用环境，比如Offset Calculation策略适用于CPU或GPU内存分配，但对于GPU textures，则不适用，因为GPU textures需要考虑全局的内存占用情况。而贪心算法本身就是在局部空间中搜索最优解。Shared Object策略适用于GPU textures。

同时可以看到，Shared Object策略的分配结果是一堆shared objects集合。如果把这些shared objects放置在一个连续的内存空间中，则转化成了Offset Calculation策略。

不过，针对我目前碰到的问题和需求而言，仍需对上述算法（Greedy by Size for Offset Calculation）进行改造。文章提出的算法和示例中，所有算子排成一个队列，顺序执行，未考虑两个或多个算子并行执行的场景。如果两个算子Conv和MaxPooling可以同时执行，那么这两个算子的output tensor不能交叠。

此外，某些算子可能支持inplace操作，则不需为其output tensor重新分配空间。

另外一点，如果支持多个算子并行，那么有些不影响其他算子执行的算子（如搬运数据的算子），是否可以提前执行？如果可以， 那提前到什么时候执行可以达到更优的访存性能？
