做 PCIe 的人，迟早都会被几个地址绕进去。

刚开始看资料的时候，感觉名字都差不多：<strong>PCIe 地址、CPU 地址、DMA 地址</strong>。再往后看驱动、看 DTS、看 BAR、看 iATU，越看越乱。最让人头疼的是，它们不只是叫法不一样，很多时候连数值本身都不一样。

于是问题就来了：**明明像是在说同一块东西，地址怎么还能变来变去？

这个问题，几乎每个刚接触 PCIe 的人都会遇到。
而且一旦这里没想明白，后面看 BAR 映射、看 DMA、看地址转换，都会有一种“每个字都认识，连起来不知道在说什么”的感觉。

其实这件事没那么玄。
你只要先接受一个很重要的前提：

地址从来不是孤零零存在的，地址一定属于某个视角。**

也就是说，在问“这个地址是多少”之前，最好先问一句：

<strong>这个地址是谁在看，谁在用。</strong>

同一块资源，在 CPU 眼里，可以有一个地址；在 PCIe 总线眼里，可以有另一个地址；到了设备做 DMA 的时候，它手里拿着的，又可能是第三个地址。**它们说的可能是同一个地方，但因为站的角度不一样，所以地址不一定一样。

这个感觉，其实和现实生活很像。

同一栋楼，外卖员记的是门牌号，物业后台记的是楼栋编码，地图软件里又是另一套定位。
你说它们是不是在指同一个地方？大概率是。
但你说它们的编号一定一样吗？不一定。

PCIe 里的这几种地址，差不多也是这个意思。

![](/images/collections/0.raw/zhihu/%E4%BD%93%E7%B3%BB%E7%BB%93%E6%9E%84/asset/img_e63eba4cbe8f.jpg)

先从 CPU 地址说起。

所谓 CPU 地址，说白了，就是 CPU 自己发起访问时使用的地址。
CPU 去读内存、写内存，或者去访问某个映射进来的设备寄存器，用的都是它这边地址空间里的地址。
对 CPU 来说，它并不天然知道后面连着的是 DDR，还是 PCIe 设备的 BAR。它只是在访问一个自己“看得见”的地址。

比如，系统把某个 PCIe 设备的 BAR0 映射到了 CPU 地址空间里的 `0x40100000**`。**这时候如果 CPU 想去读这个 BAR 里的某个寄存器，比如 offset `0x40`，那它眼里看到的其实只是一个普通地址：

`0x40100040`

CPU 的想法非常朴素：
“我要访问 `0x40100040**` 这个地址。”

它并不会在心里默念：“我要去访问 PCIe 设备 BAR0 里的某个寄存器。”**那是我们人类在看系统结构图时的理解，不是 CPU 真正“看到”的东西。

但事情到了 PCIe 控制器那里，就不一样了。
RC 会把这次 CPU 发起的访问做一次地址转换，然后变成一笔 PCIe 总线事务，最后落到设备 BAR0 里的 offset `0x40` 上。

也就是说，同一件事，从 CPU 这边看，是在访问 `0x40100040**`；从设备这边看，是 BAR0 里偏移 `**0x40**` 的寄存器被访问了。

![](/images/collections/0.raw/zhihu/%E4%BD%93%E7%B3%BB%E7%BB%93%E6%9E%84/asset/img_8c13a84e2827.jpg)

这个地方特别容易让初学者犯迷糊。**因为大家很容易下意识觉得：既然访问的是同一个寄存器，那地址应该就是同一个。
但实际上不是。

这里更接近真实的说法应该是：

同一个寄存器，在不同视角下，可以有不同的地址表达方式。**

对 CPU 来说，它在 `0x40100040`。**对设备来说，它是 BAR0 里的 offset `0x40`。
这不是两个寄存器，而是同一个寄存器在两个不同坐标系里的位置。

![](/images/collections/0.raw/zhihu/%E4%BD%93%E7%B3%BB%E7%BB%93%E6%9E%84/asset/img_72996fea0abb.jpg)

到这里，其实 CPU 地址和 PCIe 地址的差别就已经出来了。

CPU 地址，是 CPU 发起访问时使用的地址。
PCIe 地址，则更像是 PCIe 总线世界里的地址，是事务真正到了总线层之后，PCIe 协议在使用的地址。

如果文章只讲到这里，很多读者通常还能跟上。
真正让人开始乱掉的，往往是 DMA。

因为前面的场景里，是 CPU 主动去访问设备。
而 DMA 这个场景里，发起访问的已经不是 CPU 了，而是设备自己**。

比如 NVMe 要把数据写进内存，网卡要把收到的数据搬到 DDR，或者一个 DMA 控制器要从内存里取一段数据，这时候设备都必须先拿到一个地址。**这个地址，就是它 DMA 时真正要使用的地址。

很多人刚开始都会冒出一个很自然的想法：

既然最终是要写到内存，那直接把 CPU 看到的那个内存地址告诉设备，不就行了吗？

有些很简单的平台上，看起来还真差不多。
但从概念上说，这种理解并不稳，因为设备和 CPU 看到的地址空间未必一样<strong>。</strong>中间可能有 IOMMU，可能有 RC 的入站地址转换，也可能有 SoC 自己内部的地址重映射。于是就会出现一种非常常见的情况：

同一块内存，CPU 看到的是一个地址，设备 DMA 时使用的却是另一个地址。

比如一块 DDR buffer，CPU 这边看它可能在 `0x30000000**`。**但设备做 DMA 的时候，真正该写出去的地址，可能是 `0x80000000**`。

你没看错，的确可能差很多。**但这不是出错了，而是因为它们本来就不是给同一个主体使用的地址。

![](/images/collections/0.raw/zhihu/%E4%BD%93%E7%B3%BB%E7%BB%93%E6%9E%84/asset/img_8248d51c58f5.jpg)

这时候，DMA 地址这个概念其实就很好理解了。

DMA 地址，不是“CPU 觉得好像可以用的一个地址”，而是设备真正拿去发 DMA 事务时使用的地址<strong>。</strong>所以在驱动里，才会有 `dma_alloc_coherent()`、`dma_map_single()`** 这一类接口。它们的意义，本质上就是帮你拿到一个“设备能用”的地址，而不是让你随手拿个 CPU 地址就塞给设备。

很多人第一次接触这块时，会觉得驱动代码特别别扭。**明明 buffer 是我申请的，为什么又冒出来一个 DMA 地址？
其实原因很简单：CPU 看到的地址，未必就是设备能直接使用的地址。**

![](/images/collections/0.raw/zhihu/%E4%BD%93%E7%B3%BB%E7%BB%93%E6%9E%84/asset/img_688073c4ad98.jpg)

讲到这里，可以停一下，回头看一眼前面这两个场景。**你会发现，很多时候我们不是被“地址太多”绕晕了，而是把两种完全不同的访问方向混在了一起。

一种是 CPU 主动去访问设备<strong>。</strong>另一种是 设备主动去访问内存**。

别看只是主语换了一下，背后的地址语义其实已经变了。

前一种场景里，CPU 是发起者，所以我们更关心 CPU 地址怎么通过 RC 转换成 PCIe 地址，最后落到设备 BAR 上。**后一种场景里，设备是发起者，所以我们更关心设备拿着 DMA 地址发起事务后，怎么经过总线和地址转换，最后落到 CPU 这边的内存地址上。

如果把这两个场景并排放在一起，其实就特别清楚了

![](/images/collections/0.raw/zhihu/%E4%BD%93%E7%B3%BB%E7%BB%93%E6%9E%84/asset/img_6016d33cb931.jpg)

这个时候，再回过头去记三个名字，就会轻松很多。

`CPU 地址，是 CPU 发起访问时用的。`

真正重要的，不是死记这三句话，而是理解它们背后的逻辑：
地址不是绝对的，地址一定依附于某个使用者。**

你甚至可以把这个逻辑记成一句更口语的话：

<strong>别只盯着地址值，要先看这个地址是给谁用的。</strong>

不过读到这里，很多人还会有一个自然的疑问：**既然你说这几个地址经常不一样，为什么我有时候又觉得它们差不多？

这个问题问得很好。
因为很多平台确实会把地址做得比较“平”。

比如没有 IOMMU，没有复杂的重映射，RC 也没有搞很多花哨的地址窗口，整个系统做得比较简单，这时候 CPU 地址、DMA 地址、PCIe 地址就可能看起来差不多，甚至接近 1:1。

这时候你会产生一种错觉：

“咦，DMA 地址不就是 CPU 地址吗？”
“PCIe 地址看起来也一样啊。”

这种现象不是在说明三者概念上相同，而只是说明这个平台刚好把不同视角下的地址做得比较接近。
一旦平台复杂起来，中间多几层转换，这几个地址很快就会分家。

![](/images/collections/0.raw/zhihu/%E4%BD%93%E7%B3%BB%E7%BB%93%E6%9E%84/asset/img_fd3f327099ff.jpg)

说到这里，其实很多原来看起来很玄的现象，就都能解释了。

为什么 CPU 能通过一个地址访问设备 BAR，但设备手册里写的却像是另一套地址？
因为 CPU 看到的是 CPU 地址，而设备文档描述的往往是设备或总线视角下的地址空间。

为什么驱动里打印出来的 DMA 地址，和你以为的物理地址对不上？
因为 DMA 地址本来就是给设备使用的地址，不保证和 CPU 视角下的一模一样。

为什么看 DTS 的 `ranges`、看 RC 的 iATU、看驱动里的 DMA 映射，总觉得每一层都像在讲不同的话？
因为它们确实就在描述不同阶段、不同视角下的地址关系。

很多时候，并不是谁写错了，也不是哪个寄存器在骗人。
而是你在不知不觉中，把不同坐标系里的地址拿来直接对比了。

这也是为什么，真正做 PCIe 调试时，一个特别有用的习惯就是：
每看到一个地址，先停一下，问自己一句：

这个地址是谁拿来用的？**

是 CPU 在访问？**是 RC 在做转换？
还是设备在发 DMA？

这个问题一旦问清楚，很多原本像一团毛线一样缠在一起的现象，立刻就会顺很多。

![](/images/collections/0.raw/zhihu/%E4%BD%93%E7%B3%BB%E7%BB%93%E6%9E%84/asset/img_6765a66335f9.jpg)

如果非要把这篇文章再压缩成一句话，那其实就是：

同一块资源，可以有不同的地址，因为不同的人，在不同的地址空间里看它。**

而如果再进一步压缩成一句最适合当结尾的话，我会更想写成这样：

<strong>别急着问这个地址是多少，先问这个地址属于谁。</strong>

因为 PCIe 里的很多概念，难不在“信息量大”，而在“不同视角经常被混着讲”。
一旦你把视角拆开，把“谁在访问、谁在发起、谁在看这个地址”这件事想明白，原本那些让人头大的 BAR、DMA、地址转换，都会一下子顺起来。

![](/images/collections/0.raw/zhihu/%E4%BD%93%E7%B3%BB%E7%BB%93%E6%9E%84/asset/img_182a5122f540.jpg)
