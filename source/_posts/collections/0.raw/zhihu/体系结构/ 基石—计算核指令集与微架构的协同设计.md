### 1. 引言：编程模型——软硬件协同的基石与灵魂

在 NPU 的设计哲学中，编程模型并非事后的软件适配层，而是驱动硬件架构设计的<strong>先导性约束</strong>。它定义了软件开发者与硬件之间的“交互协议”，直接决定了芯片的易用性、性能上限和生态价值。

现代 NPU 的计算核通常采用一种<strong>以图灵完备的通用控制核为主体，扩展多个专用计算单元</strong>的异构架构。这种设计面临的核心挑战是：<strong>如何在保持 CPU 编程范式易用性的同时，高效地集成并暴露张量、向量、搬移等专用模块的能力？</strong>

这需要从<strong>耦合边界设计</strong>出发，构建一个既能体现硬件性能潜力，又对开发者友好的编程抽象。

### 2. NPU芯片微架构现状简析

#### 2.1 华为昇腾：DaVinci（AI Core）微架构现状简析

![](/images/collections/0.raw/zhihu/%E4%BD%93%E7%B3%BB%E7%BB%93%E6%9E%84/asset/img_8446a8e629c4.jpg)

davince微架构简图达芬奇（DaVinci）AI Core 的组织方式可以概括为：三类基础计算资源 + 显式片上存储层级 + 多队列并行执行 + 显式同步原语。在计算资源上，AI Core 包含三种基本单元：矩阵计算的 Cube Unit、向量计算的 Vector Unit、以及承担控制与标量运算的 Scalar Unit。三者分别对应矩阵/向量/标量三类计算模式，在实际 kernel 执行中各司其职，形成相对独立的计算通路。

<strong>（1) 控制域与多队列：把并行执行“队列化”</strong>

从公开资料看，达芬奇采用“<strong>顺序程序 + 多队列并行执行</strong>”的领域专用架构：控制域负责顺序推进标量程序，并将不同类型的操作分发到对应的执行队列，例如 <strong>Cube Queue、Vector Queue、MTE Queue</strong> 等；队列内保持顺序语义，队列间允许并行推进。控制域常见构成包括系统控制、标量指令处理/调度队列（如 PSQ）、以及指令分发单元等。 

这种“队列化并行”的核心价值是：并行性主要来自 <strong>Cube/Vector/MTE 多个异步引擎并行工作</strong>，而不是把所有并行性强行塞进同一条超长指令字；同时也为硬件提供了更好的抖动容忍度，但它要求配套的同步机制把跨队列依赖刻画清楚。

<strong>（2) 显式片上存储层级与 MTE：数据供给闭环的核心</strong>

达芬奇 AI Core 强调显式片上存储层级：围绕 Cube/Vector 的数据复用，配置了多级片上 buffer（例如靠近矩阵计算的数据/累加缓冲，以及统一缓冲等），并通过 MTE（Memory Transfer Engine）承担主要的数据搬运与布局组织，使“搬移—计算—回写”能够形成流水闭环。公开资料中也明确指出其显式内存层级由 MTE 管理。 

从微架构协同角度看，MTE 的角色并不只是 memcpy：它更像“片上数据编排引擎”，负责把来自更高层存储（L2/DDR/HBM 等）的数据，以适合 Cube/Vector 消费的形态搬入片上 buffer。

<strong>（3) 指令体系定位：标量控制 RISC-like + 领域专用加速指令 + 显式同步</strong>

在 ISA/编程模型上，更严谨的表述是：达芬奇采用面向 AI Core 的<strong>领域专用指令体系</strong>。其中标量部分承担循环、分支、地址计算等控制逻辑，呈现更接近传统 RISC 的控制流风格；而矩阵/向量/搬移对应的是面向专用单元的操作指令，它们被分发到不同队列执行，并通过显式同步原语来建立跨队列依赖。 

在异步指令的同步管理上：使用 <strong>Set Flag / Wait Flag</strong> 这类“手工插入的二值信号量（binary semaphore）事件”来管理并发硬件单元之间的执行依赖——即由开发者/编译器显式插入 set/wait 来定义并行流水的逻辑边界。

#### 2.2 寒武纪 MLU：多流水线并行 + 显式同步的执行模型

![](/images/collections/0.raw/zhihu/%E4%BD%93%E7%B3%BB%E7%BB%93%E6%9E%84/asset/img_7fbfeac7544c.jpg)

mlu微架构简图寒武纪 MLU（Machine Learning Unit）采用的微架构设计可以概括为四类指令：<strong>标量指令</strong>、<strong>向量指令</strong>、<strong>张量指令</strong>与<strong>访存/搬移指令</strong>。其中，标量指令采用典型的 <strong>RISC 架构</strong>，主要负责控制流（如循环与分支）以及轻量级的特殊运算逻辑。向量指令用于执行向量计算，张量指令则用于卷积、矩阵运算等高并发计算任务。访存指令则主要负责数据搬移与传输，在不同存储资源间提供数据流向支持。

<strong>(1) 变长指令与多流水线并行</strong>

寒武纪 MLU 的关键特点之一是，<strong>向量、张量与访存指令的处理数据规模是可变的</strong>。这意味着每条指令的执行时延也会随着数据规模的变化而变化。如果将这些指令放入单流水线中执行，则长时延指令会阻塞后续指令的执行，导致系统吞吐量下降。因此，寒武纪采用了<strong>多条指令流水线并行执行</strong>的方式，以此来隐藏延迟。每一条流水线内的指令串行执行，而不同流水线的指令并行执行，并且在需要的地方通过同步原语显式管理指令间的依赖关系。

<strong>(2) MLU Core 的四条指令流水线：IO / Move / Compute / Scalar</strong>

MLU Core 内部包含四条并行的指令流水线：

- <strong>IO 流</strong>：执行所有涉及读写片外 DDR（如 GDRAM、LDRAM）的指令。
- <strong>Move 流</strong>：执行片上存储间的数据搬移指令（如 NRAM/WRAM/SRAM 之间的数据传输）。
- <strong>Compute 流</strong>：执行向量与张量计算指令。
- <strong>Scalar 流</strong>：执行所有标量指令（主要是控制流与标量算术计算）。
默认情况下，四条流水线是并行工作的。MLU Core 通过这种方式有效地实现了“计算隐藏 IO”的目标：通过合理调度访存与计算任务，减少同步点，最大化并行执行。

<strong>(3) 依赖管理：自动处理寄存器依赖，显式管理存储依赖</strong>

寒武纪在依赖管理方面作出了工程上的折衷：<strong>硬件默认自动维护 Scalar 流与其他流之间的寄存器依赖</strong>。具体来说：

-  当 IO、Move 或 Compute 流的指令写入标量寄存器时，<strong>Scalar 流中的读取指令必须等到写入完成后才能执行</strong>。
-  反之，当 Scalar 流写入寄存器时，其他流的读取指令必须等到 Scalar 流的写操作完成后才会开始执行。
这种机制通过硬件自动保证了寄存器级别的 <strong>RAW（Read-After-Write）</strong> 和 <strong>WAR（Write-After-Read）</strong> 依赖。然而，<strong>存储层级（如 NRAM/WRAM/SRAM 与 DDR/HBM）的数据依赖</strong>，以及<strong>指令间的数据生产与消费</strong>，则需要通过**显式同步原语（如 `sync_io`）来管理**。

<strong>(4) 显式同步：通过 sync_io 等屏障控制依赖</strong>

当指令间依赖涉及不同存储区域的读写时，硬件不会自动处理这种依赖。在这种情况下，用户或编译器需要通过插入同步屏障（例如 `sync_io`）来显式管理数据依赖，确保正确的数据顺序。例如，在一个流水中，如果 IO 流完成数据搬移后，Compute 流需要依赖该数据进行计算，**`sync_io` 会确保 Compute 流在 IO 流完成搬移后再开始执行**。

sync_io` 的语义可以定义为：

- <strong>同步的流</strong>：它作用于 IO 流、Move 流和 Compute 流之间的顺序控制，确保数据生产和消费按照正确的时序进行。
- <strong>作用范围</strong>：`sync_io` 会在不同流之间生成顺序约束，保证跨流的指令按照预期的依赖顺序执行，避免并行性过度切割。
- <strong>与 fence 的关系</strong>：`sync_io` 与 fence 类似，但更多聚焦于 <strong>数据可见性同步</strong>，而不是硬件内存屏障的低级操作。

#### 2.3 燧原：以 VLIW 为中心的微架构

与昇腾、寒武纪相比，燧原在公开材料中对其计算核内部微架构与 device-side 编程模型披露较少。就可获得的公开信息而言，明确提到其 DTU/GCU 计算核采用 <strong>VLIW cores</strong> 的组织方式，并在核心内部集成面向矩阵/向量的专用计算单元（例如 tensor ALU 等）以加速矩阵与向量运算。

![](/images/collections/0.raw/zhihu/%E4%BD%93%E7%B3%BB%E7%BB%93%E6%9E%84/asset/img_9c7e152e0fca.jpg)

燧原计算核微架构简图<strong>（1） VLIW 的设计哲学：把指令级并行从“硬件发现”转移到“编译期显式编排”</strong>

VLIW（Very Long Instruction Word）的核心思想是：处理器每个周期可以发射多个操作，但<strong>并行性不由硬件动态挖掘</strong>，而由编译器在编译期完成“指令打包、依赖消解、资源冲突规避”，硬件执行时按包内并行/包间顺序推进，从而用更低的控制复杂度换取更高的能效与面积效率。

可以把它概括为一句工程化的口号：

<strong>“硬件做得更瘦，时序表由软件写出来。”</strong><strong>（2） 在 NPU 上使用 VLIW 的优势：能效、确定性与“可榨干的热点内核”</strong>

VLIW 在 NPU 场景的优势通常体现在三点：

- <strong>控制逻辑更轻</strong>** 少做（甚至不做）复杂的乱序调度、寄存器重命名等硬件结构，把更多晶体管预算留给张量/向量算力与片上带宽，从而提高单位面积、单位功耗的有效吞吐。
- 性能更可预测（在边界清晰时）**** 当算子形状与内存访问模式相对稳定、热点 kernel 可被充分建模时，静态排程能形成非常“紧”的软件流水，峰值逼近能力强，且 tail latency 更容易控制。
- 对“专用算子库/固定工作负载”极友好**** 在算子集合相对确定、由厂商算子库提供高质量 micro-kernel 的情况下，用户不需要直接面对 VLIW 的复杂度，系统可以以较小硬件代价获得很强的算子级能效。
（3） 在 NPU 上使用 VLIW 的劣势：全栈不确定性会把复杂度“反弹”回 ISA/编译器/生态

但当问题从“单算子内核”扩展到“真实训练/推理全栈”，VLIW 的典型挑战也会出现，而且它们往往不是理论问题，而是产品工程中反复遇到的现实约束：

- <strong>对时延与资源细节高度敏感，排程表脆弱</strong>** VLIW 的静态排程强依赖“访存延迟、bank/端口冲突、流水线占用”等微结构假设。一旦内存系统出现抖动（bank 冲突、NoC 仲裁、DMA 抢占、片外带宽波动），即使硬件加入最小互锁来保证正确性，也会出现“bundle 空槽扩大、并行收益被吞噬”的现象：原本为了并行打包的多个操作会因为其中一个被阻塞而整体效率下降。
- ISA/编译器复杂度容易膨胀**** 为了对冲不确定性，系统往往会不断加入：预取、双缓冲、显式同步/事件、bank hint、特殊搬移语义、甚至任务队列等机制。结果是：VLIW 省掉的硬件复杂度，可能以“更复杂的 ISA + 更难的编译器 + 更难的性能稳定性”形式回流。
- 动态形状与控制流带来 kernel 变体与验证压力**** 当模型存在动态 shape（推理 batch/seq 波动、MoE 路由、ragged tensor 等），静态排程需要更多版本与特化策略（AOT 枚举或 JIT 特化）。这会扩大编译、缓存、回归验证与工具链复杂度，最终影响生态扩张效率。
- 跨引擎协同时更容易走向“全局排程难题”**** 现代 NPU 往往是张量核 + 向量核 + DMA/搬移 + layout/压缩等多引擎协作。若希望用静态方式把这些引擎全局编排到极致，排程问题很快变成资源约束极强的组合优化，工程维护与调试归因门槛显著提高。
（4） 小结：VLIW 不是“好或坏”，而是“把坡度放在哪里”

因此，对于燧原这类以 VLIW core 为中心的路线，更准确的评价是：

- <strong>当工作负载边界清晰、热点 kernel 可被充分建模且由高质量算子库承接时，VLIW 是极具竞争力的能效路线</strong>；
- <strong>当目标转向更强的动态性、更广的算子泛化、更低的开发/调试门槛时，系统工程会更倾向把一部分不确定性留给运行时与硬件（例如更强的动态调度/依赖管理），以换取更平缓的全栈爬坡路径。</strong>

### 3. 计算核PE硬件总体设计

结合国内主流 NPU 的设计取向，下面将逐步深入 NPU 计算核（PE）的微架构设计。本节重点给出整体设计视角，并明确各模块的基础目标。总体上，PE 可划分为控制面、数据面与同步面：控制面负责控制流与任务编排（循环/分支、地址生成、队列与事件管理），数据面负责张量/向量计算及数据搬运，同步面提供多流水并行的依赖与 barrier 机制。

<strong>在控制面选择上，我们采用 RISC-V 作为基座 ISA。</strong>一方面，RISC-V 具备成熟的工具链与生态（尤其是 LLVM 编译器体系），可显著降低编译、调试与工程落地成本；另一方面，其开放且可裁剪的指令集便于面向 NPU 需求添加轻量自定义扩展，从而构建稳定、可演进的控制平面。

<strong>在加速指令设计上，我们采用 CISC 形式的定制扩展。</strong>用更高层的tile级语义封装数据面常见的复合操作，以降低指令带宽与调度开销，并为软件栈提供更稳定的算子接口。

#### 3.2 异步计算域

（1）VectorCore（向量核心）

- <strong>功能定位</strong>：处理向量级并行计算
- <strong>典型工作负载</strong>：**

- 激活函数（ReLU、Sigmoid、GELU、SiLU等）
- 逐元素算术（Add、Mul、Sub、Div、Reip、Sqrt）
- 规约操作（Sum、Max、Min）
- 超越函数(Exp、Ln、Sin、Cos)
- 排序操作(Sort)

在当前AI负载中，尤其是随着Transformer架构的普及，向量计算（逐元素操作、规约、激活函数等）的比例显著增加。一个强大的VectorCore可以显著提升NPU在处理这类负载时的性能，并且增强其泛化能力，以支持更广泛的应用，是其追上GPGPU表现的关键之一。

如何设计一个用户友好、性能优越的Vector单元，将在本章后续章节详细描述。

（2）TensorCore（张量核心）

TensorCore是一个专门用于执行矩阵乘加（GEMM）和卷积（可转换为GEMM）的硬件模块。这个模块经过多年的时间，通常是脉动阵列或者外积展开阵列，已经形成了稳定的设计风格，本系列文章不对TensorCore进行过多赘述，其需要注意以下要点：

- Conv类算子的支持，TensorCore本身即可支持Conv的intrinsic
- 支持多种数据格式，能高效复用，具备较高的能效比
- 支持结构化的稀疏功能（重要性降低）
<strong>（3）DMACore（搬移核心）</strong>

<strong>DMACore = 数据平面的“第二个计算核”，把“搬运”从指令细节提升为“张量级事务”</strong>。在很多 NPU 里，算力不缺，缺的是“把正确的数据、以正确的布局、在正确的时刻送到 scratchpad/片上 buffer”。如果 DMACore 设计到位，张量核/向量核的利用率和性能稳定性都会上一个台阶，要考虑如下设计要点。

-  以 <strong>tile / tensor slice</strong> 为基本单位描述搬移（而不是字节流）
-  支持 <strong>多维 stride、布局变换、广播/填充、压缩/解压</strong> 等“数据准备”语义

#### 3.3 内存与通信域

在 PE 的设计中，片内内存域通常不是传统意义上的 Cache，而是一块（或多块）<strong>显式管理的 Scratchpad Memory（SPM）</strong>。它是 PE 数据平面的“主工作台”：

- <strong>DMACore</strong> 把外部数据以 tile/slice 的粒度搬入 SPM；
- <strong>TensorCore / VectorCore</strong> 绝大多数计算都以 SPM 作为输入输出驻留区；
-  计算完成后，DMACore 再将结果写回到更高层的片上/片外存储。
这种“DMA 主导的数据搬运 + SPM 驻留计算”的模式，核心价值在于：<strong>带宽可控、延迟可预测、能效更高</strong>，也更适合 NPU 的大吞吐工作负载。但它也把几个关键架构决策推到了台前。

在内存域之外，PE 必须与片上/片外系统交互。通常会把通信域显式分成两张网络（或至少两条逻辑平面）：

#### （1）Ctrl NoC：控制与管理平面（低带宽、控制语义）

Ctrl NoC 主要服务 <strong>RISC-V 控制核域</strong>与系统其他组件之间的交互，包括：

-  任务下发：kernel/command 的提交与 doorbell
-  寄存器/状态访问：配置 DMA、查询完成状态、读写性能计数器
-  中断与异常：fault 上报、超时、ECC 错误、访问越权
-  系统级控制：电源管理、时钟、reset、虚拟化/安全相关控制路径
Ctrl NoC 的特点是：<strong>带宽需求不高，但语义要可靠、顺序要可控、调试要友好</strong>。它更接近“SoC 管控总线”的逻辑。

#### （2）Data NoC：数据平面（高带宽、强 QoS，服务 DMA 与存储层次）

Data NoC 则是 <strong>DMACore 的生命线</strong>：负责把大吞吐的数据在 PE 与外部存储层次之间搬运，包括：

-  PE SPM ↔ 片上共享存储（常见是 L2 Scratchpad 或共享 SRAM）
-  片上共享存储 ↔ HBM/DDR 控制器
-  以及多 PE/多 cluster 的数据流动（如果做片上数据重用或广播/归并）
Data NoC 的设计通常更关注：

-  峰值带宽与可持续带宽（sustained BW）
-  仲裁与 QoS（避免某个 PE 或某类流量把别人饿死）
-  尾延迟与抖动（对 pipeline 稳定性很关键）
-  多播/广播能力（可选，常用于权重共享、集体通信的片上阶段）

### 4. AsyncInstDispatch：掌握异步指令流的“咽喉”

在 PE 的异构微架构中，CPU 域负责控制流与系统语义，异步计算域（Tensor/Vector/DMA 等）负责吞吐密集的数据面执行。两者之间的关键矛盾是：<strong>CPU 想用“顺序、可理解”的编程模型表达控制逻辑，而异步域必须用“并行、流水、可重叠”的方式榨干硬件。</strong>

AsyncInstDispatch正是解决这个矛盾的核心枢纽：

-  向上，它提供一种对软件友好的抽象，让 kernel 代码舒适地组织异步任务；
-  向下，它负责把这些任务分发到 DMA/Vector/Tensor 等不同引擎，并管理它们之间的<strong>依赖关系、资源冲突与完成事件</strong>；
-  更重要的是，它决定了整个 PE 是否能形成稳定的 <strong>异步流水线（pipeline）</strong>：计算与搬移能否重叠、数据依赖能否被正确表达。
在展开 AsyncInstDispatch 的具体微架构之前，我们先梳理几种常见的“异步指令控制/同步”的实现范式。第一种，也是最朴素且非常适合 SPM/DMA 主导数据流的方式，是 <strong>Tag 机制</strong>。

在展开 AsyncInstDispatch 的具体微架构之前，我们先梳理几种常见的“异步指令控制/同步”的实现范式。

#### 4.1 Tag 机制——用“内存片段状态”表达数据依赖

#### (1）核心思想：数据准备与数据消费之间的“契约”

Tag 机制把依赖关系绑定到内存片段（tile/buffer region）上：

-  内存域（scratchpad/L1 buffer，甚至可扩展到 L2 scratchpad）中，每个可管理的 buffer region 关联一个 tag；
-  tag 不是数据本身，而是这段内存的<strong>可用性状态</strong>：它告诉系统“这段数据是否已准备好可读 / 是否为空可写”。
这是一种非常数据流化的同步方式：它不关心“哪个指令先后”，而关心“哪个数据先后”。这与 NPU 的 tile/pipeline 编程模型天然契合。

#### (2）Tag 的对象模型：tag pool + tag 与内存类型/region 的绑定

一个可实现的组织方式是：在 PE 内提供一个 <strong>Tag Pool（tag 池）</strong>，由硬件/运行时统一管理 tag 资源。

- <strong>Tag 的归属</strong>：tag 逻辑上属于某种“内存类型”（比如 SPM 的某个 bank group，或某个 buffer class），也可以更细绑定到具体 region（base + size）。
- <strong>Tag 的粒度</strong>：通常以 tile 为粒度（例如一个双缓冲的 A/B 各自对应一个 tag），而不是任意字节范围。粒度越细并行度越高，但 tag 数量与管理开销也越大。
- <strong>Tag 的数量</strong>：tag 池大小是一个关键架构参数，它决定可同时在 flight 的异步事务数量上限（DMA/compute 的并行度窗口）。

#### (3）Tag 状态机：Full / Empty（可扩展）

最简状态机包括两态：

- <strong>EMPTY</strong>：该 region 可被写入（表示“这里还没有有效数据”或“已被消费完”）
- <strong>FULL</strong>：该 region 可被读取（表示“数据已准备好”）
这是经典的生产者-消费者（producer-consumer）模型，非常适合 DMA→Compute→DMA 的流水。

#### (4）Tag 指令语义：alloc / set / wait等

为了让软件能操控这套机制，ISA 或 runtime 需要提供最少一组 tag 原语指令。：

<strong>a) alloc_tag：分配 tag 并绑定 region</strong>

-  输入：内存类型 mem_type，region 描述（base、size 或 region_id），初始状态（可选）
-  输出：tag_id（可写入通用寄存器）
-  语义：从 tag pool 分配一个 tag，并把它与指定 region 绑定，初始化为 EMPTY（常见）或 FULL（少见）
-  异常：tag 池耗尽、region 非法、权限不足等
<strong>b) set_tag：显式更新状态（FULL/EMPTY）</strong>

-  输入：tag_id，目标状态（FULL 或 EMPTY）
-  语义：把 tag 状态切换到目标状态，并可选择触发事件（唤醒等待者）
-  用途：用于边界情况或“非 DMA/非 compute”的状态转换，比如软件填充、异常回滚等
<strong>c) wait_tag：等待某个状态成立</strong>

-  输入：tag_id，期望状态（FULL 或 EMPTY）
-  语义：阻塞当前CPU流水线，直到 tag 达到期望状态

#### (5）Tag 与异步指令绑定：让依赖“自动发生”

真正让 Tag 机制强大的，不是软件显式 wait，而是 <strong>异步指令本身可以携带 tag 依赖与 tag 更新规则</strong>，从而把常见的流水线模式变成“默认行为”。

可以把每条异步指令的提交参数扩展为：

- `wait_tags[]`：该指令启动前必须满足的 tag 条件

-  例如：DMA load 必须等待目标 region 的 tag 为 EMPTY（表示可以写）
-  Tensor compute 必须等待输入 region 的 tag 为 FULL（表示可读）

- `update_tags[]`：该指令完成时需要更新哪些 tag

-  例如：DMA load 完成后把目标 region tag 置为 FULL
-  Tensor compute 完成后把输入 tag 置为 EMPTY（表示已消费），把输出 tag 置为 FULL（表示已产出）

这样，就得到了一个非常自然的流水：

- `DMA_LOAD(dst=A, wait A==EMPTY, done set A=FULL)` 
- `TENSOR_GEMM(in=A, out=B, wait A==FULL & B==EMPTY, done set A=EMPTY, B=FULL)` 
- `DMA_STORE(src=B, wait B==FULL, done set B=EMPTY)` 
这套机制把“同步点”从显式 barrier 变成“数据就绪条件”，能显著减少 CPU 控制代码的复杂度，也降低了编译器静态排程的负担。

#### (6)   总结

Tag 机制乍看之下非常契合 NPU：它把同步边界绑定在数据（scratchpad 的 tile/buffer）上，天然适合“DMA 生产—计算消费—再写回”的流水线。但从编程模型的角度看，Tag 也意味着<strong>把一部分运行时依赖管理显式化</strong>，从而不可避免地增加了开发者的心智负担。

在一个典型的 NPU 编程中，用户（或编译器/算子库作者）本就需要承担两类困难任务：

- <strong>依赖序（调度序）的确定</strong>** 用户要明确每条指令/每个异步任务之间的前后依赖：哪些可以重叠，哪些必须等待；这本质上是在构造一个局部的执行 DAG。
- Scratchpad 上的 tensor 分配与生命周期管理**** 由于片内 scratchpad 是显式管理的，用户需要为每个 tensor（更准确是 tile）确定：起始地址、大小、驻留区间，以及复用时机。也就是说，用户不仅写“算什么”，还要写“数据放哪、何时可覆盖”。
如果我们承认：在以 scratchpad 为中心的数据面架构中，tensor 的地址与生命周期分配在很多场景下是程序员（或编译器）难以完全逃避的负担**——那么 Tag 机制带来的额外复杂度在于：它在 tensor 分配之外，引入了一套独立的、同样需要维护的同步抽象。

具体而言，Tag 让开发者需要在“tensor 层”之上再做三件事：

- <strong>为每个 buffer/region 额外分配与管理 tag 资源</strong>（tag 池、tag 生命周期、tag 与 region 的绑定关系）；
- <strong>显式描述依赖关系的实现方式</strong>：在何处 wait、何处 set，哪些异步指令携带哪些 wait/update tag；
- <strong>保证同步语义正确且可维护</strong>：避免漏等、避免早置 FULL/EMPTY、避免死锁，并能在性能分析时解释 stall 来源。
从结果上看，Tag 的确能把硬件做得更轻量，把依赖管理从“复杂的动态调度器”转移到“显式同步原语”。但这也意味着：原本在 CPU/GPU 等体系中由 <strong>scoreboard、硬件调度、运行时</strong>隐式承担的一部分工作，被搬到了编程模型层面，成为开发者或编译器必须显式维护的“额外维度”。

因此，Tag 机制虽然在数据流化 NPU 上非常自然，但它并非“免费午餐”：

-  它降低了硬件复杂度，提升了可控性；
-  同时也提高了编程抽象的显式性与心智成本。

#### 4.2 mbarrier 机制 —— 用“完成事件”表达执行依赖

mbarrier`（memory barrier object）是 Hopper 引入的<strong>基于完成事件的同步原语</strong>，用于表达“某些操作都完成后，才允许消费”的语义。相对于上一节提到的tag语义，是一种更优化的方式。

它不同于传统以线程到达为中心的 barrier（`__syncthreads()`），也不同于 tag 的“内存片段状态驱动”——mbarrier 直接绑定“未完成的操作集合（pending operations）”，并由计数器跟踪完成进度：当 `arrived_count == expected_count` 时，barrier 成立并翻入下一轮。重要特性包括：

- <strong>对象模型与可见范围</strong>：mbarrier 作为一个可计数同步对象存放于 shared memory / CTA 作用域内（同一 block/CTA 内的任意 warp/thread 可 init/arrive/wait，但不能跨 block）。
- <strong>状态机</strong>：典型为 `INIT → WAITING → SATISFIED → NEXT_PHASE`，天然支持循环流水（phase 自动切换），免去每轮重新分配同步对象的开销。
- <strong>基本指令语义</strong>：`init(bar, expected)` 设置期望计数；`arrive(bar)` 非阻塞递增到达计数；`wait(bar)` 阻塞直到满足；`test_wait` 可轮询；`arrive_drop` 支持动态参与者退出。
- <strong>硬件触发与异步协作</strong>：关键在于 `arrive` 可以由硬件异步单元触发（例如 TMA/DMA 在把 tile 写入 shared memory 后自动对对应 mbarrier 执行 arrive），从而把“数据可见性”语义由软件轮询转为事件驱动。相比仅保证“指令提交完成”的机制（如传统 wait_group），mbarrier 保证<strong>内存可读</strong>这一更强语义。
- <strong>编程与流水映射</strong>：mbarrier 便于表达生产—消费流水（例：`TMA load (auto arrive)` → `mbarrier.wait` → `TensorCore compute`），能实现 warp specialization 与深度流水而无需显式线程级同步。
与 Tag 机制对比的要点：

- <strong>同步依据</strong>：Tag 以内存 region 的状态（FULL/EMPTY）驱动；mbarrier 以“操作完成计数”驱动，更加灵活和细粒度。
- <strong>管理归属</strong>：Tag 通常需要软件分配 tag id、绑定 region 并维护生命周期；mbarrier 由软件初始化 expected count，但到达/完成由硬件与线程协同管理，减少了对 tag id 管理的负担。
- <strong>表达能力</strong>：mbarrier 内建计数与 phase 支持更细粒度的多源完成语义（多人/多 warp 协作），天然适合异步 DMA + 硬件到达的场景；Tag 在表达“数据就绪/可写”上更直观，便于显式数据流控制与资源复用。

#### 4.3 Notify机制——指令间依赖控制机制

Notify机制的核心思想是：把某条指令（或某个异步事务）的<strong>完成</strong>抽象为一个可传播的事件，当事件发生时即可唤醒后续依赖指令继续推进。基于事件的通知天然支持多种依赖拓扑——<strong>一对一</strong>（单生产者→单消费者）、<strong>一对多</strong>（单生产者→多个消费者广播唤醒）、以及<strong>多对一</strong>（多个生产者汇合后才释放消费者），因此非常适合表达 NPU 中常见的生产者-消费者流水与阶段性汇合点。

这种模式上节提到的的 CUDA 的 TMA/mbarrier里也广泛使用：TMA 搬移通过 `mbarrier` 的 <strong>arrive/expect_tx（登记与通知）</strong> 和 <strong>wait（等待与放行）</strong> 把搬移完成事件显式化，随后由线程侧在合适的时机继续发起下一阶段操作。其工程意义在于：以较低的硬件复杂度实现“指令级依赖管理”，并将其用于组织预取/搬移与计算的流水排布——先尽早提交未来的数据搬移，在真正消费数据前再等待对应事件，从而实现稳定的 pipeline 重叠。

<strong>Notify</strong> 可以被实现为一种轻量级“事件（event）”机制：用一个 <strong>notify_id</strong> 表示某个异步事务的完成信号，并允许其他指令以该 id 作为依赖条件，从而实现指令级的通知与等待。

#### (1) ID 与路由信息：静态指定 vs 动态分配

- <strong>静态指定</strong>：由编译器/算子库在编译期为某一段流水预先约定 notify_id，并确定其作用域（PE 内、cluster 内、全局）与路由（本地事件表/跨 PE NoC 广播等）。优点是实现简单、开销低；缺点是需要软件栈管理 ID 生命周期，规模变大时容易带来静态资源管理负担。
- <strong>动态分配</strong>：由运行时或硬件从 event pool 中分配 notify_id，并在任务结束后归还。优点是更灵活、适配动态 shape/动态并发；缺点是需要额外的分配/回收与可观测性支持，硬件/运行时复杂度更高。

#### (2) Notify 与异步指令绑定：把完成事件变成依赖条件

实现“指令级通知”的关键，是把 notify_id 作为异步指令的元数据绑定到指令上，形成类似下面两类字段：

- <strong>signal（发信号）</strong>：某条异步指令完成时，自动触发 `notify_id`（置位、计数递减或 phase 推进），作为对后续的“通知”。
- <strong>wait（等信号）</strong>：某条异步指令在发射前声明需要等待一个或多个 notify_id 满足条件（例如置位、计数归零、达到某个 phase），条件满足后才允许进入执行队列。
这样，Notify 就从“线程显式 wait”升级为一种更通用的依赖表达：<strong>生产者指令完成→自动 signal；消费者指令发射前→自动 wait</strong>。

#### (3) 跨核场景：一对多和多对一

Notify 的强价值还在于它对 <strong>一对多 / 多对一</strong> 的自然支持：这使得我们可以在多 PE 之间构建更强的同步与协作能力，例如跨 PE 的预取广播、跨 PE 的阶段性汇合、以及多核协同的流水推进。换句话说，Notify 不仅是单核内的依赖管理工具，也可能成为多核系统级同步的基础原语。

但与此同时，它也会引入新的系统工程问题，尤其是<strong>跨核语义与状态管理</strong>：

- <strong>是否需要跨 PE 的一致性语义？</strong>** 如果 notify 事件本身与数据可见性绑定（例如“搬移完成意味着某段数据可读”），那么在跨核场景下就需要明确：事件与数据在不同 PE 观察到的顺序关系是什么。这会牵涉到缓存/片上存储的可见性边界，甚至影响是否需要引入某种一致性机制或显式的 fence 规则。
 
- 如果不引入一致性，notify 往往趋向“静态化”**** 例如，编译时固定约定“大家都等 event_id=10”，这种静态 ID 的依赖表达虽然简单，但意味着：编译器/运行时必须承担 event/tag ID 的分配、回收与生命周期管理；并且在复杂程序里要保证不同阶段不冲突。这实际上把一部分依赖管理从硬件转移到了编译/软件栈，形成额外的工程负担。
因此，Notify 机制的设计并不只是“加一条通知指令”，而是要在吞吐、可扩展性、跨核语义、以及 ID/状态管理成本**之间做出平衡：把 notify 作为低层能力固然强大，但如果缺乏合理的抽象封装与自动化管理，它同样可能像 tag 一样，把新的心智负担叠加到开发者与编译器身上。

#### 4.4 基于地址的自动依赖管理：把“同步”从编程模型收回到硬件

在对比 Tag 与 Notify 两套机制之后，可以看到它们的共同代价在于：无论是显式的状态位（tag），还是显式的事件 ID（notify），最终都要求软件在“描述计算”之外，还要额外承担一部分“描述依赖”的工作。换句话说，依赖关系从硬件中被外显到了编程模型层面，增加了用户与编译器的心智负担和工程复杂度。

一个自然的反向思路是：<strong>能否像 CPU 一样，把依赖分析重新交回给硬件？</strong>** 在通用 CPU 中，load/store 指令即使看起来是顺序发射的，微架构仍然必须处理大量在途访存的冲突与重排。为此，CPU 通常引入 Load/Store Queue（LSQ）或相关结构：当一条 load 发出时，硬件会自动检查其地址是否与在途 store 冲突，必要时进行转发、等待或重排，从而保证在弱一致/乱序执行下仍然维持正确的内存语义。对软件而言，这些复杂性被硬件吸收，编程模型保持简洁。

沿着这一思路，我们可以把 NPU 的异步指令视作“更粗粒度的访存操作”：每条 DMA/计算指令本质上都在读取或写入某段片内 scratchpad的 tile 区域<strong>。如果我们把地址粒度从字节提升到 tile/region，那么完全可以构建一种</strong>tile 级 LSQ**：通过硬件做地址相关性检查（address dependency check），自动建立指令间的 RAW/WAR/WAW 依赖，从而实现无需显式 tag/notify 的依赖控制。

<strong>机制概要：Tile-LSQ + 地址检测驱动的动态发射：</strong>
#### （1）指令抽象：每条异步指令携带“访问集合”

为使地址检测可行，每条异步指令在进入调度队列时，需要携带其“访存足迹”（footprint），至少包含：

- <strong>访问类型</strong>：Read / Write
- <strong>目标地址域</strong>：L1、L2 scratchpad
- <strong>访问范围</strong>：`base + size` 
- <strong>可选信息</strong>：步长/多维切片的保守包围盒（bounding box），用于近似检测
这相当于把“我要访问哪些 tile”作为指令的显式元数据，而不是把“我要等谁”显式写出来。

#### （2）队列结构：为并发 in-flight 指令提供 FIFO/窗口

为了支持并行与重叠，需要为不同异步引擎建立并发窗口（window），典型结构是：

-  每类引擎一个 <strong>命令 FIFO</strong>（DMA FIFO、Tensor FIFO、Vector FIFO…）
-  或者统一入口队列 + 逐引擎分发队列（由 AsyncInstDispatch 做路由）
-  队列内部维护每条指令的 footprint 与状态（ready / blocked / issued / done）

#### （3）地址检测模块：像 LSQ 一样做冲突判定

当队列头部指令准备发射时，地址检测模块会检查它与“在途未完成指令”的 footprint 是否有交叠，并按依赖类型决定能否发射：

- <strong>RAW（Read After Write）</strong>：读依赖先前的写

-  若当前指令为 Read，且与某个 in-flight Write 区域交叠

- <strong>WAW（Write After Write）</strong>：写写冲突

-  若当前指令为 Write，且与某个 in-flight Write 区域交叠

- <strong>WAR（Write After Read）</strong>：写必须等先前的读完成

-  若当前指令为 Write，且与某个 in-flight Read 区域交叠

如果不存在交叠冲突（或仅与无关区域交叠），则指令可以直接发射到对应异步引擎执行。

<strong>这里的关键是：依赖关系由地址交叠自动推导</strong>，而不是由软件显式表达。软件只需保证地址/region 分配正确，依赖由硬件自然产生。
#### （4）完成回写：释放表项，唤醒后继

当某条指令执行完成，其 footprint 从“in-flight 表”中移除，相当于释放该 region 的读/写占用。地址检测模块随后重新评估被阻塞的队列头指令，必要时将其从 blocked 转为 ready 并发射，从而形成一种事件驱动的推进。

<strong>相对 Tag/Notify 的优势：更自然、更低心智负担</strong>

与 Tag 相比，这种方式的最大优势在于：

-  不需要额外引入 tag 资源及其生命周期管理
-  不需要显式书写 wait/set 来描述依赖
-  依赖由硬件按地址交叠自动建立，更符合“访存语义”的直觉
与 Notify 相比，它减少了 id 的分配、路由与跨核管理负担，避免把依赖关系静态固化在一组 ID 上。

#### （5）地址相关的缺点

这一套“tile 地址相关性检测”虽然更贴近 CPU/LSQ 的直觉，但它的代价是：<strong>依赖判定的精确性很难做到像 tag/notify 那样“按语义精确”</strong>，尤其遇到带 stride 的高维张量访问时，硬件往往只能保守近似，从而引入“多余屏障”。

#### 4.5 为什么选择地址相关的模式

在对比了 <strong>Tag、Mbarrier、Notify 与 Address 相关性检测等</strong>异步指令控制机制之后，如果我们要为 NPU 选择一套“作为核心控制逻辑的默认路径”，我倾向选择<strong>地址相关性检测</strong>。

#### （1) 为什么主体选择地址相关性：用户体验优先于极致机制完备

NPU 的成败很大程度上取决于软件生态与开发者体验，而异步编程的第一原则是：<strong>让正确性与依赖管理尽可能“默认成立”</strong>。** 地址相关性检测的优势在于它贴合开发者最自然的心智模型：开发者只需要描述“这条指令读/写哪块 buffer”，依赖关系由硬件自动推导（RAW/WAR/WAW）。这与 CPU 的 load/store 依赖管理类似，把复杂性留在微架构内部，对上层暴露一个更接近“顺序语义”的编程体验。

相比之下，Tag/Notify 更像是把依赖关系外显为额外的编程对象：你不仅要管理 tensor 的地址与生命周期，还要再管理 tag/event 的分配、绑定、等待与更新。即便这些复杂度后期可以通过 DSL/编译器部分吸收，现实中仍然会带来沉重的系统工程代价：

-  编译/运行时需要维护额外的资源与生命周期（tag/event pool、ID 管理、路由/作用域）
-  调试与性能归因需要理解更多隐式状态
-  跨代演进时，抽象边界更难保持稳定
换句话说：DSL 能“隐藏语法”，但很难完全消除背后的系统复杂度与维护成本**。因此，把 Tag/Notify 作为主路径会让整个栈长期背负更高的工程负担。

此外，Notify在多核中，具有其独特的优势，在后续的章节中，会在核间依赖的处理中，考虑引入类似的机制。

#### （2) 地址相关性的缺点更可控：双缓冲是天然的“结构化规避”

地址相关性检测的主要问题在于复杂 footprint（stride/permute 等）会迫使硬件采用保守近似，从而引入假相关、造成多余屏障。但在实际 NPU 编程中，一个非常重要的事实是：<strong>高性能实现天然倾向于 double buffer / ping-pong 的流水组织</strong>。也就是说，数据搬移与计算往往分别落在两个分离的 buffer region 上（A/B 交替使用），地址空间本身就是结构化分离的。

这使得地址相关性检测在主流路径里并不会频繁触发“误判冲突”，反而能以较低的硬件复杂度提供很好的默认体验和正确性保证。

#### （3) 用“可选显式提示”修补地址检测：让专家绕开假相关

为了进一步克服地址相关性在复杂访问模式下的保守性，我们可以提供一条可控的增强路径：允许用户或编译器在指令层面<strong>手动传递更精确的相关性信息</strong>，从而把“检测对象”从粗粒度范围缩小到地址子集（footprint subset）。

具体做法可以是：

-  指令携带 <strong>更精细的 footprint 描述</strong>（可以用户传递相关地址），让硬件用子集进行冲突判定；
-  提供显式的 <strong>依赖覆盖/声明</strong>：例如“本次访问只涉及某些 tile 子块”，避免被 bounding box 误伤；
这样形成一个分层策略：

- <strong>默认路径</strong>：地址相关性自动依赖（最好用、最少心智负担）
- <strong>增强路径</strong>：显式传递地址子集/提示，提升并行度与稳定性

### 5. VectorCore设计：决定 NPU 通用能力上限的关键模块

在现代大模型负载中，越来越多的时间花在“非 GEMM”部分：逐元素算子、规约、激活、归一化、softmax、topk 等等。它们往往算术强度不高、访存敏感、且形态多变。因此 VectorCore 的设计几乎决定了 NPU 的<strong>通用性上限</strong>，也是 NPU 在端到端性能上接近 GPU 的关键模块之一。

VectorCore 的设计目标不能只看峰值吞吐，更重要的是：在高负载多样性下仍能保持<strong>指令表达完备性、可组合性、性能可预测性</strong>。围绕这些目标，我们可以考虑三条路线。

#### 5.1 路线一：纯 SIMT 向量核（“小 GPU”式的通用向量计算域）

<strong>思路</strong>：VectorCore 本身具备类似 GPU 的 SIMT 执行语义（线程束/warp、谓词掩码、分支、共享寄存器/本地存储等）。CPU/运行时把一段向量 kernel 打成指令包或线程程序，投递给 VectorCore 执行。

<strong>优点</strong>

-  表达能力最强，几乎可以覆盖任意向量算法与控制流
-  对上层编译器/运行时更友好：接近 GPU 的编程心智
-  算子适配成本低，长尾算子更容易覆盖
<strong>代价</strong>

-  硬件开销最大：取指/译码/寄存器文件/分支与发散处理/调度等接近“再造一个小 GPU”
-  验证与扩展压力大：后续每一代扩展都会牵动大面积的通用控制逻辑
-  系统整合复杂：与张量核、DMA 的协同需要更复杂的调度与一致性边界设计
适用结论：如果你把 VectorCore 当成“第二计算主域”，并且愿意为通用性付出显著硬件代价，这条路线最直接。

#### 5.2 路线二：定制向量指令集 + 专用硬件模块（以性能与可控为中心）

<strong>思路</strong>：VectorCore 不追求完整 SIMT，而是提供一组面向向量数据流的 ISA / micro-op 集合：load/store、逐元素算术、规约、转置/重排、超越函数等；通过 mask 与 compare 提供有限控制能力。核心是用“足够完备的指令集合”覆盖主流向量算子，并尽可能在硬件上把热点做深做透。

<strong>必须强调的两点</strong>

- <strong>完备性</strong>：只做算术指令是不够的，必须具备完整的 compare + mask + select/merge 语义，否则你很难表达门控、mask fill、稀疏处理、topk 相关逻辑等常见模式。
- <strong>性能闭环</strong>：对大模型热点必须有专项优化路径，例如 softmax / layernorm 的关键子步骤（max-reduction、sum-reduction、exp、归一化）要能形成高效的数据通路（带宽、寄存器复用、流水深度）。
<strong>优点</strong>

-  硬件成本可控，能效更好
-  性能更可预测，易于针对热点算子做深度优化
-  与张量核/ DMA 的协同边界更清晰
<strong>缺点</strong>

-  长尾算子覆盖压力更大：指令集不够完备就会频繁 fallback
-  复杂向量算子往往是“多步流水”：add/mul/exp/reduce…如果缺少足够的调度能力，容易退化成串行执行，资源利用率不高
适用结论：多数 NPU 最终会落到这条路线，但它对指令集完备性与算子库质量要求极高。

#### 5.3 路线三：以 RISC-V / 微控制器为编排核心 + 向量微码/硬件单元（“可编排的数据流流水线”）

<strong>思路</strong>：引入一个轻量 RISC-V 核（或专用微控制器）作为 VectorCore 的控制面；具体向量运算由硬件实现的微码/子单元完成。微控制器负责发射微指令、安排流水、处理少量控制逻辑。微指令之间通过 <strong>tag/事件</strong> 进行依赖管理与流水编排。

这条路线的关键动机在于：<strong>纯硬件定制向量单元很难在多个功能单元之间做“深流水”的高效编排</strong>。举例来说，一个 softmax 的向量路径往往需要连续使用：load → max-reduce → exp → sum-reduce → normalize → store。** 如果缺少依赖分析/事件机制，最简单的实现只能“发一条等一条”，导致功能单元利用率不理想；而引入微控制器 + tag 后，依赖可以显式化，从而更容易组织成多级流水，形成vector chaining的效果：

注：这里使用softmax举例可能不够恰当，因为softmax本身的规约操作会阻断流水，但是沿head维度可以流水。

-  前一批数据在做 exp 的同时，下一批数据可以做 max-reduce
-  reduce 单元、exp 单元、mul/add 单元可以被更稳定地填满
-  在访存与计算之间形成更好的双缓冲/多缓冲节拍
优点

-  在不把 VectorCore 做成完整 SIMT 的情况下，获得更强的“编排能力”
-  通过微码/算子库升级，更容易适配新算子或对热点做版本迭代
-  更利于实现“跨功能单元流水”，提升单位硅面积的持续吞吐
-  可以通过细粒度的tag，实现更深层次的融合，比如元素级的融合。
<strong>代价</strong>

-  引入微控制器带来额外控制开销与验证面（但远小于完整 SIMT）
-  微码生态需要建设：工具链、调试、性能分析都要跟上
-  需要清晰定义 tag/event 的作用域与内存可见性边界
在 VectorCore 的微码/微内核层，引入 tag 并不会像“面向普通用户的 NPU 编程模型”那样带来不可接受的复杂度，原因有三：

- <strong>受众不同</strong>：微码/算子内核通常由厂商或深度开发者维护，属于专业化开发。对这类人群，显式依赖描述是可接受的工程手段。
- <strong>规模可控</strong>：微内核长度有限、模式高度结构化（例如固定的 softmax pipeline），tag 的管理范围小、可模板化，远比整图级别的 tag 管理简单。
- <strong>收益显著</strong>：tag 直接换来“跨单元流水可控性”和“资源利用率”，属于小成本换大收益，且对最终用户透明。
因此，可以把 tag 定位为：<strong>VectorCore 内部的专业级排布原语</strong>，而不是暴露给普通用户的通用同步机制。

<strong>综合来看，如果我们把“通用性逼近 GPU”视为目标，但又不愿意承担完整 SIMT 的硬件代价，那么路线三（微控制器 + 微码/子单元 + tag/事件编排）提供了一种折中：在保持硬件可控的同时，获得足够强的算子编排能力与持续吞吐；同时把 tag 的心智负担限制在“深度开发者/厂商算子库”范围内，对普通用户保持简单抽象。</strong>

### 6. DMACore 设计：从“搬移单元”到“性能上限”的决定者

在大模型负载下，NPU 的瓶颈越来越多地从“算力”迁移到“数据供给”。无论是张量核还是向量核，要持续接近峰值吞吐，前提都是 <strong>DMACore 能以可预测的节拍把数据喂到 scratchpad，并把结果稳定写回</strong>。因此，DMACore 不是一个简单的 memcpy 引擎，而是决定 NPU 端到端性能上限的核心模块之一。

从语义层看，DMACore 需要支持至少 4D 张量粒度的搬移与布局变换，覆盖从规则到不规则的主流模式，包括但不限于：

- <strong>memcpy / tiled copy</strong>：带 stride 的分块拷贝、2D/ND memcpy
- <strong>const filling</strong>：常量填充/初始化、mask fill
- <strong>transpose / permute</strong>：维度交换、layout 变换（例如 NHWC↔NCHW 的片内片外搬移）
- <strong>broadcast</strong>：按某些维度展开或重复加载
- <strong>gather / scatter</strong>：基于索引的非连续访存（大模型中重要性显著提升）
一个关键的架构抽象是：把复杂语义拆成若干“基础搬移原语”，并围绕这些原语构建可扩展的实现路径。下文提出两条路线。

#### 6.1 路线一：硬件语义解析 + 基础搬移原语（强硬件、强吞吐）

<strong>核心思想</strong>：DMACore 在硬件中内置语义解析与调度能力，把复杂操作拆解为少数基础搬移原语，并通过多通道流水执行。

#### (1) 语义拆解：以“四大基础原语”为主干

可以把高频搬移抽象为四类基础单元（可作为硬件管线或可重用的数据通路）：

- <strong>Memcpy（含 ND-stride copy）</strong>：`base + Σ(i_k * stride_k)` 的规则访问
- <strong>ConstFilling</strong>：生成常量流写入目标 region
- <strong>Transpose（含 layout transform）</strong>：在搬移过程中完成局部重排/转置
- <strong>Broadcast</strong>：以低成本复制/展开某些维度（避免上层重复搬运）
在此基础上，permute 可以视为 transpose 的一般化（或多个 transpose 组合）。

#### (2) Gather/Scatter：需要“索引流 + 数据流”的双流水

在大模型场景中，gather/scatter 的权重上升，使 DMACore 需要具备处理“不规则访存”的能力。在“强硬件路线”下，一个典型做法是：

-  在 DMACore 内部引入专用的 <strong>Index Fetch 子引擎</strong> + <strong>Index Buffer</strong>
-  通过 Ctrl/Config NoC 或 Data NoC，自动把索引矩阵（indices）搬入内部 buffer
-  Data fetch 引擎根据 index 计算偏移，发起数据搬运
这实际上要求 DMACore 内部支持两条并行流水：

- <strong>index 流水</strong>：indices 的预取、缓存、对齐、甚至压缩解码
- <strong>data 流水</strong>：按 index 发起多点读取/写入、合并访问、带宽仲裁
关键在于两者要“咬合”：index 供给与 data 访问必须形成稳定的 producer-consumer 节拍，否则会出现明显的 bubble。

<strong>优点</strong>

-  吞吐潜力高，能把 gather/scatter 这类不规则模式做得更接近硬件上限
-  运行时开销小，指令层更轻量（更多由硬件自动推进）
<strong>缺点</strong>

-  硬件复杂度与验证成本高，尤其是 gather/scatter 的异常处理与边界条件
-  语义一旦固化，扩展新模式（新 layout、新稀疏形式）会更“硬”，迭代成本高
-  如果设计不当，容易形成“强但死板”的搬移引擎

#### 6.2 路线二：微控制器+ 基础搬移原语（强灵活、强演进）

<strong>核心思想</strong>：把复杂语义拆解与调度更多交给 DMACore 内部的微控制器固件完成。硬件保持“少而强”的基础搬移原语，微控制器负责编排与流水化。

#### (1) 微控制器形态

-  使用精简的 <strong>微控制核(如RISCV)</strong>：去除或简化 cache/复杂流水
-  仅保留少量本地 SRAM 存放固件代码与关键状态
-  通过寄存器/命令队列驱动基础搬移单元

#### (2) 软件拆解与调度

微控制器固件负责：

-  将 memcpy/transpose/broadcast/permute 等复杂语义拆成基础原语序列
-  管理双缓冲/多缓冲，组织搬移与计算/写回的重叠
-  为不同 tensor 的 tile 生成地址、stride、边界处理
对于 gather/scatter：

-  index 读取可以由微控制器通过 NoC 主动发起（或驱动一个简单 index DMA）
-  由固件计算偏移并下发数据搬运任务
-  把“复杂异常与边界语义”更多留给固件处理，降低硬件验证压力
<strong>优点</strong>

-  灵活度高、扩展性强：新增模式更多是“升级固件/算子库”
-  硬件实现难度低，尤其适合早期产品快速迭代
-  更容易覆盖长尾模式（先保证能跑，再逐步热点硬化）
<strong>缺点</strong>

-  性能不一定足够强：固件111调度与地址生成可能成为瓶颈
-  DMACore 内部的流水排布质量取决于固件水平，可能难以长期稳定逼近峰值
-  并发压力：若需要多路 DMA 并行，单一微控制核可能不够，需要多核或更强的硬件队列/dispatch，导致面积与复杂度上升

#### 6.3 对比与结论：强硬件 vs 强固件的取舍

路线一是经典的“强大 DMACore”范式，吞吐潜力高，但硬件与验证代价显著，语义固化后扩展更困难。路线二更像“微码化的 DMACore”：以基础搬移单元为锚点，把复杂度上移到固件，优势是灵活与可演进，代价是性能上限与并发能力更依赖固件与控制面设计。

若目标是极致带宽利用与对 gather/scatter 的硬核加速，路线一更有上限；若目标是快速迭代、覆盖长尾语义并降低硬件风险，路线二更平滑，并可在热点成熟后逐步把关键路径硬化回路线一。

#### 6.4 DMACore 传参与语义描述：小问题背后的软硬件协同本质

随着 DMACore 能力增强，它需要表达更高维张量（至少 4D）与更复杂的搬移语义（stride、layout、permute、gather/scatter 等），因此“参数如何传递”逐渐成为不可回避的系统问题。而RISC-V 作为精简指令集，天然面临编码空间与单条指令可携带立即数/寄存器数目的限制。

一个经典的行业做法是引入 <strong>DMA 描述符（descriptor）/命令队列</strong>：CPU 通过写描述符把语义描述充分，DMACore 从队列中取 descriptor 执行。需要注意的是，这并不仅仅是“CPU 多写一块内存”这么简单，它会牵涉一整套 CPU↔DMACore 的协作机制：描述符队列的生产/消费协议、空闲查询、完成回写、还需要考虑中断/事件、异常上报、以及调试可观测性等。

从“用户体验优先”的角度，我们不希望把这种 descriptor/queue 协议作为<strong>用户可见的编程接口</strong>，原因在于：

- <strong>复杂度外溢</strong>：一旦用户需要理解队列、描述符格式等概念，编程心智会从“写一条搬移指令”跃迁到“写一个 描述符控制小系统”，考虑描述符的占用释放等等逻辑，代价高。
- <strong>硬件机制复杂</strong>：围绕 CPU、descriptor、DMACore 三者的完整正确协作，需要引入较多状态机与边界条件（并发、回收、异常、重放），验证与调试成本上升。
- <strong>可观测性与控制链变长</strong>：descriptor 作为中介会让“谁下发的、下发了什么、执行到了哪、为什么卡住”这些问题更难追踪，尤其在异常处理与精度/一致性调试时，控制面与数据面之间的关联更容易被稀释。
我们的目标是尽量在 ISA 层提供更直接、可组合的传参与控制方式，让“发指令—观察状态—处理异常”保持短链路、强可观测。因此，我们考虑如下的实现方式：

<strong>（1）栈上 DMA 描述符（memref 参数块，硬件自取）</strong>

<strong>把 DMA 的长参数封装为一个软件定义的描述符结构体（descriptor struct）</strong>，由软件在栈/线程本地内存中构造完成后，通过一条指令把“描述符地址指针”传给 DMACore；随后 DMACore 主动读取该结构体并执行搬移。用户视角接近：

- `DMA_LAUNCH desc_ptr`（或 `DMA_LAUNCH a0`，a0 指向 desc）
-  可选 `DMA_WAIT token / DMA_QUERY status` 
这条路线的优点在于：

- <strong>接口仍然短链路</strong>：用户不需要理解队列、doorbell、completion ring 等概念，仍像“发指令”一样下发一次搬移。
- <strong>承载能力强</strong>：结构体字段可扩展，天然适配 4D+、复杂 permute、gather/scatter、边界规则等“长参数”。
- <strong>版本演进友好</strong>：通过 `version/size` 字段即可做兼容；新增字段不必改 ISA 编码。
但它的关键难点集中在 <strong>CPU Cache 视角 vs DMA 视角</strong> 的一致性适配上，且比队列协议更“隐蔽”，更需要在体系结构层明确约束。

<strong>(a) Cache 一致性：descriptor 与间接数据的“可见性”</strong>

- <strong>问题 A：descriptor 本身</strong>** CPU 在栈上写 descriptor，若该 cacheline 尚未写回内存，DMACore 读取到的可能是旧值/脏值。
- 问题 B：descriptor 指向的间接表<strong>（如 gather index 表、segment 表）</strong> 即使 descriptor 已可见，间接数据仍可能不可见。
- 问题 C：数据缓冲区<strong>（src/dst 数据）</strong> 若系统非全一致（常见于 NPU），DMA 读写的数据与 CPU cache 的一致性也需要约定。
工程上必须回答：这套系统是 “HW 全一致” 还是 “SW 管理一致性”？

-  若 <strong>全一致（I/O coherent）</strong>：DMACore 的读写走 coherent 互连，硬件保证 cache 可见性与失效/回写；实现成本高，但用户体验最好。
-  若 <strong>非全一致</strong>：必须提供清晰的 <strong>cache 管理原语</strong> 与 <strong>内存属性</strong>：

-  descriptor 必须放在 <strong>non-cacheable / write-combining</strong> 区域，或在 launch 前显式 `CLEAN`；
-  DMA 目标数据区需遵循 `flush/invalidate` 规则或使用 SPM/uncached 映射；
-  用 <strong>fence</strong> 确保顺序：`write desc` → `cache clean` → `DMA_LAUNCH`。 

<strong>(b) 生命周期与安全：栈对象何时可回收？</strong>

descriptor 在栈上意味着它的生命周期受函数返回影响：

-  若软件发起 DMA 后立刻返回，栈帧被复用，DMACore 可能读到被覆盖的 descriptor。** 因此需要约束：
-  descriptor 必须位于 调用者保证存活** 的区域（例如线程本地持久缓冲、runtime pool），或
- `DMA_LAUNCH` 语义规定：<strong>硬件会在 launch 时把 descriptor 拷贝进内部 shadow</strong>（一次性抓取），之后不再回读。** 后者是更“用户体验优先”的做法，但要求 DMACore 具备“参数抓取+校验”的前端。
(c) 可观测性：指针传参容易让“下发内容”变成黑盒

相比 CSR/Bundle 的“指令级可追踪”，descriptor 方案需要额外机制避免调试变难：

-  DMACore 需要在状态寄存器/trace 中暴露：`desc_ptr`、抓取到的 `desc_hash/version/size`、关键字段摘要（维数、长度、地址、layout）
-  错误定位要能指到字段：例如 `ERR_STRIDE_INVALID`、`ERR_ADDR_ALIGN`、`ERR_PERMUTE_UNSUPPORTED`** 否则“为什么卡住/为什么错”会退化成内存排查。
（2）面向 RISC-V 的三类传参机制组合：编码细化 + CSR 上下文 + 指令集合

为了在不引入用户可见 descriptor 的前提下承载复杂 DMA 语义，我们可以采用三种机制的组合，它们分别解决“语义分发”“上下文复用”“单指令携带能力不足”三个问题。

<strong>（a) 细化指令编码：按语义族拆分 opcode（把“类型”放进编码）</strong>

把 DMACore 的高频语义拆成若干指令族，让 opcode 本身承载“这是哪类搬移”：

- `DMA_MEMCPY`（含 ND-stride copy）
- `DMA_FILL`（const filling）
- `DMA_TRANSPOSE` / `DMA_PERMUTE` 
- `DMA_BROADCAST` 
-  （可选）`DMA_GATHER` / `DMA_SCATTER` 
优点是：解码直接、编程直观、硬件路由清晰；缺点是：指令族变多，需要好的抽象边界与版本兼容策略。

<strong>（b) CSR 寄存器：把“变化慢”的参数放到可复用上下文里</strong>

把跨多条搬移指令可复用、变化频率低的参数放进一组 <strong>DMA CSR 上下文寄存器</strong>（也可以是 memory-mapped 寄存器或专用 config port），例如：

-  tensor layout 描述（维数、stride、element size、swizzle）
-  目标/源地址基址（base）、地址空间选择（SPM/L2/HBM）
-  tile shape、对齐策略、边界处理策略
-  gather/scatter 的 index 基址/格式（如压缩、位宽）等
这样做的关键收益是：<strong>把“长参数”从每条指令里挪出去</strong>，并允许在一个 kernel 内复用同一套配置；指令只需携带“本次启动的局部变化”（比如偏移、tile id、count）。

<strong>（c) 指令集合（Instruction Bundle / 多条连续指令描述一次事务）</strong>

当某些语义确实需要携带较多一次性参数（例如复杂 permute、gather 的多段 segment、或多维边界规则），可以采用“指令集合”的方式：用多条连续指令构成一个事务描述，最后用一条 `DMA_COMMIT`/`DMA_LAUNCH` 提交。

这种方式的优点是<strong>可扩展性强</strong>（新增参数不必改动单条指令格式），并且依然保持“指令级可观测性”；缺点是需要硬件/dispatch 支持“原子打包与解析”，以及一定的错误处理（参数不完整、bundle 中断等）。

DMACore 的传参设计看似琐碎，实则是软硬件协同的缩影，非常体现架构设计思路：它决定了<strong>复杂语义如何被表达、如何被观测、以及如何被调试</strong>。在用户体验优先的前提下，我们更倾向于通过 <strong>opcode 细化 + CSR 上下文复用 + 指令集合扩展</strong>来承载复杂搬移语义，而不是使用descriptor 这类重协议。

### 7. L1 Buffer：面向用户体验的 Scratchpad 设计原则

在 NPU 的 PE 设计中，L1 层级的片上存储（Scratchpad / Local Buffer）是最基础、也是最关键的共享资源：它承载了 DMACore 的数据搬运落点，同时也是 VectorCore 与 TensorCore 读写数据的主要载体。L1 设计的好坏，直接决定两件事： 1）上层编程与编译的心智负担；2）端到端吞吐是否稳定。

从用户体验出发，L1 Scratchpad 的设计必须直面两个现实：

- <strong>bank 冲突几乎不可避免</strong>，它是多 bank SRAM 架构的基本代价；
- <strong>过多的 memory 域/Buffer 形态会增加用户心智负担</strong>，尤其当用户需要在不同 buffer 之间搬运、切换或推理其可见性语义时。
因此，L1 的第一原则仍然是：<strong>尽量减少“用户需要理解的内存域数量”，并让默认访问模式尽可能不容易踩到 bank 冲突。</strong>

#### 7.1 Bank 组织：弱化显性感知，同时保留可控性

为了降低用户对 bank 冲突的显式感知，同时在极端场景下仍保留可控性，我们采用“<strong>低位交织为主 + 高位交织可控</strong>”的 bank 组织策略：

<strong>低位交织作为默认策略</strong>** 让连续地址的访问自然分散到不同 bank（按 word/cacheline 粒度交织），在最常见的顺序/连续访存模式下显著降低冲突概率，使性能更接近“默认正确”：用户不需要首先理解 bank 才能获得可接受的吞吐。

高位交织/可调映射作为高级能力**** 在张量核块访问、向量规约、DMA 多通道写入等高并发模式下，低位交织仍可能出现结构性热点。此时引入高位参与 bank 映射（例如  bank group 选择），给专家用户/编译器留下可操作空间：通过调整 tile 起始地址、对齐、布局，让热点请求分布到不同 bank，降低系统性冲突。

更强的“冲突容忍度”来自硬件相关性控制的动态发射能力**** 需要强调的是，我们对指令间相关性采用硬件管理，这使得系统具备更强的动态性。

特定stride下的优化策略

低位交织的特点会让访存在某个固定的stride下，会触发bank冲突，导致性能劣化。需要设计特定的低位交织的优化方案规避该问题。

#### 7.2 张量核专用缓冲：显式分域以换取带宽与确定性

虽然减少内存域有利于用户体验，但从硬件实现出发，TensorCore 对片上存储的带宽与端口需求远高于其它模块：其访问高度密集、模式规则且吞吐敏感。若张量核与 DMA/向量核共享同一组 bank/端口，很容易形成严重争用，导致吞吐波动甚至系统性退化。

因此，我们采取更务实的设计：<strong>为张量核引入专用的本地缓冲（Tensor Local Buffer / Accumulator Buffer）作为独立的存储域</strong>。这块缓冲用于承载张量核的中间结果、累加、局部重排等高频读写路径，使张量核的“热数据通路”与通用 L1 scratchpad 在物理上隔离，从而获得更稳定的带宽与更可预测的执行节拍。

需要明确的是：这里并不强行维持“软件视角仍只有一个统一 L1”的抽象。相反，<strong>张量核专用缓冲是可被软件显式操作的资源</strong>：

-  用户/编译器需要在合适的时机显式触发搬运（例如通过 DMACore 或专用指令）把张量核缓冲中的数据写回到 L1 主 scratchpad，或从 L1 主 scratchpad 预取到张量核缓冲；
-  这样做虽然增加了一个可见内存域，但换来的是张量核路径带宽的确定性与系统吞吐的稳定性，整体上是更可控、更工程化的取舍。
最终效果是：

-  在硬件侧：张量核热路径与通用 L1 分域，显著降低 bank/端口争用；
-  在软件侧：用户确实需要理解“张量核本地缓冲”的存在，并显式控制数据在该缓冲与 L1 主 scratchpad 之间的搬运，但内存域数量仍然被控制在最少（通用 L1 + 张量核本地缓冲），避免无谓的碎片化；
-  在系统层：依靠硬件相关性控制与动态发射，使对微小 bank 冲突更不敏感，整体吞吐更平滑。

### 8. 总结

本文以一个 NPU PE（Processing Element）的计算单元为对象，从“指令集选择—异步指令控制—微架构模块划分”三个层次，给出了一个面向落地的协同设计框架。贯穿全文的核心原则是：<strong>以用户体验为第一目标，在性能、易用性与工程可实现性之间取得可持续的平衡</strong>。

在指令集与执行模型上，我们明确选择了“<strong>硬件动态调度优先</strong>”的路线：在单个PE核对应的编程模型中，相较于将复杂度完全转移给编译器的静态排程（如极端 VLIW），以及显示的同步管理，我们更倾向于由硬件/运行时承担必要的依赖管理与异步推进能力，使得系统能够更好地应对现代 AI 负载中的不确定性与动态性，同时降低上层开发与调试成本。

在微架构层面，我们将 PE 拆分为清晰的控制域与异步计算域，并围绕张量核、向量核与 DMACore 等关键模块讨论了设计要点。整体设计风格是：<strong>尽量保持指令集与抽象边界简洁</strong>，把复杂度放在更易工程化的位置，从而为后续的编译器、运行时与算子库生态留出稳定的演进空间。

当然，本文主要聚焦于 PE 内核层面的“基石设计”，并且讨论了一些设计问题，仍有大量细节尚未展开。比如，如果使用Notify的方式，Notify是异步指令之间交互，还是异步指令与控制cpu之间交互？到底要实现哪种的fence、sync等同步语义去适配地址相关的调度模型？张量核、向量核、搬移核的计算访存比例？比如DMACore、TensorCore对Mask的需求讨论？

本节虽然在说微架构和编程模型，但从来没给出具体的intrinsic的表述，也没给出具体的编程模型示例（实则是我们的完整编程模型的层次是更高更大的，无法在一个单一计算核中表达编程模型），这些将作为下一篇 SoC 章节的重点，也会给出更多的示例，以更完整的系统视角下进一步补齐与论证。
