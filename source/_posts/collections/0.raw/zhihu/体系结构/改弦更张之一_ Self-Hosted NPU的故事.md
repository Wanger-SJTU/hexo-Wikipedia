有一句话，体系结构圈里的人都爱说，叫复杂度守恒。

这句话当然是对的。复杂度不会凭空消失，它只会从一个地方搬到另一个地方，从硬件搬到软件，从编译器搬到 runtime，从架构师的图纸搬到工程师的深夜DTS单里。你今天省掉的一个状态机，明天可能就会变成三层 runtime 的补丁；你今天砍掉的一条L1 buffer到GM路径，明天可能就会变成一堆晦涩的 kernel launch、event synchronization 和 profiler 里看不懂的空洞。

所以过去很多人接受了一个看似自然的分工：device 只负责计算，host 负责那些复杂的事情。进程管理、虚拟化、页表、内存拷贝、任务提交、异常处理、runtime 调度，都放在 host 上；device 则保持纯粹，像一个只负责干活的计算车间。这个分工听起来很优雅，因为它似乎把复杂度隔离了，host 管世界，device 管算力，大家各司其职，井水不犯河水。

但我恰恰想从这里开始反过来问一句：**如果复杂度真的守恒，那么 host-device 这种分裂，究竟是在管理复杂度，还是在制造另一种更昂贵的复杂度？**

![](https://pic1.zhimg.com/v2-4b4f771f8a8b256e19eabe858236a524_r.jpg)这就是 Self-Hosted NPU 这个故事的起点。

今天 GPU 对 AI 的胜利，在很大程度上是 NVIDIA 的胜利，是 CUDA、library、compiler、runtime、profiler、通信库、调优经验和工程生态的胜利，而不应该被简单理解成 GPU 历史模型本身的胜利。GPU 身上有很多东西，本来并不是为大语言模型、Agent、MoE、长上下文和动态推理设计的，它们是从图形时代一路带过来的老行李，比如 kernel 化的执行模型，host-device 的系统分裂，大量 thread 和 warp 的组织方式，warp scheduling，path divergence，以及 kernel launch、kernel switch、synchronization 带来的各种边界成本。

这些东西今天没有压垮 AI，不是因为它们天然适合 AI，而是因为 NVIDIA 花了二十年时间，把这些历史包袱一层一层包成了可用的工程体系。用户今天感受到的是 CUDA 好用、库成熟、工具完整、生态顺手，但这并不等于底层抽象就是最自然的；就像一座老城可以通过高架桥、地铁、环线和智能红绿灯继续高效运转，但这不代表它最初的街巷布局就是现代交通的理想答案。

所以我并不是反 GPU，也不是要轻飘飘地说 CUDA 不好。恰恰相反，只有足够尊重 CUDA，才会明白它真正强在哪里；也只有足够理解 GPU 的成功，才会看清它的历史边界在哪里。

这里还有一个常见误解需要拆掉。很多人会说 GPU 依赖 host，是因为 GPU 不是图灵完备的。这个说法严格讲并不稳，因为现代 GPU 当然能写复杂程序，CUDA kernel 里可以有循环、分支、函数调用，也可以做 persistent kernel，甚至可以在 device 侧维护队列和做一部分调度。

真正的问题不是 GPU 能不能表达复杂计算，而是它通常不是系统里的 root of control。它不拥有完整的服务生命周期，不负责外部 I/O，不自然承担进程、地址空间、异常、保护、调试和长期运行 runtime 的全部语义。它更像一个超级强壮的执行者，而不是一台自己当家的计算机。

如果今天从零开始，只为 AI 设计一台机器，我们还会不会主动发明出 host-device这种编程模型？我们还会不会天然地把程序切成一个个 kernel，让 host 不断发令、device 不断执行？我们还会不会把进程、状态、调度、页表、虚拟化、异常、KV cache 账本这些东西都放在另一台 CPU 上，然后让最贵、最快、带宽最高的 AI 芯片，每生成一个 token 都像学生举手一样问一句，老师，我下一步可以算什么？

大多数情况下，我的答案是否定的。

因为大语言模型推理已经不再是一个单纯的矩阵乘问题。它当然需要矩阵乘，需要 CUBE，需要 Tensor Core，需要 HBM，需要大带宽和大算力，但它同时也需要状态，需要调度，需要内存管理，需要上下文生命周期，需要 KV cache 的分配、共享、迁移和释放，需要 sampling、grammar、tool call、speculative decoding 的接受和回滚。换句话说，它需要一台计算机，而不只是一个被 host 喂任务的计算器。

过去我们总觉得 device 越纯粹越好，最好只算数，其他复杂东西都丢给 host。可到了 LLM serving 这个场景，纯粹有时候反而变成了一种幼稚。device 只算数，意味着它不知道这个数属于哪个 request，不知道这段 KV cache 对应哪个上下文，不知道当前 token 是否已经触发停止条件，不知道下一段 DMA 应该预取哪里，不知道这个 expert 是否在本地，不知道这个 batch 下一轮该怎么变。它拥有肌肉，却没有神经；拥有仓库，却没有账本；拥有引擎，却没有方向盘。

所谓 self-hosted NPU，难道就是在 NPU 里面塞几颗 CPU 吗？
这个问题问得很关键。

从最直观的实现上看，确实可以这么做。以昇腾 Ascend 950 这一类设计思路来看，芯片里放几颗 CPU，并不是一件奇怪的事情。这些 CPU 可以运行操作系统，可以承载复杂 runtime，可以处理非规则任务，也可以对互联、网络、拓扑、容错、虚拟化做更灵活的编排。换句话说，它们不是来抢 CUBE 的活，也不是来跟矩阵乘阵列比谁更会做乘法，而是来承担那些过去必须交给 host 的系统性工作。

![](https://pica.zhimg.com/v2-2afbe9c6cd0b549659d83f30e10b4fee_r.jpg)Image Generated By GPT Image2 不代表芯片结构然而最近，pyPTO的出现，就是像让runtime跑在这个CPU上，对NPU进行MPMD的调度。这种感觉，就更像让整个芯片变成了一个完整的CPU。

但这里有一个非常微妙、也非常尴尬的地方。

在一颗 AI 芯片里，每一平方毫米面积都是钱，每一瓦功耗都要算账。你多放一颗 CPU，就意味着少放一点 SRAM、少放一点向量通路、少放一点矩阵乘资源，或者至少意味着控制面要从原本属于纯算力的预算里切一块出来。于是很多人第一反应会是，这是不是不划算？我买 AI 芯片，是来买乘法器的，不是来买 CPU 的；我想要的是 CUBE 更大、带宽更宽、算力更猛，而不是在芯片里面养几颗看起来不直接产出 TOPS 的标量核。

这个直觉很自然，但它未必对。

因为真正的问题不是 CPU 贵不贵，而是如果你不在芯片本地提供这套控制能力，那么你就不得不在芯片外面，用更复杂的软件栈、更重的 host 参与、更别扭的 runtime、更频繁的 kernel launch、更难调试的异步队列，把同样的复杂度重新发明一遍。

复杂度不会因为你不放 CPU 就消失。它只是换了件衣服，躲进了 driver、runtime、graph capture、kernel fusion、stream event、host scheduler、KV metadata manager 和一堆 profiler 里看不懂的空白间隙。

所以，真正贵的不是像 CPU。

真正贵的，是为了**绕开 CPU，最后重新发明一套更难用、更难编译、更难调试、更难维护的东西**。

让NPU变成CPU？值得么
很多人会有一种直觉：

CPU 太复杂、太通用，所以一定不适合做极致高效 AI；

于是，AI 芯片应该尽量摆脱 CPU 风格，变成更纯粹、更专用的东西。

我恰恰觉得，这种直觉经常会把账算反。

CPU 确实复杂，但 CPU 的复杂，是一种**被整个行业消化过很多年的复杂**。硬件工程师知道怎么设计 CPU 风格的执行单元、缓存、异常、中断、地址翻译、内存保护；软件工程师知道怎么给这种机器写编译器、运行时、库、操作系统接口。

换句话说，CPU 不是最简单的东西，但它是**最被人类整体知识体系理解透彻的复杂东西之一**。

如果我偏离这个方向，去发明一套“更 AI 化”的 LPU Systolic执行模型，那么我并没有真正消灭复杂度，我只是把复杂度从“已经被行业掌握的复杂度”，换成了“需要我自己重新承担的软件和硬件复杂度”。

进程、状态、调度、页表、异常、虚拟化、内存保护这些 CPU 世界里已经被行业理解了几十年的概念，不能继续和大算力、大带宽、大 SRAM、大 HBM 分离。标量、向量、矩阵不应该住在三个世界里；控制、数据、内存、调度不应该靠远程请示维持秩序；一颗面向 AI 推理的芯片，如果永远只能等待 host 喂 kernel，那它再强，也只是一个昂贵的外设。

Host CPU 到底在忙什么
很多人低估 host CPU，是因为他们把 host 的工作想象成 launch 一下 kernel。

这个理解太轻了。

![](https://pic1.zhimg.com/v2-3d1e327fb3a111c8d7c7b9737e815420_r.jpg)在今天的 LLM serving 里，host 不是站在门口按一下开关的人，它更像一个过劳的总管家：它要把 kernel、memcpy、event 放进 stream，要处理 ACL Graph 的 capture、instantiate、update 和 replay，要等 device 返回，要推进 request 状态，要处理 completion event，还要在各种 callback、queue、runtime 状态之间来回穿梭。

单个 kernel launch 的开销也许只有微秒级，看上去像桌面上的一粒灰，不值得大惊小怪；但 decode 阶段最可怕的地方，恰恰是它有大量短小、动态、频繁的操作。这些微小缝隙单独看都不大，叠在一起，就会变成 P99 延迟里很难看的空洞。

系统性能里最阴险的东西，往往不是那个巨大的慢，而是一堆看起来无害的小等。

Host 还要做 scheduler。这个 scheduler 不是简单排队叫号，不是来了一个请求就发一个号码牌那么轻松。它要在每个 serving step 里判断哪些 request 能进入 batch，哪些 request 要等 KV 空间，哪些要优先处理，prefill 要不要切 chunk，decode 能不能继续，低优先级请求是否要被抢占，某个请求完成以后空出来的资源应该给谁。如果把它看成 OS scheduler 或 packet scheduler，反而更接近真实情况。因为它调度的不是普通函数调用，而是 token、request、KV slot、算力窗口和延迟预算。

Host 还要管 KV cache，而 KV cache 正是 LLM serving 最不像传统神经网络的地方。普通 tensor 算完就释放，像一次性纸杯，用完就扔；KV cache 不是，它是 request 的长期记忆。它会随着 token 增长而扩展，随着 request 完成而释放，随着 prefix cache 命中而共享，随着 sliding window 改变可见范围，随着 speculative decoding 接受或回滚，随着 offload 策略在 HBM、DRAM、SSD、远端节点之间迁移。

所以 KV cache 不是显存里的一块普通 buffer。谁拥有 KV 的账本，谁就拥有长上下文推理的命脉。

Host 还经常参与 sampling、structured output 和 grammar control。logits 从 device 出来以后，事情没有结束。系统还要做 temperature、top-k、top-p、repetition penalty，要判断 EOS 和 stop words，要维护 finished request，要处理 JSON schema，要解析 tool call。模型输出的 token 本身会改变下一步控制流，这就让 host 不再只是启动者，而成了 token-level state machine 的主人。

再往现代 serving 系统里看，host 还要处理 disaggregated serving、remote KV、KV offload、prefix cache、跨实例迁移这些胶水逻辑。数据在 HBM、SRAM、DRAM、SSD 和 network 之间奔跑，但 metadata 和决策如果仍然集中在 host 上，就会出现一个非常拧巴的结构：

数据在前线打仗，账本在后方盖章。

真正的分水岭，是谁拥有 token loop
大模型推理最容易被误解的地方，是大家总把它想成一次 forward。

输入 prompt，模型计算，输出答案。听起来很干净，也很像教科书。

但真实的在线推理，尤其是 autoregressive decode，根本不是一次 forward，而是一个高频状态机。每生成一个 token，系统都要检查当前有哪些 request 还活着，哪些新 request 可以插进 batch，哪些 request 的 KV cache 已经不够，哪些请求应该被抢占，哪些请求已经完成，prefill 和 decode 怎么混排，当前 token budget 够不够，下一轮 attention 要读哪些 KV block，logits 出来以后怎么 sampling，grammar mask 是否要更新，JSON schema 是否还合法，stop condition 是否触发，streaming output 要不要返回给用户。

如果是 Agent，这件事还会更复杂。模型生成一半，说我要调用搜索，于是 host 要解析 tool name 和 JSON 参数；外部工具跑完以后，结果要拼回上下文；prompt 或 KV 状态要更新；然后模型再继续 decode。它可能又要查数据库，又要调用计算器，又要读文件，又要把输出格式压成某个 schema。每一次 tool call、每一次 structured output、每一次 speculative decoding 的接受或回滚，都会让下一步控制流发生变化。

所以大模型推理不是一块矩阵乘到底，而是矩阵计算、向量处理、标量状态机、内存管理、队列调度和外部 I/O 交织在一起的服务循环。device 负责最重的 data plane compute，这当然没错。GEMM、attention、MLP、expert、logits，这些重活必须交给 CUBE、Vector、SRAM、HBM 和 DMA。可是今天很多系统里，host 仍然掌握 control plane。它决定下一步算什么，给谁算，怎么组织 batch，KV 怎么分配，什么时候结束，什么时候调用工具，什么时候发起下一轮计算。

于是系统就出现了一个很尴尬的结构：

**最贵的算力在 device，最关键的状态机却在 host。**

如果这个状态机只是偶尔参与一下，问题不大；可在 LLM decode 里，它每个 token 都参与。于是整套系统看起来像一台跑车，发动机很强，轮胎很贵，油路很宽，但方向盘装在后面一辆自行车上。自行车师傅也很努力，可你不能指望他在高速上稳定指挥一台超跑。

标量、向量、矩阵，本来就不该被拆成三个世界
讲到这里，就该回到 AI 芯片最底层的计算形态。

今天很多 AI 芯片讨论里，有一个很隐蔽的误区，就是大家太容易把矩阵计算当成 AI 计算的全部。只要 CUBE 足够大，Tensor Core 足够多，HBM 足够宽，好像这台机器就天然会强。

但做过系统的人都知道，矩阵乘只是舞台中央最亮的演员。它当然重要，没有它整场戏演不下去；可是如果灯光、道具、场记、调度、演员上场顺序全在另一个城市，那主角再会演，也只能站在台上等电话。

大模型推理其实是标量、向量、矩阵三种计算形态不断咬合在一起的系统。

矩阵负责最重的 GEMM、attention、MLP、expert 计算。向量负责 normalization、activation、softmax、mask、logits processing、quant/dequant、reduction 这些把矩阵块串起来的中间工作。标量负责那些看起来小得不起眼、但每一步都决定系统往哪儿走的状态，比如 request 当前生成到第几个 token，batch 里哪些请求还活着，KV block table 指向哪里，某个 buffer 的引用计数是否归零，MoE routing 选中了哪个 expert，speculative decoding 接受了几个 token，grammar state 走到了哪个状态，DMA descriptor 下一步搬哪里，某个队列是否还有 credit。

这些标量状态单独看都很小，小到不像性能问题。可它们有一个非常讨厌的特点：它们发生得太频繁，而且总是卡在大张量计算前后。

矩阵阵列再强，也要等这些小状态告诉它下一步算什么、读哪里、写哪里、给谁算、什么时候停。于是系统里最危险的瓶颈，经常不是大东西太慢，而是小东西太远。

如果标量在 host，向量被切成一堆小 kernel，矩阵在 device，中间靠 stream、event、graph、driver、runtime 来回传话，那系统就像一个健身冠军，肌肉在训练馆，神经在隔壁楼，血管还要走审批流程。你不能说他不强，但他每做一个动作都要先发邮件确认。最后拖死他的不是力量，而是协调系统。

所以标量、向量、矩阵本来就应该紧密配合。

这不是说它们要用同一种硬件来做。矩阵当然应该交给 CUBE，向量当然需要高效 vector datapath，标量当然需要灵活控制核和本地状态机。关键在于，它们必须在同一个本地运行时里互相看得见，必须围绕同一个 request、同一段 KV、同一个 token loop 协同推进，而不是被切成 host 和 device 两个世界。

这就是SuperScalar NPU 真正要表达的东西。

它不是 CPU 加 NPU。也不是 NPU 旁边放几个小核。它是让 CPU 世界里的进程、状态、调度、异常、内存管理、队列这些概念，和 NPU 世界里的大算力、大带宽、大 SRAM、大 HBM、大规模矩阵阵列重新合在一起。

把标量放到 device 本地，不是为了算标量，而是为了不让标量拖死张量
这里还要再往深处讲一步。

我们说要把标量分散到每个 device 上，不是因为标量计算本身需要多强的算力。算一个 request counter，改一个 pointer，更新一个 bitmap，判断一个 EOS，本身都不难。真正的收益在于，这些小状态不要再集中在远处的 host 上，不要再让每一次大张量计算都等一个外部裁判吹哨。

标量控制的价值，不是让标量跑得更快，而是别让标量拖死张量。

把标量放到 device 本地以后，最直接的变化是 token loop 可以在本地往前滚。device 算完 logits，本地 runtime 可以处理 sampling fast path，判断这个 request 是否结束，更新 token position 和 KV metadata，从本地 free list 里拿下一个 KV slot，把下一轮 CUBE task 塞进队列，同时安排 DMA 预取下一段 KV 或 expert 权重。只有遇到 tool call、外部 I/O、全局安全策略、严重异常这些慢路径，才把事件抛给 host。

这和自动驾驶里的本地控制很像。车遇到前方急刹，不能先把视频传回总部，请总部开会判断要不要踩刹车。总部可以制定策略，可以做全局调度，可以事后分析，但刹车必须在车上完成。

token loop 里的很多标量控制也是这个性质。它不是全局战略，它是局部反射。

KV cache 是最典型的收益场景。KV block 本身在 HBM 或 SRAM 附近，但如果 block table、slot bitmap、引用计数、prefix cache 命中状态、eviction metadata 都在 host 上，那就是数据在身边，账本在远方。每次读哪块、写哪块、释放哪块、迁移哪块，都要围绕远程账本转。

把这部分标量状态放到负责这段 KV 的 device 上，KV 管理和 KV 访问就处在同一个局部性范围内。本地 scheduler 可以直接把 block table 翻译成 DMA 和 tensor task，而不是让 host 在中间做账房先生。

这件事在多 device 系统里更明显。单卡时 host 勉强还能当总管；多卡、多芯片、多实例以后，如果所有小状态都集中在 host，每个 device 生成 token 后都要汇报，每个 batch mutation 都要请示，每个 KV movement 都要登记，host 就会变成全系统最大的会议室，所有人都在里面开小会。

分散标量状态以后，每个 device 可以先做本地自治，只把边界事件报告出去。request 完成了，上报；tool call 需要外部执行，上报；KV block 要跨 device 迁移，发消息；本地队列压力太高，申请调度；某个 expert cache 需要远端协助，再走跨 device 协议。

这不是无政府状态，而是分布式所有权。

属于某个 request shard 的状态，就放在负责它的 device。属于某段 KV block 的状态，就放在拥有这段 KV 的 device。属于某个 expert cache 的状态，就放在管理这个 expert 的 device。属于全局准入、公平性、计费、安全、外部工具调用的状态，仍然留给 host 或上层服务。

状态不能到处复制，复制一时爽，一致性火葬场。

状态应该有主人。

有主人，才有局部性；有局部性，才有低延迟；有低延迟，才有真正的 self-host。

更微妙的收益，是标量控制可以和张量计算重叠。标量如果在 host 上，流程往往是 device 先算，算完等 host；host 更新状态，再发下一轮；device 再算。这个流水线像一个人跑步，每跑十米就停下来填表。

标量在 device 本地以后，当前 CUBE 还在算，本地控制器已经可以准备下一批 descriptor；attention 还在读一段 KV，本地 DMA scheduler 已经可以预取下一段；MoE 当前 expert 还在跑，本地 runtime 已经可以根据 routing 结果安排下一个 expert 的 activation movement。

于是标量不再是张量计算之后的审批流程，而是张量流水线旁边的小神经系统。

这就是为什么我一直说，标量、向量、矩阵不能分家。

矩阵是肌肉，向量是韧带，标量是神经。肌肉再强，如果神经在远方，动作就会变成木偶戏。

而 self-host NPU 真正要做的，就是把神经接回肌肉旁边，把账本放回仓库旁边，把方向盘放回车里。

Self-host NPU 到底应该 self-host 什么？
讲到 self-host NPU，很多人第一反应是，这是不是说 NPU 里面要能跑一个 for 循环，或者说芯片里塞几颗 RISC 小核，就算 self-host 了。

这个理解不能说错，但太浅。

因为 self-host 的关键，不是这颗 NPU 能不能执行几段控制代码，而是它能不能拥有推理热路径的关键所有权。会跑控制代码，只是手里有笔；能不能自己推进 token loop，才是会不会写文章。

真正的 self-host NPU，首先要把 request 从 host runtime 里的一行 metadata，变成芯片本地可以调度、可以排队、可以推进、可以释放的对象。今天很多系统里，request 的生老病死都在 host 那边，device 只是不断被喂任务；而 self-host NPU 要做的是让 request 在本地有身份、有状态、有队列位置、有资源配额。它不是一张远处调度表里的名字，而是芯片本地 runtime 眼前正在处理的一件事。

它还要把 KV cache 从 host 维护的远程账本，变成本地内存系统的一部分。KV cache 不只是 HBM 里的一堆数据，它是上下文的骨架，是长上下文推理的记忆，是每个 token 能不能继续往前走的路标。KV block 在 HBM 或 SRAM 附近，账本却在 host 手里，这就像仓库在前线，库管在后方，每拿一箱弹药都要等电报批复。self-host NPU 的意义，是让拥有 KV 的地方，也拥有管理 KV 的状态；让 block table、slot bitmap、引用计数、prefix 命中、eviction、prefetch，都尽量贴着数据和 DMA 发生。

它更要把 CUBE task、vector task、DMA task、sampling task、routing task 放进同一个本地事件循环里。传统 host-device 模式下，device 做完一段计算，就把球踢回 host，由 host 更新状态，再拼下一段执行计划，再重新发令。这个流程像一个人跑步，每跑十米停下来填表。self-host NPU 要反过来，让本地 runtime 能把这些任务串成连续的推理生命线：CUBE 在算，vector 在接，DMA 在预取，scheduler 在排下一步，sampling 在 logits 附近完成常规状态转移，routing 根据本地 expert 和队列压力直接决定 activation 去哪里。

所以 self-host 的本质，不是芯片里有没有 CPU，而是芯片有没有能力在本地回答那个最关键的问题：下一步该算什么。

只有遇到外部工具调用、安全策略、全局部署、严重故障、跨服务边界这些慢路径事件时，它才应该把事情抛回 host。host 当然还在，但它不应该像一个焦虑的班主任，每个 token 都点一次名；它更应该像校长，负责制度、资源、安全和全局方向，而不是每个学生写一笔都要亲自批准。

这样的芯片当然需要本地 control cluster，但这个 control cluster 不能简单理解成传统大 CPU。它不一定要追求宽乱序，不一定要追求巨大的分支预测，不一定要追求豪华 cache。它真正需要的是 CPU-like 的系统语义，是本地队列、调度、地址空间、保护、异常、profiling、fault handling、低成本分支、函数调用和状态推进能力。它不是来替 CUBE 做矩阵乘的，它是让矩阵乘知道自己为什么而算、给谁而算、算完以后谁接着算。

这句话很重要：control cluster 不负责搬砖，它负责让工地不乱。

如果没有它，CUBE 阵列再强，也只是一个巨大的肌肉块；有了本地控制面，CUBE 才开始像一台计算机里的执行器，而不是一台等人投喂任务的外设。

当然，self-host NPU 还不能只有标量控制。它必须有足够强的 vector datapath。很多人谈 AI 芯片时，容易从标量控制直接跳到矩阵阵列，中间的向量层被忽略了。可真实模型里，normalization、softmax、activation、mask、logits processing、quant/dequant、reduction 这些高频操作，恰恰是把矩阵块串起来的筋骨。矩阵是拳头，向量是手腕和关节。只有拳头，没有关节，打出去就是僵的；只有 CUBE，没有高效 vector glue，系统就会被大量小操作切碎，然后再靠 fusion、graph、megakernel 去缝。

所以向量不是配角。

向量是矩阵之间的韧带。

它当然还需要大规模 CUBE arrays 或 tensor core。GEMM、attention、MLP、expert 这些重活，必须由高效率专用数据面完成。这里绝不能为了 self-host 就把主计算 CPU 化。让 CPU-like control 去硬做主矩阵计算，就像让总经理亲自搬砖，精神可嘉，效率感人。self-host NPU 的方向不是用 CPU 替代 NPU，而是让 CPU 世界的系统语义服务 NPU 的算力面，让标量控制贴近矩阵阵列，但不要让标量控制抢矩阵阵列的饭碗。

它还需要 software-managed SRAM。因为推理热路径里有大量生命周期明确、访问模式明确的数据，比如 KV hot block、activation tile、routing metadata、DMA staging buffer、runtime queue。这些数据不应该完全丢给黑盒 cache 去猜。SRAM 更像厨房里的工作台，常用刀具、调料、半成品都应该放在手边。你不能每切一次菜，都去地下仓库找刀；也不能每做一个 token，都去远处问账本。

HBM、DRAM、SSD 也要被重新组织成清晰的层级。active weights 和 active KV 应该在 HBM 或更近的位置，更冷的 prefix、历史 KV、日志、模型 shard 可以放到 DRAM、CXL、SSD 或远端存储，但 SSD 绝不能进入 token-by-token 的内层 decode loop。SSD 是档案室，不是灶台；档案室可以保存历史，但不能让厨师每炒一勺菜都跑过去翻说明书。

最后是 DMA 和 network。它们不是边角料，不是芯片外围的杂活，而是 AI serving 的血管系统。MoE expert prefetch、remote KV、prefill/decode 分离、multi-chip shard、prefix cache migration，这些都依赖 DMA、network 和 scheduler 协同。算力是心脏，KV 是血液，DMA 和网络是血管。心脏再强，血管如果像乡间小路，最后照样堵在村口。

所以 self-host NPU 不是一颗 NPU 加几颗小 CPU，也不是一颗 CPU 挂一坨矩阵阵列。它应该是一台围绕 AI 推理重新组织过的计算机：标量负责状态和调度，向量负责矩阵之间的高频胶水，矩阵负责重吞吐，SRAM/HBM/DMA/network 负责把数据在正确时间送到正确位置，本地 runtime 负责把这些器官组织成一条连续的 token loop。

这时候，self-host 才不是宣传词。

它不是在 NPU 里放一个会说话的控制核，而是让整颗芯片知道自己下一步为什么而算。

为什么一大波软件会因此更高效？
如果 self-host NPU 真能把标量、向量、矩阵和本地 runtime 合在一起，收益不会只是少几个微秒的 kernel launch，虽然这件事本身也很重要。更大的收益是，软件栈的角色会变。

今天很多 AI 软件之所以复杂，并不是工程师天生喜欢复杂，而是机器本身被拆成了两个世界。host 维护 request state，device 执行 kernel；host 维护 graph，device replay graph；host 更新 KV metadata，device 读写 KV；host 处理 sampling 和 stop condition，device 等下一轮任务。于是软件里长满了 stream、event、graph capture、graph update、callback、polling、queue、driver call、profile correlation。

这就像一套房子被强行拆成两套住。锅在东边，冰箱在西边，菜谱在楼下，水龙头在隔壁。于是大家发明了智能传菜、电梯调度、实时定位、共享日历和自动提醒。这些技术当然聪明，也确实能提升效率，但最根上的问题是，厨房为什么一开始要拆成这样。

CUDA Graph 要解决的是 host 反复发令的问题。它很有用，但它也说明 host 反复发令本身就是问题。persistent kernel 要解决的是 kernel 不断 launch 的问题。megakernel 要解决的是算子边界和 kernel boundary 太碎的问题。vLLM、SGLang、TensorRT-LLM 要在 host 上维护复杂 scheduler、request state 和 KV metadata。PagedAttention 要把 KV cache 变成类似 OS paging 的东西。MoE runtime 要在 routing、expert cache、activation movement、load balance 之间不断协调。structured output runtime 要在 logits、grammar state、sampling state、request state 之间频繁切换。

这些软件都非常聪明，但它们有相当一部分聪明，是在帮一台被拆开的机器重新接线。

如果 token hot loop 在 device 本地拥有调度和状态，很多事情的性质就变了。decode scheduler 不需要每轮站在 host 上远程指挥，它可以变成本地队列和本地策略；KV manager 不需要把 HBM 里的数据和 CPU 里的账本分开维护，它可以贴着 SRAM、HBM 和 DMA 做本地分配、预取和释放；sampling 和 grammar fast path 不需要每个 token 都回 host 过一遍，它可以在 logits 附近完成大多数常规状态转移；MoE routing 不需要先把小小的 routing metadata 拉回中央，再决定 activation 去哪里，它可以根据 expert locality、队列压力和 cache 命中情况，直接发起本地或邻近 device 的搬运。

profiling 也会变得更有意义。今天排查一个 token 为什么慢，经常像在拼凶案现场，Python runtime、driver、ACL/CUDA event、GPU/NPU kernel、KV allocator、network trace，每一块都有一小片线索，拼起来以后才知道原来中间某个地方空等了。可如果本地 runtime 统一记录 token 为什么等、等在哪里、下一步由谁触发，trace 就不再是一地碎玻璃，而是一条连续的时间线。

这并不是说 PyTorch、vLLM、compiler、driver、Profiler 都不要了。恰恰相反，上层生态仍然需要它们。训练、编译、模型加载、部署、调试、监控都离不开它们。真正变化的是，它们不再需要每个 token 都跨 host-device 边界做细粒度指挥，而是可以把更多策略 lower 到芯片本地 runtime，让 host 负责部署、安全、外部工具、全局资源和慢路径异常。

软件栈不是消失了。

软件栈是站到了更合适的位置。

过去很多软件是在两个世界之间当翻译，现在它们可以在一个本地世界里当建筑师。翻译的工作，是把双方听不懂的话硬转过去；建筑师的工作，是从一开始就把房子设计得少走弯路。self-host NPU 的软件收益，就在这里。

它最先应该在哪些地方打出价值？
我不认为 self-host NPU 一上来就应该去挑战所有 GPU 场景。大 batch training、规则 dense GEMM、静态图执行，这些地方 GPU 很强，而且会继续强很久。跑到对方最舒服的地方硬碰硬，很多时候不是勇敢，而是把自己的长处扔掉，去参加别人的考试。

真正该打的，是 GPU 历史模型最不舒服的地方。

低延迟 decode 是一个。batch 不大，token step 高频，状态更新多，host 参与越多，P99 越容易抖。这里最怕的不是某个 GEMM 慢，而是每个 token 都被 host 小小地绊一下，最后小绊脚变成大尾延迟。

长上下文是一个。KV cache 变成核心资源，block table、prefix cache、eviction、migration、offload 都是内存系统问题，不是单个 GEMM 问题。长上下文不是只考算力，它考的是谁能管理记忆。

MoE 是一个。expert routing、activation movement、expert cache、load balance、跨 device 调度，全部依赖标量 metadata 和张量移动紧密配合。MoE 的难点不只是 expert 会不会算，而是 token 去哪里、何时去、带着什么数据去、回来以后谁接着算。

speculative decoding 是一个。draft、verify、accept、rollback，每一步都在改变状态。它不是静态图喜欢的规整流水线，而是一个不断试探、确认、回滚、前进的动态过程。

structured generation 和 Agent 更不用说。grammar mask、JSON schema、tool call、外部 I/O、上下文更新、重新 prefill 或继续 decode，本来就是动态控制流的大杂烩。它们天然不喜欢每一步都回 host 排队盖章。

多租户低延迟 serving 也是一个。host CPU 会受到 OS scheduler、TLB、LLC、allocator、网络栈、日志、后台线程的干扰。你可以 pin core，可以用 huge page，可以做 cache partitioning，但这些本质上都是在保护一个不该每个 token 都参与的瓶颈。把热路径标量控制搬到 device 本地以后，host 当然还会抖，但它不再能每个 token 都把 device 卡住。

所以 self-host NPU 的价值，不是证明 GPU 不行，也不是说 CUDA 时代一夜结束。它真正承认的是，不同 workload 需要不同系统边界。GPU 过去的 host-device 模型，非常适合某些时代和场景；但动态推理正在把边界成本推到台前。

打败旧范式的方式，不是在旧范式最强的地方卷得更狠，而是在它最别扭的地方换一张桌子。

self-host NPU 要换的，就是这张桌子。

它不再把 device 当成 host 后面的一块算力外设，而是让 device 本地拥有 token loop；不再让标量、向量、矩阵分居两地，而是让它们围绕 request、KV、DMA 和 CUBE 在同一个运行时里协同；不再让软件栈拼命替一台被拆开的机器接线，而是让软件栈去组织一台本来就长在一起的 AI 计算机。

说到底，self-host NPU 的目标不是让芯片更像 CPU，也不是让 NPU 失去专用性。

它的目标是让 AI 芯片不再只是会算，而是知道自己为什么而算、下一步算什么、算完以后谁来接。

结尾：不是把 NPU 做成 CPU，而是把 AI 芯片做成计算机
讲到这里，可能听起来很热血，好像只要把 host 从热路径里拿掉，把标量、向量、矩阵重新合在一起，self-host NPU 就能一路高歌猛进。

但真正做架构的人都知道，越是看起来漂亮的方向，越容易在落地时长出荆棘。

这条路最大的风险，不是技术上不够激进，而是激进错了地方。为了追求 CPU-like 语义，如果把 control plane 做成一组豪华大核，塞进宽乱序、大缓存、复杂一致性、庞大 OS surface，最后把原本应该留给 CUBE、SRAM、HBM 和 DMA 的面积功耗吃掉，那就不是 self-host NPU，而是买椟还珠。我们要的不是把传统 CPU 原封不动搬进 NPU，更不是在矩阵阵列旁边修一座金碧辉煌的控制宫殿；我们要的是把 CPU 世界里最有价值的系统语义拆出来，压缩、重组、下沉，放到 AI 推理最需要它的位置。

![](https://pic4.zhimg.com/v2-9931bafdca318f159a430768d3be7e2b_r.jpg)所以真正合理的方向，应该是一种双平面设计。control plane 要能管理 queue GQM、request descriptor、metadata、scheduler state，要有保护、异常、调试和局部一致性；data plane 则必须保持干净、直接、显式，用 tensor buffer、software-managed SRAM、DMA、scoped consistency 去搬 weights、KV、activation 和 collective buffer。标量和 metadata 要灵活，张量和带宽要高效。不能为了让控制面舒服，就让所有 tensor traffic 都去走昂贵的全局一致性；也不能为了让数据面纯粹，就把所有状态都扔回 host，然后再让软件栈把这台被拆开的机器重新缝起来。

分散标量状态也一样，绝不是把状态到处复制一份。复制一时爽，一致性火葬场。真正要做的是划分所有权。属于某个 request shard 的状态，就放在负责它的 device；属于某段 KV block 的状态，就放在拥有它的 device；属于某个 expert cache 的状态，就放在管理它的 device；属于全局准入、公平性、计费、安全、外部工具调用的状态，仍然留给 host 或上层服务。状态不能没有主人，也不能有太多主人。没有主人，系统会乱；主人太多，系统会吵。

所以 self-host NPU 不是一个单纯的芯片问题。它是硬件、编译器、runtime、serving framework、内存系统、网络系统一起重构的问题。它难，正因为它不只是多放几个乘法器；它有价值，也正因为它不是多放几个乘法器。

AI 芯片的下一场战争，不只是算力战争，而是控制权战争。
如果 host 拥有 token loop，那么 device 再强，也只是一个强大的执行器。它可以像巨人一样搬山，却仍然要等远处的人告诉它下一步往哪儿走。它会被限制在阿姆达尔定律的框架中。

如果 device 本地 runtime 拥有 token loop，那么它才开始从外设变成计算机。它不再只是等人喂 kernel 的算力机器，而是能把 request、KV、scheduler、DMA、vector glue、CUBE task 放进同一个本地事件循环里，自己推进状态，自己组织数据，自己安排下一步，只有遇到外部工具、安全策略、全局部署、严重故障这些慢路径时，才把事件交还给 host。

当一颗 AI 芯片不仅会算矩阵，还知道这些矩阵属于哪个请求，处在什么状态，下一步该读哪段 KV，该送到哪个 expert，该不该结束，该不该采样，该不该预取，该不该把事件交给外部世界时，它就不再是一块等人喂任务的加速器。

它才是一台真正的 AI 计算机。

而这也许就是 GPU/CUDA 之后，AI 芯片真正值得改弦更张的地方：不是在旧范式里把外设做得更强，而是让外设终于长成主机；不是让算力继续等待命令，而是让算力第一次拥有自己的节奏、记忆和意志。
