最近“韬定理”如火如荼，朋友圈里人人都在谈系统、谈封装、谈先进工艺之后的第三条路，听起来每个人都像刚从未来十年穿越回来。作为菊场一名朴素的牛马，仰望星空当然也要仰望，毕竟谁不想在技术史的长河里顺手捞一瓢水；但低头看一眼自己的工位，屏幕上还挂着一堆算子性能、客户问题、流水断点和 profiling 图，心里马上就踏实了：宏大叙事先让大佬们飞一会儿，咱还是先把昇腾这颗核里的水管、电线、阀门和红绿灯理明白。

![](https://pic3.zhimg.com/v2-baada3031582543d1b09482dc85baf80_r.jpg)昇腾 950 已经开始大规模进入客户现场，卡卖得多了，用户多了，模型多了，框架多了，问题自然也多了。过去有些问题藏在实验室里，像墙角一小片返潮，看着不严重；等客户真正把模型一批批搬上来，长序列、低 bit、推荐、广告、搜索、动态 mask、MoE、通信融合全都往上怼，才发现这不是返潮，这是楼上浴缸忘关了。我们最近的状态也很像救火队员，一边拎着水管冲进去，一边还得给业主解释：房子主体结构是可靠的，钢筋水泥都没问题，就是管线有点复杂，开关有点多，个别阀门藏得比较深，操作手册写得像绝地武士训练纲要。

昇腾这辆车，发动机其实很猛。CUBE 该有的爆发力是有的，Vector 也不是吃素的，搬运引擎、Fixpipe、各种格式转换和低精度能力，拆开看都挺能打。问题在于，它有点像一辆性能很好的手动挡赛车，离合、油门、档位、转速、路线全都给你了，理论上能开得飞快，实际上要开出 Speed of Light，驾驶员最好是天行者安纳金，闭着眼都能感受到原力在 L0A、L0B、L0C 和 UB 之间流动。普通人上去一脚油门，车没坏，路也没堵，就是突然发现自己还没挂对档，副驾驶的 CUBE 已经在催，后排的 Vector 还没系安全带，Scalar 正在翻说明书，Fixpipe 在旁边冷静地说：别急，量化参数还没配完。

这也是很多人吐槽 CUBE 和 VEC 分开的原因。单独看，每个单元都有自己的道理；合起来跑复杂模型，就会发现数据总在倒腾。CUBE 算完一块东西，Vector 马上要做 scale、mask、softmax、reduce；Vector 处理完，CUBE 又要接着算下一轮。算法图上是一条流畅的线，落到硬件里就变成了几段接力：这块数据先在哪，下一步谁用，要不要搬，要不要转格式，要不要等同步，要不要释放 buffer，要不要小心踩到另一个 pipe。写算子的人本来是来写数学的，写着写着就像在调度一个微型物流园区，叉车、仓库、闸口、传送带全要自己盯。

低精度也是一样。听起来很美，bit 少了，算力高了，带宽省了，模型成本降了，大家一起鼓掌。但真到芯片里跑，事情马上变得很现实：数据要打包解包，scale 要加载对齐，格式要转换，L0C 要搬出，Fixpipe 要接住，Vector 要做后处理，转置路径还要亲和。CUBE 在前面喊“我准备好了”，后面的数据流像早高峰地铁换乘，入口、扶梯、闸机、站台全在排队。低 bit 的峰值很性感，低 bit 的端到端很诚实。

950 把 SIMT 加进来以后，很多不规则场景终于不用再硬拧 SIMD 或折腾 Host 了，这一步方向当然是对的。动态 mask、离散访问、复杂控制流，这些东西迟早要在核内解决。但昇腾的 SIMT 又不是 GPU 那套土生土长、从小练到大的 SIMT，它更像是我们给一支原本纪律严明的方阵配了一支轻骑兵，能绕路、能侦察、能处理复杂地形，但马厩、粮草、指挥链和主力部队之间的协同还得继续补。于是很多算子就变成了混合作战：一段 SIMT，一段 SIMD，中间还要搬数据、对齐、同步、切 shape。能打，但累人；能赢，但每次赢完都想回去重构。

我们做 PTO 虚拟指令集，初心其实很朴素，甚至有点理想主义：底下这些 CUBE、Vector、MTE、Scalar、SIMT、Fixpipe，各有脾气，各有祖传接口，各有一套“你最好按我喜欢的姿势来”的使用说明。那能不能往上封一层，把这些异构单元包装成一组简单、统一、稳定的 Tile 操作？用户写的是我要搬一块数据、算一块矩阵、做一次重排、完成一次同步，至于底下到底是哪条 pipe、哪个 buffer、哪个 event、哪个奇怪的配置字段，最好别让人天天背口诀。结果做了一波以后，客户也很真诚地告诉我们：抽象很好，但是我还想要硬件底层。

这话听起来完全合理。毕竟大家做性能优化，谁都不想隔着一层毛玻璃看硬件。问题是，底层一给出去，事情马上开始变得玄学。参数多，约束多，组合多，亲和路径多，挂死姿势也多。你给他一个简单接口，他说不够透明；你把底层打开，他说怎么这么难用。最后我们夹在中间，像一个人格分裂的导游：上午给游客讲“大家放心，这是一条统一路线”，下午又偷偷补一句“但是这段山路要自己换挡，那个弯道要提前踩离合，前面还有个隐藏开关，没开可能直接熄火”。

PTO 想解决的是统一抽象，可现实里的硬件接口却像一座老城区。每条街都有名字，每个路口都有历史，每个单元都有自己的小规矩。比如原子操作这种东西，按理说应该是一个很清楚的系统能力：我要同步，我要交换信息，我要保证顺序，我要让多个核之间有一个可靠的握手机制。结果一看实现，标量有一套，向量有一套，MTE 又有一套，能力不完全一样，语义不完全一样，路径不完全一样，性能也不完全一样。你想做一个多核同步，先别急着写代码，先开一场科普会，解释清楚“你这个 atomic 到底是哪个 atomic”。

这件事表面上很好笑，往深了看其实很疼。它说明我们现在的硬件能力虽然丰富，但缺少一个统一的核内管理和调度语义。每个单元都在努力把自己的事情做好，可系统层面缺少一个能把这些能力收拢起来的共同语言。PTO 想往上抽象，客户又需要底层控制；底层一暴露，复杂度又反噬软件；软件接不住，就继续靠专家经验、靠文档补丁、靠群里答疑、靠一轮又一轮解释。

更深一层看，昇腾当前遇到的这些问题，表面上散落在 C/V 交互、低 bit、SIMT、DMA、Scalar、通信、DFX、TDP 各个方向，像一张到处贴便利贴的问题墙；真正的根子其实很集中，就是<strong>核内的调度和管理问题</strong>：现有核还是围绕固定流水和显式 buffer 管理来组织计算，缺少一个统一的数据流调度层。计算单元各自很强，交接成本却不低；片上存储层级很丰富，软件却要记住太多物理细节；低 bit 峰值上去了，scale、重排、搬出和 Vector 后处理没有被放进同一套调度；SIMT 有了处理不规则场景的能力，还没完全成为主路径；通信越来越像模型数据流的一部分，却仍然带着外部控制动作的影子。

## 1. 大模型负载变了，芯片痛点也变了

过去的 AI 核像一条高效的工业产线。原料规整，工序稳定，最重的工序是矩阵计算，硬件把这个工序做得足够快，整条产线自然有很高吞吐。

现在的模型更像一座繁忙城市。城市里仍然有主干道，也有越来越多的小路、岔路、临时管制和跨区调度。大矩阵乘还是主干道，但低 bit、稀疏 attention、MoE、动态 mask、长序列 KV、推荐离散访问、小算子融合、A-F 分离和多流通信都在增加“路口”和“换乘”。城市的通行效率不再只取决于最宽那条路，还取决于匝道是否堵、信号灯是否合理、快递能不能送到最后一公里、调度中心能不能看清全局。

这也是昇腾当前痛点开始集中爆发的原因。现有核擅长规则高密度计算，但复杂模型把大量非规则、非矩阵、非连续、非静态的工作推到前台。只要其中某一段没有跟上，矩阵阵列就会等数据，Vector 就会等搬运，SIMT 就会等资源，Scalar 就会等 cache，通信就会等 doorbell 或 CQE，端到端性能自然跑不满。

一个简单的性能表达式能说明问题：

T_layer ≈ max(T_cube, T_vector, T_memory, T_comm)
          + T_reorder
          + T_scalar_control
          + T_sync
          + T_tail_latency
在规则大矩阵时代，`T_cube` 往往最大，其他项被掩盖。到了低 bit、稀疏和长序列时代，`T_cube` 下降，`T_reorder`、`T_memory`、`T_scalar_control`、`T_sync` 和 `T_tail_latency` 反而变得更显眼。继续只增加矩阵峰值，会让公式里的其他项更加刺眼。

未来昇腾核要优化的核心对象，应该从单个计算单元转向这条完整的数据流。

## 2. 当前最根本的痛：计算单元很强，单元之间交接太重

昇腾现有核把 CUBE、Vector、Scalar、搬运引擎拆得很清楚，这种设计在规则算子上很有效。CUBE 负责大块矩阵，Vector 负责辅助计算，搬运引擎负责把数据送到合适位置，Scalar 负责控制和参数组织。分工越清楚，规则场景下越容易做到高能效。

复杂模型把这个优势变成了负担。一个融合 attention 算子里，CUBE 计算完 QK，Vector 很快要做 scale、mask、softmax、reduce，后面 CUBE 又要接 PV；低 bit GEMM 里，矩阵计算前后都伴随 scale、quant、dequant、layout 转换和搬出；推荐场景中，SIMT 可能生成 mask 或索引，Vector 处理特征，CUBE 做 MLP，中间结果不断跨执行域流动。

算法上这些步骤是一条连续数据流，硬件上却像几个隔着墙的车间。CUBE 的结果在自己的地方，Vector 要到另一个地方干活；Vector 干完以后，如果结果还要给 CUBE 用，又要重新搬到 CUBE 能消费的位置。每次交接都要搬运、同步、格式转换和 buffer 管理。

这类开销最痛的地方在于，它很容易被误认为是“某条搬运带宽不够”或者“某个算子没调好”。带宽确实会影响结果，调优也确实能缓解一部分问题，但本质上，数据没有一个跨 CUBE、Vector、SIMT 的统一身份。软件只能用“数据在哪一级 buffer”来表达状态，用搬运指令来表达交接，用同步指令来表达依赖。

未来昇腾核应该把逻辑 Tile 提升为核心数据对象。矩阵 tile、向量 tile、mask tile、scale tile、低 bit packed tile，都应该成为硬件统一认可的逻辑实体。CUBE 产出一个 Tile，Vector 可以直接消费；SIMT 产出的 mask Tile 可以直接进入 Vector 或 CUBE 的后续计算；Vector 处理完的 scale 或 dequant Tile 可以继续作为矩阵计算输入。

物理结构仍然可以保留 L0、SRAM bank、寄存器堆和专用 datapath，但软件不再用这些物理位置表达算法依赖。软件看到的是 Tile，硬件负责决定 Tile 落在哪里、什么时候 ready、能不能旁路、需不需要搬运、是否可以重命名和复用。

这一步是未来核架构的第一块地基。没有统一 Tile，C/V/SIMT 融合会继续依赖手工编排；有了统一 Tile，融合算子才有机会在硬件上真正连起来。

## 3. 片上存储要从“手工仓库”走向“Tile 寄存器体系”

昇腾现有的多级片上存储有明确历史价值。L1、L0A、L0B、L0C、UB 等层级让矩阵数据能够高效进入计算阵列，也让不同阶段的数据拥有各自亲和的位置。问题出现在软件可见性上：高性能算子开发者必须理解并管理这些层级。

一个复杂算子要跑好，开发者要决定 L1 装什么，L0A/L0B 如何切，L0C 何时搬出，UB 放哪些临时结果，double buffer 怎么开，哪些数据要转格式，哪些地方要对齐，哪些 pipe 要 wait/arrive，哪些 buffer 可以复用。每多一级显式 buffer，软件就多一本账；每多一种 layout，账本就多一列；每多一种 bit width，账本又要重算。

这对专家不是问题，对生态是问题。专家能写出好性能，但模型和 shape 一变，模板就会分叉；普通开发者能写出功能，但性能容易掉进各种边界；编译器可以做一部分工作，但如果硬件暴露的物理约束太多，编译器也会背上过重的搜索空间。

未来昇腾核应该把片上共享存储“Tile 寄存器化”。这个说法的重点不在“寄存器”这三个字，而在寄存器体系背后的能力：逻辑命名、物理映射、重命名、ready 状态、依赖追踪、生命周期管理和异常恢复。

在这样的体系里，软件声明的是逻辑 Tile：

```text
Tile q = load_tile(Q, layout_q);
Tile k = load_tile(K, layout_k);
Tile s = matmul(q, k);
Tile p = softmax(s, mask);
Tile v = load_tile(V, layout_v);
Tile o = matmul(p, v);
store_tile(O, o);
```

硬件内部仍然需要决定 q、k、s、p、v、o 分别落在哪块 SRAM、哪个 bank、是否需要进入矩阵阵列旁边的局部 buffer、是否可以直接旁路给 Vector、是否需要 spill 到更低层级。这些复杂性没有消失，只是从手工账本变成硬件和编译器共同管理的资源映射。

这样做的价值很直接。第一，软件不再把每一级 buffer 的生命周期写死，算子泛化性会好很多。第二，CUBE、Vector、SIMT 之间可以通过 Tile ready 状态自然衔接，减少显式同步。第三，异常发生时，硬件可以记录逻辑 Tile 到物理存储的映射，DFX 能看到真正的数据流状态。第四，未来硬件改变某一级 SRAM 容量或路径时，软件接口不需要跟着大改。

片上存储层级仍然存在，但它们应该逐渐退到 Tile Register 的背后。开发者写数据流，硬件管仓库。

## 4. 下一代核需要 Tile 级乱序，把复杂模型里的气泡吃掉

现有 AI 核的高效率，很大程度来自软件提前把流水排好。规则算子里，每一块数据什么时候从 GM 搬进来，什么时候进入片上 buffer，什么时候送给 CUBE，什么时候由 Vector 接手，什么时候写回，软件都可以在编译期或者 tiling 阶段安排得比较清楚；硬件只要按照这个节拍往前推，搬运和计算就能像工厂里的传送带一样咬合起来。只要模型足够规则、shape 足够稳定、访存足够连续，这种方式非常有效，因为它把硬件做得简单，把调度压力交给软件，把确定性换成了高能效。

问题出在今天的模型已经没有那么听话了。

复杂模型里的很多等待，不再是软件排流水时能完全预知的等待。稀疏访问会让某些 Tile 的数据回来得比预期更晚，PageAttention 里的某个 page miss 会拖住一小段数据流，动态 mask 会让不同 Tile 的控制路径不一样，低 bit 场景里 scale 可能提前 ready 也可能被 layout 卡住，通信返回有远端时延，小 shape 下单个 block 可能根本填不满一个执行核。于是原来那种“我提前知道每一步要花多久，所以我把流水排得刚刚好”的假设开始失效。流水一旦失效，就会出现气泡：CUBE 有空但数据没来，Vector 有空但前序 Tile 没搬完，Memory Engine 有空但软件没把下一批请求提前发出去，旁边明明有已经 ready 的工作，却因为软件预排顺序还没走到它，只能跟着一起等。

这个时候，继续让软件手工重排流水，当然可以缓解一部分问题，但它会越来越吃力。因为动态性越强，软件越难在静态阶段把所有情况都排好；模型 shape 越多，模板越多；layout 越多，亲和路径越多；通信和稀疏越多，运行时的不确定性越多。软件能做的是给出一个大致合理的执行图，但执行过程中到底哪个 Tile 先 ready，哪个 Tile 被 memory 拖住，哪个 Tile 可以提前做后处理，哪个 Tile 的 scale 可以预取，这些信息只有硬件在运行时看得最清楚。既然信息在硬件手里，调度也应该有一部分回到硬件手里。

这里需要的不是把 AI 核做成一个通用 CPU，也不是在每条标量指令上复制 CPU 那套乱序窗口。AI 核的数据粒度更大，计算结构更规整，真正值得乱序的对象不是一条条普通指令，而是一块块有明确输入输出关系的 Tile。一个 Tile 可以代表一次矩阵块计算，一次低 bit 数据重排，一次 scale 对齐，一次 softmax/reduce，一次 gather 访问，或者一次通信等待。只要硬件能够知道这些 Tile 之间的依赖关系，知道每个 Tile 的输入是否 ready，知道对应执行后端是否空闲，知道内存顺序和异常边界，就可以在不破坏程序语义的前提下，把已经 ready 的 Tile 先发出去。

这就是 Tile 级乱序的本质：把过去由软件静态安排的“固定流水”，变成硬件在运行时根据 Tile ready 状态动态推进的“数据流调度”。

为了做到这一点，下一代核需要在前端建立一套围绕 Tile 的状态系统。逻辑 Tile 要能映射到物理 Tile 存储，这样软件看到的是稳定的数据对象，硬件可以在内部做重命名和复用；等待执行的 Tile 操作要进入一个队列，硬件根据输入 ready、资源 ready 和内存依赖来选择发射；Tile 的生产和消费关系要有明确记录，某个执行后端写回以后，依赖它的后续 Tile 可以被唤醒；内存访问要进入独立的建序结构，既允许不相关访问并行推进，又能在别名、越界和异常时保持可解释；已经发射的 Tile 要有提交状态，这样出错时能够知道哪个 Tile 在飞、哪个 Tile 已经完成、哪个 Tile 可以回滚或丢弃。

这套机制听起来像 CPU 乱序，但粒度完全不同。CPU 乱序关心的是几条加法、load、branch 之间的依赖；Tile 乱序关心的是一个 BMM tile、一个 reorder tile、一个 scale tile、一个 vector tile、一个 communication tile 之间的依赖。它不追求在极细粒度上榨干每一条标量指令，而是要在 AI 模型真正的执行粒度上，把大块等待重叠起来，把本来会空转的 CUBE、Vector、SIMT、Memory 和 Comm 填起来。

有了 Tile 级乱序以后，很多过去必须靠软件手工安排的事情，就可以交给硬件运行时处理。某个稀疏 load 还没回来，不相关的矩阵 Tile 可以继续发；某个通信 Tile 在等远端事件，本地已经 ready 的 Vector 后处理可以先做；低 bit 的 scale Tile 可以提前搬进来，不必等到 MMA 前一刻才发现 scale 没到；reorder Tile 可以插在 memory 和 compute 之间，尽量和上一块计算重叠；小算子不必作为一段单独流水硬插进去，而可以在资源空隙中被调度出去。这样做的结果不是让单个操作本身变快，而是让整条模型数据流少等一点。

复杂模型最怕的，往往不是某一个操作慢，而是很多小等待凑在一起。一次 page miss、一段 scale 对齐、一点通信静态时延、一次 descriptor 准备、一块小 tile 的尾巴，看起来都不大，叠在几十层、几百个算子、几千个 Tile 上，就会变成端到端性能里很厚的一层灰。Tile 级乱序的意义，就是让硬件不再傻等软件排好的下一步，而是在保证正确性的前提下主动找活干，把这些灰一点点擦掉。

## 5. 低 bit 不是换一种数据格式，而是重新设计一条量化数据流

量化这件事，很容易被讲窄。

最简单的说法是，把 FP16 换成 FP8，把 FP8 再往 FP4 压，bit 少了，算力高了，带宽省了，模型自然更快。这个说法不能算错，但它只讲了量化最表面的一层。真正在大模型里把量化做好，难点从来不是“能不能把一个数编码成 4bit”，而是这 4bit 还能不能代表原来那堆数里真正重要的信息。

所以量化首先是一个误差分配问题。

一组 tensor 里，大多数值可能很小，少数值特别大；有些 channel 对结果很敏感，有些 channel 量化粗一点也没事；activation 往往比 weight 更难压，因为它的动态范围更不稳定，还经常有 outlier。直接拿一个统一 scale 往下压，看起来硬件最简单，实际很容易让小值被淹掉，或者让大值把整个 block 的 scale 拉歪。最后 bit 是省了，误差也一起带进模型里了。

这就是为什么好的量化方法都在做同一件事：想办法把动态范围变得更适合硬件。

SmoothQuant 的思路，是把 activation outlier 的压力转移到 weight 上，让 activation 更容易量化。AWQ 的思路，是不要平均看待所有 weight，而是根据 activation 分布找出更重要的 channel，把这些重要通道保护好。MXFP、NVFP4 这类格式，则是在硬件数据格式层面做类似的事：不要让太大一片数据共用一个粗 scale，而是缩小 block，让 scale 更贴近局部数据分布。

所以，量化真正要回答的是三个问题。

第一，scale 怎么选。scale 粗了，硬件简单，但误差大；scale 细了，精度好，但 scale 本身要搬、要存、要对齐、要参与计算。E8M0 这种 power-of-two scale 好实现，乘法可以变成指数调整，但它对局部数值分布的拟合比较粗。更细的 scale 表达能力更强，但硬件要付出更多代价。这里没有免费的午餐。

第二，scale 粒度怎么定。按 tensor 量化最简单，但误差最大；按 channel 好一些；按 group 或 micro-block 更适合低 bit。FP4 这种格式尤其依赖小粒度 scale，因为 4bit 本身表达能力太弱，如果 block 太大，里面的数值动态范围一拉开，很多信息就丢了。低 bit 越低，scale 越不能粗放。

第三，scale 和数据怎么在硬件里流动。很多量化方案在论文里看起来很漂亮，落到芯片上会遇到一堆很现实的问题：scale 放在哪里，和 packed data 是否连续，按什么 layout 对齐，转置时 scale 怎么办，MMA 前要不要 unpack，累加后怎么 requant，结果搬出时走哪条路径，Vector 后处理能不能跟上。

可以把一次低 bit 计算拆成这样：

原始高精度数据
    ↓
统计局部动态范围
    ↓
生成 scale
    ↓
按 group / block 量化成 packed low-bit
    ↓
搬入片上
    ↓
unpack / reorder / scale align
    ↓
低 bit MMA
    ↓
高精度累加
    ↓
acc convert / requant / dequant
    ↓
按目标 layout 写回
这条链路里，MMA 只是中间一环。它当然重要，但它不是全部。只把 MMA 做快，前面 unpack 和 scale 对不齐，后面 requant 和搬出接不住，性能一样会掉下来。

未来昇腾核要做好量化，应该把量化当成一条完整的数据流来设计，而不是当成 CUBE 支持的一个新 dtype。

首先，Tile 类型里要显式描述量化语义。一个 low-bit Tile 不能只有 dtype，还要带上 packed layout、scale format、scale granularity、group size、accumulation type、valid mask、reorder policy。硬件只有看见这些信息，才知道这块数据不是普通矩阵，而是一块带 scale、带 group、带布局约束的量化 Tile。

其次，scale 要进入调度图。scale 不能只是算子里临时读一下的小参数，它应该和数据一样被 load、被 cache、被对齐、被复用。低 bit 场景里，scale 的位置和时机非常关键。scale 提前搬，MMA 就少等；scale layout 和数据 layout 对齐，Vector 和 Fixpipe 就少倒腾；scale 能复用，带宽压力就小很多。

第三，unpack 和 reorder 要靠硬件数据流接住。低 bit packed 数据天然和计算阵列喜欢的 layout 不一定一致。如果每次都靠软件拆路径、补转置、调特殊指令，低 bit 算子会很快变成模板地狱。更合理的方式，是让 Tile Memory Engine 在搬入时顺手做 unpack、reorder、padding 和 scale align，把后端真正要吃的 Tile 准备好。

第四，累加和 requant 要有固定套路。低 bit 乘法通常不能低 bit 累加，累加结果要保持更高精度，然后根据下一阶段需要做 acc convert、requant 或 dequant。这里最怕的是每个算子各写一套路径，结果精度、性能和溢出行为都不一致。未来应该把这些动作收敛成统一的 Tile 原语，让软件知道语义，硬件知道路径。

第五，量化要和模型结构一起看。训练、Prefill、Decode、MoE、推荐、长序列，对量化的敏感点不一样。有些场景 weight-only 就够，有些场景 activation 也要压，有些场景 scale 粒度要细，有些场景更在意转置和反向路径，有些场景更在意 KV cache 的存储效率。硬件不应该只给一个固定格式，而应该给出几套清楚的量化数据流，让软件能按场景选择。

## 6. SIMT 要成为主路径，服务不规则模型，而非偶发兜底

未来模型中的不规则性会越来越多。推荐场景有离散 embedding 和动态特征；稀疏 attention 有索引和 mask；FlexAttention 这类表达方式需要运行时 score_mod；MoE 有 token routing；长序列推理有 page 和 KV 命中。用传统 SIMD 处理这些逻辑，会遇到分支、predicate、离散地址和小粒度访存的限制；用 Scalar 处理，会直接把控制单元拖死。

SIMT 的出现解决了“能不能表达”的问题，下一步要解决“能不能跑满”的问题。如果 SIMT 的寄存器容量不足，LD/ST buffer 不深，Block 并发不支持，IPC 偏低，predicate 和 branch 处理不强，开发者就会陷入混合开发。复杂部分用 SIMT，规则部分用 SIMD，中间还要搬数据、同步、调 shape。算子写出来以后，同一个算子换输入 shape，性能可能大幅波动。

未来昇腾核里的 SIMT 应该成为 Tile 体系的一等执行后端。它和 Vector、CUBE 使用同一个逻辑 Tile 数据对象，SIMT 生成的 mask Tile 可以直接被 Vector softmax 消费，SIMT 生成的索引 Tile 可以直接驱动 gather，SIMT 做完的动态控制结果可以进入后续矩阵或搬运操作。

硬件侧要补齐几类能力。首先是 Block 并发，一个执行核应支持多个 Tile Block 同时驻留，用更多独立工作填满资源。其次是 SIMT LD/ST 通路，要针对离散访问和连续访问都提供足够 outstanding、合并和缓存能力。再次是寄存器和 predicate 资源，不规则控制流天然消耗更多状态，寄存器不足会直接降低 occupancy。最后是调度和 issue，SIMT 不能只依赖简单顺序发射，需要能在 Tile 调度框架下和 Vector、Memory、CUBE 共同排队。

未来核理想的使用方式是，开发者写 Tile 程序，编译器根据控制流和访存特征选择 SIMD 或 SIMT 后端。规则密集段走 Vector/SIMD，复杂分支段走 SIMT，二者围绕同一批 Tile 自然交接。这样才能减少手工混合开发，把 SIMT 从补充能力变成主路径能力。

## 7. 搬运引擎要从固定 DMA 走向消费者视角的数据获取系统

现有搬运和格式转换能力在亲和场景下很强。问题在于，模型 layout 演进太快。Attention 的 Q/K/V/O 可以有多种布局，low-bit 有 packed layout 和 scale layout，PageAttention 有 page layout，SparseAttention 有 index layout，推荐模型有离散 layout。靠不断增加专用搬运指令，短期有效，长期会越来越被动。

这里有一个设计视角问题。很多传统搬运指令在描述“硬件已经支持哪些固定路径”，开发者需要把自己的数据格式迁就到这些路径上。未来更合理的方式是描述“消费者想要什么数据”。也就是说，Vector 或 CUBE 想消费一个怎样的 Tile，软件把这个目标描述清楚，硬件选择最合适的获取方式。

一个消费者视角的 Tile Memory Engine 应该接收类似这样的描述：

目标：生成一个 Tile A
来源：Global Tensor X
逻辑形状：[M, K]
源布局：layout_src
目标布局：layout_dst
数据类型：dtype
scale 布局：scale_layout
有效区域：mask
访问策略：continuous / gather / page / sparse
缓存策略：stream / reuse / bypass
硬件收到后可以选择路径。常见高频布局走硬化 fast path；非亲和布局走可编程 reorder path；稀疏访问走 gather/scatter path；小粒度访问走 sector path；跨页访问走预取和 TLB 优化路径。

这样，搬运引擎从“几条固定高速路”变成“有导航能力的物流系统”。高速路仍然保留，常见路径仍然硬化，但新 layout 出现时，不必马上补一条全新指令，先通过可编程重排和 Tile 描述承接。

这对未来生态很重要。模型变化速度会继续高于硬件迭代速度，搬运能力必须具备一定的可编程性和自适应能力。

## 8. 小粒度访存要靠 AGU、Index/MaskGen 和 Gather 引擎接住

传统 AI 核最舒服的访存形态，是一整块连续 tensor 按 tile 搬进来。地址可以用简单的 base + stride 描述，burst 足够长，对齐足够好，搬运引擎只要持续发请求，就能把带宽吃满。这种场景像高速公路，车道宽、车流顺、出口少，系统优化的重点是让车一直跑，不要断流。

但大模型现在越来越多的访存，不再是这种形态。

KV cache、PageAttention、SparseAttention、embedding lookup、动态 mask、token routing 这些场景，数据经常不是连续的一整块，而是“按索引取一批小块”。它们的共同特点是：每次访问的数据量不大，地址之间有间隔，部分请求跨页，部分请求可以合并，部分请求要按 mask 过滤。表面看起来像随机访问，细看又不是完全随机，因为 index、page、block、sequence length、head、batch 之间往往有结构。

这类访问如果直接交给传统 DMA，会遇到一个问题：DMA 擅长搬连续块，不擅长理解 index。它能很快搬一条直路上的货，却不知道这些散在几个街区的小包裹应该怎样合单、怎样绕开空地址、怎样提前看下一页。

如果全部交给 SIMT，又会遇到另一个问题：SIMT 确实灵活，可以一条条算地址、一条条判断 mask、一条条发 load，但这样会把 SIMT 用成搬运苦力。SIMT 原本应该处理复杂控制流和不可预测逻辑，如果常见的 page lookup、sparse index、embedding gather 都让它逐条展开，寄存器、LD/ST 队列、issue 带宽很快会被地址生成和小 load 吃掉。最后 SIMT 还没开始做真正有价值的计算，就已经被碎地址淹没了。

所以这里真正要拆清楚的是三件事：地址怎么生成，哪些位置有效，请求怎么合并。

连续 DMA 把这三件事默认得太简单，SIMT 又把这三件事全交给程序去做。下一代核需要在两者中间放一组硬件：通用 AGU、Index/MaskGen 和 Gather Engine。

可以从一个简单的访存模型看这个问题。假设一次 tile 需要取 `N` 个元素，每个元素大小为 `E` 字节，理论有效数据量是：

UsefulBytes = N × E
如果这些元素连续，硬件发出的总请求量接近 `UsefulBytes`，带宽利用率自然高。可如果这些元素分散在很多 cache line 或 page 里，真实搬运量会变成：

TrafficBytes ≈ NumberOfTouchedLines × LineSize
真正的带宽效率就是：

Efficiency = UsefulBytes / TrafficBytes
问题不在 HBM 峰值，而在 `NumberOfTouchedLines` 被离散访问放大了。一个 4KB 的有效数据，如果散落在很多 128B line 里，硬件实际搬的可能远不止 4KB。再叠加 TLB miss、请求队列开销、返回乱序和同步等待，端到端代价会继续放大。

这就是为什么小粒度访存不能只说“提高带宽”。峰值带宽解决的是主干道宽度，离散访问浪费的是每个包裹进出小区的成本。真正要优化的是访问集合本身：哪些地址可以合并，哪些 line 可以复用，哪些 page 可以提前走表，哪些元素根本无效不该发请求。

AGU 负责第一步，把结构化地址展开。很多所谓离散访问，其实有规律。PageAttention 里的 page/block 映射，SparseAttention 里的 block index，embedding lookup 里的 table base 和 offset，multi-head 场景里的 batch/head/sequence 坐标，都可以被描述成多维地址生成问题。AGU 不应该只会 base + stride，它要能处理多维 stride、分段 offset、page table、block table、tile 内坐标和循环展开，把“看起来散”的访问先规整成一组结构化地址流。

Index/MaskGen 负责第二步，把有效访问筛出来。长序列里不是每个 block 都有效，sparse attention 里不是每个 token 都参与，动态 mask 里不是每个位置都应该被取。与其让 Scalar 或 SIMT 一条条判断，不如让硬件根据 length、offset、index table、predicate 和 bit mask 生成 tile 级访问集合。这样后面的 gather 引擎拿到的就不是一堆原始循环，而是一组带有效位的访问描述。

Gather Engine 负责第三步，把访问集合变成高效请求。它要看地址之间的距离，能合并相邻请求，能把同一 cache line 内的多个元素合到一次访问里，能识别跨页边界，能提前发 page walk，能把返回数据按目标 layout 装回 Tile。它不是简单 load 单元，而是一个小型的“访问整理器”。

这三者连起来，访问路径应该长这样：

Index/MaskGen 生成有效访问集合
        ↓
AGU 展开结构化地址
        ↓
Gather Engine 合并 line、处理跨页、重排返回数据
        ↓
Tile Memory Engine 交付后端可消费的 Tile
这里有一个关键边界：SIMT 仍然需要保留，但它应该兜底真正复杂的部分。比如用户自定义的特殊 score_mod、非常规 index 计算、不可预测分支、临时 fallback 路径，这些交给 SIMT 很合理。常见的 page lookup、block sparse、embedding gather、mask filtering，如果已经成为主流模型的稳定模式，就不该每次都让 SIMT 手工展开。能硬化成 AGU/Mask/Gather 的，就应该沉到硬件里；只有模式还不稳定、规则还没收敛的部分，才由 SIMT 接住。

这样分工以后，SIMT 不会被碎访存耗光，DMA 也不需要假装所有数据都是连续的。AGU 负责算路，MaskGen 负责筛货，Gather Engine 负责拼车，SIMT 负责处理那些地图上没有画出来的野路。

未来昇腾核如果只继续提高 HBM 峰值，真实模型里仍然会被小粒度访问拖住。因为长序列、稀疏化和推荐类负载的瓶颈，很多时候不是“内存不够快”，而是“有效数据太碎，硬件没有在足够早的地方把它们重新组织起来”。下一代核要把小粒度访存放进主设计指标里：短 burst 要有效率，跨页要能预取，index/mask 要能硬件生成，gather 请求要能合并，返回数据要能直接形成 Tile。

大块 DMA 解决的是高速公路，小粒度 gather 解决的是城市配送。模型越复杂，城市配送越重要。未来的核不能只修高速，也得把快递站、分拣中心和最后一公里一起设计进去。

## 9. Scalar 要从“填表员”变成乱序控制核

复杂算子里，Scalar 经常是那个最不起眼、但最容易把整条流水卡住的角色。

它要读 tiling 参数，拷贝结构体字段，拼 descriptor，算 bitfield，算地址，发搬运，设同步，敲 doorbell，轮询状态，还要处理分支。说白了，它干的已经不是“配置一下加速器”这种轻活，而是在做一个小 CPU 的工作。

问题是，它干着 CPU 的活，却没有 CPU 的身板。

复杂模型里同时活跃的状态很多：base 地址、stride、shape、offset、loop counter、mask、descriptor 片段、实际序列长度、稀疏索引、通信状态、同步 token。它们不是简单的常量，也不是靠一组 uniform register 就能兜住的东西。很多状态会随着循环、分支、动态 shape 不断变化。寄存器不够，就只能 spill；一 spill，就打 Dcache；Dcache 一 miss，CUBE、Vector、MTE 都在旁边干等。

所以 ScalarBound 的本质，不是某几条 Scalar 指令慢，而是控制复杂度已经超过了现有顺序 Scalar 能承受的范围。

未来昇腾核里的 Scalar，应该升级成真正的块级控制核。它需要更多架构寄存器，给复杂 kernel 留出足够的活跃状态空间；也需要更接近乱序 CPU 的能力，能做分支预测、寄存器重命名、Load/Store 排队、乱序发射和有序提交。它不一定要做成大 CPU，但不能再只是一个顺序配置小核。

更多架构寄存器很关键。复杂控制流里，很多东西都是动态状态，不是固定常量。uniform register 可以放一些 loop invariant，但解决不了寄存器压力的根。真正能减少 spill、减少栈访问、减少 Dcache 压力的，是更多通用架构寄存器，以及更好的寄存器重命名和调度能力。

乱序能力也很关键。Scalar 在算地址、读参数、准备 descriptor、判断分支、发 TileOP 的过程中，有不少工作可以提前做，也有不少工作可以和 memory miss 重叠。如果还是强顺序执行，一个参数 miss 就可能把后面全堵住。乱序 Scalar 至少可以把不相关的准备工作先推进，不要让 CUBE 和 Vector 等它填表。

当然，Scalar 变强不是为了让它继续填更多表。搬运和计算接口也要收敛，descriptor 要支持 base + delta，常用配置要能缓存，底层字段不要一遍遍让软件重拼。Scalar 应该负责组织 Tile 数据流、做依赖管理、处理异常和动态控制，而不是天天给各个加速器抄配置单。

一句话，下一代核不能再把 Scalar 当小秘书用。它应该是块级调度的大脑。CUBE、Vector、SIMT、MTE 都很强，但没有一个足够强的乱序 Scalar 把它们组织起来，复杂模型还是会卡在控制、参数和动态调度上。

## 10. 通信要进入 Tile 数据流

MoE、A-F 分离、长序列推理和多流融合让通信越来越频繁。过去通信更多是层间或系统层开销，现在通信静态时延可能直接进入 token 级路径。一次通信几微秒，层数多、次数多以后，会被放大成端到端延迟的大块组成。

当前很多通信行为仍像算子外部动作。doorbell 要特定通路触发，CQE 可能需要轮询，Atomic 能力在不同写 GM 通路上不一致，通信 task 和计算 task 的 profiling 难以统一关联。硬件调度系统看不清通信，也就难以自然重叠通信和计算。

未来昇腾核应该把通信抽象为 Tile Communication Operation。通信不再是旁路控制代码，而是数据流中的节点：

TPUT / TGET       点对点 Tile 传输
TGATHER / TSCATTER 稀疏或路由型通信
TBCAST            广播型通信
TATOMIC           同步和信息交换
TDOORBELL         事件通知
TWAIT_EVENT       CQE 或远端事件等待
这些操作进入 Tile 依赖图后，硬件可以知道哪个 Tile 在等远端，哪个 Tile 可以先执行，哪个通信可以和本地计算重叠，哪个异常来自本地访问，哪个异常来自远端访问。Atomic 和 doorbell 也应该具备一致的数据类型、通路和内存语义，支持多核 mailbox、生产者消费者队列、低时延同步和通信触发。

未来模型里的通信会越来越细、越来越频繁。通信如果不进入统一执行体系，就会成为调度盲区。

## 11. DFX/RAS 要和执行模型一起设计

复杂模型上线后，最怕的不是慢，而是看不清为什么慢；最怕的也不是出错，而是出错以后不知道错在哪里。异步 pipe、outstanding 请求、多流任务、远端访问、跨核通信叠在一起后，如果 PC 不准、现场保不住、错误码不细、带宽统计不准、task trace 串不起来，性能调优和问题定位都会变成猜谜。

未来昇腾核引入 Tile 级调度后，DFX/RAS 更要前置设计。Tile ROB 可以保存块级提交状态，Tile Rename Table 可以保存逻辑 Tile 到物理位置的映射，Load/Store Queue 可以保存内存访问顺序和 range，task trace ID 可以串起 CUBE、Vector、SIMT、Memory、Comm 的事件链。

异常发生时，系统应该能回答几个问题：

- 哪个 Tile 出错；
- 这个 Tile 来自哪个 task；
- 输入 Tile 和输出 Tile 的逻辑身份是什么；
- 物理存储映射是什么；
- 错误发生在本地内存、远端内存、通信路径还是执行后端；
- outstanding 请求有哪些；
- 是否能安全丢弃、重试或恢复；
- 是否存在跨核或跨 task 内存越界。生产系统需要的不只是峰值性能，还需要可解释性。未来核应该让性能数据、错误现场、内存保护、通信 trace 和功耗统计都围绕 Tile/task 统一组织。这样调优和定位才有共同语言。

## 12. 持续功耗和动态资源配比要成为架构能力

长序列、多模态和高并发推理会让 CUBE、Vector、Memory、Comm 长时间保持高利用率。短时间 benchmark 很漂亮，持续运行一段时间后触发 power cap，频率下降，TPOT 波动，客户看到的是性能不稳。

这类问题不能只靠更保守的功耗策略解决。模型不同阶段对资源的需求不同：Prefill 更吃矩阵和带宽，Decode 更吃 KV 和小粒度访存，MoE 更吃通信和路由，推荐场景更吃 SIMT 和离散访问，低 bit 场景可能让 Vector 和搬运成为主瓶颈。固定 C/V/Comm 配比和粗粒度降频会伤害真实性能。

未来昇腾核需要支持动态资源配比：

- CUBE、Vector、SIMT、Memory、Comm、uncore 独立观测；
- 分域 DVFS；
- 多档 power profile；
- AICore 启用数配置；
- Tile/task 级 QoS；
- 独立 AMU/DFX 统计；
- profiling 和功耗统计解耦；
- 长时间高负载下的性能预测模型。理想状态下，系统知道当前模型阶段在消耗什么资源，也知道该保护哪条路径、压低哪条路径。功耗控制不再像一把大锤，而像一个分区调度器。

## 13. 未来昇腾核的参考架构

综合上面的推导，未来昇腾核可以围绕“逻辑 Tile + 块级乱序 + 统一执行后端”展开。

### 13.1 前端：块控制核心

前端负责 TileOP 取指、译码、rename、依赖分析、发射和异常处理。它维护 Tile ROB、Tile Issue Queue、Tile Rename Table、Tile Load/Store Queue 和 task trace。Scalar 能力仍然保留，但主要服务块级控制，而非大量低层字段拼装。

### 13.2 数据承载：Tile Register 体系

Tile Register 是未来核的中心数据对象。它可以承载矩阵 tile、向量 tile、mask tile、scale tile、低 bit packed tile、稀疏索引 tile。硬件负责逻辑 Tile 到物理 SRAM、寄存器堆、局部 buffer 的映射，支持 ready 状态、重命名、生命周期和异常 dump。

### 13.3 执行后端：CUBE、Vector、SIMT 统一消费 Tile

CUBE 执行矩阵类 TileOP，Vector 执行 elementwise/reduce/transform 类 TileOP，SIMT 执行动态控制流、离散访问和 mask 生成类 TileOP。三者通过 Tile Register 交接数据，减少显式 buffer 搬运和同步。

### 13.4 内存后端：Tile Memory Engine

Tile Memory Engine 负责 TLOAD/TSTORE、layout reorder、unpack、scale 对齐、gather/scatter、跨页访问、sector cache、TLB 预取和 memory QoS。它采用消费者视角接口，由目标 Tile 描述驱动实际路径选择。

### 13.5 通信后端：Tile Communication Engine

通信后端处理 TPUT/TGET/TGATHER/TSCATTER/TATOMIC/TDOORBELL/TWAIT_EVENT，让通信、同步和事件通知进入 Tile 数据流，并与 task trace、异常上报和 profiling 统一关联。

### 13.6 DFX/RAS：基于 Tile 的精确状态

Tile ROB、Tile Rename Table、Memory Queue、task trace、range protection、错误码和上下文 dump 共同组成生产可观测能力。未来核的 DFX 不应该只记录 pipe 计数器，还应该记录数据流状态。

## 14. 软件生态形态：稳定 Tile 接口，保留高效专用路径

未来架构不能要求开发者直接面对更复杂的硬件。硬件内部引入 Tile 级调度后，软件接口反而应该更稳定、更清晰。

建议形成一层稳定的 Tile 编程接口。它表达 shape、dtype、layout、scale、mask、memory policy、execution hint 和 dependency，而不直接暴露每一级物理 buffer。高性能库可以围绕这层接口做模板推导和手写优化，编译器可以围绕这层接口做调度、路径选择和资源分配。

这层接口需要兼容两类路径。常见 GEMM、BMM、标准 Attention、常见 low-bit layout 仍然走硬化 fast path，保证峰值和能效；新 layout、新稀疏模式、新动态 mask 可以先走可编程 Tile path，保证功能和性能下限。随着场景稳定，再把高频路径硬化。

这样既保护现有生态，又给未来模型变化留出空间。

## 15. 训练和推理：统一核心架构，资源配比差异化

未来昇腾核不宜在训练和推理上形成两套割裂的核心结构。训练和推理确实有不同瓶颈：训练更看重大规模矩阵、通信 goodput、稳定性和恢复能力；推理更看重低时延、KV cache、小粒度访存、低 bit、MoE、采样和通信静态开销。但如果核心编程模型、Tile 接口、执行后端和调度体系分裂，软件生态成本会非常高。

更合理的路线是统一核心架构，通过 SKU 和 profile 做资源配比差异化。训练优先型号可以强化 CUBE、HBM、scale-out 通信、RAS 和 checkpoint 相关能力；推理优先型号可以强化 SIMT、小粒度访存、SRAM/KV、低 bit、communication latency 和功耗 profile。核心 Tile 数据流、Tile Register、Tile Memory、Tile Communication 和 DFX 体系保持一致。

生态连续性是昇腾未来竞争力的一部分。硬件可以分 SKU，软件心智不能分裂。

## 16. 结论

昇腾当前遇到的问题，已经不能简单归结为某个单元算力不够、某条通路带宽不够、某条指令还不完备。真要这么简单，大家早就把表格拉出来，哪个弱补哪个，年底再贴一张“全面提升”的胶片，问题就算闭环了。可惜架构这东西，从来不是 Excel 里把短板涂红就能解决的。

真正的矛盾来自模型形态变化之后，数据流变得更碎、更动态、更低精度、更依赖通信、更依赖小算子和不规则访存，而现有核仍然主要依赖显式 buffer、固定流水和软件手工编排来组织这些工作。于是我们就进入了一种很熟悉的状态：CUBE 说我已经很努力了，Vector 说你算完倒是把数据给我啊，MTE 说我也想搬但参数有点多，Scalar 说别吵我还在拼 descriptor，SIMT 说我能处理复杂场景但别指望我一夜之间变成 GPU，DFX 在角落里默默补一句：你们先跑，挂了以后记得别问我现场去哪了。

这当然是玩笑话，但玩笑背后就是现实。计算单元各自都不弱，弱在交接；片上存储不是不丰富，难在管理；低 bit 不是没有峰值，痛在全链路；SIMT 不是没有能力，缺在成为主路径；通信不是不能做，问题在于它越来越像模型数据流的一部分，却还带着外部控制动作的影子。过去靠专家手工把这些东西拧在一起，像老师傅开手动挡赛车，听发动机声音就知道该不该换挡；未来客户越来越多、模型越来越多、shape 越来越野，再指望每个算子都由绝地武士亲自调原力，显然不太现实。绝地武士也要休假，牛马也想准点下班。

因此，未来昇腾核的核心方向，应当从矩阵峰值转向复杂模型的数据流效率。这个方向包含几个关键判断：逻辑 Tile 要成为统一数据对象；片上存储要向 Tile Register 体系演进；CUBE、Vector、SIMT 要成为统一 Tile 的执行后端；搬运引擎要从固定 DMA 升级为消费者视角的 Tile Memory Engine；低 bit 要作为端到端数据流设计；SIMT 要成为不规则模型主路径；通信、Atomic、Doorbell、CQE 要进入 Tile 数据流；DFX/RAS 要基于 Tile 精确状态内建；功耗和资源配比要支持模型阶段动态调节。

如果说过去的昇腾核是一台高效的矩阵机器，未来昇腾核应该成为一台面向大模型的 Tile 数据流机器。它仍然要保留 NPU 的高能效矩阵能力，毕竟发动机不能丢；但它还要长出更好的变速箱、更顺的传动轴、更聪明的导航、更清晰的仪表盘，以及出问题以后能告诉你“刚才到底是谁在第几个路口压了线”的行车记录仪。块级乱序、统一数据承载、可编程重排、SIMT 并发、通信事件化和生产可观测能力，本质上都是为了让这台机器不再只会在理想赛道上跑 peak，而是能在真实道路上跑业务。

架构做到最后，最好的状态应该是：高手仍然有空间把性能压到 Speed of Light，普通工程师也能在不献祭周末的情况下写出靠谱代码；硬件底层足够强，软件抽象也接得住；客户想看底层时看得明白，不想看底层时也不用被迫考古。到那个时候，我们再讲 PTO、Tile、下一代核，就不用像推销一份复杂说明书，而可以更有底气地说：这不是包皮，也剪不掉，这是硬件真的开始理解数据流了。

这会是下一代昇腾核架构最重要的方向。至于我们这些菊场牛马，愿望也很简单：少解释几遍 atomic，少抢救几个挂死，多让模型自己跑满。真到那一天，哪怕韬定理继续在天上飞，我们在地上拧螺丝的人，也算终于把这辆车从“手动挡性能怪兽”，慢慢调成了一台普通人也敢开、高手还能飙的好车。
