### 1. ISA 的定位——计算机体系的「顶层契约」

#### 1.1 ISA 是什么？

ISA(Instruction Set Architecture, 指令集架构)是一个处理器的可编程接口（Programmable Interface），定义了软件（如编译器、汇编程序员）与硬件的交互规范。在软件的视角下，ISA 告诉了它硬件能做什么（如指令操作类型、GPR、数据类型、内存模型、寻址方式等）；在硬件视角下，ISA 是自己必须实现的功能规范。说人话就是，ISA 是软件和硬件的共同语言。有了 ISA，软件可以向下将代码拆解成硬件能看懂的指令，硬件则组织各电子元件向上履行对软件的承诺（所以 ISA 是软件和硬件双向奔赴的终点，笑）。

那么 ISA 定义了什么呢？

- 指令格式：每条指令的位宽、操作码（opcode）字段、操作数字段（operand）等的布局和编码方式
- 指令操作类型：如算术运算、逻辑运算、移位、比较、跳转、load/store、分支操作、特殊函数等
- 指令数据类型：整数和浮点数位宽（如 / 位等）
- 寻址方式：定义操作数如何被定位。例如寄存器寻址、立即数寻址、直接寻址、间接寻址、基址寻址、变址寻址、相对寻址等
- 寄存器堆：通用寄存器（GPR）的数量、名称、位宽、用途等。特殊寄存器（如 PC、exec mask、状态寄存器等）。
- 内存模型：地址空间大小、对齐要求、内是否保证多核顺序一致性、是否提供显式屏障指令
- 控制流机制：条件与无条件跳转指令、函数调用与返回机制
- ……

#### 1.2 ISA 不是什么？

ISA 只定义了硬件能做什么，但没有规定它怎么做；ISA 只定义了软件能用什么，但没规定它怎么用——凡是不影响程序正确性的实现细节，它一概不管。

- ISA 不是微架构
ISA 和微架构是“规范”和“实现”的关系。举个例子：ISA 只规定“硬件要支持单精度浮点加法运算”，而具体的实现方案是微架构要关注的事情：用几级流水线、gpr 带宽设置为多少、顺序执行还是乱序执行、单发射还是多发射……

实际上，硬件只要做到“支持单精度浮点加法运算”就已经满足 ISA 的要求，后面那一堆实现细节只是特定微架构下关于 PPA 的 trade-off。

2. ISA 不是硬件本身

ISA 是处理器的设计蓝图、是一种抽象概念；而硬件是实现宏伟蓝图的物理实体。那什么叫“ISA 不是硬件本身”呢？

举个例子：ISA 要求支持 64 位的整数加法指令，那硬件就必须有 64 位的 ALU 吗？非也，用一个 32 位 ALU 分别对高 32bit 和低 32bit 进行加法，并对结果进行拼装（当然还要考虑 carry bit），仍然可以实现 64bit 的整数加法。

再举例：ISA 规定了要使用 100 个 GPR，那硬件就必须用 100 个 GPR 吗？非也。如果你只有 90 个寄存器可以吗？可以！虽然不常见，但硬件也可以通过透明的内存溢出来模拟更多寄存器，但这通常会带来巨大的性能惩罚。那硬件超出 100 个 GPR 可以吗？也可以！实际上，多线程、register renaming 都需要用到比 ISA 规定的多的 gpr 数量。

3. ISA 不是编译器优化策略

ISA 为编译器提供了“武器库”，但如何组合使用这些武器以达到最优，是编译器的职责，ISA 本身不规定这些策略。

### 2. 微架构的定位——ISA 的实现

#### 2.1 微架构是什么？

维基百科上的定义很简单：

<strong>In electronics, computer science and computer engineering, microarchitecture</strong>, also called <strong>computer organization</strong>and sometimes abbreviated as <strong>μarch</strong>or <strong>uarch</strong>, is the way a given instruction set architecture(ISA) is implemented in a particular processor.<span class="wikilink wikilink--missing" title="未导入的页面">1</span>(https://link.zhihu.com/?target=https%3A//en.wikipedia.org/wiki/Microarchitecture%23cite_note-1)微架构（Microarchitecture, uarch）是在特定处理器上，对给定 ISA 的实现方式。即，它是处理器内部的硬件组织方式与实现细节，是在 ISA 规范约束下，为实现指令功能、提升 PPA 而设计的具体硬件架构，包括流水线、执行单元、缓存、调度器、寄存器堆等模块的组织与交互逻辑。

微架构必须保证 ISA 规定的功能实现正确，但对实现的方式有绝对的自由度。它与 ISA 的关键区别在于，它是软件不可见的，因为软件无需关心实现方式。这保证了同一份软件能在同一 ISA 的不同微架构实现上正确运行。

那么微架构包含哪些内容？

- 指令 pipeline：比如经典的 cpu 5 级流水线（取值-译码-执行-访存-写回）。
- 指令调度器：决定哪条指令、在什么时刻、去哪个功能单元执行，基于数据冒险状态最大化指令吞吐量
- 译码单元：解析指令，分析这条指令要做什么（操作码、操作数、数据类型、寻址方式等）
- 运算执行模块：如 ALU、FPU、SFU、访存单元（执行 LD/ST）、向量单元（SIMD/SIMT 支持）
- 存储层次模块：包括寄存器堆、L1/L2/L3 缓存、内存接口。用于暂存指令、数据，减少访存延迟——需匹配 ISA 的内存模型。（不过有的 ISA 扩展指令也会暴露存储层次模块给软件，所以这条不绝对）
- 状态管理模块：负责架构状态的暂存、更新与一致性维护（如 ROB 重排序缓冲区、寄存器重命名表）—— 保证乱序执行时，架构状态更新符合 ISA 规则。

#### 2.2 微架构设计的核心目标：PPA 的 trade-off

其实上文已经提到了，微架构就是在 ISA 约束下，权衡 “性能 - 能效 - 面积”。

- 性能：通过流水线、乱序执行、指令融合、缓存优化等手段，提升指令执行吞吐量、降低延迟
- 能效：在保证性能的前提下，减少硬件功耗（如精简流水线级数、动态关闭闲置执行单元）
- 面积：控制硬件资源开销（如寄存器数量、访存带宽、缓存大小、执行单元数量），降低芯片制造成本

### 3. 有限状态机视角下的 ISA 与微架构

如果我们跳出具体细节，将处理器视为一个黑盒，那么其行为可以抽象为一个巨大的、确定性的有限状态机（FSM）。每个时钟周期，它读取当前状态（和输入（指令），并输出新状态和可能的输出。只不过，ISA 管理的状态是架构状态（Architectural State）、而微架构管理的状态是微架构状态（Uarch State）。

#### 3.1 架构状态

架构状态是 ISA 明确规定的、软件可见/可修改的处理器状态的集合，是程序执行的唯一合法状态载体。

架构状态包括：

- 通用寄存器：软件可以通过指令访问修改 GPR 的值
- 程序计数器（PC）：顺序指令执行后，PC 自动+1；分支指令执行后，更新为目标指令的地址
- 内存状态：通过访存指令访问修改内存
- 特殊寄存器：如 SIMT 的 exec mask 寄存器，通过控制流指令更新
架构状态有 3 个重要属性：

- 软件可见性
- 语义确定性：已知当前的架构状态，执行一个特定指令，必然能得到固定的下一个架构状态
- 兼容性：不同的微架构，只要遵循同一个 ISA，那么其架构状态和更新规则完全一致

#### 3.2 微架构状态

微架构状态是微架构为提升性能、降低功耗而设计的、软件不可见的硬件内部状态。它是实现 “硬件优化不影响软件兼容性” 的核心手段。

微架构状态包括：

- 流水线控制类状态：流水线各级的控制信号、指令的 “就绪 / 执行 / 完成” 状态标记
- 执行优化类状态：重排序缓冲区（ROB）、保留站（Reservation Station）、物理寄存器堆
- 预测优化类状态：分支预测器的 BTB（分支目标缓冲区）、RAS（返回地址栈）
- 存储优化类状态：缓存的标签阵列、脏位、有效位；TLB（快表）的页表映射
对应的微架构也有 3 个重要属性：

- 软件不可见（注：虽然在功能规范上不可见，但通过侧信道（Side Channel）（如 Spectre/Meltdown 漏洞），恶意软件实际上是可以探测到缓存、分支预测器等微架构状态的。这也是现代微架构设计面临的新挑战。）
- 优化导向性：微架构状态的唯一目的是提升硬件性能或能效，不影响程序的最终执行结果
- 设计灵活性<strong>：</strong>同一 ISA 对应的不同微架构，其微架构状态的设计可以完全不同—— 这是微架构的创新空间
架构状态和微架构状态的关系，可一言以蔽之：<strong>微架构通过维护复杂的“微架构状态”，来加速“架构状态”的合法转移。</strong>

#### 3.3 对 ISA 和微架构的新认知

在有限状态机的视角下， ISA 和微架构的联系与区别将变得豁然开朗：

- ISA 定义了“宏观的状态跳变”：它规定了一条指令执行后，系统状态（如 GPR、PC、内存）应该如何从 State A 演变为 State B。
- 微架构实现了“微观的状态路径”：为了从 State A 高效地到达 State B，微架构在内部构建了多个中间状态（如流水线寄存器、ROB 条目）。
- 兼容性的本质就是：不同微架构，只要它们实现的 FSM 与 ISA 定义的 FSM 在“架构状态转移”行为完全等价，它们就是兼容的。

#### 4 总结

总的来说，ISA 是“做什么”的规范，微架构是“如何做”的工程<strong>。</strong> 两者之间由“架构状态”这一抽象边界清晰地划分开来，而微架构的所有魔法，都发生在边界之内。有了这个基本框架，我们便获得了一把解剖处理器的解剖刀。接下来，是时候深入微架构设计的殿堂了。
