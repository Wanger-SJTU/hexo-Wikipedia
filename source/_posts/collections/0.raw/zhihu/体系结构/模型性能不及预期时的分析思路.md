在 AI Infra 的日常工作中，”模型跑起来了，但是慢”是最常见也最棘手的问题之一。它不像功能 Bug 那样有明确的报错信息，也不像 OOM 那样有清晰的边界。耗时不及预期的背后，可能是 CPU 瓶颈、内存拷贝、算子效率低下、显存带宽打满等多种原因的叠加。

本文分享一套**从硬件到软件、从宏观到微观、从端到端到单算子**的系统化分析方法论。

### 第零步：读懂硬件 —— 在写下第一行 Profile 命令之前

很多人拿到性能问题就急于上工具。但有经验的工程师，**看到硬件参数的第一秒就能大致判断瓶颈方向**。这不是直觉，而是对硬件特性的深刻理解。

#### 0.1 核心问题：这块卡是”带宽型”还是”算力型”？

每款 GPU 都有两个关键指标：

- **峰值算力（Peak FLOPS）**：每秒能完成多少次浮点运算
- **峰值显存带宽（Peak Memory Bandwidth）**：每秒能搬运多少字节
两者之比决定了硬件的**算术强度平衡点（Arithmetic Intensity Balance Point）**：

`Balance Point = Peak FLOPS / Peak Bandwidth  (单位：FLOPs/Byte)`

以几款典型卡为例：

GPUFP16 Tensor 算力显存带宽平衡点 (FLOPs/Byte)特征A100 SXM312 TFLOPS2.0 TB/s~156相对均衡H100 SXM989 TFLOPS3.35 TB/s~295算力增长远超带宽，更易带宽受限H20148 TFLOPS4.0 TB/s~37典型带宽型卡，专为推理设计B2002250 TFLOPS (FP4)8.0 TB/s~281算力爆炸式增长，带宽压力更大**这意味着什么？**

- 在 H100 上，一个算子的算术强度低于 295 FLOPs/Byte 就会是带宽受限的。而同样的算子在 A100 上（平衡点 ~156）可能是计算受限的。**同一份代码在不同硬件上的瓶颈类型可能完全不同。**
- 从 A100 到 H100，算力涨了 3 倍，带宽只涨了 1.7 倍。这意味着**带宽受限的算子在新硬件上的加速比远低于计算受限的算子**。如果你的模型以 Memory-Bound 算子为主（如 LLM 的 Decode 阶段），换到更贵的卡时加速比可能令人失望——这不是你的代码有问题，而是硬件特性决定的。

#### 0.2 浮点精度支持：不只是”能不能用”，而是”用了差多少”

现代 GPU 对不同精度的支持差异巨大，这直接影响优化策略的选择：

精度A100H100H20说明FP3219.5 TFLOPS67 TFLOPS74 TFLOPS传统精度，算力最低TF32 (TensorCore)156 TFLOPS495 TFLOPS—GEMM 默认走此路径FP16/BF16 (TensorCore)312 TFLOPS989 TFLOPS148 TFLOPS主流训练/推理精度FP8 (TensorCore)不支持1979 TFLOPS296 TFLOPSH100 新增，算力翻倍INT8 (TensorCore)624 TOPS1979 TOPS296 TOPS推理量化常用**关键判断**：

- **FP16 → FP8 的收益是否值得？** 在 H100 上，FP8 算力是 FP16 的 2 倍。如果你的 GEMM 已经 Compute-Bound，切换到 FP8 理论上可以直接获得接近 2x 加速。但如果是 Memory-Bound（如 Decode 阶段的小 Batch GEMM），算力翻倍并无帮助，因为瓶颈在带宽——此时 FP8 的收益主要来自数据量减半带来的带宽节省。
- **TensorCore 是否被正确使用？** 如果你的矩阵维度不是 8⁄16 的倍数，可能会回退到 CUDA Core 路径，算力直接缩水一个数量级。NCU 中看到 `sm__pipe_tensor_op_hmma` 利用率为 0 就说明 TensorCore 没有被用上。
- **某些卡有明确的”偏科”**：H20 的显存带宽（4.0 TB/s）甚至超过 H100（3.35 TB/s），但 FP16 算力只有 H100 的 15%。这张卡就是为 LLM 推理 Decode 阶段的带宽受限场景量身定制的。如果你在 H20 上做大 Batch 训练的 Prefill，那就是用错了卡。

#### 0.3 先算后测：一秒钟估算理论耗时

有经验的工程师在跑 profile 之前，会先做一个”信封背面计算”：

**示例：估算一次 GEMM（M=4096, N=4096, K=4096, FP16）在 H100 上的理论耗时**

`FLOPs = 2 × M × N × K = 2 × 4096³ ≈ 137.4 GFLOPS

计算受限耗时 = FLOPs / Peak_FLOPS = 137.4G / 989T ≈ 0.139 ms
数据量 = (M×K + K×N + M×N) × 2 Bytes ≈ 96 MB
带宽受限耗时 = Data / Peak_BW = 96M / 3.35T ≈ 0.029 ms

算术强度 = 137.4G / 96M ≈ 1431 FLOPs/Byte >> 295 (平衡点)
→ 计算受限，理论耗时 ≈ 0.139 ms`

如果实测耗时是 0.15 ms，说明已经非常接近理论上限，优化空间有限。如果是 0.5 ms，那中间 3x 的差距就是你需要追查的目标。

**这个”先算后测”的习惯至关重要** ——它让你在拿到 profile 数据之前就有了预期，知道什么是”正常”，什么是”异常”。

### 第一步：端到端 Profiling —— 用 Nsight Systems 建立全局视野

性能分析的第一原则是：**先看全貌，再看局部**。过早地钻入某个算子的性能细节，往往会”只见树木，不见森林”。

Nsight Systems (nsys) 是这个阶段的核心工具。它提供了 CPU 与 GPU 活动的**时间线视图**，让你能一眼看到整个推理/训练过程中时间都花在了哪里。

#### 1.1 关注 GPU Bubbles（气泡）

GPU Bubble 指的是 GPU 处于空闲状态的时间段。在 nsys 的 Timeline 视图中，它表现为 GPU 行上的**空白区域**。

常见的 Bubble 成因：

成因典型表现排查方向CPU-bound LaunchGPU 等待 CPU 发射 kernelCPU 侧函数调用耗时过长，Python GIL，数据预处理未异步同步操作cudaDeviceSynchronize 或隐式同步避免不必要的 .item()、.cpu()、print(tensor)数据搬运阻塞H2D/D2H 拷贝与计算串行未使用 CUDA Streams 做 overlap，或 pinned memory 未启用通信等待多卡场景下 AllReduce/AllGather 前后的空白计算与通信未做流水线 overlap（如 TP/PP 编排问题）**实践建议**：采集 profile 时，先跑几个 warmup iteration，再开始录制，避免 CUDA context 初始化、JIT 编译等噪声干扰。

`nsys profile --delay=10 --duration=30 \
    --trace=cuda,nvtx,osrt \
    --output=model_profile \
    python run_inference.py`

#### 1.2 审查 CPU 调用链

nsys 不仅看 GPU，CPU 侧的调用栈同样关键。常见的 CPU 侧陷阱：

- **数据预处理**：Tokenizer、Image Transform 等占用大量 CPU 时间，导致 GPU “喂不饱”
- **Python 开销**：动态 shape 推导、过多的 Python 层调用（尤其是未编译的 eager 模式）
- **框架调度**：PyTorch 的 dispatcher 开销在小算子密集场景下不可忽视

#### 1.3 内存拷贝分析

在 nsys 中筛选 `memcpy` 和 `memset` 事件，重点关注：

- **H2D（Host to Device）拷贝频率与大小**：是否存在频繁的小块拷贝？能否合并？
- **D2H 拷贝是否在关键路径上**：是否有不必要的数据从 GPU 搬回 CPU？
- **Pageable vs Pinned Memory**：未使用 `pin_memory()` 的拷贝会走 pageable 路径，带宽大幅下降

#### 1.4 针对 Bubble 的优化手段

定位到 Bubble 之后，以下是一系列行之有效的优化方法：

#### CUDA Graph：消灭 CPU Launch 开销

当你在 nsys 中看到大量短小的 kernel 之间存在规律性的间隙，这往往是 CPU 端逐个发射 kernel 的开销。**CUDA Graph** 将一系列 GPU 操作（kernel launch、memcpy 等）录制为一张静态图，之后每次推理只需一次 launch 即可重放整张图，将 CPU 侧的发射开销从”每个 kernel 一次”降低为”整张图一次”。

`# PyTorch 中使用 CUDA Graph
static_input = torch.randn(batch_size, seq_len, hidden, device='cuda')
static_output = torch.zeros_like(static_input)

# 录制
g = torch.cuda.CUDAGraph()
with torch.cuda.graph(g):
    static_output = model(static_input)

# 重放（极低开销）
static_input.copy_(real_input)
g.replay()`

**适用场景**：输入 shape 固定、计算图不变的推理场景（如 LLM Decode 阶段）。动态 shape 或含控制流的场景需要额外处理。

**效果**：在小 Batch 推理等 CPU-bound 场景下，CUDA Graph 可以带来 **2x~5x** 的吞吐提升，因为它几乎完全消除了 kernel launch 间的 CPU 开销。

#### torch.compile：让编译器帮你做融合和优化

`torch.compile` 是 PyTorch 2.0+ 的核心优化手段，它通过 Dynamo 追踪 + Inductor 后端编译，自动完成：

- **算子融合**：将多个 element-wise 算子融合为一个 kernel，减少显存读写
- **内存规划优化**：减少中间 tensor 的分配
- **自动选择最优 kernel 实现**
`model = torch.compile(model, mode="max-autotune")`

在 nsys 中，编译后的模型表现为：kernel 数量显著减少、Bubble 减少、单个 kernel 做了更多的事情。

#### 数据加载流水线化

如果 Bubble 出现在 iteration 边界（一个 step 结束到下一个 step 开始之间），往往是数据加载的问题：

`dataloader = DataLoader(
    dataset,
    batch_size=32,
    num_workers=8,        # 多进程预取
    pin_memory=True,      # 使用 pinned memory 加速 H2D
    prefetch_factor=2,    # 每个 worker 预取 2 个 batch
    persistent_workers=True  # 避免反复创建进程
)`

#### 计算与通信 Overlap

在多卡训练/推理场景中，如果 AllReduce 和 GEMM 完全串行，可以通过以下方式实现重叠：

- **Tensor Parallel**：将 AllReduce 拆分为 ReduceScatter + AllGather，与下一层的计算 overlap
- **Pipeline Parallel**：合理编排 micro-batch 的前向/反向，使不同 stage 的计算和通信交错
- **DeepSpeed ZeRO / FSDP**：参数的 AllGather 与当前层的计算 overlap

### 第二步：定位热点算子 —— 从 nsys 过渡到 NCU

当通过 nsys 确认瓶颈确实在 GPU 计算侧（而非 CPU 或数据搬运），下一步就是用 **Nsight Compute (NCU)** 深入分析具体 kernel 的性能。

#### 2.1 识别 Top-N 热点 Kernel

从 nsys 的统计视图中，按**累计耗时**排序，找出占比最高的 kernel。典型的热点包括：

- GEMM 类（矩阵乘法）：`ampere_*gemm*`、`cutlass::*`
- Attention 类：`flash_attn_*`、`mem_efficient_attention_*`
- Element-wise 类：`vectorized_elementwise_kernel`
- 归约类：`reduce_kernel`、LayerNorm、Softmax

#### 2.2 使用 NCU 采集单 Kernel 数据

`ncu --set full \
    --kernel-name "regex:gemm" \
    --launch-skip 100 --launch-count 10 \
    --output gemm_analysis \
    python run_inference.py`

NCU 会给出极其详尽的 kernel 级数据，包括但不限于：

- **SM 利用率 (Compute Throughput)**
- **显存带宽利用率 (Memory Throughput)**
- **L1/L2 Cache 命中率**
- **Warp 占用率 (Occupancy)**
- **指令吞吐与 Pipeline 利用率**
当然，很多大厂的服务器卡上没有给工程师root权限，而没有root权限是无法使用ncu的。在这种情况下，我们可以自行计算roofline

### 第二步半：AI 驱动的 Kernel 优化 —— 让机器替你做实验

传统的 kernel 优化是一项极其依赖专家经验的手艺活：调 Tile Size、选访存模式、排列 Shared Memory Layout、处理 Bank Conflict……每一次修改都要手动编写、编译、profiling、记录、对比。一个资深 CUDA 工程师优化一个关键 kernel 可能需要数天甚至数周。

**但这个局面正在被 AI 彻底改变。**

#### 2.5.1 为什么 Kernel 优化特别适合 AI 介入？

Kernel 优化具备几个天然适合 AI 自动化的特征：

- **评价函数明确**：耗时（ms）、带宽利用率（%）、算力利用率（%）——不需要人类主观判断”好不好”，跑个 benchmark 就有确定性结论
- **搜索空间有界但庞大**：Tile 维度、Warp 数量、流水线深度、向量化宽度……组合爆炸式增长，人类凭直觉只能覆盖极小子集，而 AI 可以系统性地探索
- **反馈循环极短**：写一版 kernel → 编译 → 跑 100 次取均值 → 得到结果，整个循环可能只需要几十秒，天然适合自动化迭代
- **知识可迁移**：Triton / CUDA 的优化 pattern 是有规律可循的，AI 可以从大量公开的高性能 kernel 实现中学习到这些 pattern

#### 2.5.2 Auto-Research 范式：自动实验 + 自动记录

借鉴 Auto-Research 的思想，可以构建一套”AI 自动做实验”的 kernel 优化流水线：

### 第三步：Roofline Model —— 定性判断算子瓶颈类型

拿到 NCU 数据后，很多人会面对几十个 metrics 不知从何下手。**Roofline Model 是将这些数据转化为可操作结论的关键框架。**

#### 3.1 Roofline 模型核心思想

Roofline 模型将每个 kernel 的性能放在一个二维空间中分析：

`Performance          ┌─────────── Compute Bound ───────────
(FLOPS)              │          ╱ (计算天花板)
                     │        ╱
                     │      ╱
                     │    ╱
                     │  ╱  ← Roofline (理论上限)
                     │╱
                     ├──────────────────────────────────────
                     Memory Bound
                     (带宽天花板)
                     └──────────────────────────────────────→
                        Arithmetic Intensity (FLOPs/Byte)`

- **横轴**：算术强度（Arithmetic Intensity）= FLOPs / Bytes Accessed
- **纵轴**：实际达到的算力（FLOPS/s）
- **屋顶线**：由硬件的**峰值算力**和**峰值带宽**共同决定
这也是为什么第零步”读懂硬件”至关重要——**Roofline 的形状完全由硬件参数决定**。同一个算子在 H20（低平衡点）和 H100（高平衡点）上画出的 Roofline 形状截然不同，瓶颈判断也可能完全相反。

#### 3.2 两类瓶颈及优化方向

**Memory-Bound（带宽受限）**：算子落在 Roofline 的斜坡区域

- 优化方向：  

- **算子融合（Kernel Fusion）**：减少中间结果的显存读写，如将 Bias + GeLU + Dropout 融合
- **减少数据搬运**：使用更低精度（FP16/BF16/FP8）降低带宽需求
- **提高 Cache 命中**：优化数据布局和访存模式
- **量化（Quantization）**：将权重/激活从 FP16 量化到 INT8/FP8/INT4，直接减少显存访问量，对带宽受限算子效果尤为显著

**

Compute-Bound（计算受限）**：算子落在 Roofline 的平坦区域

- 优化方向：  

- **选择最优 Tile 策略**：确保 GEMM 使用了合适的 TensorCore 路径
- **使用更低精度**：FP16 → INT8/FP8 可直接翻倍算力上限。在这一环节你会发现，不同的推理框架对于不同精度的数据类型的开发程度天差地别。比如triton的bf16做得非常好，fp8则一言难尽，这里面有一些门道，可以多多了解
- **调整 Batch Size / Sequence Length**：让矩阵维度更适合硬件分块

**

#### 3.3 NCU 中的 Roofline 视图

NCU 内置了 Roofline 分析（`--set roofline`），可以直接在图形界面中看到每个 kernel 距离理论上限的差距：

`ncu --set roofline \
    --kernel-name "regex:gemm|layernorm|softmax" \
    --launch-skip 100 --launch-count 5 \
    python run_inference.py`

关键看点**：

- kernel 的点离屋顶线有多远？差距就是优化空间
- 是在斜坡段还是平顶段？决定了优化方向
- 与不同精度的 roofline 对比，判断是否选错了精度

#### 实战心法

**1. 先读卡，再跑 Profile。** 花一分钟看硬件 spec，算出平衡点和理论耗时。这决定了你后续所有分析的参照系。在一张 H20 上追求 GEMM 的算力利用率是缘木求鱼，在一张 H100 上纠结小算子的带宽利用率同样可能是抓小放大。

**2. 关注”最大的一块”，而非”最差的一块”。** 一个 Occupancy 只有 25% 但总耗时仅 0.1ms 的 kernel，远不如一个 Occupancy 80% 但总耗时 50ms 的 GEMM 值得优化。Amdahl 定律永远成立。

**3. 优化是一个迭代过程。** 解决了一个瓶颈，新的瓶颈会浮现。每轮优化后重新跑 nsys，确认全局分布的变化。

**4. 建立 Baseline 意识。** 动手优化之前，先搞清楚理论上限是多少。用 Roofline 模型计算出算子的理论最优耗时，如果实际值已经达到理论上限的 80% 以上，继续压榨的 ROI 极低，应该把精力放在其他地方。

**5. 不要忽视 CPU 和 I/O。** 实践中，大量”模型慢”的问题根因不在 GPU 上。DataLoader 的 `num_workers`、`pin_memory`、数据预处理逻辑，这些”看起来不够高级”的地方，往往是最大的 low-hanging fruit。

**6. 善用 AI 做 kernel 级优化。** 不要闷头手调 Tile Size 到凌晨三点。把 NCU 数据喂给 AI，让它自动生成变体、跑 benchmark、写实验文档。你要做的是审阅实验报告、判断方向、决定何时收手。这不是偷懒，这是把人类最宝贵的判断力用在刀刃上。

**一句话总结：读硬件定预期，nsys 定方向，NCU 定瓶颈，Roofline 定策略，AI 跑实验。五步下去，模型耗时的问题基本无处遁形。**
