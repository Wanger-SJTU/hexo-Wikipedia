一、FTL架构与模块划分

### 1.1 FTL整体架构

UFS设备使用NAND闪存，其物理特性决定了FTL必须解决以下核心矛盾：

物理特性导致的限制需要FTL解决的问题写前擦除不能覆盖写，只能先擦除整个块（Block）再按页（Page）写入逻辑地址与物理地址解耦，通过映射表实现异地更新擦除次数有限TLC约1000-3000次，QLC更低，超过后块损坏磨损均衡，让所有块擦除次数接近读干扰读一个块会轻微改变邻近页的电荷，累积导致比特翻转定期刷新被频繁读的块数据保留错误长时间存放后电荷泄漏，尤其高温下定期刷新老数据，使用ECC/RAIN页编程错误/读错误写操作可能失败，读可能出现不可纠错误（UECC）RAIN恢复SLC/TLC/QLC模式差异SLC可靠性高、速度快但容量小；QLC相反混合使用，热数据放SLC，冷数据放QLC基于上述约束，FTL分为以下逻辑层，每层解决一类物理问题：

                   主机接口层（UFS协议）
                            │
                       映射管理层
        逻辑到物理转换、大容量页表内存占用、高性能查询
                            │
                   资源回收与损耗均衡层
         写前擦除、擦除次数不均（GC + Wear Leveling）
                            │
                        数据保鲜层
            读干扰、数据保留错误（Refresh + Scan）
                            │
                      持久化与恢复层
 断电后映射表重建、元数据一致性（Checkpoint + Power中断处理）

### 1.2 模块项目划分

每个模块的引入都是为了解决一个具体的NAND物理问题，以下按功能域组织进行分组。

## 1. 映射与元数据管理模块


模块解决的物理问题方案概述PPT分层映射1TB UFS需要2GB DRAM存储L2P表，片上SRAM/DRAM不足引入页表，按需换入缓存Journal Management (JM)每次写操作都更新闪存中的PPT表会极大放大写入量使用Journal Buffer记录增量映射，批量回写；
为加快访问和回写速度，引入DPT标记脏PPT region，引入 Journal List组织同一PPT region内的更新操作；LCM (L2P Cache Management)一级PPT粒度小(4MB)，二级PPT粒度大(4GB)，固定缓存分配无法适应混合读写共享缓存池，自适应调整：大范围读多给二级PPT，小范围随机读多给一级PPTData Cache即使L2P命中，每次读仍需访问闪存（数十微秒），热点数据延迟高在SRAM中缓存最近访问的用户数据，命中的读延迟降至纳秒级Checkpoint断电后需重放整个Journal才能重建映射，恢复时间过长定期将干净PPT表和Journal状态保存为检查点，断电后从最近检查点+少量Journal恢复2. 垃圾回收（GC）及其变体

GC的核心问题：闪存写前必须擦除，且只能以块为单位擦除。当空闲块不足时，必须回收含有无效页的块。

GC的基本流程：选择源块 → 搬移有效页到目标块 → 擦除源块 → 更新映射。

以下模块都是GC的变体或辅助决策：

模块解决的具体问题与基本GC的区别GC (基本)空闲块不足，需要回收块根据不同需求选择流程：

```text
* 单纯考量VPC最低的块；
* 综合VPC、擦除次数、数据冷热程度决策；Pin GC某些热数据（如文件系统日志）被频繁覆盖，若反复搬移会浪费写放大Pin概念：将特定逻辑地址区域“钉”在固定物理块，GC时跳过这些块，直到其无效页占比极高（例如 90%）才回收；
```

Pin是一种跳过策略，Pin GC是GC的特例Refresh GC某些块因读干扰或数据保留错误风险高，但有效页较多，常规GC不会主动处理触发是数据健康度阈值（读计数、ECC错误率），目标是预防数据丢失而非回收空间3. 损耗均衡（Wear Leveling）与块搬移模块的区别

Wear Leveling、Media Scan、Block Refresh、Refresh GC 都涉及“将数据从一个块搬到另一个块”，但动机和触发条件完全不同。

模块核心目标触发条件搬移后原块处理与GC的关系Wear Leveling让所有物理块的擦除次数接近，延长整体寿命检测到最大擦除次数与最小擦除次数之差超过阈值（如100次）擦除后重新放入空闲池独立后台任务，可借用GC的搬移机制，但选块逻辑不同（选冷数据放高擦除块）Media Scan发现潜在的物理错误（读干扰、保留错误、ECC接近极限）定时（如每天）或空闲时触发，扫描所有块不擦除，仅报告不搬移，只检测；检测结果触发其他模块（Block Refresh或Refresh GC）Block Refresh解决读干扰：一个块被频繁读，导致邻近页比特翻转该块的读计数器超过阈值（如10万次）擦除后释放搬移所有有效页到新块，原块擦除。类似于GC但不回收空间，目标是为了数据安全Refresh GC解决数据保留错误或Media Scan发现高风险块（ECC错误率偏高）Media Scan报告某块错误率超过阈值，或该块写入时间超过数据保留期限（如1年）擦除后释放同Block Refresh，但通常用于非读干扰场景，两者在实际实现中可能合并总结区别：

- Wear Leveling → 磨损不均 → 搬移是为了平衡寿命
- Media Scan → 只检测不搬移 → 是其他模块的眼睛
- Block Refresh → 读干扰 → 搬移是为了避免读导致的数据损坏
- Refresh GC → 数据保留/早期错误 → 搬移是为了刷新电荷4. 数据冗余与错误处理模块

模块解决的物理问题方案RAIN (跨Die/Plane XOR)TLC/QLC原始误码率高，单页ECC可能无法纠正对Super Block内所有Plane进行XOR，校验页存在最后Plane，可恢复1 Plane损坏Table RAIN映射表存储在闪存中，若存储映射表的块损坏，整个FTL不可用对映射表的物理存储同样施加RAIN保护UECC Error Handling读取时发生不可纠正错误（超出ECC能力）1) 重试读（不同电压阈值）
2) 调用RAIN恢复
3) 若失败则标记坏块并尝试从其他副本（如Write Booster中的SLC镜像）恢复EM1 (Enhanced Memory Type 1)车规/工控场景要求极低UBER（不可纠错误率），普通TLC/QLC无法满足划分独立静态SLC Block Pool，所有Host/GC/Refresh写入强制使用该池，牺牲容量换可靠性
