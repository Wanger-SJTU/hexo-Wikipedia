PCIe 里的 I/O 空间和 MMIO 空间，到底有什么区别？

收录于 · PCIe

这事最让人别扭的，不是定义难背。
而是你第一次碰上它，往往不是在看 PCIe 规范，而是在看日志、看驱动、看 BAR 分配结果的时候，突然被它绊一下。

比如枚举时，一行写着 I/O，另一行写着 Memory。

或者翻 Linux 驱动，有的地方是 inb/outb，有的地方又是 readl/writel。
再或者看别人解释 PCIe BAR，说这是给设备分配“寄存器空间”，结果下一句又告诉你：这个 BAR 是 I/O BAR，不是 MMIO BAR。

这时候脑子里冒出来的问题通常都很直接：

不都是访问设备吗？
 怎么还分成两套？
 都已经 PCIe 了，为什么还留着这么个老东西？
 还有最关键的一点——我工程里看到的那个地址，到底算 I/O 空间，还是 MMIO 空间？

尤其如果你平时主要做的是 SoC、ARM、NVMe、网卡、PCIe RC 这些东西，这种别扭感会更强。
因为你天天碰的几乎都是 MMIO，I/O 空间却像个影子：规范里有，内核里有，日志里也偶尔冒出来，但真到写代码的时候，存在感又低得很。

先把最核心的一点说透：I/O 空间和 MMIO 空间，表面上都像是在“访问设备”，但它们背后其实不是同一个地址世界。

I/O 空间，本来就不是想让你把设备当内存来用
I/O 空间这东西，从一开始就是一套独立于内存地址空间之外的访问模型。

这个思路其实很好理解。
因为早年的体系里，大家会很明确地觉得：内存和设备不是一回事。

内存是拿来放数据的。
你读它、写它，通常只是数据变了。
可设备寄存器不一样。
你读一下，状态位可能清了；
你写一下，DMA 可能就启动了；
再写一下，中断可能就 ack 掉了。
它不是一块安安静静躺在那里的 RAM，更像一个带动作、带副作用的接口。

所以那时候的设计思路很直接：既然设备访问和内存访问不是一回事，那就别硬塞进一套模型里。
干脆给设备单独开一个地址空间。
CPU 如果想访问设备，就走专门的 I/O 指令，明确告诉硬件：我现在不是在碰内存，我是在碰外设。

这就是 I/O 空间最早的出发点。

换句话说，I/O space 的核心，不是“给设备分了一段地址”，而是“给设备单独留了一个地址世界”。

你今天在日志里看到的 I/O resource，或者在一些老代码里看到的 inb/outb，本质上都还是这条路的延续。

x86 上 inb / outb 是 CPU 的 in / out 指令
真到今天的工程实践里，MMIO 才是主角
这个你只要写几个现代驱动就能感受到。

NVMe、现代网卡、加速器、FPGA endpoint、SoC 上的 PCIe 设备……它们真正暴露出来的控制接口，基本都是 MMIO。
为什么？因为现代设备的寄存器接口往往不是几个零散的小端口，而是一大块：控制寄存器、状态寄存器、doorbell、队列指针、内存窗口、调试状态、mailbox、scratchpad……这种东西天然更适合放在一段 Memory BAR 里，而不是塞进 I/O port 那种更窄、更古老的模型里。

所以如果你做的是现代 PCIe 驱动，你会有一个很直接的体感：我天天打交道的是 MMIO。
I/O space 还在，但更多是活在兼容性和历史延续里。

MMIO 则是另一条思路：不另开世界，直接借用现成的地址空间
MMIO，全称是 Memory-Mapped I/O。
 它的思路和 I/O space 不一样。

它不是再专门给设备开一个新世界，而是直接借用现成的内存地址空间。
也就是说，设备寄存器还是那个设备寄存器，只是系统不再说“你去 I/O 空间里访问它”，而是改成了：

我把它映射到物理地址空间里，你从一个地址入口进去找它。

这就是 MMIO。

所以 MMIO 的重点，不是“设备变成了内存”，而是：

设备寄存器借用了内存地址空间这套访问基础设施。

这件事的工程意义很大。
因为从那以后，很多设备访问都可以统一成一件事：给它分一段地址，然后按偏移去读写。

这也是为什么你在代码里看到的是另一套味道。

如果是 I/O space，像 x86 这种体系，会有很典型的 inb/outb、inw/outw。
它们不是普通的内存读写，而是在走专门的 I/O 访问路径。

如果是 MMIO，常见的就是 readl/writel、ioremap 这一套。
看起来像是在访问内存地址，但背后打到的其实不是 DDR，而是设备窗口。

所以这两者的特点大概就是：

I/O space 是单独开了一套设备地址空间。
MMIO 是把设备挂进了内存地址空间。

那为什么到了 PCIe，这两套东西都还在？
很多人第一次接触 PCIe，会有一种很自然的感觉：
这不是挺现代的吗？

链路训练、TLP、lane 协商、LTSSM、拓扑发现……
看起来都是很新的东西。

结果一到软件接口这一层，又会撞上一堆很有年代感的词：

配置空间
BAR
I/O space
memory space
bus master

这不是 PCIe 没进化完。
而是它在软件可见的资源模型上，继承了 PCI 时代的设计。

PCIe 的底层链路当然已经不是老 PCI 那回事了。
但它并没有把上层那套资源表达方式全部推倒重来。

所以在 PCIe 设备眼里，它今天依然可以对系统说：

我需要一段 Memory Space。
或者，我需要一段 I/O Space。

系统在枚举时，也仍然会按这个类型给它分配资源。

这就是为什么直到今天，你在 PCIe BAR 的世界里，还是能看到 I/O BAR 和 Memory BAR 两种东西。

只不过，保留归保留，主流归主流。
这两件事不是一回事。

真正让人容易混的，是 BAR 地址到底在干什么
很多人第一次接触 BAR，会下意识把它理解成“寄存器本身”。

其实 BAR 更像一个入口声明，不是寄存器内容本体。

设备通过配置空间里的 BAR 告诉系统：

我这里有一块资源窗口。

你给我分个地址。

以后 CPU 如果想访问我，就从这个入口进来。

所以系统枚举之后，给某个 BAR 分出来的地址，真正的意义不是：

“这块地址里面存着设备的数据。”

它真正的意义是：

从 CPU 视角看，访问这个地址范围，会被路由到这个 PCIe 设备对应的资源窗口。

举个直观点的例子。

如果某个 Memory BAR 最后被分配到：

0x50000000

这不是说设备“住在” 0x50000000。

它更像是在说：

CPU 以后如果访问 0x50000000 + offset，

这次访问会经过地址译码、Root Complex、PCIe 事务路由，最后打到这个设备 BAR 后面挂着的那块窗口上。

所以 BAR 地址不是“普通内存内容”，

它更像是 CPU 访问设备的一道门牌号。

后面驱动为什么会围绕它做 ioremap()、readl()、writel()，其实也就顺理成章了。

因为驱动真正要用的，就是这个入口。

所以工程里看到的那个地址，到底算 I/O 空间还是 MMIO 空间？
这个问题说白了，先别看“长得像不像地址”，而要先看它属于哪类资源。

如果它是通过 Memory BAR 分配出来的，那它就是 MMIO 资源。
CPU 看起来是在访问一个物理地址，但背后其实是设备窗口。

如果它是通过 I/O BAR 分配出来的，那它就是 I/O 资源。
在 x86 上，它会落在独立 I/O 地址空间里。
在非 x86 上，它很多时候会被平台桥接成一种“看起来像 MMIO”的访问方式，但资源属性本身仍然是 I/O。

所以判断一个地址到底算哪种空间，不是看它“像不像内存地址”，而是看：

这个 BAR 当初申请的是 Memory Space，还是 I/O Space。

为什么在 x86 上，I/O space 的存在感这么强，而到了 ARM、RISC-V 上，你几乎感觉不到它？
这个差异，其实是很多人一开始理解 PCIe、BAR、MMIO 时最容易卡住的地方。

因为从“规范”上看，这些东西是统一的；但从“体感”上看，不同架构完全是两套世界。

在 x86 体系里，I/O space 是真的存在的一套独立地址空间。
它不是抽象概念，也不是历史包袱，而是硬件层面就被明确支持的一种访问路径。

CPU 有专门的 IN / OUT 指令，
总线也会区分这是一笔 memory access，还是一笔 I/O access。

所以在 x86 上：

inb/outb 不是封装
 I/O BAR 也不是摆设
 它们背后真的有一条“单独的通道”在工作

你可以把它理解成：
除了“访存”这条路之外，x86 还保留了一条“专门用来碰设备”的路。

但一旦你换到 ARM、RISC-V 这些架构，世界观就变了。

这些架构从一开始就更倾向于一种更统一的模型：
所有外设访问，全部映射进地址空间，通过 load/store 完成。

没有额外的一套 I/O port 语义，
也没有非要保留一组独立指令去做设备访问。

于是问题来了：

PCIe 规范里明明还有 I/O BAR，
但平台自己却没有“原生 I/O space”这一说了。

那这些设备怎么用？

工程上的答案其实很现实——“包一层”。

具体做法通常是：

由 PCIe 控制器或者 Root Complex，在系统地址空间里划一段 window，
用来“代管”这块 I/O space。

设备还是老老实实声明 I/O BAR，
系统也照样给它分资源，
但 CPU 真正去访问的时候，走的已经不是 in/out，而是一段看起来像 MMIO 的地址。

然后由底层硬件再把这次访问翻译成 PCIe 的 I/O Transaction。

也就是说：

I/O space 并没有消失，
只是被平台悄悄“折叠”进了 MMIO 这套访问模型里。

这也是为什么你在 ARM、RISC-V 上写驱动、看寄存器、调 PCIe 的时候，
几乎感觉不到 I/O space 的存在。

不是它不存在，而是你已经不再直接接触它了。

32/64 位描述的是地址编码能力，不是数据访问宽度
说到这里，BAR 上那几个最容易把人看晕的属性，其实也就能慢慢顺下来了。
很多人刚把 I/O space 和 MMIO space 理明白，下一秒又会被这几个词重新绕进去：

32-bit MMIO
64-bit MMIO
prefetchable
non-prefetchable

它们看起来都像是在描述 BAR 的属性，但其实根本不是一类问题。

先把最重要的结论摆在前面：

32-bit MMIO / 64-bit MMIO，说的是这块 BAR 能被分配到多大的地址范围里。
prefetchable / non-prefetchable，说的是这块 MMIO 能不能被系统用更激进的方式访问。

前者是在回答“这块 BAR 能放到哪”。
后者是在回答“这块 BAR 该怎么碰”。

这两组属性彼此独立，而且完全可以组合出现。

所以一个 BAR 完全可能同时是：

32-bit non-prefetchable MMIO
64-bit non-prefetchable MMIO
64-bit prefetchable MMIO

看起来一长串，其实只是两类信息叠在一起而已。

先看 32-bit MMIO 和 64-bit MMIO 到底是什么意思。
更准确一点说，这里其实是在讲：

32-bit memory BAR
64-bit memory BAR 

这里的“32 位”或者“64 位”，说的不是 CPU 是 32 位还是 64 位，也不是说一次访问的数据宽度只有 32 位或者 64 位。

它真正描述的是：

这块 BAR 的基地址能用多宽来表示。

如果一个 BAR 是 32-bit memory BAR，意思就是它的基地址只能用 32 位编码。
那它最终就只能被系统分配到 4GB 以下 的地址空间。

如果一个 BAR 是 64-bit memory BAR，意思就是它的基地址可以用 64 位编码。
那它既可以落在 4GB 以下，也可以被分到 4GB 以上。

所以这里讨论的核心，不是“读写宽度”，而是“地址能力”。

还有一个特别容易漏掉，但实际调试时很常遇到的点：

64 位 BAR 会占两个 BAR 槽位。

原因不复杂。
PCI 配置空间里单个 BAR 寄存器本身只有 32 位宽，所以 64-bit BAR 只能拆成两段来放：

前一个 BAR 放低 32 位，
后一个 BAR 放高 32 位。

也就是说，它逻辑上是一块 BAR，但在配置空间里会占两个位置。

再看 prefetchable 和 non-prefetchable。
这两个词也特别容易被理解歪。
很多人一看到 prefetchable，会下意识觉得它是在说“更快”或者“能缓存”，但这样理解其实不太准。

更贴近工程直觉的说法是：

这块 MMIO 区域，能不能更像内存一点，让系统放心去做预读、合并、突发访问之类的优化。

如果一块 BAR 被标成 prefetchable，通常意味着一个非常重要的前提：

读它，不应该带来副作用。

也就是说，系统就算提前读一点、多读一点，或者把几个访问合并一下，也不应该把设备状态搞乱。

这种区域通常更像：

frame buffer
大块数据 buffer
设备内部 RAM window
memory window

它们更偏“数据窗口”，不太像“控制接口”。

反过来，如果一块 MMIO 是 non-prefetchable，意思基本就是：

别乱来，老老实实按软件要求精确访问。

因为这类区域往往带着很强的控制语义。
多读一次、少读一次、顺序变一下，结果都可能不一样。

比如：

读一次就清状态
多读一次结果就变了
不能顺手多读旁边地址
不能随便改访问顺序
写某个位就会立刻触发硬件动作

所以这类区域通常就是：

控制寄存器
状态寄存器
doorbell
中断确认寄存器
FIFO / data port

把这几个概念拆开以后，其实就没那么乱了。

32-bit / 64-bit 解决的是“这块 BAR 能分到哪里”。
prefetchable / non-prefetchable 解决的是“这块 BAR 访问时能不能激进优化”。

一个是地址范围问题，
 一个是访问语义问题。

它们经常同时出现在同一块 BAR 上，所以看起来容易混；但本质上，它们根本不是一回事。

说到底，PCIe 设备需要 BAR，是因为它总得先给 CPU 一个能进去的入口。
这个入口后面，接的可能是寄存器，也可能是一整块设备内存窗口。

I/O 空间和 MMIO 空间的区别，不是“一个访问设备，另一个不访问设备”，而是它们给设备资源安排的位置根本就不在同一个地址世界里：
 一个挂在独立 I/O 地址空间里，一个挂在内存地址空间里。

x86 因为有原生 I/O port 体系，所以对 I/O space 的感知很强；
ARM、RISC-V 这些平台因为没有这套原生机制，所以很多时候会把 I/O BAR 桥接成 MMIO 风格去访问。
这也是为什么同样是 PCIe，很多人平时几乎感觉不到 I/O space 的存在。

而 BAR 上那些最容易混的属性，其实也没那么玄：

32位/64位，是在回答“这块 BAR 能放到哪里”；
prefetch/non-prefetch，是在回答“这块 BAR 能不能更像内存那样被优化访问”。
