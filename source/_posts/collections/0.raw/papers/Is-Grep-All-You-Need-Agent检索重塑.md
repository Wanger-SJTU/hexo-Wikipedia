# 摘要

大语言模型（Large Language Model，LLM）智能体（Agent）的最新进展使得复杂的代理工作流成为可能——模型能够自主检索信息、调用工具，并在大型语料库上进行推理，以完成用户委托的任务。随着检索增强生成（Retrieval-Augmented Generation，RAG）在智能体系统中的广泛应用，现有文献缺乏对检索策略选择与智能体架构及工具调用范式之间交互关系的系统比较。一些重要的实践维度——例如工具输出如何呈现给模型、当搜索需要处理更多不相关周围文本时性能如何变化——在智能体循环中仍未得到充分探索。本文报道了一项分为两个实验的实证研究。实验一在 LongMemEval 的 116 道题目的样本上比较了 grep 检索和向量检索，使用了自定义智能体框架（Chronos）和提供商原生 CLI 框架（Claude Code、Codex 和 Gemini CLI），分别针对内联工具结果和模型需单独读取的基于文件的结果。实验二在逐步混入更多无关对话历史记录的同时比较仅 grep 检索和仅向量检索，使得每个查询嵌入在越来越多的干扰材料中，而相关段落仍然存在。在 Chronos 和各提供商 CLI 中，grep 在实验一的比较中普遍优于向量检索；同时，总体得分仍然强烈依赖于所使用的框架和工具调用风格，即使底层对话数据完全相同。

# 引言

现代 LLM 智能体越来越依赖 RAG 在推理时访问外部知识，使其能够对远超上下文窗口大小的语料库进行推理。通过工具调用，智能体发出搜索查询、接收排序结果，并迭代地深化理解，然后产生答案。在此领域中有两种检索范式占主导地位：语义向量搜索，将查询和文档嵌入到共享的潜在空间中进行近似最近邻匹配；以及词汇搜索（如 grep、BM25、正则表达式），在原始文本上进行精确或基于模式的匹配。虽然向量搜索已成为大多数 RAG 系统的默认选择，但由于其简单性、稳定性和低嵌入成本，词汇搜索在实践中仍被广泛使用。然而，检索策略如何与端到端智能体工作流中的智能体架构和工具调用范式相互作用，目前尚缺乏清晰的理解。

尽管智能体搜索的应用日益广泛，但现有研究在很大程度上将检索策略脱离智能体架构进行评估。信息检索社区已经广泛基准测试了词汇和密集检索方法，并研究了独立流程中的检索质量、分块和重排序。然而，这些评估通常假定一个固定流程，其中检索到的文档被拼接成提示，忽略了现代智能体系统所具有的迭代式、工具中介的检索循环。在实践中，智能体接收排序列表但并不将其视为终端：它们决定搜索什么、发出多少查询，以及检索结果是否足够或需要进一步细化，这些都由智能体框架（harness）及其工具调用接口来调节。此外，工具结果如何呈现给模型——是内联注入到上下文窗口还是写入智能体必须明确读取的文件——引入了一个额外的架构考虑因素，之前的工作尚未对此进行考察。

同时，提供商原生 CLI 智能体（如 Anthropic 的 Claude Code、OpenAI 的 Codex 和 Google 的 Gemini CLI）的出现创造了一类新的智能体系统，它们与自定义构建的框架有着根本的不同。这些提供商框架将工具调用嵌入到一个基于 shell 的界面中，模型可以直接访问命令行执行工具（如 grep），而自定义框架和智能体 SDK 则对工具调用循环、上下文构建和结果格式化提供细粒度控制。检索策略的有效性如何在这些架构上截然不同的框架类别中变化，尚未得到研究。

此外，检索质量的一个较少被审视的维度是对语料库噪声的鲁棒性：随着不相关文档与相关文档比例的增加，检索策略可能以不同的速度降级，理解这种扩展行为对于针对大型嘈杂语料库部署 RAG 系统至关重要。

本文旨在通过一项关于配备工具的 LLM 智能体检索策略的实证研究来填补这些空白，按实验组织（第~\ref{} 节）。我们在自定义框架（Chronos）和提供商原生 CLI 框架（Claude Code、Codex、GMini CLI）上评估词汇搜索和语义向量搜索，涵盖标准内联上下文传递和程序化基于文件的结果传递。我们在 LongMemEval 基准测试的 116 道题目的子集上评估多个 LLM，涵盖六类信息检索任务。本文做出以下三方面贡献：

1. 关于词汇检索和密集检索之间的选择如何与智能体编排层、以及工具输出是以内联方式还是通过文件呈现相结合的经验证据。
2. 表征端到端行为如何随不相关周围内容相对于任务相关材料的增长而演变，包括检索器行为与更广泛智能体循环之间的交互。
3. 一项直接比较，表明检索有效性在架构上截然不同的框架（自定义框架与提供商原生 CLI）之间并不稳定，即使底层文本语料库保持不变。

# 智能体系统中的检索概述

智能体系统中的检索是指 LLM 智能体通过该过程识别、执行和消费搜索操作以回答用户查询。与独立检索流程不同——其中固定查询与文档索引匹配，顶部 $k$ 个结果被拼接成提示——智能体检索是迭代式的且由智能体驱动：模型决定搜索什么、发出多少查询，以及检索结果是否足够或需要细化。该过程由两个设计维度共同调节，决定了端到端有效性：检索策略（词汇、语义或混合）和智能体框架。

## 检索策略

智能体搜索系统的检索策略分为三大类：词汇检索、语义检索和混合检索。每种都提供不同的准确率、延迟、成本和对查询表述的鲁棒性权衡。

### 词汇搜索

词汇检索方法在原始文本上执行精确或基于模式的匹配。BM25 等经典方法通过词频和逆文档频率对文档进行评分，而 grep 搜索使用正则表达式或子字符串匹配来定位包含特定关键词的段落。词汇方法不需要嵌入模型或向量索引，除了文本扫描本身的计算成本外几乎不产生额外成本。BEIR 基准测试表明，BM25 在各种检索任务中仍然是一个具有竞争力的基线，通常在零样本设置中优于早期的密集检索模型。SPLADE 等学习的稀疏表示通过学习的词汇表扩展查询和文档词项来扩展词汇匹配，在保持稀疏表示可解释性和效率的同时弥合了精确匹配和语义理解之间的差距。

### 语义搜索

语义搜索或密集检索将查询和文档编码为共享嵌入空间中的密集向量并检索最近邻，最常见的方式是近似最近邻（ANN）搜索。密集段落检索（DPR）通过在问答对上进行双编码器训练建立这一范式，使检索能够基于含义而非表面词项重叠来进行。RAG 系统通过将密集检索与生成模型耦合来扩展这一点，允许检索器和生成器联合优化。现代 RAG 流程通常使用预训练的嵌入模型在索引时对文档进行编码，在推理时对查询进行编码，并可选地在检索后进行重排序以细化初始候选集。虽然语义搜索在处理释义和语义相似性方面表现出色，但它引入了对嵌入模型质量、向量索引基础设施和索引延迟的依赖，这是词汇方法所避免的。

### 混合方法

混合检索结合词汇和语义信号以利用两种范式的优势。倒数排名融合（RRF）合并来自独立词汇和密集检索器的排序列表，无需分数校准。后期交互模型如 ColBERT 计算查询和文档表示之间细粒度的词级相似性，在单向量检索的效率和交叉编码器重排序的表现力之间取得了中间立场。对稀疏和密集表示互补性的研究表明，词汇和语义方法经常检索到不同的相关文档，使它们的组合比单独使用任何一种更有效。在智能体设置中，当智能体可以访问词汇和语义搜索工具并根据查询在两者之间进行选择时，混合检索也可以有机地出现。

## 智能体框架

智能体框架是管理工具调用循环的环境层：它构建提示、调度工具调用、接收结果，并决定是继续迭代还是产生最终答案。我们区分了两类框架，它们在对此过程的控制程度上有着根本的不同。

### 自定义框架

自定义框架由开发者使用智能体框架、提供商开放 SDK 或自定义代码构建。这些框架对智能体循环的每个阶段提供细粒度控制：系统提示、工具定义、上下文构建、结果格式化和迭代终止标准。ReAct 范式——将推理轨迹与工具操作交织——是自定义框架中最广泛采用的模式。开发者可以实现领域特定的优化，如动态提示（根据每个查询定制系统提示）、结果截断策略和检索段落的重排序。自定义框架还允许对上下文窗口进行显式管理，例如随着对话增长总结或丢弃早期的工具结果。代价是开发开销：构建和维护自定义框架需要大量的工程工作和提示工程、工具接口设计以及上下文管理方面的专业知识。

### 提供商原生 CLI 框架

提供商原生 CLI 框架将工具调用嵌入到基于 shell 的界面中，模型可以直接访问系统工具。在这些环境中，智能体可以执行任意 bash 命令，包括 grep、find、cat 和其他 Unix 工具，作为原生工具操作。框架根据提供商的内部实现管理上下文构建和迭代控制，这对用户来说基本上是不透明的。提供商原生框架提供最小的设置成本并利用提供商的优化上下文工程，但牺牲了自定义框架中可用的细粒度控制。值得注意的是，当 grep 作为原生 bash 工具可用时，"检索策略"和"智能体能力"之间的界限变得模糊：智能体可以动态构建自己的 grep 命令，选择搜索词、标志和文件目标，而不是局限于预定义的搜索 API。

## 工具调用架构

与框架的选择正交，工具调用架构管理检索结果在搜索执行后如何传递给模型。这一设计维度对上下文窗口利用和智能体处理大型结果集的能力有重大影响。工具调用方法模式实际上是一个上下文工程决策：内联传递直接填充上下文窗口，而程序化传递将上下文构建委托给智能体本身。

### 标准（内联）

在标准工具调用架构中，搜索结果作为工具响应消息直接返回，追加到对话上下文中。模型在上下文窗口内接收完整的结果集，可以立即对其进行推理。这是大多数 LLM API 和自定义框架中原生函数调用的默认模式。主要优点是简单：检索结果与对话内联出现，在获取和生成之间没有单独的缓冲区、路由层或后处理步骤。然而，大结果集与系统提示、对话历史和先前的工具结果竞争上下文窗口空间，造成上下文压力——一种有时被称为"上下文膨胀"的现象——可能导致长期任务性能下降。缓解这一问题的一种方法是在可能丢弃相关信息的情况下应用结果截断。

### 程序化（基于文件）

在程序化工具调用架构中，搜索结果被写入磁盘，模型仅接收文件路径或摘要指针。智能体必须采取显式操作来访问结果，这本身可以是一次搜索操作（例如在结果文件上）或一次完整读取（例如 `cat`、`rg`）。这将检索结果大小与上下文窗口压力解耦：任意大的结果集可以写入磁盘，在智能体明确读取它们之前不消耗上下文 token。权衡是间接性：智能体必须执行额外的工具调用来访问结果，这增加了延迟并要求模型理解基于文件的工作流程。程序化架构还支持渐进式披露，智能体仅根据元数据或摘要读取结果子集，这是一种智能体驱动的检索后过滤，在内联传递中是不可能的。

# 方法论

我们的实验根据第~\ref{} 节定义的的两个维度评估检索策略有效性。

## 任务与数据集

我们在 LongMemEval 基准测试的 116 道题目的代表性子集上进行评估，该基准测试考察智能体在跨越多个会话的长期对话中回答问题的能力。每个问题都伴随一定类型的会话：一个或多个包含正确回答所需信息的 oracle 会话，以及可变数量的与查询无关的干扰会话。问题涵盖六类：知识更新（跟踪随时间变化的状态）、多会话（聚合跨会话信息）、单会话助手（回忆模型生成的内容）、单会话偏好（用户个人偏好）、单会话用户（用户陈述的事实）和时间推理（计算持续时间、排序事件和解析日期）。所有对话轮次和提取的时间事件都存储在本地，作为 grep 和向量搜索的语料库。

## 检索实现

### 通过 Chronos 的结构化事件

我们的搜索层在每个问题的文件上操作，将 LongMemEval 对话轮次与使用 Chronos 预处理流程从转录本中提取的结构化时间事件一起序列化。Chronos 针对长期会话记忆，通过将显式日期、时间间隔和相关时间跨度作为一等文本记录呈现，与原始话语耦合，这是与 Chronos 强调结构化事件检索以实现时间感知智能体的理念一致的。我们采用这一层有两个原因：我们的研究评估智能体的搜索技术，而不是其时间推理能力。LongMemEval 项目中有相当一部分依赖于分散在多个轮次中的显式时间表达；将这些作为规范化记录呈现在一个紧凑的并行通道中，确保时间项目上的成功反映智能体是否能够定位相关证据，而不是模型是否能够从碎片化提及中重建日期和间隔。Chronos 的结构化事件提取反映了长期记忆智能体在部署时将使用的预处理，因此实验设置反映了现实的生产配置，而不是仅为评估构建的人工配置。

### 词汇搜索（Grep）

grep 检索工具将对话轮次和提取的时间事件从每个问题的文件加载到内存中，并对原始文本字段执行正则表达式（regex）匹配。结果按匹配计数评分并返回。该实现不需要嵌入模型、向量索引或外部服务：所有匹配都在本地文件上进行进程内执行。

### 语义搜索（向量）

向量搜索工具查询在摄取时填充的搜索索引。每个对话轮次和时间事件都被嵌入并存储在具有版本模式化的每个问题索引中。在查询时，该工具嵌入自然语言查询并使用近似最近邻搜索检索最相关的结果。重排序步骤在返回顶部 $k$ 个结果之前对检索到的段落重新评分，其中 $k$ 由智能体选择。

## 智能体框架

### 自定义框架

我们的自定义框架 Chronos 使用 LangChain 实现智能体，访问四个搜索工具（对轮次和事件的 grep 和向量搜索）。此外，在程序化模式下启用了一个 grep 工具。根据实验配置启用或禁用这些工具。遵循 Chronos 针对长期记忆智能体的设计，我们使用动态提示：系统指令、搜索提示和工具使用指导依赖于检测到的问题类别（例如，时间推理与偏好回忆），而不是对所有项目使用单一静态系统提示。因此，智能体在每个事件开始时接收类别条件引导，然后是初始广泛上下文块（前 15 个向量结果），然后工具调用循环开始。循环继续直到模型产生最终答案。

### 提供商原生 CLI 框架

我们评估了三个提供商原生 CLI 智能体。每个接收问题和一个动态生成的搜索策略，并且可以通过绝对路径调用 bash 可调用的包装脚本进行 grep 和向量搜索。在标准模式下，进程在沙箱中生成以确保模型只能访问相关文件。

## 工具调用架构

### 标准（内联）

在标准模式下，搜索脚本将结果直接打印到 stdout。对于 Chronos 框架，结果作为工具响应消息返回，注入到对话上下文中。对于 CLI 框架，stdout 由 shell 接口追加到智能体的工作上下文。结果与系统提示和对话历史竞争上下文窗口空间。

### 程序化（基于文件）

在程序化模式下，所有结果都写入一个文件，智能体可以访问该文件。然后智能体读取或搜索该文件以访问完整结果。这将检索结果大小与上下文压力解耦，并强制智能体明确选择要消费的结果。

## 模型

我们评估了五个 LLM 和一系列能力级别：Claude Opus 4.6 和 Claude Haiku 4.5、GPT-5.4，以及 Gemini 3.1 Pro 和 Gemini 3.1 Flash-Lite。

## 评估

遵循 LongMemEval 基准测试论文中指定的评估协议，我们使用辅助 LLM 评分器评估每个模型假设。我们实例化 GPT-4o 作为度量模型：对于每个问题，评分器接收问题文本、参考答案字段和智能体的假设，必须在类别条件指令下输出二元判断（例如，对时间计数误差的容忍度、偏好项目的评分标准，以及变体的弃权处理）。我们报告准确率作为评分器肯定回答的问题比例。在各条件下保持评分器模型、提示模板和解码设置不变，确保框架、检索模式和会话限制设置之间的差异反映智能体流程的变化而非评估噪声。

# 实验

## 实验一：检索模式、框架与工具调用方法

### 目标

我们将检索模式（仅 grep 与仅向量）、智能体框架（Chronos 与 Claude Code 与 Codex 与 Gemini CLI）和工具调用方法（标准内联与程序化基于文件）隔离出来，研究它们如何共同影响当每个问题的完整 haystack 暴露时的端到端长期记忆问答准确率。析因设计回答了词汇检索或密集检索在匹配的框架下是否具有一致的优势，以及将工具输出路由到文件而非内联消息是否会改变该比较。

### 讨论

综合来看，析因布局暗示两个可解释的观点。首先，LongMemEval 奖励恢复字面证据：精确日期、计数、偏好和跨度，这些在词元化下通常保持稳定。词汇工具在没有嵌入瓶颈的情况下呈现这些字符串，这可以解释为什么内联 grep 在表~\ref{} 中是一个强有力的默认设置。结果的按类别分解见附录~\ref{}。

其次，"检索模式"不是孤立测量的：框架塑造了系统提示、工具描述以及如何将命中渲染回聊天，所有这些都影响模型调度查询和决定何时停止的方式。因此，相同的底层模型在各框架下在非常不同的框架下运作，这可能促成了表~\ref{} 中观察到的框架级转变。程序化传递将任务从"读取工具消息"更改为"定位、打开和整合一个产物"。当第二个阶段脆弱时，准确率可能独立于检索质量而崩溃，这有助于解释为什么程序化条件重排了 grep--向量比较而索引没有任何变化。一个实践含义是，智能体论文应该同时报告检索机制和传递路径，因为基于文件的路由本身就是一种工具使用压力测试。在智能体循环中，词汇和密集搜索优化了不同的失败模式，而不仅仅是在排序指标上。Grep 故意收窄：它奖励模型生成高精确度模式，但会因词汇不匹配而受到惩罚——如果智能体从未猜到一个独特的子字符串，就不会检索到任何东西。密集检索故意放宽：它可以呈现释义和倾斜提及，但也会提升与问题有主题重叠的语义"接近"的干扰物，这在智能体发出短或不够明确的查询时很重要。表~\ref{} 与一种状态一致，即 LongMemEval 的答案通常由一小套字面跨度授权，因此当命中被内联注入并立即可操作时，词汇匹配的精确度偏好获胜。在相同的骨干（例如 Claude Opus 4.6）在 Chronos 和提供商 CLI 之间切换时，准确率变化幅度与在固定框架内交换检索器相当（Section~\ref{}）。一种解读方式是，框架不是被动基础设施：Chronos 的类别条件提示和受控工具表面积塑造了首先搜索什么以及如何修复失败，而 CLI 智能体继承提供商特定的工具人体工程学、沙箱和转录格式化。换句话说，表~\ref{} 中的"检索"实际上是检索加编排。这对基准测试是一个建设性的要点：仅报告静态流程中的 BM25 与 ANN 低估了智能体脚手架引入的方差。

基于文件的传递通常被动机为缓解上下文压力，这应该不成比例地有益于内联向量转储使窗口拥挤的设置。我们确实看到程序化向量在几行上超过程序化 grep。然而，相同的机制可能反转：如果模型难以完成读取-整合-重试循环，收益永远不会到达答案层。Codex/GPT-5.4 程序化 grep 的极端下降（第~\ref{} 节）是一个有用的警示故事：廉价检索（对本地 JSON 的 regex）并不是"容易"的端到端，如果框架将每个命中变成多步工作流且堆栈执行不可靠。这暗示了一个设计权衡：程序化路由用上下文带宽换取组合工具能力；只有在智能体可靠地关闭循环时才能实现收益。Claude Haiku 4.5 在 Claude Code 上的行显示了特别大的内联 grep--向量差距。没有追踪级因果归因，一个合理的假设是，较弱的模型在迭代查询细化和重排序器感知阅读方面不太一致，这比模式触发的词汇恢复更伤害密集检索——当证据 literally 存在时。如果成立，"默认为向量"的建议应该以骨干强度为条件，并且以任务是否奖励字面跨度恢复与概念融合为条件：这是聚合排行榜比较经常模糊的细微差别。

### 讨论

一个常见的实践直觉认为，词汇搜索在小型语料库上足够但在大规模下崩溃，而更具表达力的语义搜索在语料库增长时变得必要。我们的扩展研究部分支持这一点——向量检索通常在低会话计数时更强——但揭示了交叉点取决于框架和骨干而非语料库大小。扩展研究作为交互的压力测试最有用：检索族不会随着"噪声增加"而平行降级；它们与 (i) 如何为每个会话限制配置重采样干扰物、(ii) 框架特定的工具转录本、以及 (iii) 模型关于何时停止搜索的隐式策略进行交互。一个有用的抽象是，密集检索倾向于探索嵌入空间中的邻域：它可以恢复间接提及，但也会在会话积累时承认主题虚假朋友。词汇检索倾向于利用表面线索：它对措辞很脆弱，但当智能体发现区分性模式时，它可能是无情的精确。Chronos 扩展网格——其中向量通常在较小会话限制时更强，但 grep 可以关闭或稍后超越取决于骨干和列——与一个故事一致，其中语义检索在 bundle 仍然可管理时购买早期覆盖，而当智能体必须在已经消耗用于工具记帐的转录 token 的工作流下分离针和大海捞针时，regex 风格证据变得相对稳定。我们将其表述为一个假设：我们的表格没有隔离查询字符串或检索集，但如果"噪声"是一维单调的，qualitative 交叉点很难解释。Claude Code 上 Opus/Haiku 的持续 grep 优势和 Gemini CLI 上 Gemini 3.1 Pro 的持续向量优势（第~\ref{} 节）表明提供商工具引入了稳定的归纳偏见：默认提示、stdout 如何分块到转录本中、工具错误表面，甚至 CLI 智能体措辞搜索的文化默认。这提醒我们，生产中的"grep"很少是单一原语，它是 grep 加 shell 加提示。供应商稳定的模式具有科学趣味性，因为它们意味着 CLI 堆栈之间的迁移在磁盘上的语料库逐字节相同时并非检索可互换的。由于干扰物在会话限制改变时重新绘制，中网格峰值不需要指示"30 个会话比 20 个容易"；它们可以指示特定采样的干扰物集与智能体搜索轨迹之间的有利干扰。这不会削弱配对比较：grep 和向量 在每个配置中面对相同的采样 bundle。它确实意味着扩展曲线应该被读作来自随机外层的样本，而不是平滑的能力定律。最后，不完整的行（Codex 向量中间项；尚无 Codex grep 扩展行）意味着我们尚无法提供供应商完整的图景，说明在匹配的帽子下"CLI grep"如何随干扰物老化相对于"CLI 向量"。在这些行存在之前，最强的跨实验声明是有条件的：第~\ref{} 节在异构框架下的完整 haystack 建立大型端到端差异；第~\ref{} 节显示 grep--向量排序在扩展下并未保留，即使干扰物采样是配对的，但这种非保留的形状仍然取决于观察哪个堆栈。

# 局限性

从概念上讲，我们的结论与长期记忆会话问答相关：问题建立在多会话聊天、显式时间表达和个人/用户事实上。词汇工具在这里可能不成比例地有帮助，因为答案通常在字面跨度上获得许可；在证据很少是字面的领域（例如对释义摘要的科学综合、视觉重的文档或代码语义），密集检索和混合路由可能看起来不同。我们并不声称 grep"击败"向量一般情况下，只声称在我们研究的任务分布和语料库下它可以在端到端获胜。

# 结论

随着 LLM 智能体承担越来越复杂的智能体工作流，自主检索信息、调用工具并在大型语料库上推理，检索策略的选择与智能体架构和工具调用范式的交互方式现有文献尚未系统比较。实践维度——如工具输出如何呈现给模型，以及当搜索必须应对更多不相关周围文本时性能如何变化——在智能体循环中仍未得到充分探索。

在本文中，我们报告了一项分为两个实验的实证研究。实验一在 LongMemEval 的 116 道题目样本上比较了 grep 和向量检索，涵盖四个框架：自定义智能体框架（Chronos）和三个提供商原生 CLI 框架（Claude Code、Codex 和 Gemini CLI），分别针对内联工具结果和模型需单独读取的基于文件的结果。实验二在逐步混入更多无关对话历史记录的同时比较仅 grep 检索和仅向量检索，使得每个查询嵌入在越来越多的干扰材料中，而相关段落仍然存在。

在 Chronos 和各提供商 CLI 中，grep 在我们的比较中普遍优于向量检索，其中内联 grep 超过我们在每个框架-模型对评估的内联向量。同时，总体得分强烈依赖于所使用的框架和工具调用风格，即使底层对话数据完全相同，其中基于文件的传递和提供商 CLI shell 可以反转或消除词汇优势而无需对语料库进行任何更改。

这些结果强调检索机制、框架编排和传递路径作为一个联合评估的系统而非独立设计选择，激励未来在混合检索策略、非对话语料库和更广泛的供应商覆盖方面开展工作，以阐明智能体何时应该使用词汇搜索而非语义搜索。
