# Cache Engineering for Agents（面向 Agent 的缓存工程）

**作者**：Tianyu Fu*、Ruoxi Wang*、Zihan Min*、Zhongqi Ren、Zhihao Li、Tengxuan Liu、Shengxu Mu（清华大学），Hanling Zhang（香港中文大学），Yu Wang†（清华大学，通讯作者）
*共同一作；†通讯作者：yu-wang@tsinghua.edu.cn

## 摘要

大语言模型（LLM）agent 能够处理日益复杂的任务，在漫长的观察-动作轨迹中导航。随着这些轨迹增长，key-value（KV）cache 的 I/O 与存储成为主导成本。轨迹还可能超出 LLM 的最大上下文长度，因此需要控制活跃缓存的增长。先前工作采用上下文工程（context engineering），通过裁剪或总结历史来减小缓存规模。然而，修改轨迹前缀会使后续缓存状态失效，并触发对保留上下文的高昂重新预填充（re-prefill）。而若保留的上下文过少以限制 re-prefill 成本，任务准确率也可能受损。我们提出**缓存工程（cache engineering）**这一新方案：它允许 agent 直接控制自己的活跃 KV cache，而无需修改轨迹或对保留上下文重新预填充。具体而言，agent 可以主动使用 **drop** 将选定缓存排除出后续注意力计算，使用 **repos** 调整保留键的位置编码。我们形式化了这些缓存操作，并指出**历史依赖性**是服务化（serving）的核心挑战：相同的 token 序列在不同的缓存操作序列下会产生不同的缓存状态，使得前缀匹配不足以实现正确的缓存复用。为此，我们协同设计了 **AKV 服务引擎**。它提供与现有服务 API 兼容的无状态接口，同时在内部管理有状态的缓存复用、驱逐与恢复。实验表明，与常规的阈值触发式总结相比，一种工具响应滚动丢弃（rolling-drop）缓存策略平均提升基准分数 1.7 分、平均降低成本 27.7%。配合 AKV，最高可达到 1.2× 的输出吞吐量和 1.5× 的 P95 请求延迟加速。缓存策略的递归自我改进（RSI）进一步在专家设计之上再降低成本 7.1%。代码见 https://github.com/thu-nics/AKV。

## 1 引言

大语言模型（LLM）agent 能够胜任日益长程的任务。Agent 通常由负责推理和工具调用的 LLM，以及协调工具执行与上下文的 harness 组成。通过反复的推理、工具使用与环境交互，它们可以完成跨越数百轮的复杂工作（Ye et al., 2025; Liu et al., 2025b）。

随着 agent 轨迹变长，KV cache 的增长对推理成本和任务准确率都构成挑战。成本方面，保留并反复访问累积的 KV 缓存会产生可观的存储与 I/O 开销（Wu et al., 2026; Anthropic, 2026）。如图 13 所示，KV cache 读取占总 API 成本的 82.4%。任务准确率方面，若被注意的 KV 状态数量或其位置范围超出 LLM 可靠处理的范围，agent 会严重退化（Hsieh et al., 2024; Chen et al., 2026b; Zhou et al., 2025）。因此，需要对活跃 KV cache 进行精细控制，以保证 agent 执行的高效与可靠。

先前工作通过上下文工程来缩减不断增长的缓存，通常做法是裁剪或总结历史消息。虽然较旧的消息往往用处较小，但编辑它们会改变轨迹前缀、使后续 KV 状态失效并触发 re-prefill。编辑越早，需要重新预填充的保留轨迹后缀就越长。因此常见 harness 会推迟缩减，直到活跃上下文长度达到阈值，然后对大部分轨迹进行裁剪或总结，仅保留最近几轮以控制 re-prefill 长度（Pi, 2026; OpenAI, 2026）。这种激进的缩减有丢失中间轮次有用信息的风险，形成 re-prefill 成本与任务准确率之间的两难。

本文提出**缓存工程**——一种让 agent 直接控制自身活跃 KV cache 的新方案。如图 1 所示，它不修改文本轨迹，而是仅将选定的 KV 条目排除出后续注意力，并复用所有保留的 KV 状态而无需 re-prefill。这使得 agent 能在给定成本预算下，增量丢弃较旧的 KV 条目，同时保留更多的后缀 KV。为支持这种控制，在为新增 token 添加 KV 状态的常规 append 操作之外，我们引入两个额外的缓存操作：**drop** 将选定的 KV 条目移出后续注意力；**repos** 调整保留键的位置编码。在执行过程中，LLM 与 harness 选择何时以何种方式应用这些操作，反复地将其与 append 交错以塑造活跃缓存。这种可编程控制还使 agent 能够通过递归自我改进（recursive self-improvement, RSI）来搜索、评估和优化缓存工程策略。

然而，缓存工程的历史依赖性对现有 LLM 服务系统构成挑战。在标准 KV caching 下，token 前缀完全决定缓存状态（Kwon et al., 2023; Zheng et al., 2024）。相比之下，相同的 token 前缀与保留位置在不同的缓存操作历史下可能产生不同的缓存状态。如图 5 所示，轨迹①和②都保留了 B 和 C 的 KV 条目，但由于 drop 与 append 操作顺序不同，①中 C 的 KV 是在对 A 注意的情况下计算的。因此服务系统必须同时考虑 token 历史与缓存操作历史，才能正确追踪或复用缓存状态。

为此，我们协同设计了 **AKV**——一个面向缓存工程的易用高效服务系统。它提供与现有 API 化服务兼容的无状态接口，在内部处理有状态缓存管理的复杂性。Agent 只需像往常一样提交消息，并附带缓存操作指令，无需追踪哪些 KV 状态仍驻留在服务器上。系统使用扩展基数树（extended radix tree）对历史依赖的缓存状态进行正确复用与及时驱逐，并用分段批注意力（segment-batch attention）在单次 prefill 中高效重建缺失状态。AKV 将缓存工程的理论效率潜力转化为真实 agent 工作负载的更低实际延迟与更高吞吐。

**贡献**：
- **缓存工程的形式化**。我们通过显式缓存操作及其轨迹对缓存工程进行形式化，为历史依赖的缓存状态提供清晰、确定性的描述。该形式化还为 agent 提供了可编程接口，用于定义和优化自己的缓存工程策略。
- **面向缓存工程的服务系统**。我们提出首个允许 agent 直接控制缓存（此前缓存完全由系统管理）的服务系统，协同设计无状态接口、扩展基数树与分段批注意力，以支持高效的缓存复用、驱逐与恢复。
- **同时提升效率与基准性能**。在 3 个 LLM 与 4 个 agent 基准上，简单的工具响应滚动丢弃缓存策略相对常规阈值触发总结平均降低成本 27.7%、平均提升基准分数 1.7 分。配合 AKV 服务器，相当于 1.18× 输出吞吐量与 1.51× P95 请求延迟加速。基于 RSI 的策略在保留任务上再降成本 7.1%。

## 2 相关工作

**Agent 上下文工程**。在文本层面，上下文工程通过总结或裁剪交互历史来降低成本，使 agent 能在 LLM 上下文窗口之外工作。现有方法通过启发式（Wu et al., 2025）或 agent 决策（Ye et al., 2025; Sun et al., 2025）触发总结；进一步工作通过强化学习（Lu et al., 2025）或优化压缩准则（Kang et al., 2025）提升总结质量。为避免总结的成本与复杂性，裁剪方法（Lindenbauer et al., 2025; Zhang et al., 2026）直接移除相关性较低的上下文。然而，编辑较早的上下文需要对保留后缀进行 re-prefill，形成 re-prefill 成本与信息保留之间的两难。

**KV cache 压缩、驱逐与复用**。在缓存层面，先前工作通过减小缓存规模或近似复用已有状态来降低存储、访问与计算成本。压缩方法使用低秩表示（Liu et al., 2024a; Wang et al., 2024a）、量化（Liu et al., 2024b; 2026b）或聚合（Fu et al., 2025b; Wang et al., 2024b）更紧凑地表示缓存条目。驱逐方法通常依赖底层信号，如 token 位置（Xiao et al., 2024）或基于注意力的重要性（Zhang et al., 2023; Li et al., 2024; Fu et al., 2025a; Yang et al., 2026），来移除用处较小的缓存条目。复用方法通过位置编码调整（Gao et al., 2024; Ma et al., 2026; Ordonez & Parnell, 2026）或部分重计算（Wang et al., 2025），将缓存状态适配到不同位置或上下文前缀。我们的工作聚焦于驱逐与复用，让 agent 与 harness 做出高层驱逐决策，同时提供实用的服务引擎实现高效的跨请求复用与隔离。我们在附录 A.5 中讨论并发的面向 agent 的驱逐工作。

**服务系统中的 KV cache 管理**。除算法设计外，先前工作还探索高效缓存存储、共享与请求调度的系统优化。现有系统使用前缀缓存（prefix caching）在共享前缀的请求间复用 KV 状态，同时保持与完整 prefill 的等价性（Zheng et al., 2024; Ye et al., 2024）。针对 agent 工作负载，近期系统批量处理上下文编辑以减少缓存失效（Xu et al., 2026），或将 re-prefill 与正在进行的执行重叠以隐藏其延迟（Pan et al., 2026）。而缓存工程还额外要求追踪缓存操作历史，因为相同的 token 前缀在不同操作下可能产生不同状态。

## 3 缓存工程

缓存工程让 agent 直接控制自己的活跃 KV cache，无需重写轨迹或对保留上下文重新预填充。第 3.1 节介绍基本概念，第 3.2 节介绍设计动机，第 3.3 与 3.4 节形式化缓存操作及其轨迹。

### 3.1 预备知识

自回归 LLM 基于前序 token 序列 x1:t 预测下一个 token：

pθ(xt+1 | x1:t).  (1)

现代 LLM 服务使用 KV caching 避免重算先前 token 的状态。此时下一 token 预测以当前 token xt 与前序 token 的缓存为条件：

pθ(xt+1 | xt, C1:t−1),  (2)

其中 C1:t−1 表示由 token x1:t−1 计算得到的 KV 状态。

Agent 的轨迹（trajectory）是用于后续模型计算的有序文本历史，包括 prompt、assistant 消息与工具响应。形式上，轨迹是一个逻辑 token 序列 x1:t，t 是其逻辑 token 长度。

在缓存工程中，缓存规模不必等于逻辑 token 长度。我们因此定义**活跃缓存（active cache）** C 为可供后续注意力使用的 KV cache 状态；对应的 token 序列称为**活跃上下文**，其长度等于 C 中的 token 条目数。注意"活跃"指算法层面参与注意力，而非服务引擎中的物理缓存驻留。缓存条目的位置编码索引也可以独立于其 token 在轨迹中的逻辑索引进行调整。

上下文工程通过裁剪或总结修改逻辑 token 序列；而缓存工程通过缓存操作直接修改活跃缓存，同时保持逻辑 token 序列不变。

### 3.2 设计动机

缓存工程的设计源于对三个关键问题的思考：为什么需要直接修改缓存、保留缓存的哪些部分、以及如何管理其编码位置。

**为什么直接修改缓存**。缓存工程缓解上下文工程中 re-prefill 成本与任务准确率的两难。我们在前 100 个 BCP 任务上评估 GPT-OSS-120B，每任务 4 次试验、至多 100 个 agent 轮次。基于裁剪的上下文工程（仅保留最近 12 轮工具响应）成本是全上下文基线的 1.85 倍；基于总结的上下文工程（48k 阈值）成本降低约 7% 但准确率下降 5 个百分点（图 3）。相比之下，直接丢弃较旧的工具响应缓存可以复用剩余缓存，同时提升准确率并降低成本（图 3）。保留的缓存还可能在其计算过程中保存了来自已丢弃历史的信息（Xiao et al., 2024; Fu et al., 2026; Zou et al., 2025），如图 1 所示。

**保留缓存的哪些部分**。缓存选择应反映消息角色、时新性与任务需求，而非仅靠 token 级重要性启发式。图 2 显示较旧的 token 获得的注意力少于较新的 token，且在相近相对位置上工具响应获得的注意力少于 assistant 消息。因此我们以工具响应滚动丢弃作为主要示例：保留所有推理与最近工具响应的缓存，丢弃较旧的工具响应缓存。我们后续还探索了包括基于 RSI 的缓存工程在内的替代策略。

**如何管理位置编码**。默认情况下，即使缓存被缩减，位置编码索引仍随逻辑轨迹增长。丢弃缓存既不改变保留条目的位置编码，也不重置下一 token 的位置索引，因此即使缓存很小，索引也可能达到模型上限。我们将位置编码索引与逻辑索引及缓存规模解耦，使用单独的缓存操作通过 RoPE 旋转（Su et al., 2023）重新定位缓存键，而无需 re-prefill。

### 3.3 缓存操作

我们为缓存工程定义三个基本缓存操作：append、drop 和 repos，它们直接操作缓存而不重写已有逻辑 token 序列。

**Append**。append 是 LLM 推理中的标准缓存更新：处理一个新 token xt+1，以其活跃缓存为条件，并将其缓存条目 Ct+1 追加进来：

append(xt+1): C ← [C; Ct+1].  (3)

我们将 C 表示为按逻辑索引排序的 KV 条目序列，[·;·] 表示拼接。Token 可来自 prompt、工具响应或模型生成。位置编码索引从零开始，每次 append 后加一；repos 可以重置下一索引。

**Drop**。drop 将选定的 KV 状态移出后续注意力，同时保留状态本身、其位置编码与逻辑 token 序列均不变（图 1）：

drop(P): C ← C \ {Ci : i ∈ P},  (4)

其中 P 是被选为丢弃目标的活跃逻辑 token 索引集合，\ 表示从缓存中移除并保持保留条目的顺序。注意 drop 不改变后续 append 操作使用的位置编码索引。

**Repos**。repos 按逻辑 token 顺序更新缓存键的位置编码，并重置后续 append 的位置索引。设保留 r 个缓存条目，其位置索引变为 0, …, r−1，下一个追加的 token 使用索引 r。对旋转位置编码（RoPE）（Su et al., 2023），我们将缓存键 K 从位置索引 p 移到 q：

K ← R(q)R(p)^−1 K,  (5)

其中 R(p) 是位置 p 的旋转矩阵。缓存的 value 保持不变。

这些操作定义了算法层面注意力可见的缓存。服务系统在第 4 节中单独处理缓存的物理存储、驱逐与复用。

### 3.4 缓存操作序列

为了清晰、确定性地描述缓存操作，我们使用缓存操作序列：

o1:m = (o1, …, om), oj ∈ {append(x), drop(P), repos}.  (6)

其中 m 计数操作数，x 是 token，P 包含要丢弃的活跃逻辑 token 索引。对固定的 LLM，从空缓存出发，该序列决定当前缓存状态。

缓存操作序列是必要的，因为缓存状态是历史依赖的：仅有 token 与保留位置不足以确定下一 token 的概率。例如图 5 中，三条轨迹都保留 B 和 C，但①中计算 B 与 C 时 A 的缓存均可用，②中只有 B，③中两者皆无。因此 C 的缓存状态在三条轨迹中各不相同。类似地，repos 会改变后续 append 使用的位置编码（图 8）。因此正确的缓存复用与恢复需要同时记录 token 历史与缓存操作历史。

## 4 AKV 服务系统

AKV 遵循"无状态接口、有状态服务"的原则。Agent 通过指定缓存操作来控制后续注意力使用的缓存（第 4.1 节），而服务器在内部处理物理缓存的复用、驱逐与恢复（第 4.2 节）。

### 4.1 服务接口

服务接口必须保证每个请求的输出分布独立于物理缓存驻留与其他请求的缓存操作。例如，drop 只能影响发起请求的注意力，即使其他请求共享相同的前缀缓存，其输出分布也不能被改变。每个请求还必须完整描述它使用的缓存状态，而不依赖前几轮残留在服务器上的物理缓存。这样，即使内存压力导致轮间驱逐，服务器也能完整恢复缺失的缓存状态。

为此，AKV 扩展标准 LLM 服务 API，同时指定 token 历史与缓存操作历史。如图 6 所示，已有的 messages 字段提供完整逻辑 token 序列，可选的 cache 字段以 operate-after 语法指定 drop 与 repos 操作序列。注意 messages 中所有条目都隐式指定 append 操作。drop 中每个键标识在哪个消息索引之后应用该操作，其值列出要丢弃缓存的消息索引列表。reposition 字段列出在哪些消息索引之后应用 repos。消息索引从零开始，同一消息边界上 drop 先于 repos。对于多轮 agent 工作负载，客户端按照标准 LLM 服务流程，在每轮后扩展消息与缓存操作历史。

### 4.2 缓存状态管理

#### 4.2.1 设计目标与挑战

AKV 旨在保持常规 LLM 服务系统的三个关键性质：(1) 当且仅当缓存状态与所需状态等价时才复用；(2) 驱逐未使用的缓存状态而不损害请求隔离；(3) 在一次 prefill 内恢复被驱逐的缓存状态。

支持缓存工程时，服务系统面临三个对应挑战：(1) token 前缀不再单独决定缓存状态，普通前缀匹配可能错误地复用来自不同缓存操作历史的状态（图 5(b)）；(2) 被一个请求 drop 的 KV 缓存可能仍被另一个请求需要，不区分其他请求的驱逐会造成不必要的重算或破坏请求隔离；(3) 普通的因果 prefill 无法复现 drop 与 repos 产生的缓存状态，而重放操作历史需要多次前向传播。AKV 分别用扩展基数树、drop 感知驱逐与分段批注意力解决这三个挑战。

#### 4.2.2 Drop 感知的缓存管理

**用 drop 节点实现复用**。AKV 用 drop 节点扩展基数树前缀匹配。当请求调用 drop 时，AKV 在该请求路径的触发点插入一个 drop 节点 Δ，记录被丢弃缓存的逻辑 token 索引。由于 drop 不改变保留状态但影响后续注意力计算，这种放置在保持前缀共享的同时区分后续状态。在扩展基数树上做前缀匹配，可沿匹配的 token 与操作前缀复用缓存。图 5(c) 中，轨迹①②共享 A–B 前缀，但因 drop A 的时机不同而保持不同的 C 状态；轨迹③则走单独分支。处理 D 时，每条轨迹直接复用各自的 B、C 缓存。

**drop 感知的驱逐**。AKV 利用 drop 信息在请求结束前回收不再使用的缓存。一个缓存条目只有在没有任何进行中的计算或恢复需要它时才可驱逐。例如图 5 中，一旦请求①②都 drop 了 A，A 的缓存即可释放，即使它们还在生成 D。驱逐释放物理存储但在树中留下空占位节点，使缓存的后代仍可通过前缀匹配访问。在可驱逐的缓存条目中，AKV 优先驱逐被 drop 的缓存，其次才是已完成请求的缓存，因为后者更可能在下一轮被复用。

**用分段批注意力恢复**。AKV 用分段批注意力在单次 prefill 中恢复缺失的缓存状态。在每一层，查询在 drop 触发点处切分，每个分段因果地注意自己的 token 以及来自更早分段的活跃缓存。被丢弃的缓存被排除在后续分段之外，但对原本使用它的更早分段仍然可用（图 10）。只有注意力被分段，FFN 仍将完整序列作为一个批次处理，避免为每个分段重复读取 FFN 权重——这是内存流量的主要来源。

#### 4.2.3 Reposition 感知的缓存管理

drop 不改变保留缓存，而 repos 高效地修改其键的位置编码。因此不同请求可能需要相同缓存的不同位置编码版本。恢复也必须复现计算各阶段所用的编码。

**用键旋转实现复用**。AKV 在 repos 之后通过复制缓存状态并旋转键来复用缓存，而不重算隐藏状态。图 8(c) 中，请求 2 将 B、C 从位置 1、2 复制到位置 0、1，而请求 1 继续使用原始 B。在基数树中，这些副本形成带更新位置索引的新分支，并在 C 后记录一个 reposition 节点。前缀匹配同时检查 token 与操作历史：位置索引匹配则可直接复用，索引不同则需键旋转。附录 A.1.2 解释了 reposition 节点的必要性，并详述匹配规则与位置变换。

**独立驱逐位置版本**。AKV 独立驱逐每个位置编码版本——当它不再被任何进行中的计算或恢复使用时。例如图 8(c) 中，原始 B 仍被请求 1 使用，而原始 C 变为可驱逐。

**用临时 KV 版本恢复**。AKV 扩展分段批注意力，使每个分段使用其原始计算时的位置编码。查询也在 repos 触发点切分。在每层，AKV 旋转键并复制值，为需要不同位置的分段创建临时 KV 版本，详见附录 A.1.1。

## 6 结论

我们提出缓存工程，使 agent 能直接管理活跃 KV 状态，并无重算地复用保留缓存。我们协同设计了 AKV 服务系统，通过无状态接口、扩展基数树与分段批注意力，高效支持缓存的复用、驱逐与恢复。在各 agent 基准上，缓存工程在降低推理成本的同时提升平均任务性能，AKV 将这些效率收益转化为更高的服务吞吐与更低的延迟。

**局限**。缓存工程策略的进一步探索、在此方案下训练 agent、以及将服务支持扩展到线性注意力模型，是未来的工作。

### A.1 AKV 系统设计细节

#### A.1.1 分段批注意力恢复

**分段**。在第 4.2.2 与 4.2.3 节的基础上，每当 drop 或 repos 操作改变可见历史或其位置映射时，AKV 通过划分查询来恢复缺失的 KV 状态。每个分段选择对应的 KV 页并应用标准因果注意力，从而在不构造稠密自定义掩码的情况下编码历史可见性。

> **图 10**：分段批注意力恢复。(a) 中的请求产生 (b) 中的四个注意力分段。数字表示 query/key 位置；有色格表示允许的注意力。示例中：分段 1 因果计算 A0、B1、C2；drop B 并 repos 后，分段 2 用键 (A0, C1, D2) 计算 D2；drop D 开启分段 3：E3 注意 (A0, C1, E3)；尽管分段 2、3 共享位置映射，但因 D 对 E 不可见需要分开的 KV 视图（drop 不压缩位置）；第二个 repos 将 E 从位置 3 移到 2，分段 4 用 (A0, C1, E2, F3) 计算 F3。

**批量化恢复**。在每层内，AKV 写入新计算的 KV 状态，并通过重编码 K、复制 V 构建额外的位置版本（如 C1、E2）。随后将各分段的页列表与查询范围一起提交给批注意力。因此全部四个分段在单次模型前向中执行，无需为每个位置版本重算隐藏状态，也无需在操作边界重放多次前向。

#### A.1.2 Reposition 方案

**设计目标**。Reposition 感知的缓存管理必须区分位置版本，同时复用其共享的计算状态。我们先用精确匹配找出可直接复用的缓存，再用 retrigger 匹配找出可通过位置变换复用的前缀，避免不必要的隐藏状态重算。

**Token 节点表示**。每个 token 节点表示为 T(x, p)，x 是 token ID，p 是其缓存 K 中当前编码的位置。位置标签描述的是存储的缓存，而非 token 最初计算时的位置。例如图 11 中，C 在三条轨迹中都在位置 2 计算；repos 后轨迹 1、3 使用 (C, 0)，轨迹 2 使用 (C, 1)。路径上的操作节点保存支配计算的操作历史。

**为什么需要位置标签与 reposition 节点**。位置标签区分不可互换使用的缓存表示：例如轨迹 1、2 中 C 的原始计算历史相同，但分别被 repos 到位置 0 和 1，其 K 编码不同，复用前需要位置变换。Reposition 节点区分共享最终位置但来自不同计算的状态：轨迹 1 与 3 都在 ABC 后 drop B，但轨迹 3 在计算 D 之前先执行 RC。计算 D 时，A、C、D 的位置分别为 (0,2,3) 与 (0,1,2)：D 与 A 的相对距离改变而 D 与 C 不变，可能为 D 产生不同的隐藏状态与 KV 条目。两条轨迹随后都 drop A 并执行 RD 将 C、D 移到位置 0、1——后续变换无法抹除 D 中已形成的计算差异。因此路径必须在 D 之前保留 RC，防止对 D 及其后缓存状态的错误复用。

**精确匹配与 retrigger 匹配**。精确匹配比较 token 节点的全部字段：

T(x, p) ≡ T(x′, p′) ⟺ x = x′ ∧ p = p′，

并要求操作节点及其参数完全一致。Retrigger 匹配只忽略存储的位置编码索引，保留全部操作记录：

φ(T(x, p)) = T(x)，φ(ΔP) = ΔP，φ(R) = R。

两个前缀若投影相同则历史兼容。系统先用最长有效精确前缀初始化结果，再从根搜索兼容分支；候选仅在有效且匹配严格更长前缀时替换当前结果（并列时保留精确匹配）。Retrigger 匹配在首个 token 或操作不匹配处停止。选中的源缓存被复制并按需做位置变换后使用。

**Retrigger 匹配的正确性**。在固定模型与位置编码配置、精确算术下，投影相同的前缀保证每个 token 原始计算之前的 token 与操作历史一致，因此产生相同的隐藏状态与未旋转 KV 内容。之后的 repos 只改变 K 的位置表示，可将源版本 s 变换为目标版本 t：

Kt = R(pt)R(ps)^−1 Ks，Vt = Vs，

无需重算隐藏状态。保留操作节点防止该变换跨越计算历史的分叉：例如轨迹 1、3 在 D 之前的 RC 上不一致，retrigger 匹配不能跨它们复用 D。有限精度变换可能引入舍入误差；此正确性论证不要求与重算逐位等价。

#### A.1.4 工作负载重放与评估协议

**任务选择**。为模拟具有大量累积上下文的真实长程 agent 工作负载，我们选取 SWE-bench Verified 中轨迹上下文最长（无任何总结操作）的 80 个任务。这些任务反映长上下文推理的难度。我们按峰值长度排序，用固定种子打乱所选任务，所有方法使用相同任务与顺序。每种方法重放在其自身上下文/缓存工程策略下收集的轨迹，因此轮数与输出预算在方法间可能不同。

**轨迹重放**。对每一轮，从完整记录的消息历史（含推理与工具调用内容）中减去输入中已有的生成前缀，重建输出 token 预算。我们使用 temperature 0 与 ignore eos=True 生成规定数量的 token。新生成的 assistant 响应保留在历史中供后续轮使用，工具响应从记录轨迹重放而不重新执行工具。没有可用 assistant 响应的终止输入被排除在重放之外。

**并发与测量窗口**。我们维持 C 个客户端任务并发，任务内轮次顺序执行。每个测量窗口的任务数目标为 max(3×C, 30)；测量包含用于维持并发的补充任务请求。对 C ∈ {14, 16} 的 AKV，我们在前 30 个任务完成时截断存档运行，统计该窗口内全部请求而不仅是那 30 个任务的请求。对大并发的 Standard，KV cache 容量压力导致反复 prefill，服务严重退化，因此我们对这两次运行报告固定一小时窗口的结果，截止时仍有部分请求未完成。

#### A.2.1 评估配置

**评估 harness**。BCP、SWE-bench Verified、GAIA-Text、xbench-DeepSearch-2510 分别采用官方 BrowseComp-Plus harness、mini-SWE-agent（Yang et al., 2024）、来自 observation-masking（Zhang et al., 2026）的 browser-agent 脚手架，以及 WebExplorer 的评估 harness（Liu et al., 2025a）。

**检索与网页阅读**。BCP 评估遵循官方任务 prompt，用 Qwen3-Embedding-8B（Zhang et al., 2025）从基准固定语料检索文档。所有模型与方法都可使用 search 与官方可选的 get document 工具（返回所选文档全文）。xbench-DeepSearch-2510 用 GLM-5.2（Z.ai, 2026）响应 agent 查询从网页提取信息。

**答案评分**。三个问答基准都用 GLM-5.2 作为答案评审，评分 prompt 分别遵循 BCP 官方实现、observation-masking（GAIA-Text）与 WebExplorer（xbench-DeepSearch-2510）。SWE-bench Verified 用官方测试脚本与评分函数评估提交补丁，不使用 LLM 评审。

**Agent 步数上限**：BCP 100；SWE-bench Verified 250；GAIA-Text 200；xbench-DeepSearch-2510 100。

#### A.2.2 上下文工程基线细节

上下文工程基线采用 Pi 的总结 prompt、对话序列化、切点选择与总结生成长度预算（earendil-works, 2026），各实验组统一 reserveTokens=16,384、keepRecentTokens=20,000。总结使用 agent 自身的模型与推理设置，用摘要替换较旧对话，同时保留系统与开发者指令及所选近期消息。

与 Pi 基于上下文窗口减 reserve 预算的原生触发不同，我们在精确 prompt token 数达到 5.1 节所述阈值时触发压缩。我们也拒绝空总结，并按基准错误协议处理总结失败而不重试。

Pi 定义四个 prompt 模板：共享系统 prompt、初始总结 prompt、更新总结 prompt 与轮前缀 prompt。摘录如下：

**文本 1（共享系统 prompt）**："你是一个上下文总结助手。阅读用户与 AI 助手的对话，然后按指定格式产出结构化总结。不要继续对话，不要回答对话中的任何问题，只输出结构化总结。"

**文本 2（轮前缀 prompt）**："这是一轮因过大而无法保留的 PREFIX（前缀），SUFFIX（近期工作）被保留。请总结前缀为保留的后缀提供上下文：## 原始请求 [用户本轮要求什么？] ## 早期进展 [前缀中的关键决策与已完成工作] ## 后缀上下文 [理解保留的近期工作所需的信息]。请简洁，聚焦理解保留后缀所需的内容。"

### A.4 补充实验结果

#### A.4.1 加速分解

AKV 主要通过减少全注意力时间加速解码。如图 12 所示，相同批次大小下，AKV 相对 Standard 将全注意力时间降低 59.8%，总 decode 步时间降低 16.0%。丢弃较旧工具响应 KV 缩短活跃上下文，后续 decode 步从 GPU 内存加载更少 KV 数据并做更少注意力计算。

> **图 12**：延迟分解。相同批次大小下 GPT-OSS-120B 的 decode 步时间按操作分解：Standard 总计 26.186 ms（全注意力 16.764、SWA 注意力 7.082、MoE 专家+路由 0.866、注意力投影 0.839、TP 通信 0.487、其他+空隙 0.149）；AKV 总计 21.990 ms（全注意力 16.785→实际为主项、SWA 2.849、注意力投影 0.873、TP 通信 0.468、其他 0.149）。全注意力项大幅下降。

#### A.4.2 成本分解与活跃上下文长度

**成本分解**。AKV 通过减少缓存读取与重复 prefill 降低成本。如图 13 所示，丢弃较旧工具响应 KV 减少了后续请求读取的缓存历史量，相对 Standard 降低缓存读取成本约 17%。相对 Text Engineering，AKV 直接复用保留 KV 而无需总结重写历史引发的 re-prefill，降低重算并使缓存未命中输入成本降低约 48%。

**活跃上下文长度**。图 14 显示 AKV 如何减缓活跃上下文增长。一旦工具响应超过保留预算 K 轮，AKV 持续丢弃较旧工具响应 KV，保留最近 K 轮与推理 KV。活跃上下文随推理积累仍会增长，但速率大幅放缓。相比之下，Standard 持续累积历史，直到总结触发上下文长度的骤降。

> **图 13**：成本分解。GPT-OSS-120B 在 BCP 上的每任务平均成本（Standard 13.1 = 缓存读 10.8 + 输出 1.6 + 未命中输入 0.6；Text Engineering 12.6 = 缓存读 8.5 + 输出 2.9 + 未命中 1.2；AKV 11.4 = 缓存读 9.0 + 输出 1.5 + repos 0.3 + 未命中 0.6）。

#### A.4.3 跨消息历史的注意力

> **图 15**：跨消息历史的注意力密度。在 10 条 BrowseComp-Plus 轨迹上平均的逐 token 注意力密度，按层与消息索引展示，分为旧推理、旧工具响应与近期历史。

为解释工具响应滚动丢弃策略为何优先丢弃较旧的工具响应 KV，我们分析了分配给不同类型历史消息的注意力。图 15 显示 10 条 BCP 轨迹上逐 token 注意力按层的平均：在多数展示的层中，旧工具响应获得的注意力少于旧推理，而近期历史通常获得更多注意力。这一模式表明对历史消息的直接注意力同时依赖时新性与消息类型，为"保留近期工具响应与推理、优先丢弃旧工具响应 KV"提供了经验支持。结合前述任务性能与成本结果，该观察有助于解释 AKV 如何在维持任务性能的同时减少 KV cache 访问。

**与 Harness 的兼容性**。为评估 AKV 能否改进现有 harness，我们将其与 Pi（earendil-works, 2026）集成并在 BCP 上评估。对 GPT-OSS-120B 与 GPT-OSS-20B，加入 AKV 相对无压缩的原生 Pi harness 提升准确率 3%，相对带压缩的 Pi harness 提升 4%。

### A.5 补充相关工作

**并发工作**。并发的相关工作将 KV 驱逐适配到 agent 轨迹不断变化的注意力需求。AgentKV（Liu et al., 2026a）用不同执行阶段的查询缓冲区为 KV 条目打分，保留基于时新性打分会遗漏的信息。IntentKV（Li et al., 2026）结合跨轮查询记忆与学习的重要性估计，在有限 KV 预算下保留有用历史。SideQuest（Kariyappa & Suh, 2026）通过辅助推理分支探索模型导向的保留——识别过期工具结果并发出缓存删除命令，但其当前策略限于工具响应，服务集成也只为该特定驱逐流程定制。Context Language Models（CLMs）（Shao et al., 2026）主要研究模型驱动的上下文管理，将实时上下文视为可编辑文件并学习如何维护；CLM 还引入 Suffix Cache Reuse 在文本编辑后保留未变的下游 KV 状态，其服务支持以会话局部复用为中心：迁移的状态留在共享基数缓存之外的私有缓冲区，缺乏对这些历史依赖状态进行索引、管理与恢复的统一机制。AKV 直接解决这些服务化问题：通过无状态接口暴露与策略无关的缓存操作，用扩展基数树同时追踪 token 与缓存操作历史，将保留状态整合进共享缓存复用、内存管理与恢复。
